# 백로그

미착수 항목의 단일 추적처다. 스코프 태그([파이프라인]/[vada])를 붙이고, 착수 시점(트리거)이 있으면 명시한다. 완료하면 행을 삭제한다. 진행 상태는 `HANDOFF.md`, 화면별 발견은 각 파일럿 문서의 마찰 로그가 원본이다.

| 스코프 | 항목 | 트리거 |
| --- | --- | --- |
| 파이프라인 | 래스터 이미지 자산 미지원 — normalizePaint가 `imageRef`만 남기고 바이트를 export하는 경로가 없다 | 이미지가 있는 화면 등장 시 |
| 파이프라인 | 원본 저장 번들 세대 표식 — raw+SVG 11+PNG 13회 PUT의 부분 실패 시 혼합 세대를 파일만으로 식별 불가 | 부분 실패가 실제로 관측되면 |
| 파이프라인 | 시각 회귀 기준선(마찰 6 잔여) — 시나리오 e2e+스크린샷 자동 생성은 도입됨(AI가 직접 실행·판독). 잔여: 승인된 구현 스크린샷을 기준선으로 한 회귀 비교(toHaveScreenshot). reference.png와의 픽셀 자동 대조는 ÷0.875 환산 때문에 구조적으로 무의미 | 화면 수 증가로 수동 판독이 부담될 때 |
| vada | option-sources 값 형식·예시 응답 계약(마찰 3) — mock의 `sch-001` id는 임시 | 백엔드 계약 확정 시 |
| vada | select 활성 상태 placeholder(마찰 8) — 비활성 사유 문구가 활성화 후 부적합, 스키마 확장 여부 | select 요소가 있는 다음 화면 착수 전 |

| 파이프라인 | 내비게이션 정합성 — **의미론은 계약으로 정의 완료**(element-types.md: 미등록 이동=명시적 오류, vada-web ScreenRouter가 참조 구현). 잔여: 검증기의 스펙↔구현 화면 집합 교차 검사 | 화면 3개 이상 또는 라우팅 도입 시 |
| 파이프라인 | action `submit`·`mutations.json` 카탈로그·`scopeEvent` **스키마화** — 방향은 확정됨(element-types.md). 스키마·검증기·판정기·구현 반영 | 첫 제출 버튼 등장 시(ORG-01 예상) |
| 파이프라인 | 스펙 준수 테스트를 e2e까지 확대 — 현재 `conformance.test.tsx`는 jsdom 렌더만 본다. 실제 브라우저에서만 드러나는 소비 누락(포커스·스크롤·CSS 의존)은 여전히 사각이다 | 그런 필드가 실제로 등장하면 |
| 파이프라인 | JSON Schema→TS 타입 코드젠 — 계약의 수동 이중화(`spec/types.ts`)로 인한 drift를 시스템이 막지 못함 | 스키마 변경 시(예: 마찰 8의 enabledPlaceholder) |
| vada | fetch 실패 재시도 어포던스 — error 상태에 재시도 버튼 없음. 카탈로그 `messages` 계약에도 재시도 개념이 없어 스펙 구멍이기도 함 | 백엔드 연동 시 또는 다음 select 화면 |
| vada | ONB-01의 하드코딩 섹션("기본 프로필"/"학적 정보")을 `group` 요소로 이전 — 계급은 스키마로 해결됐으나 기존 인스턴스가 남아 있다. 디자인에 근거가 있다(`7:22`·`7:36`이 `Section` 이름에 `Paragraph` 제목을 가진다) | ONB-01을 다시 손댈 때 |
| 파이프라인 | `input.validation` 왕복 소실 — 스키마가 `readOnly`라 플러그인이 항상 `[]`로 덮어쓴다. AI가 로컬 JSON에 쓴 규칙이 `이 화면 저장` 한 번에 조용히 사라진다(실증됨). 보존하거나 스키마에서 제거해야 한다 | 검증 규칙이 실제로 필요한 화면 등장 시 |
| 파이프라인 | 커밋 훅이 테스트를 돌리지 않음 — `validate-specs`만 실행하므로 계약 회귀(테스트 red)를 막지 못한다. 루트 `npm test`가 생겼으니 훅에 추가만 하면 된다(실행 시간 약 2분이 커밋마다 붙는 것이 유일한 쟁점) | red 커밋이 실제로 발생하면 |
| 파이프라인 | 버튼 강조도(주/보조) 필드 — 흐름 순서 판별은 흐름을 넘는 이동에서 무력하다(ORG-01 마찰 3) | 버튼 2개 이상인 화면이 하나 더 등장하면 |
| 파이프라인 | **wireframeKey 오타를 UI로 되돌릴 수 없다** — 문서 루트 pluginData에 한 번 쓰이면 입력란이 영구 `readOnly`가 된다(ui.mjs). 오타나면 엉뚱한 폴더가 생기고 플러그인만으로는 복구 불가 | 오타가 실제로 발생하거나 wireframe이 둘 이상이 될 때 |
| 파이프라인 | **screenId 형식 검증이 늦다** — `registerActiveScreen`은 공백 제거만 하고, 브리지의 `IDENTIFIER_PATTERN`은 저장 시점에만 적용된다. 한글·공백 screenId로 등록해 요소를 다 채운 뒤 저장에서 400을 맞는다. 등록 시점에 같은 패턴을 적용하면 된다 | 요소 등록 주체 결정 후 |
| 파이프라인 | **추출기의 `list` 감지** — ORG-02의 조직도(HQCard·DeptCardSetup·OrgBranch)에서 목록을 유도하지 못한다. 사례가 하나뿐이라 일반화하지 않았다 | 목록이 있는 화면이 하나 더 등장하면 |
| 파이프라인 | **추출기의 버튼 묶음 판별** — 나란한 버튼들이 '각각 별도 버튼'(ONB-02 카드)인지 '하나 고르기'(ORG-02 라디오 카드)인지는 이 wireframe에서 선택 상태 색으로만 갈린다. 제품 디자인 시스템 지식이라 파이프라인이 알 수 없어 질문으로 남긴다. wireframe별 힌트(interpretation의 기계 판독 승격)를 주면 자동화 가능 | interpretation의 JSON 승격을 할 때 |
| 파이프라인 | `list.rootItem`의 일반성 — 조직도의 고정 루트에서 나온 형태다. 다른 목록에 루트 개념이 없으면 별도 요소로 갈라야 할 수 있다 | 목록이 있는 화면이 하나 더 등장하면 |
| vada | 제출 mock이 성공만 반환한다 — `mutations.json`의 `messages.error` 경로가 실제로 그려지지 않는다. 실패 주입 수단이 없다 | 백엔드 연동 시 또는 오류 화면 검증이 필요할 때 |
| 파이프라인 | 추출기를 플러그인에 연결 — 지금은 CLI(`draft-screen-spec.mjs`)라 `figma.design.json`이 있어야 한다. 플러그인이 화면 등록 직후 초안을 보여주면 사람이 확인만 하면 된다 | 다음 화면 사이클에서 CLI 왕복이 번거로우면 |
| 파이프라인 | 추출기의 `note` 유도 — 완성된 문자열과 다른 화면 필드 값의 일치를 대조하면 파생 여부를 추정할 수 있다(ORG-01의 '한양대학교 ERICA · …'는 onboardingDraft의 라벨 조합이다). 지금은 질문으로만 보고한다 | note가 있는 화면이 하나 더 등장하면 |
| 파이프라인 | **screenId 유일성을 아무도 검사하지 않는다** — 두 FRAME이 같은 screenId를 가질 수 있고, 검증기는 화면 폴더 단위라 구조상 못 잡는다. 화면 복사 시 `suggestScreenId`가 양쪽에 같은 ID를 제안하는 것이 주 발생 경로. 폴더 신원 검사(409)가 피해는 막지만 원인은 남아 있다 | 요소 등록 주체 결정 후 |
| 파이프라인 | **화면 후보 판별이 느슨하다** — `getScreenCandidate`가 `type === 'FRAME'`만 보므로 다른 화면 내부의 Container도 작업 화면 후보로 뜬다. `plugin-model.mjs`의 `isScreenBoundary`(부모가 PAGE/SECTION)를 재사용하면 된다 | 요소 등록 주체 결정 후 |
| 파이프라인 | **화면 사이클 절차의 카탈로그 감지 시점이 틀림** — 원본 저장 *전*이 아니라 *후*여야 한다. design.json이 있어야 AI가 select를 뽑아 카탈로그와 대조할 수 있다. 지금의 순서 제약은 "사람이 플러그인에서 요소를 등록한다"를 고집할 때만 생긴다(ORG-01은 안 지켰고 잘 굴러갔다) | 요소 등록 주체(플러그인 vs AI) 결정 후 |
| 파이프라인 | **드롭다운 select의 선택지는 wireframe에 없다** — 자식 없는 빈 Dropdown 프레임이다(ONB-01 7:75, ORG-01 14:217). AI는 "여기 목록이 필요하다"까지만 감지하고 내용은 만들 수 없어 사람의 도메인 답변이 필수다. 펼친 형태(choiceGroup)는 반대로 디자인에서 그대로 뽑힌다. 이 구분이 어디에도 기록돼 있지 않다 | vada 마찰 3(값 형식·예시 응답 계약)과 함께 처리 |
| 파이프라인 | **플러그인이 못 하는 일의 경계가 미기록** — 카탈로그 생성 불가(브리지가 GET만 허용), `meta` 편집·표시 불가, `flows.json`은 브리지 라우트 자체가 없어 읽지도 못한다. 문서(HANDOFF 목표 흐름 2번)에도 UI에도 안내가 없어 select를 등록하다 막힌다. 고칠 자리는 기존 `option-source-readiness` 표시 장치 | 요소 등록 주체 결정 후 |
| vada | 린트 강화 — oxlint에 react-hooks 계열 규칙 부재 | 컴포넌트 수 증가 시 |
