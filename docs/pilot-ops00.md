# OPS-00(운영 허브) 파일럿

세 번째 데스크톱 화면이다. 수렴을 판정하려고 고른 화면인데, **판정 재료가
나오지 않았다** — 뒤에서 설명한다.

## 1. 이 화면은 MY-01을 시험하지 못한다

MY-01에서 연 세 자리가 여기서는 하나도 쓰이지 않는다.

| MY-01의 자리 | OPS-00에서 |
| --- | --- |
| `itemList.params` | 필터도 탭도 없다 |
| `itemList.itemAction` | 누를 수 있는 목록이 없다 |
| `select.optionCounts` | 선택 컨트롤이 없다 |

OPS-00은 **네비게이션 허브**다 — 갈 곳 넷을 늘어놓고 각각의 건수를 곁들인다.
MY-01은 **작업 목록**이다. 둘 다 "대시보드"로 묶었지만 표현 요구가 다르다.

**수렴 판정에는 같은 계열의 화면이 필요하다.** 데스크톱 화면이라는 것만으로는
부족하다는 것이 이 사이클의 가장 중요한 발견이다.

## 2. 카드 4개 — 새 유형을 만들지 않았다

카드 하나는 아이콘 + 제목 + 설명 + 라벨-값 쌍 2개 + 이동 링크다. 그리고
**디자인에서 카드 전체가 하나의 Button 노드**다(16:614).

등록 노드 계약("요소의 nodeId는 그 요소의 모든 부분을 포함하는 가장 안쪽
노드")상 한 노드는 한 요소다. 그래서 `summary` + `button`으로 가를 수 없다.

세 갈래를 놓고 판단했다. 근거는 저장소의 기존 결정과 업계 기준이다.

| 갈래 | 판정 |
| --- | --- |
| 새 유형 `spaceCard` | **아니오**. 데이터 구조가 `summary`와 같다 — 서버에서 읽는 라벨-값 쌍이다. 업계 기준도 "데이터 구조가 실제로 다를 때만 새 타입을 만든다"이다 |
| `button` + description에 통계 | **아니오**. 서버 값이 고정 문자열로 들어간다. 백로그가 HOME-01K에서 이미 문제로 적어 둔 것이고 여기서 4건이 더 나왔다 |
| `summary`가 자기 동작을 갖는다 | **예**. `itemList.itemAction`이 이미 같은 규칙을 세웠다 — 표시 요소가 자기 동작을 갖는다 |

`button.action`·`itemList.itemAction`·`summary.action`으로 같은 모양이 세 번째가
되어 `element-action.schema.json`의 `$defs.displayAction`으로 뽑았다. `button`은
제출(submit)과 mutation을 더 갖고 있어 그대로 두었다.

이 판단이 백로그의 **`button.description`이 서버 값을 담는다**를 해소한다.
답은 "button에 dataSourceKey를 주자"가 아니라 **"고정 카피는 button, 서버 값은
summary"**다.

## 3. 세는 말이 대상마다 다르다

디자인이 업무는 `4건`, 행사는 `2개`로 센다. MY-01 구현은 `건`을 코드에
박아 두고 있었다 — 이 화면이 그것을 드러냈다.

단위는 시각이 아니라 확정된 카피다(한국어에서 세는 말은 대상의 성질이 정한다).
`summary.items[].unit`을 열고 MY-01도 명세로 옮겼다.

## 4. 요구되는 신규 계급

| # | 계급 | 근거 | 처분 |
| --- | --- | --- | --- |
| 1 | 묶음의 설명 문장 | 카드마다 설명이 있고, 허브 안내문은 서버가 완성한다 | `summary.description`·`descriptionField` |
| 2 | 값의 단위 | 업무는 '건', 행사는 '개' | `summary.items[].unit` |
| 3 | 표시 요소가 눌린다 | 카드 전체가 Button 노드다 | `summary.action` (공통 정의로 승격) |

| 사이클 | 신규 계급 |
| --- | --- |
| ORG-02 | 1 |
| ORG-01 | 2 |
| INV-01 | 2 |
| HOME-01K | 3 |
| MY-01 | 4 |
| **OPS-00** | **3** |

**셋 다 `summary` 하나를 넓힌 것이다.** 새 요소 유형도, 새 카탈로그도 없다.
MY-01이 넷 중 하나가 새 개념(`shell.json`)이었던 것에 비하면 **새 개념은 0건**이다.

그리고 `shell.json`은 이 화면에서 **고치지 않고 그대로 쓰였다** — 사이드바가 세
화면째 동일하고, 추출기의 셸 제외도 그대로 돌았다(질문 15→10, 사이드바 미등장).
한 번 세운 것이 손대지 않고 재사용된 첫 사례다.

## 5. AI 읽기 마찰

| 무엇을 | 어디서 | 왜 명세에 없었나 | 추측했나 |
| --- | --- | --- | --- |
| 카드 아이콘·화살표 | `figma.design.json`의 assetRef | (C) 시각은 design이 갖는다 | 아니오 |
| 카드 2×2 배치 | 디자인 스크린샷 | (C) 배치는 design이 갖는다 | 아니오 |
| 공간 넷이 조직마다 같은지 | 사용자에게 질문 | (C) 제품 기획이다 | 아니오 |
| 카드의 이동 대상 | 사용자에게 질문 | (A) 디자인에 없다(기존에 아는 한계) | 아니오 |
| 8개 건수의 fieldKey 작명 | 지어냄 | (C) 명세를 만드는 쪽의 몫 | **예** |

**(A) 1건**, 전부 기존에 알던 종류다. 새 종류의 마찰은 없었다.

## 6. 자산 단위 규칙이 두 아이콘을 묶었다

`16-615.svg`가 **383×35**다. 카드 머리 줄 전체 — 왼쪽 아이콘과 오른쪽 화살표를
한 덩이로 담았다.

원인은 자산 단위 규칙("가장 바깥의 벡터만 있는 노드")이다. 아이콘 하나가 벡터
여러 개로 이루어진 경우에는 맞지만, **서로 다른 아이콘 둘이 나란히 있고 그
사이에 텍스트가 없으면** 둘을 묶어 버린다.

지금은 원래 비율대로 그려서 디자인과 맞는다(머리 줄 전체가 하나의 이미지가 된다).
다만 카드 폭에 따라 아이콘 크기가 함께 변한다. 사례가 하나뿐이라 규칙을
고치지 않고 기록만 한다.

## 7. 스크린샷 판독이 잡은 것

- 카드 아이콘을 `size-6`으로 그렸더니 383×35 자산이 점으로 찌그러졌다. 테스트는
  전부 통과했다 — 자산은 스펙 준수의 대상이 아니기 때문이다. **MY-01에 이어 두
  번째로 판독만이 잡은 결함이다.** 백로그 항목의 트리거가 충족됐다.
