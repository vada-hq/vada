# 제품 기획 명세 관리 규칙

> [!WARNING]
> 이 폴더는 JSON 정본을 설계하기 전에 만든 과도기 산출물이며 더 이상 제품 정본이 아닙니다. AI와 구현은 [`product-specs/`](../../product-specs/README.md)의 승인 JSON만 기준으로 사용합니다.

> 상태: 초안 0.2 · Notion 재정 공식 문서 대조 완료  
> 목적: Figma와 실제 플로우 하나까지 대조하기 전의 검증용 규칙이다. 이 문서와 양식은 아직 승인된 개발 기준선이 아니다.

## 1. 해결하려는 문제

개발 AI가 방대한 기획 전체를 한 번에 읽거나 화면만 보고 제품 규칙을 추정하지 않게 한다. AI는 현재 작업과 관련된 **최신 승인 정보만 찾아 읽고**, 정보가 미정이거나 출처가 충돌하면 구현 전에 이를 보고해야 한다.

## 2. 사실 종류별 정본

같은 사실을 여러 도구에 복사하지 않는다. 각 도구는 다음 정보만 소유한다.

- **Notion**: 기획 초안, 논의, 결정 이유, 승인 기록과 미정 사항
- **Figma**: 화면 구조, 시각 표현, 화면 상태와 상호작용의 디자인
- **`docs/product/domains/`**: 여러 플로우가 공유하는 용어·처리 단위·불변 규칙의 기준선
- **`docs/product/flows/`**: 개발에 승인된 개별 사용자 행동과 완료 결과의 기준선
- **`contracts/`**: 코드가 직접 소비하는 권한·데이터·도메인·API 계약
- **코드와 테스트**: 승인된 명세와 계약의 구현 및 검증 증거

Notion과 Figma는 기획·디자인을 만드는 작업 공간이고, 승인된 플로우 명세는 개발 기준선이다. Notion이나 Figma가 나중에 수정되더라도 승인된 명세가 자동으로 바뀐 것으로 간주하지 않는다.

## 3. 문서 구조와 탐색

도메인 공통 기준과 플로우 하나는 각각 다음 위치에서 관리한다.

```text
docs/product/domains/<DOMAIN-ID>/
├─ draft.md
├─ R1.md
└─ R2.md

docs/product/flows/<FLOW-ID>/
├─ draft.md   # 승인 전에는 이 파일만 수정
├─ R1.md      # 최초 승인본
└─ R2.md      # 의미가 바뀐 다음 승인본
```

- 도메인 ID는 `DOMAIN-<DOMAIN>`, 플로우 ID는 `FLOW-<DOMAIN>-<NNN>` 형식을 우선 사용하고 실제 재정 자료 매핑을 끝낸 뒤 확정한다.
- ID는 승인 후 바꾸지 않는다. 구현 작업과 계약은 파일명에서 최신 번호를 추정하지 않고 정확한 `ID@R<n>`을 참조한다.
- `draft.md`는 검토 중에 수정할 수 있다. 승인본 `R<n>.md`는 수정하지 않고, 변경이 필요하면 새 리비전을 만든다.
- 저장소의 에이전트 지침에는 제품 내용을 복사하지 않고 이 문서와 플로우 ID를 찾는 방법만 둔다.

## 4. 플로우를 나누는 기준

플로우는 사용자가 하나의 관찰 가능한 결과를 시작부터 끝까지 완수하는 단위다.

- 화면 수, CRUD 동작, API 또는 프론트엔드·백엔드 계층만으로 나누지 않는다.
- 독립적으로 시연하고 완료 여부를 판정할 수 있을 때 별도 플로우로 나눈다.
- 여러 화면을 지나더라도 하나의 사용자 목적을 완수하는 연속 행동이면 하나의 플로우일 수 있다.
- 여러 플로우가 함께 사용하는 처리 단위, 용어, 권한 원칙, 상태 소유 관계와 표시 계산은 도메인 기준선에 한 번만 기록하고 플로우에서는 정확한 리비전을 참조한다.
- 하나의 기획 페이지에 제출·검토·보완처럼 서로 다른 사용자의 완료 결과가 함께 설명돼 있어도 페이지 단위로 플로우를 만들지 않는다.

## 5. 승인과 변경 규칙

상태는 `draft → review → approved → superseded`만 사용한다.

- `draft`: 작성 중이며 개발 근거로 사용할 수 없다.
- `review`: 제품 책임자가 전체 의미를 검토 중이다.
- `approved`: 현재 개발 기준선이다. 현재 범위를 바꾸는 차단 미정 사항이 없어야 한다.
- `superseded`: 더 최신 승인 리비전으로 대체됐으며 신규 구현에 사용하지 않는다.

승인은 문서 형식이 아니라 **사용자 행동과 제품 의미**에 대해 한다. 문구 정리처럼 의미가 그대로인 수정은 다음 초안에 반영할 수 있지만, 권한·필수 입력·상태·결과·예외 행동이 바뀌면 새 리비전이 필요하다.

## 6. 출처와 최신성 확인

모든 도메인·플로우 명세는 근거로 사용한 정확한 Notion 페이지와 Figma 프레임을 참조하고, 출처가 보고한 최종 수정 시각과 AI가 마지막으로 확인한 시점을 구분해 기록한다.

- 각 출처에는 `current_rule`, `approval_evidence`, `pending_input`, `history`, `visual_design` 중 역할과 관찰 당시 상태를 기록한다.
- 수정 시각이 더 최근이라는 이유만으로 `pending_input`이나 `history`를 현재 규칙보다 우선하지 않는다.
- 구현 전 AI는 참조가 열리는지, 승인 리비전인지, 출처가 승인 후 수정됐는지 확인한다.
- 출처가 더 최근에 수정됐으면 최신 변경을 임의로 합치지 않고, 기존 승인본과의 차이를 정리해 새 초안 검토를 요청한다.
- 서로 충돌하는 출처가 있으면 우선순위를 추정하지 않는다. 충돌하는 문장·화면과 구현 영향을 함께 보고한다.

## 7. AI의 컨텍스트 로딩 규칙

개발 AI는 제품 전체를 선행 입력으로 받지 않는다.

1. 요청된 플로우 ID와 승인 리비전을 확인한다.
2. 플로우가 고정한 도메인 기준선 리비전과 해당 플로우 명세를 읽는다.
3. 두 명세가 참조하는 결정, Figma 프레임, 계약만 추가로 읽는다.
4. 현재 코드와 테스트를 조사해 승인 결과와의 차이를 찾는다.
5. 근거가 없는 행동은 구현하지 않고 미정 사항으로 보고한다.

`draft`나 `review` 상태의 내용을 제품 행동으로 구현하려면 별도의 탐색 작업이라는 명시적 승인이 필요하다. 탐색 결과는 사용자에게 공개되는 제품 기준선으로 취급하지 않는다.

## 8. 플로우 명세의 필수 내용

각 명세는 다음 질문에 답해야 한다.

- 이 플로우가 어떤 도메인 기준선 리비전을 전제로 하는가?
- 누가, 무엇을 이루기 위해, 어떤 조건에서 시작하는가?
- 사용자는 어떤 순서로 행동하고 시스템은 무엇을 보여주거나 기록하는가?
- 정상 흐름에서 벗어나는 중요한 실패·빈 상태·권한·재시도 분기는 무엇인가?
- 완료됐음을 어떤 관찰 가능한 시나리오로 증명하는가?
- 어떤 Notion 결정, Figma 프레임, 실행 계약을 근거로 삼았는가?

현재 범위와 관련된 질문에 답하지 못하면 `결정 대기`, `의도적 보류`, `외부 근거 대기` 중 하나로 구분한다. 승인본에는 현재 완료 기준을 바꾸는 차단 미정 사항을 남기지 않으며, 보류·외부 근거 대기 항목은 구현 금지 경계로 명시한다.

## 9. 초안 확정 절차

1. `domain-spec.template.md`와 `flow-spec.template.md`를 임시 양식으로 사용한다.
2. Notion의 재정 공통 규칙을 도메인 양식에, Figma 재정 흐름 하나를 플로우 양식에 매핑한다.
3. 들어가지 않는 정보, 중복 항목, 기획자가 실제로 답하기 어려운 항목을 찾는다.
4. 규칙과 양식을 수정한 뒤 제품 책임자의 승인을 받아 R1로 확정한다.
5. 그다음에만 다른 도메인으로 확장하고 자동 검증을 추가한다.
