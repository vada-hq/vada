# 행사 구매 요청 제출

## 한 줄 결과

구매 요청 권한 보유자가 특정 행사에 필요한 하나 이상의 구매 품목을 한 요청으로 제출하고, 저장된 요청과 품목별 검토 대기 결과를 다시 확인할 수 있다.

## 시작과 종료

- **사용자**: 현행 공식 역할 문서가 구매 요청 작성 권한을 부여한 부서장과 재정부 구성원.
- **시작 계기**: 사용자가 특정 행사 운영 중 물품·제작·인쇄·대여·용역 구매가 필요해 해당 행사의 재정 영역에서 요청을 시작한다.
- **시작 조건**: 행사가 존재하고 사용자가 해당 조직과 행사 맥락에서 구매 요청을 제출할 수 있어야 한다.
- **완료 결과**: 하나의 행사에 연결된 구매 요청과 하나 이상의 구매 품목이 생성되고, 각 품목은 검토 대기 상태로 조회되며 새로고침 후에도 유지된다.

## 정상 흐름

| 단계 | 주체 | 행동 | 시스템의 관찰 가능한 결과 |
| --- | --- | --- | --- |
| 1 | 사용자 | 특정 행사의 재정 영역에서 구매 요청 작성을 시작한다. | 행사와 로그인 요청자가 자동으로 연결되고 기본 요청 부서가 제시된다. |
| 2 | 사용자 | 요청 제목·구매 목적·필요일 등 요청 전체 정보를 입력한다. | 요청 전체에 공통으로 적용될 내용이 한 묶음으로 표시된다. |
| 3 | 사용자 | 하나 이상의 품목을 추가하고 품목명·구매 유형·수량·단위·예상 단가·예산 항목·가격 근거를 입력한다. | 품목별 예상 합계와 요청 금액이 수량과 예상 단가에서 계산된다. |
| 4 | 시스템 | 필수 정보, 양수 수량·금액, 필요일, 가격 근거·첨부자료, 예산 항목을 확인한다. | 제출을 막는 문제와 수정 대상을 사용자에게 알린다. 정확한 화면 표현은 Figma 연결 후 확정한다. |
| 5 | 사용자 | 구매 요청을 제출한다. | 요청 하나와 소속 구매 품목들이 생성되고 품목별 검토 대기 결과가 표시된다. |
| 6 | 사용자 | 생성된 요청을 다시 열거나 새로고침한다. | 원래 요청 내용과 각 품목의 현재 결과가 동일하게 조회된다. |

## 중요한 분기와 실패

| 조건 또는 사건 | 기대되는 행동 | 사용자가 확인하는 결과 | 근거 |
| --- | --- | --- | --- |
| 제출 권한이 없음 | 작성·제출 동작을 노출하지 않는다. 직접 요청의 서버 거부 방식은 권한 계약에서 확정한다. | 구매 요청을 생성할 수 없다. | 재정 공식 문서 `02`; 재정 권한 계약 미작성 |
| 품목이 없음 | 제출을 허용하지 않는다. | 하나 이상의 품목이 필요하다는 문제를 확인한다. | 재정 공식 문서 `03` |
| 필수 정보 누락 또는 수량·금액이 0 이하 | 제출을 허용하지 않고 수정 대상을 알린다. | 요청과 품목이 생성되지 않는다. | 재정 공식 문서 `03` |
| 사용 가능 예산 초과 | 제출 자체는 허용한다. | 요청은 검토 대기로 생성되지만 해당 문제가 해소되지 않으면 승인할 수 없다. | 재정 공식 문서 `03` |
| 여러 품목 또는 서로 다른 구매 유형 포함 | 한 요청에 함께 제출할 수 있다. | 하나의 요청 아래 각 품목이 독립된 검토 단위로 생성된다. | 재정 공식 문서 `01`, `03` |

## 제품 규칙

- `DOMAIN-FIN@draft`의 처리 단위·역할·상태 소유·기록 원칙을 따른다.
- 구매 요청은 정확히 하나의 행사에 연결하고 하나 이상의 구매 품목을 포함한다.
- 요청 전체 정보와 품목별 정보를 구분한다.
- 예상 합계와 요청 금액은 `수량 × 예상 단가`에서 계산하며 직접 입력하지 않는다.
- 금액에 따라 입력 항목을 숨기거나 생략하지 않는다.
- 같은 요청 안의 품목은 제출 후 독립적으로 검토·보완·반려될 수 있다.
- 현행 공식 문서에 적힌 공통 제출 정보는 현재 규칙으로 사용한다. 8월 2일 입력 기준 작업에만 추가된 구매 유형별 상세 필드와 세부 필수·선택 구분은 상태가 `진행 전`이므로 승인된 기준으로 사용하지 않는다.

## Figma 연결

정확한 Figma 프레임을 아직 확인하지 못했다. 화면 구조·오류 표시·품목 추가 방식·제출 후 이동 경로는 추정하지 않으며 프레임 연결 전에는 디자인 구현 기준선으로 승인할 수 없다.

| 흐름 단계 또는 상태 | Figma 프레임 | 이 명세가 설명하는 비시각적 의미 |
| --- | --- | --- |
| 요청 작성 | 연결 대기 | 한 행사에 연결된 요청 전체 정보와 하나 이상의 품목 입력 |
| 제출 오류 | 연결 대기 | 생성 없이 입력 문제를 수정해야 하는 상태 |
| 제출 완료 | 연결 대기 | 요청과 품목별 검토 대기 결과가 영속된 상태 |

## 완료 시나리오

### AC-01 · 한 품목 요청 제출과 영속성

- **조건**: 제출 권한이 있고, 행사와 유효한 예산 항목이 존재한다.
- **행동**: 필수 요청 정보와 유효한 품목 하나를 입력해 제출한다.
- **결과**: 요청과 품목이 한 번만 생성되고 품목은 검토 대기로 조회되며, 새로고침 후에도 동일한 내용이 유지된다.

### AC-02 · 여러 품목의 독립 생성

- **조건**: 제출 권한이 있고 서로 다른 구매 유형을 포함한 품목 정보가 유효하다.
- **행동**: 둘 이상의 품목을 하나의 요청으로 제출한다.
- **결과**: 요청은 하나만 생성되고 각 품목은 독립된 기록과 검토 대기 결과를 가진다.

### AC-03 · 유효하지 않은 요청 차단

- **조건**: 품목이 없거나 필수 정보가 누락됐거나 수량·금액이 0 이하이다.
- **행동**: 제출을 시도한다.
- **결과**: 문제 항목을 확인할 수 있고 요청·품목·이력 데이터는 생성되지 않는다.

### AC-04 · 예산 초과 요청 제출

- **조건**: 입력은 유효하지만 품목의 요청 금액이 현재 사용 가능 예산을 초과한다.
- **행동**: 요청을 제출한다.
- **결과**: 요청과 품목은 검토 대기로 생성되지만 예산 초과 상태에서는 승인할 수 없다.

### AC-05 · 미보유자의 생성 차단

- **조건**: 사용자가 구매 요청 제출 권한을 보유하지 않는다.
- **행동**: 화면과 직접 요청 경로로 구매 요청 생성을 시도한다.
- **결과**: 작성·제출 동작이 노출되지 않고 직접 요청도 거부되며 데이터가 생성되지 않는다.

## 범위 경계

- 재정부의 품목별 승인·보완 요청·반려는 별도 플로우다.
- 요청자의 보완·재제출과 선진행 제안 응답은 별도 플로우다.
- 승인 이후 주문·수령·증빙·예산 확정은 이 플로우에 포함하지 않는다.
- 임시 저장은 현재 공식 기획에서 확인되지 않았으므로 포함하지 않는다.
