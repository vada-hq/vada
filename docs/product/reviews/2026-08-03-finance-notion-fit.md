# 재정 Notion 기획 자료 적합성 검토

> 상태: 완료  
> 검토 목적: 제품 기획 명세 관리 규칙과 양식 초안이 실제 VADA 재정 기획을 손실 없이 분리할 수 있는지 확인

## 확인한 현재 진입점

- `재정 공식 문서`: https://app.notion.com/p/3ae68a85148e801e997ee7a1d0b7ecf5
- 상위 페이지가 현행 규칙의 우선순위를 선언하고 `01~10` 주제별 페이지를 현재 기준으로 연결한다.
- 이번 검토는 공통 구조·권한·요청 흐름·상태 표시·보류·결정 이력을 확인하기 위해 `01`, `02`, `03`, `08`, `09`, `10`을 읽었다.

## 초안에서 발견한 누락

최초 초안은 플로우 명세만 분리했다. 실제 재정 기획에는 여러 플로우가 공동으로 사용하는 다음 정보가 존재한다.

- 구매 요청·품목·승인 묶음·실행분·증빙 묶음의 처리 단위와 관계
- 역할별 능력과 열람 범위
- 원본 상태, 대표 표시, 재정부 처리 단계와 칸반 위치의 구분
- 변경 이력과 덮어쓰기 금지 같은 감사 기록 원칙

이를 각 플로우에 복사하면 같은 권한·상태 규칙이 여러 문서에서 달라질 수 있다. 따라서 `도메인 기준선 → 플로우 기준선`의 두 계층이 필요하다.

## 플로우 분리 결과

Notion의 `03. 구매 요청·검토·보완` 페이지는 하나의 플로우가 아니다. 최소한 다음과 같이 서로 다른 사용자의 완료 결과를 함께 설명한다.

- 요청자가 여러 품목의 구매 요청을 제출한다.
- 재정부가 품목별로 승인·보완 요청·반려를 결정한다.
- 요청자가 보완 대상 품목을 수정해 재제출한다.
- 혼합 결과일 때 재정부가 선진행을 제안하고 요청자가 전체 동의 또는 거부한다.

따라서 Notion 페이지 수나 제목을 플로우 수로 사용하지 않고, 독립적으로 시연·판정할 수 있는 사용자 결과를 기준으로 나눠야 한다.

## 미확정 정보 분류 결과

재정 문서에는 성격이 다른 미확정 정보가 함께 존재한다.

- `결정 대기`: 현재 제품 책임자의 답이 필요한 사항
- `의도적 보류`: 현재 범위에서는 구현하지 않기로 한 사항
- `외부 근거 대기`: 학교 감사 지침처럼 외부 자료가 있어야 확정할 수 있는 사항

세 종류는 개발 착수와 구현 금지 범위가 다르므로 하나의 `미정` 값으로 합치지 않는다.

## 초안에 반영한 변경

- `domain-spec.template.md`를 추가했다.
- 플로우가 정확한 `DOMAIN-<DOMAIN>@R<n>` 기준선을 고정하도록 했다.
- 출처의 최종 수정 시각과 AI 확인 시각을 분리했다.
- 미확정 정보를 결정 대기·의도적 보류·외부 근거 대기로 구분했다.
- Notion 페이지 단위가 아니라 사용자 완료 결과로 플로우를 나누는 규칙을 명시했다.
- 현재 규칙·승인 근거·미승인 입력·이력·디자인 출처를 구분하고 수정 시각만으로 우선순위를 판단하지 않게 했다.

## 실제 초안 작성 중 확인한 드리프트

- `구매 요청 입력 기준 확정` 작업은 상세 답변이 작성돼 있지만 상태가 `진행 전`이다. 따라서 해당 세부 필드표는 `pending_input`으로만 참조하고 현재 제품 규칙으로 사용하지 않았다.
- 완료된 `구매 요청 접근 권한 확정` 작업은 제출자를 `각 부서장`으로 적었지만 현행 역할 문서는 부서장과 재정부 모두 구매 요청을 작성할 수 있다고 적는다. 상위 공식 문서가 충돌 시 자신을 우선하도록 명시하므로 현재 제품 규칙은 `부서장·재정부`이며, 작업 페이지는 현재 규칙의 근거가 아니라 드리프트 증거로 취급한다.
- `구매 요청 최종 결과 표시 규칙 확정` 작업은 본문 답변이 현행 공식 문서와 대부분 일치하지만 상태가 `진행 전`이다. 이는 제품 의미의 미정이라기보다 작업 상태 투영이 뒤처진 경우다.
- `구매 요청 최종 검토 규칙 확정` 작업은 `진행 전`인 입력 기준 작업을 필수 선행으로 두면서 자신은 `완료` 상태다. 선행관계와 상태 중 적어도 하나를 정정해야 한다.
- 현재 세션에는 사용할 수 있는 브라우저나 Figma 전용 연결이 없어 정확한 프레임·버전·개발 준비 상태를 확인하지 못했다. 로컬 프로토타입은 참고 자료이므로 대신 기준선으로 사용하지 않았다.

## 2026-08-03 정합성 판정

### 현행 공식 규칙으로 바로 사용할 수 있는 내용

- 구매 요청 작성자는 부서장과 재정부다.
- 구매 요청은 하나의 행사에 속하고 하나 이상의 품목을 포함한다.
- 요청 안의 품목은 독립적으로 검토되며 재정부가 승인·보완 요청·반려한다.
- 재정부 구성원의 자기 요청 검토는 허용하되 처리자·시각·결과·사유를 동일하게 기록한다.
- 요청자는 자신의 요청 내용과 품목별 결과·사유·처리자·처리 시각을 확인한다.

### 승인 전에는 후보로만 사용할 내용

- `구매 요청 입력 기준 확정` 작업에만 있는 구매 유형별 상세 필드와 세부 필수·선택 구분
- 현행 공식 문서가 `구매 요청 조회`라고만 표현한 일반 부원의 정확한 목록·상세 열람 범위
- 제출 성공 뒤 이동할 화면과 즉시 보여 줄 결과
- 정확한 Figma 프레임, 버전과 개발 준비 상태

## 노션 정정 후보

이 목록은 제품 의미를 새로 결정하는 질문이 아니라 현재 공식 규칙과 작업 데이터베이스를 다시 맞추기 위한 검토안이다. 승인 전에는 노션을 수정하지 않는다.

1. `TSK-1`의 제출자를 `각 부서장`에서 현행 공식 규칙인 `부서장·재정부`로 정정하고, 일반 부원 조회 범위를 별도 미정으로 분리한 뒤 상태를 `검토 필요`로 바꾼다.
2. `TSK-2`는 작성된 답변 중 공식 문서와 일치하는 공통 규칙과 추가 승인이 필요한 구매 유형별 상세 필드를 분리한 뒤 상태를 `검토 필요`로 바꾼다.
3. `TSK-3`도 답변이 작성됐으나 승인·반영 완료 전이므로 `검토 필요`로 바꾸고, `TSK-4`는 TSK-2 선행관계를 유지한 채 TSK-2 승인 전까지 `차단`으로 바꾼다.

`완료`는 답변이 존재한다는 뜻이 아니라 완료 기준에 적힌 승인과 관련 문서·계약 반영까지 끝났다는 뜻으로 사용한다. 현재 재정 실행 계약이 없으므로 TSK-1과 TSK-4의 기존 `완료` 표시는 자체 완료 기준과도 맞지 않는다.
