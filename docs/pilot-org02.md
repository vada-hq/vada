# ORG-02 사이클

네 번째 화면 사이클. 지금까지 중 표현력 시험의 수확이 가장 컸다 — 현재 체계로 표현할 수 없는 것을 3가지 들고 왔고, 예약해 둔 `action.submit` 계약의 첫 소비자가 됐다.

## 사이클 기록 (2026-08-18)

1. 사용자: Figma에서 화면 지정 → `Figma 원본 JSON 저장`. **요소 등록은 하지 않았다**(새 분업의 첫 적용).
2. 정규화 CLI → 자산 14, 검증 오류 0.
3. 추출기(`draft-screen-spec.mjs`) 실행 → 7개 중 2개만 정확(이전·조직 만들기). 라디오 카드를 개별 버튼으로 오인하고 조직도 전체를 놓쳤다. **추출기 결함이 아니라 스펙 체계에 그 요소가 없어서다.**
4. 결정 6건을 사용자에게 확인(범위·제출 여부·초기화 규칙·편집 범위·이동 대상·개수 제한).
5. 스키마 확장 → 스펙 데이터 작성 → 구현 → 테스트 50 + e2e 5.
6. 검증: e2e 스크린샷 4장 자동 생성·AI 판독. 조직도·연결선·라디오 카드·전환 초기화 모두 reference와 일치.

## 완료 기준

1. 레이아웃: 구조·순서·정렬·상대 비율이 `reference.png`와 일치. — 통과
2. 동작: 기본/빈 전환 시 부서 초기화, 부서 추가·이름 수정·삭제, 회장단 이름 수정, 제출 성공 시 ORG-10 이동 + 스코프 제거. — 통과
3. 검증: 빌드·린트·검증 CLI 오류 0 유지. — 통과

## 스펙 필드 소비 점검

| 필드 | 소비 |
| --- | --- |
| `meta.eyebrow`·`title`·`description`·`footerNote` | 렌더 |
| `select.label: null` | 라벨 없는 필드로 렌더(없는 카피를 지어내지 않는다) |
| `select.initialValue` | **이번에 처음 소비.** 스코프가 비었을 때의 유효값 |
| `select.presentation: choiceGroup` + `options[].description` | 라디오 카드 |
| `list.*` 전체(rootItem·initialItems·resetOnChangeOf·minItems·maxItems·itemActions·itemNote·addLabel) | OrgTree |
| `action.submit`·`mutationKey`·`onSuccess.navigate`·`onSuccess.scopeEvent` | 제출 → 이동 → 스코프 제거 |
| `mutations.json`의 `request`·`payloadScope`·`messages` | mock 전송·상태 문구 |

**신규 마찰 계급 3건(1·2·3).** 방법론의 수렴 조건은 여전히 미달성이지만, 성격이 다르다 — ORG-02는 목록·제출이라는 **큰 미개척 영역**을 한 번에 흡수했다.

## 새 분업의 첫 측정

| | ORG-01 | ORG-02 |
| --- | --- | --- |
| 추출기 재현율 | 8/9 | 2/7 |
| 사람이 답한 결정 | 15건(추출기 질문) | 6건(설계 결정) + 10건(추출기 질문) |

재현율이 떨어진 이유는 추출기 성능이 아니라 **스펙 체계에 없는 요소가 많았기 때문**이다. `list`와 `options[].description`이 생겼으니 같은 화면을 다시 뽑으면 재현율이 오른다 — 다음 사이클에서 확인할 것.
