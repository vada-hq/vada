# 덩어리 만드는 순서

다시 만들기(`docs/superpowers/specs/2026-10-19-rebuild-design.md`)의 덩어리는 모두 이 순서로 만든다. 에이전트와 사람이 같은 순서를 따른다.

## 결정하는 방법

- 설계 결정, 설계서, 계획은 사람에게 묻지 않는다. 에이전트가 유사 서비스(예: 카카오톡, Slack, Matrix)를 벤치마킹하고 업계 표준(공식 문서, 표준 문서, 정석 자료)을 웹에서 찾아 권장대로 정한다.
- 근거상 둘 다 가능하면 나중에 바꾸거나 되돌리기 쉬운 쪽을 고른다.
- 정한 것은 근거와 출처, 되돌리기 쉬운 정도와 함께 남긴다. 설계를 바꾸는 결정은 vada-docs의 결정 기록과 설계 문서에, 나머지는 설계서와 진행 기록(`progress.md`)에 적는다.
- 사람은 다 만들어진 결과와 '정한 것' 목록을 보고 검토한다.

## 한 덩어리의 순서

| 단계 | 하는 일 | 남는 것 | 사람 |
|---|---|---|---|
| 0. 도구·규칙 점검 | 사전 조사를 시작할 때 아래 목록을 본다. 걸리는 항목마다 지금 정할 규칙, 시험, 도구를 사전 조사의 '정할 것'에 넣는다 | 사전 조사 파일 맨 위의 '도구·규칙 점검' 줄(없으면 "없음") | |
| 1. 사전 조사 | 앞 덩어리를 만드는 동안 시작한다. 설계 문서(vada-docs), 옛 코드(git 기록), 앞 덩어리가 주는 연결점, 유사 서비스와 업계 자료를 모아 정할 것을 뽑는다 | `.superpowers/research/`(git 밖) | |
| 2. 결정 | 정할 것마다 벤치마킹과 업계 표준 근거로 권장대로 정한다(위 '결정하는 방법'). 설계가 바뀌면 vada-docs에 먼저 적는다(결정은 `decisions/`, 표는 `physical-model.md`) | 결정 그림(`notes/`), vada-docs 커밋 | |
| 3. 설계서 | 범위, 결정, 화면, API, 테스트, 원칙 대조를 적는다 | `docs/superpowers/specs/` | |
| 4. 계획 | 작업마다 계약, 지켜야 할 조건, 작업 사이의 관계, 받아들일 테스트, 커밋 제목을 적는다. 코드는 실행 때 한 번만 쓴다. 서로 기대지 않는 일은 갈래로 나눈다(계약 먼저 → 서버 갈래·화면 갈래). 설계서의 요구와 작업·테스트의 대응을 따로 점검한다 | `docs/superpowers/plans/` | |
| 5. 실행 | 작업마다 새 작업자가 만들고 다른 검토자가 본다(아래 '실행 규칙') | 덩어리 가지의 커밋, `.superpowers/sdd/<계획>/progress.md` | |
| 6. 마무리 검토 | 가지 전체를 한 번 더 본다. 같은 때 가지에서 CI를 돌린다. 지적은 한 번에 고치고 고친 곳만 다시 본다 | 수정 커밋, CI 기록 | |
| 7. 검토와 반영 | 사람이 다 만들어진 결과와 '정한 것' 목록을 검토한다. 반영하라고 하면 가지를 main에 fast-forward로 합쳐 올린다. Render가 배포한다 | main | 검토, "반영해" |
| 8. 확인 | 공개 주소 → 데스크톱 Chrome → 아이폰·갤럭시 순서로 확인한다(아래 '배포 뒤 확인') | `docs/device-checks.md` | 기기로 해 본다 |
| 9. 넘기기 | 정한 것 목록을 사람이 읽을 그림으로 만들고, 미룬 작은 항목과 확인 안내를 다음 덩어리의 기록으로 옮긴다 | `notes/`, 다음 덩어리의 `progress.md` | |
| 10. 회고 | 넘기기 뒤, 다음 덩어리를 실행하기 전에 한다. 단계별로 걸린 시간(커밋 시각과 에이전트 시간), 검토가 잡은 것의 종류와 수, 다시 한 일, 기다린 곳을 세어 병목을 찾는다. 고칠 것은 근거와 함께 이 문서에 반영하고, 그다음 덩어리를 실행한다 | `notes/`의 회고 그림, 이 문서의 수정 커밋 | 회고를 보고 정한다 |

## 0단계 점검 목록

이 덩어리가 아래를 새로 만드는가?

- **뒤에서 돌리는 일**(예약 실행, 대기열, 재시도). 여러 번 돌아도 결과가 같은가, 겹쳐 돌지 않게 막는가, 실패를 어디서 보는가를 정한다. 옛 배송 실행기는 GitHub Actions 예약 실행과 `concurrency`를 썼다(origin/main의 `.github/workflows/delivery-worker.yml`).
- **파일 올리기**(영수증 R2). 크기와 형식 상한, 올리기 주소 만료, 공개되지 않는 버킷, 이름과 형식 검사를 정한다([OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)).
- **속도 제한**(로그인, `/api/public/` 참가 신청, 알림 보내기). 기준(사람·IP·학생회)과 상태를 어디에 둘지(서버 한 대의 메모리인가 DB인가) 정한다.
- **외부 webhook과 콜백**. 서명 확인과 재전송 막기를 정하고, `boundary.test.ts`의 `outsideGuard`에 이유를 적는다(AGENTS.md '새 API를 만들 때').
- **새 비밀 값이나 환경 변수**. `runtime.ts` 필수 목록, CI 운영 모드 시작의 가짜 값, Render 설정, `.env.example`을 함께 고친다. 비밀이 늘면 기준선 조사(`.superpowers/research/2026-10-20-engineering-baseline.md`) 2절 '비밀 스캔'의 다시 볼 조건을 확인한다.
- **새 의존성**. 정확한 버전으로 넣고, 관리가 되는지와 라이선스를 본다. 운영 의존성(`dependencies`)이면 `npm audit` 결과를 본다.
- **새 표, 칸, 제약**. AGENTS.md '마이그레이션' 순서를 따른다.
- **새로 저장하는 개인정보**. 로그와 Sentry에 넣지 않고(`scrubEvent`), 보관 기간을 정한다.
- **새 라우트 모듈**. `AppOptions`로 연결하고 경계 시험을 둔다(AGENTS.md '새 API를 만들 때').
- **새 경계 규칙**. "이 폴더는 저것을 import하지 않는다" 같은 규칙이 생기면 문장 대신 `no-restricted-imports` override로 강제할 수 있는지 본다.
- **기준선 조사 2절의 '다시 볼 때' 조건이 이번 덩어리에서 걸리는가.** 예를 들어 결제, webhook, 파일 올리기는 SAST와 비밀 스캔의 조건이다. PGlite와 Postgres 차이로 결함이 나면 postgres 컨테이너, 사람 개발자가 합류하면 PR 필수다.

## 실행 규칙

- 가지는 덩어리마다 하나다. 작업마다 로컬에 커밋하고, 가지는 GitHub에 백업으로 올린다. main은 사람이 반영하라고 할 때만 올린다. 올리면 바로 배포된다.
- 작업자는 저장소 옆의 작업 폴더(git worktree)에서 일한다. 서로 기대지 않는 갈래(예: 서버와 화면)는 갈래마다 작업 폴더를 따로 두고 동시에 만든다. 갈래가 함께 쓰는 계약은 먼저 넣고 고정한다. 갈래마다 코드를 쓰는 작업자는 늘 하나다.
- 저장소 폴더는 합친 커밋을 따라간다. 검토자와 품질 검사는 그 폴더나 git 기록을 본다.
- 작업 N이 커밋되면 N의 검토와 N+1의 작업을 함께 시작한다. N의 수정은 그 갈래의 N+1이 커밋된 뒤에 한다.
- 주소, 인증, 권한, 데이터, 운영 DB의 경계를 건드리는 작업은 가장 큰 모델이 검토하고, 나머지는 중간 모델이 검토한다.
- 노력값(effort)은 역할마다 정한다. 진행·조사·계획·마무리 검토, 경계를 건드리는 작업의 검토, 코드를 새로 쓰는 작업자는 xhigh, 코드가 정해진 작업자와 그 밖의 검토는 high, 기계적인 일은 medium이다. max는 쓰지 않는다(Anthropic 안내: 코딩과 에이전트 작업은 high나 xhigh에서 시작하고 max는 가장 어려운 문제에만). 하위 에이전트는 따로 정하지 않으면 진행 대화의 노력값을 물려받는다.
- 작업 중에는 바뀐 곳에 영향을 받는 테스트만 돌린다. 전체 테스트는 갈래마다 작업자가 커밋 전에 한 번, 그리고 마무리의 가지 CI에서 돌린다. 검토자는 코드를 읽다 의심이 생긴 곳의 테스트만 돌린다. 전체 테스트(서버 전체, 화면 전체)는 컴퓨터 전체에서 한 번에 하나만 돈다. `npm test`가 잠금을 잡고, 잡혀 있으면 기다린다. 진행 에이전트의 합친 뒤 검사도 타입 검사 → 서버 → 화면 → 빌드 차례로 돌린다. 까닭(바탕 회고): 둘을 겹치면 시험 하나가 0.6초에서 1.3~1.7초로 느려져 임계 경로가 14분 늘었고, 코어가 이미 꽉 차 있어 동시에 돌려도 전체로는 빨라지지 않는다(리틀의 법칙, 칸반의 동시 작업 제한).
- 작업자는 커밋 전에 `npm run check`(형식 확인, 린트, 타입 검사)를 돌려 0으로 끝낸다. 형식은 Prettier가 정하므로 검토에서 형식을 지적하지 않는다.
- 검토자는 패키지를 새로 깔지 않는다. 그 갈래의 작업 폴더나 저장소 폴더를 읽기만 한다. 코드를 일부러 고장 내 테스트가 잡는지 보는 확인은 주소, 인증, 권한, 데이터, 운영 DB의 경계 항목에만 한다. 그때는 복사본을 만들되 저장소 폴더의 `node_modules`를 연결해 쓴다. 까닭: 바탕에서 재검토 하나가 새로 깔고 고장 23개를 돌리느라 17분이 걸렸고, 같은 때 서버 전체 테스트가 76초에서 252초로 늘었다. 에이전트들이 한 컴퓨터를 나눠 쓴다.
- 작업자는 브라우저를 열지 않는다. 화면은 진행을 맡은 에이전트가 `/ui.html`을 데스크톱 폭과 휴대폰 폭(390px)으로 찍어 본다. 휴대폰 폭은 HTTP로 띄운 틀 안의 iframe으로 찍는다. 파일로 연 틀은 빈 화면이 될 수 있다.
- 계획의 지킬 조건과 작업 지시는 아래 '자주 잡힌 것'을 가리킨다. 작업자는 커밋 전에 스스로 확인하고, 검토자는 같은 목록으로 본다(Deming "검사에 기대지 말고 품질을 만들어 넣어라", Google 코드 리뷰 지침의 작성자 쪽 안내). 두 작업 이상에서 다시 잡힌 것만 목록에 더한다.
- 진행 에이전트는 넘긴 일이나 끝을 기다리는 일이 있을 때 사람의 답을 기다리는 질문 창을 쓰지 않는다. 답 없이 할 수 있는 일을 먼저 다 보내고, 물을 것은 턴 끝 글에 한 줄로 남긴다. 저장소 밖 일(전역 설정, 계정)은 넘기기의 '사람이 정할 것'에 모은다. 작업이 닫힐 때와 30분마다 '지금 위치' 한 줄을 남긴다. 까닭(바탕 회고): 밤 2시의 질문 하나가 9시간 41분 진행을 멈췄다(제약 이론: 제약을 굶기지 말라).
- 하위 에이전트 지시는 15줄 이하의 틀(목표, 읽을 파일 경로, 결과 모양, 하지 말 것)로 쓰고 자세한 것은 지시 파일에 둔다. 진행 기록은 사건마다 한 줄(판정, 숫자, 커밋)이고 긴 내용은 보고 파일로 보낸다(Anthropic "Effective context engineering for AI agents").
- 계획과 다르게 정한 것은 기록(`progress.md`)에 `Ruling:`으로 남기고, 덩어리가 끝나면 사람이 읽을 목록으로 옮긴다.
- 작업자와 검토자는 `.env`를 읽지 않고, 실제 DB에 닿는 명령을 실행하지 않는다.

## 자주 잡힌 것

바탕(덩어리 2)의 검토에서 두 작업 이상 다시 잡힌 것이다. 계획과 작업 지시가 가리키고, 작업자는 커밋 전에 확인한다.

1. 대상이 사라지거나 권한을 잃은 대화상자와 양식은 닫고 이유를 보인다.
2. 진행 중인 버튼은 막는다(두 번 보내기 금지).
3. 오류는 그 동작 옆에 보인다(390px에서 보이는 곳).
4. 401·403·404 경로마다 시험을 둔다.
5. 한국 날짜 경계는 ±1초로 시험한다.
6. 다른 학생회 사람으로 시험한다.
7. 맥락이 없으면 거부한다(기본 거부).
8. 응답은 거래 안에서 만든다.
9. 두 번째 복사가 생기면 공유 도우미로 옮긴다.
10. 시험은 고정 시간 대기 대신 끝난 일을 기다린다. 명령줄 입구는 얇게 두고, 인자 읽기와 실행은 시험이 있는 모듈에 둔다.

## 함께 진행하는 것

- 다음 덩어리의 사전 조사, 결정, 설계서, 계획은 지금 덩어리를 실행하는 동안 진행한다.
- 다음 덩어리의 실행은 지금 덩어리의 회고(10단계) 뒤에 시작한다. 회고에서 고친 규칙을 다음 덩어리의 계획에 먼저 반영한다.
- 같은 파일을 건드리지 않는 일만 동시에 한다. 같은 파일을 건드리면 차례로 한다.

## 사람이 하는 것

- 다 만들어진 결과와 '정한 것' 목록을 검토한다.
- "반영해"로 운영 배포를 정한다.
- 운영 DB에 적용하는 것(바꾸는 날)을 승인한다.
- 실제 기기로 확인하고, 계정이 필요한 일(Neon, Render, Google 등)을 한다.
- 설계 결정, 설계서, 계획은 따로 승인하지 않는다(위 '결정하는 방법').

## 배포 뒤 확인

1. 공개 주소에서 바뀐 정적 파일과 경로가 기대한 상태 코드를 주는지 본다.
2. 데스크톱 Chrome으로 운영 주소에서 그 덩어리의 흐름을 한 번 해 본다. 휴대폰보다 먼저 한다.
3. 아이폰과 갤럭시로 `docs/device-checks.md`의 단계를 해 보고 결과를 적는다.
4. 막히면 Render에서 이전 배포로 되돌린다.
