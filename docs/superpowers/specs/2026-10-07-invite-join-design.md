# 학생회 가입·초대 설계

2026-10-07 작성. 정책은 [구매 모델의 정책 결정 1번](../../purchase-model.md#정책-결정-2026-10-07)을 따른다.

## 목표

학생회 사람이 DB 작업 없이 스스로 들어온다. 지금은 `apps/api/scripts/manage-test-data.ts`로 사람마다 소속을 직접 넣는다.

완료 기준:
- 초대 링크를 받은 사람이 로그인하고 [참여하기]를 누르면, 바로 그 학생회의 행사 화면으로 간다.
- 링크 대신 8자리 초대 코드를 직접 입력해도 같은 흐름으로 들어온다.
- 카카오톡으로 받은 링크를 눌러도 로그인할 수 있다.
- 부원은 사이드바에서 초대 링크와 코드를 복사할 수 있다.
- 학생회는 지금처럼 스크립트로 미리 만든다.

## 정책 (확정)

- 학생회마다 초대 코드가 하나 있다. 초대 링크는 이 코드를 담은 주소다. 받은 사람은 로그인한 뒤 바로 가입하고, 부서는 고르지 않는다.
- 링크와 코드는 부원 누구나 공유한다. 관리자 역할은 두지 않는다.
- 판단 기준은 사용자에게 가장 직관적이거나 구현이 가장 간단한 쪽이다. 링크를 악용할 여지는 고려하지 않는다.

## 와이어프레임과의 관계

Figma `B5OHqrl9bbvXCUkhME4Sfo`의 가입 흐름은 SIGN-IN(`568:2`) → 프로필 입력 ONB-01(`3:2`) → 시작 방식 선택 ONB-02(`10:2`) → 초대 코드 입력 INV-00(`13:2`) → 학생회 확인 INV-01(`9:2`) 순서다. 초대 링크로 들어오면 ONB-02를 건너뛴다.

- **맞춘 것:** 참여하면 "미배정 구성원"으로 등록되고 부서는 나중에 배정한다(INV-01). 초대 코드는 8자리 영문 대문자·숫자다(INV-00 예시 `AB12CD34`). 링크와 코드는 같은 초대 권한이다(ORG-03C `30:5153`).
- **앞서 정한 대로 다르게 둔 것:** 초대는 누구나 할 수 있다. 와이어프레임 ORG-04(`30:6177`)는 회장단과 부서장만 초대할 수 있지만, 지금 앱에는 역할이 없다. 링크·코드 재생성과 만료는 만들지 않는다. 와이어프레임에 "다른 학생회 참여 중" 오류 예시가 있지만, 지금 앱은 여러 학생회 참여를 지원하므로 막지 않는다.
- **와이어프레임 확정 후로 미룬 것:** 프로필 입력(ONB-01, INV-01의 소속 입력). 학교→단과대학→학부·학과 검색에 대학·학과 데이터가 필요하고, 학번·학년의 저장 위치는 ERD에서 정한다. 학생회 만들기(ORG-01 `11:2`, ORG-02 `12:2`), 부서 배정(ORG-03B `30:4684`), 역할, 카카오 로그인, 구성원 내보내기(ORG-03D `617:2`)도 미룬다.
- 나중에 프로필 입력을 넣을 때는 "코드 확인 → 프로필 입력 → 참여" 순서로 확인 화면과 참여 요청 사이에 끼운다. 이 설계의 API는 바꾸지 않아도 된다.

## 부서와의 관계 (잠정)

부서 편성은 초대보다 늦을 수 있고, 행사마다 달라질 수 있다. 와이어프레임도 행사 운영 조직을 "기본 학생회 조직과는 별도로 관리"한다(EVT-01 `20:6519`). 그래서 가입과 부서 편성을 떼어 놓는다. 부서 구조와 편성 방식은 와이어프레임을 보고 ERD와 함께 정한다.

그때까지는 다음과 같이 한다.
- 소속의 부서는 비어 있을 수 있다. 부서 없는 부원도 채팅, 행사, 구매 요청을 모두 쓴다. 구매 요청의 부서도 비워 둔 채 저장한다.
- 재정 승인은 지금처럼 재정부(`handles_finance`) 소속만 한다. 부서 없는 부원은 재정 기능을 쓰지 못한다.
- 재정 담당은 지금처럼 스크립트(`assignDepartment`)로 지정한다. 초대로 들어와 부서가 비어 있는 소속에도 부서를 넣을 수 있게 고친다. 이미 부서가 있으면 지금처럼 덮어쓰지 않는다.
- 부서 없는 부원의 구매 요청을 허용한 것은 구현이 간단한 쪽을 고른 잠정 결정이다. 막을지는 ERD 때 다시 정한다. 그때는 서버 검사만 더하면 된다.

## 데이터

마이그레이션 `0009_organization_invite_code.sql` 하나로 바꾼다. `npm run db:generate`로 만든 파일 맨 앞에 코드 생성 함수를 직접 추가한다.

| 변경 | 내용 |
|---|---|
| 함수 `vada_invite_code()` 추가 | `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`(헷갈리는 0·1·I·O를 뺀 32자)에서 8자를 뽑는다. 글자마다 `gen_random_uuid()`의 첫 바이트를 32로 나눈 나머지를 쓰므로 고르게 뽑힌다(40비트) |
| `organizations.invite_code` 추가 | text, NOT NULL, UNIQUE, 기본값 `vada_invite_code()`, CHECK `invite_code ~ '^[2-9A-HJ-NP-Z]{8}$'` |
| `memberships.department_id` | NOT NULL을 푼다 |
| `purchase_requests.department_id` | NOT NULL을 푼다 |

- 기본값은 호출할 때마다 새 값을 만든다. 그래서 마이그레이션 때 기존 학생회마다 서로 다른 코드가 들어가고, 이후 만드는 학생회도 코드를 자동으로 받는다.
- 경우의 수는 2^40(약 1.1조)이다. 학생회가 10개여도 아무 코드나 맞히려면 로그인한 상태로 평균 약 1,100억 번을 시도해야 한다. 그래서 따로 횟수 제한을 두지 않는다.
- 학생회와 부서를 함께 참조하는 복합 외래 키는 그대로 둔다. 부서가 비어 있으면 검사하지 않고, 부서가 있으면 지금처럼 같은 학생회의 부서만 허용한다.

## API

| 경로 | 인증 | 동작 |
|---|---|---|
| `GET /api/me/memberships` (기존) | 로그인 | 소속마다 `organization.inviteCode`를 함께 준다. 부서가 비어 있으면 `department`는 `null`이다 |
| `GET /api/invites/:code` | 로그인 | `{ organization: { id, name }, joined }`를 준다. `joined`는 요청한 사람이 이미 그 학생회 소속인지다. 경로의 코드도 본문과 같은 검사(`InviteCodeSchema`)를 거친다. 검사를 통과하지 못한 코드(NUL 등)와 모르는 코드는 모두 404 `NOT_FOUND`다 |
| `POST /api/organizations/join` | 로그인 | 본문은 `JoinOrganizationSchema = z.strictObject({ code: InviteCodeSchema })`. 코드가 맞으면 부서 없는 소속을 만들고 `{ membership }`을 준다. 모르는 코드는 404 `NOT_FOUND`다. 이미 소속이 있으면 새로 만들지 않고 기존 소속을 그대로 준다 |

- `InviteCodeSchema`는 `token(16)`에 대문자 변환을 더한 것이다. 사용자가 소문자로 입력해도 같은 코드로 찾는다.
- 두 라우트는 기존 `createAccessRoutes`에 넣는다. 그래서 `AppOptions`와 경계 테스트의 모듈 목록은 바뀌지 않는다.
- `POST /api/organizations/join`은 `/api/organizations/` 아래에 있어 공통 가드(출처·형식·크기)를 받는다. `json(JoinOrganizationSchema)`가 인증보다 먼저 검사하고, 경계 테스트가 이 라우트를 자동으로 포함한다.
- `GET /api/invites/:code`는 읽기 전용이라 가드 밖에 둔다. 코드 자체가 초대이므로, 소속이 없는 사람에게도 코드가 맞으면 학생회 이름을 보여 준다.
- 같은 사람이 동시에 두 번 보내도, `(organization_id, user_id)` 유일 제약과 `ON CONFLICT DO NOTHING` 때문에 소속은 하나만 생긴다.
- 코드는 로그에 남기지 않는다. 오류 로그는 지금도 경로 패턴(`/api/invites/:code`)만 남긴다.
- 부서가 비어 있을 때 기존 코드는 이렇게 동작한다.
  - 소속 조회(`queryMemberships`)는 부서를 left join으로 바꾼다. 그래서 부서 없는 부원도 `requireMembership`을 통과한다.
  - 배송 라우트의 재정 검사(`deliveries/routes.ts`)는 부서가 없으면 재정 담당이 아닌 것으로 본다.
  - 재정 확인 쿼리(구매의 `requireFinance`, 배송 서비스)는 inner join이라 고칠 필요 없이 재정 담당이 아닌 것이 된다.
  - 구매 요청은 부서를 비워 둔 채 저장한다. 계약의 `PurchaseSummary.departmentId`는 `string | null`이 된다.

## 화면

링크 형식은 `{origin}/join/{code}`다. 서버(`apps/api/src/web.ts`)는 `/join/:code` 경로에도 `index.html`을 준다.

1. **카카오톡 안의 브라우저:** 구글은 앱 안에 내장된 브라우저에서의 로그인을 막는다(403 `disallowed_useragent`). 사용자 에이전트에 `KAKAOTALK`가 있으면 화면을 그리기 전에 `kakaotalk://web/openExternal?url=<현재 주소>`로 기본 브라우저를 연다. 넘어가지 못하고 남은 경우에는 로그인 화면에 "카카오톡 안에서는 Google 로그인이 막혀 있어요. 메뉴에서 '다른 브라우저로 열기'를 눌러 주세요."를 보여 준다.
2. **로그인 전:** 초대 링크로 들어왔으면 기존 로그인 화면에 "학생회 초대 링크로 들어왔어요. 로그인하면 참여할 수 있어요." 한 줄을 더한다. Google 로그인의 `callbackURL`과 `errorCallbackURL`을 현재 초대 경로로 두어, 로그인 뒤 같은 링크로 돌아온다.
3. **코드 입력 (소속이 없을 때):** 지금의 "소속 미지정" 안내 대신 "초대 코드를 입력해 주세요", 입력칸, [학생회 확인]을 보여 준다. 버튼 활성화는 `InviteCodeSchema.safeParse`로 판단한다.
4. **학생회 확인:** 초대 링크로 들어왔거나 코드를 확인하면 `apps/web/src/access/JoinOrganization.tsx`를 보여 준다. 내용은 "OO 학생회에 참여할까요?", "참여하면 미배정 구성원으로 등록돼요.", [참여하기], [참여하지 않기]다.
5. **참여 후:** 참여에 성공했거나 이미 참여한 학생회면, 주소를 `/`로 바꾸고(`history.replaceState`) 소속을 다시 불러온다. 그다음 그 학생회를 선택한 행사 화면을 연다. [참여하지 않기]를 누르면 주소를 `/`로 바꾸고 평소 화면으로 간다.
6. **복사:** 사이드바의 학생회 이름 아래에 [초대 링크 복사]와 [코드 복사]를 둔다. `navigator.clipboard.writeText`가 성공하면 "복사했어요"를 보여 주고, 실패하면 링크와 코드를 읽기 전용 입력칸에 보여 준다.
7. **부서 표시:** 사이드바와 소속 목록에서 부서가 비어 있으면 "미배정"으로 보여 준다. 재정 배지와 재정 화면은 지금처럼 재정부 소속에게만 보인다.

## 실패 처리

| 경우 | 결과 |
|---|---|
| 모르는 코드, 형식이 틀린 코드 | "초대 코드가 올바르지 않아요. 다시 확인해 주세요." 링크로 들어왔으면 [VADA로 가기]를 함께 보여 준다. 누르면 주소를 `/`로 바꾸고 평소 화면으로 간다 |
| 초대 확인이나 참여 요청 실패(네트워크, 5xx) | 오류 문구와 [다시 시도] |
| 이미 참여한 학생회 | [참여하기] 없이 바로 그 학생회 화면으로 간다 |
| 로그인 실패(`?error`) | 기존 오류 문구를 보여 주고 초대 경로는 유지한다 |
| 버튼을 두 번 누름 | 요청 중에는 버튼을 끈다. 서버도 소속을 하나만 만든다 |
| 카카오톡 브라우저에서 외부 브라우저로 넘어가지 못함 | 로그인 화면에 '다른 브라우저로 열기' 안내를 보여 준다 |

## 테스트

- **API (`access.test.ts`):** 다음을 확인한다.
  - 성공하면 부서 없는 소속이 생긴다. 소문자로 보내도 같은 학생회에 참여한다.
  - 이미 참여한 사람이면 기존 소속과 부서가 그대로다.
  - 미인증은 401, 모르는 코드는 404다. 경로 코드에 NUL이 있거나 상한+1이어도 500이 아니라 404다.
  - 본문의 필수값 누락, 빈 문자열, 공백만, 상한+1(이모지 포함), NUL, 홀로 쓰인 서러게이트, 모르는 키는 400이다.
  - 소속 응답의 `inviteCode`는 자기 학생회 것만 나온다.
  - 부서 없는 부원도 학생회 라우트(행사 목록)를 통과한다.
- **부서 없는 부원 (`purchases.test.ts`, `deliveries/routes.test.ts`):** 구매 요청 초안을 만들 수 있고, 부서는 비어 있는 채로 저장된다. 재정 검토와 배송 등록은 403이다.
- **스크립트 (`scripts/test-data.test.ts`):** 부서 없는 소속에 부서를 넣을 수 있다. 다른 부서가 이미 있으면 거부한다.
- **경계 테스트:** 새 `POST`가 자동으로 포함되는지 확인한다. 테스트 코드는 바꾸지 않는다.
- **마이그레이션 (`migrations.test.ts`):** 0009 적용 전에 학생회 2개와 소속을 넣고 적용한 뒤 다음을 확인한다.
  - 학생회마다 형식(`^[2-9A-HJ-NP-Z]{8}$`)에 맞는 서로 다른 코드가 생긴다.
  - 기존 소속의 부서는 그대로다.
  - 부서 없는 소속을 저장할 수 있다.
  - 다른 학생회의 부서는 여전히 거부된다.
  - 같은 코드와 형식이 틀린 코드는 거부된다.
- **계약 (`packages/contracts`):** `InviteCodeSchema`가 소문자를 대문자로 바꾸고, 앞뒤 공백을 지우고, 제어 문자를 거부한다.
- **웹 서버 (`web.test.ts`):** `/join/abc`가 `index.html`을 주는지 확인한다.
- **화면 (vitest):** 다음을 확인한다.
  - 카카오톡 사용자 에이전트면 외부 브라우저 주소로 이동하고, 그 밖의 브라우저면 이동하지 않는다.
  - 로그인 전 초대 문구와 `callbackURL`.
  - 코드 입력 → 학생회 확인 → 참여 후 그 학생회 선택.
  - 잘못된 코드, 이미 참여, [참여하지 않기].
  - 복사 성공과 실패, "미배정" 표시.
- **실제 확인 (사용자):** 배포 후 학생회 소속이 없는 Google 계정으로 다음을 해 본다. Google 로그인과 카카오톡이 필요하다.
  - 카카오톡에서 초대 링크 열기 → 기본 브라우저로 넘어가는지 → 가입.
  - 코드 직접 입력 → 가입.

## 배포 순서

새 코드는 `/api/me/memberships`에서 `invite_code`를 읽는다. 마이그레이션 전에 배포하면 모든 사용자가 소속을 불러오지 못한다. 그래서 제약을 추가할 때와 반대로 마이그레이션을 먼저 적용한다. 마이그레이션은 함수·칸 추가와 NOT NULL 해제뿐이라, 지금 배포된 코드는 그대로 동작한다.

1. 브랜치에서 구현하고 테스트한다.
2. 승인을 받은 뒤 dev(`.env`의 `DATABASE_URL`)와 m1-preview에 0009를 적용한다. 적용 전에 이미 적용된 기록이 로컬 파일과 순서·해시까지 일치하는지 확인한다.
3. main에 병합하고 푸시한다(자동 배포). 운영에서 잘못된 코드의 초대 링크와 소속 응답을 확인한다.
4. AGENTS.md의 마이그레이션 절에 "새 컬럼을 읽는 코드는 두 DB에 마이그레이션을 먼저 적용한 뒤 배포한다"를 추가한다. ERD.md에는 `invite_code`와 비워 둘 수 있게 된 부서 칸을 반영한다.
