# 다시 만들기: 설계대로 새 표 위에

2026-10-19. vada-docs의 설계(model.md, logical-model.md, physical-model.md, DEC-12~45)는 vada 코드와 따로 만들었다. 시범 운영 전에 vada를 그 설계대로 새로 만들기로 했다(vada-docs DEC-43). 무엇을 어떤 등급으로 만들지는 vada-docs RFC-7에, 시범 운영에서 할 세 시험은 RFC-8에 있다.

이 문서는 다시 만들기 전체의 방법을 정한다. 일을 어떤 덩어리로 나눠 어떤 순서로 만드는지, 표를 어떻게 바꾸는지, 막히면 어떻게 되돌리는지다. 덩어리마다의 기능 설계는 덩어리마다 spec을 따로 쓴다. 첫 덩어리는 `2026-10-19-mobile-path-design.md`다.

## 정한 것과 짐작

- **정한 것(사용자)**
  - 시범 운영 전에 설계대로 다시 만든다(DEC-43). 꼭 할 것, 되도록 할 것, 할 수 있으면 할 것을 모두 계획에 넣는다. 꼭 할 것은 들일 시간의 60%를 넘지 않게 잡는다.
  - 가장 불확실한 것을 실제 기기로 먼저 확인한다. 카카오톡에서 바깥 브라우저로 넘어가 로그인하고, 홈 화면에 추가하고, 알림을 받는 일이다.
  - 지금 vada를 시연용으로 남기지 않는다. 따로 띄우지 않고 main에서 바로 바꾼다(20261019).
    - 바탕을 배포하는 날부터 옛 기능은 vada-m1에서 사라진다.
    - 새 기능은 만든 데까지만 보인다.
  - 점검과 시작 판단을 둔다. 날짜는 GitHub Project `vada-hq` #2에서 관리한다(DEC-43).
- **짐작(틀리면 고친다)**
  - 만드는 사람은 한 명과 AI다. vada의 커밋은 모두 한 사람의 것이다.
  - 배포 DB에는 시연 데이터만 있다. 옮길 실제 데이터는 없다(RFC-7).

## 덩어리

| 덩어리 | 만드는 것 | 지금 vada에서 가져오는 것 | 다 됐다고 보는 때 |
|---|---|---|---|
| 1. 휴대폰 길 | 카톡에서 못 넘어갔을 때의 화면, 홈 화면 설정(manifest)과 아이콘, 서비스 워커, 알림 켜기와 시험 알림, 아이폰 홈 화면 앱 안의 로그인 | 카톡 넘기기, Google 로그인 | 아이폰과 갤럭시에서 링크부터 시험 알림까지 끝까지 된다 |
| 2. 바탕 | 새 DB와 첫 마이그레이션, 기록과 판(DEC-33, DEC-34), 학생회·기수·운영진·부서·직급·소속(DEC-16, DEC-17), 권한(DEC-27, DEC-28), 들이기와 내보내기, 초대 코드 바꾸기, 알림 받을 기기 | 로그인 표 4개, 공통 가드와 입력 검사, 오류 기록, 화면 부품, 테스트 틀 | 권한 엔진과 조직 칸, 공통 규칙을 테스트로 확인했다. 나머지 칸은 그 기능의 덩어리가 더한다. vada-m1이 새 DB 위에서 로그인, 학생회 만들기, 들이기가 된다 |
| 3. 대화와 알림 | 전체방·회장단방·부서방·1:1(DEC-12, DEC-18, DEC-20), 사진, 안 읽은 수, 공지(DEC-14), 부르기, 새 글과 부름 알림 | 대화 화면 틀 | 휴대폰 두 대로 주고받고 알림이 온다 |
| 4. 업무 | 학생회 업무와 행사 업무, 담당자, 마감, 상태(DEC-22, DEC-39), 배정 알림 | 행사 업무 | 업무를 맡기면 맡은 사람의 휴대폰에 알림이 온다 |
| 5. 구매와 지출 | 회계 기간과 예산 항목, 요청과 품목과 품목마다 결재(DEC-15, DEC-41, DEC-42), 지출(DEC-40, DEC-45), 증빙과 사진, 메시지에서 요청이나 지출 만들기, 결과 알림 | 지출, 증빙, 영수증 저장소(R2) | 대화 속 부탁에서 지출 기록과 사진 증빙까지 휴대폰으로 된다 |
| 6. 시작 준비 | 행사 만들기와 책임자(DEC-28), 계좌(DEC-45), 처리방침과 약관과 가입 동의, 유료 서버, 로그인 앱 게시, 백업, 새 표에 맞춘 시연 데이터, 남는 시간에 되도록 할 것 | 행사 만들기, 시연 데이터 도구 | 리허설이 끝까지 된다 |
| 7. 쓰기 전에 | 참가 신청과 QR과 열람 기록(DEC-3, DEC-28, DEC-44), 정산과 환급, 결산과 이월과 감사 증빙 묶음 | 신청, QR 출석, 정산, 결산, 엑셀 | 시범 운영 중 각각 처음 쓰기 전 |

- 덩어리마다 spec, plan, 구현, 배포, 확인을 한 번씩 거친다.
- 덩어리 1은 표와 상관이 없어 지금 vada 위에서 만든다. 2부터는 새 표 위에서 만든다.
- 되도록 할 것(RFC-7)은 6에서 남는 시간에 한다. 할 수 있으면 할 것은 7 뒤에 한다. 점검에서 늦으면 되도록 할 것부터 뺀다.
- 7은 시범 운영 중에 배포한다. 운영진이 쓰는 동안이라, 배포 전에 시연 학생회에서 먼저 확인한다(DEC-43).

## 관문

- **점검:** 2~5가 새 표 위에서 휴대폰으로 되는지 본다. 남은 일이 있으면 되도록 할 것을 모두 빼고 리허설 시간을 지킨다.
- **시작 판단(리허설):** 다음이 휴대폰으로 끝까지 되면 시작한다. 안 되면 시작을 미룬다(DEC-43).
  - 로그인과 알림
  - 사진
  - 구매 부탁부터 지출 기록까지

## 표를 바꾸는 방법

### 새 DB

- Neon에 새 프로젝트를 만든다.
  - PostgreSQL 18이다. 새 프로젝트의 기본값이다.
  - 지금 DB와 같은 지역에 둔다.
  - 가지는 둘이다. 기본 가지를 배포용으로 쓰고, 거기서 딴 `dev` 가지를 개발용으로 쓴다. 지금은 개발 DB가 기본 가지(`production`)이고 배포 DB가 `m1-preview`라 이름이 거꾸로다. 이것도 여기서 바로잡는다.
- 새 DB를 쓰는 까닭은 세 가지다.
  - 설계는 식별자를 `uuidv7()`로 만든다(physical-model.md). 이 함수는 PostgreSQL 18부터 있다. 지금 DB의 버전은 확인하지 않았다.
  - 옮길 실제 데이터가 없다. 그리고 옛 마이그레이션 기록과 부딪치지 않는다.
  - 옛 DB가 그대로 남아 되돌릴 수 있다.
- 옛 DB 둘(`production`, `m1-preview`)은 시범 운영이 시작할 때까지 지우지 않는다.

### 첫 마이그레이션

- `apps/api/migrations`를 새로 시작한다. 옛 마이그레이션 29개는 지운다. git 기록에는 남는다.
- `0000_baseline.sql` 하나에 다음을 담는다.
  - **로그인 표 4개:** users, accounts, sessions, verifications. 지금 정의 그대로다. 설계 밖이다(RFC-7).
  - **physical-model.md의 SQL 블록:** 손으로 옮기지 않는다. `apps/api/scripts/baseline-from-design.ts`가 옆 폴더 `../vada-docs/physical-model.md`에서 뽑는다.
  - **설계 밖 표 3개:** 로그인 잇기, 초대 코드, 알림 받을 기기다(RFC-7). 바탕 spec(`2026-10-19-foundation-design.md`)에서 정했다.
- 운영진(`member`)과 로그인 계정(`users`)은 '로그인 잇기' 표(설계 밖)로 잇는다. 이메일은 바뀌거나 다른 사람에게 다시 쓰일 수 있어 식별자로 쓰지 않는다(OpenID Connect 5.7, 20261019 바탕 설계에서 고침).
- 이 뒤로 표를 바꿀 때는 physical-model.md를 먼저 고친다. 그다음 `drizzle-kit generate --custom`으로 빈 마이그레이션을 만들고 SQL을 쓴다. 지금의 마이그레이션 규칙(AGENTS.md)은 그대로 따른다.

### 조회용 표 정의와 맞춤 검사

- `apps/api/src/db/schema.ts`를 새 표에 맞춰 다시 쓴다. 표를 만드는 데는 쓰지 않고, 조회의 타입에만 쓴다.
  - `drizzle-kit generate`로 표를 만들지 않는 까닭: physical-model.md에는 drizzle 정의로 담지 못하는 제약이 있다. `EXCLUDE`, 하위 표의 `(id, kind)` 외래 키가 그렇다.
- **CI에서 도는 테스트:** PGlite에 마이그레이션을 적용한 뒤, DB 목록(`information_schema`)과 drizzle 정의를 맞댄다. 표, 칸, 타입, NULL 여부를 본다.
- **로컬 검사(`npm run check:design --workspace @vada/api`):** 마이그레이션을 적용한 DB와 physical-model.md를 그대로 적용한 DB를 맞댄다. 표, 칸, 제약, 인덱스를 본다. 옆 폴더의 vada-docs가 있어야 해서 CI에는 넣지 않는다. 표를 바꿀 때 돌린다.
- vada-docs의 검증 도구(`tools/schema-check`)에 있는 작업 확인은 덩어리마다 해당 기능의 API 테스트로 옮긴다. 판 보관, 신청자 정보 지우기, 계좌별 금액이 그렇다.

### 공통 모듈

- **기록과 판(DEC-33, DEC-34):** 모든 쓰기는 한 모듈을 거친다. 이 모듈이 `record` 행과 하위 행을 함께 만들고, 바꿀 때 판(`record_version`)을 남긴다. 사유를 받는 동작은 이 모듈이 사유를 강제한다.
- **권한(DEC-27, DEC-28):** 권한표 하나를 코드로 두고, 라우트는 그 표만 묻는다. 권한표의 칸마다 테스트를 둔다.
- 두 모듈은 바탕에서 만들고, 3~7은 이 모듈 위에서 만든다. 자세한 것은 바탕 spec에서 정한다.

### 옛 코드

- 바탕의 첫 작업에서 다음을 먼저 지운다(사용자 결정, 20261019).
  - 옛 기능 모듈과 그 테스트. 서버 약 1.3만 줄, 화면 약 1.5만 줄이다.
  - 옛 표 정의와 마이그레이션
  - 계약 패키지의 옛 기능 스키마
- 먼저 지우는 까닭: 표가 바뀌면 어차피 다시 써야 한다. 남겨 두면 구현하는 쪽이 옛 소속·권한 방식을 따라 하게 된다. 지운 코드는 git 기록에 남는다.
- 지운 뒤에는 로그인, 빈 작업 공간, 휴대폰 길만 남은 상태에서 덩어리 2~7을 쌓는다. 끝까지 도는 얇은 뼈대 위에 기능을 붙여 나가는 방식이다(walking skeleton).
- 저장소를 전부 비우지는 않는다. 아래 배관(약 1,700줄과 CI, 배포 설정, 저장소 규칙)은 실제 실패로 다듬은 것이라, 다시 만들면 같은 실패를 다시 겪는다(Spolsky).
- 그대로 가져오는 것은 다음과 같다.
  - Google 로그인(better-auth)
  - 공통 가드, 입력 검사(`packages/contracts`의 `text`, `token`), 경계 테스트
  - 오류 처리와 Sentry
  - 화면 부품(`components/ui`), 카톡 넘기기
  - 영수증 저장소(R2), PGlite 테스트 틀
- 가져온 것의 규칙(AGENTS.md)은 그대로다. 행사 잠금처럼 옛 표에 묶인 규칙은 다시 만드는 기능의 spec에서 새로 정한다.

## 바꾸는 날(바탕 배포)

순서:

1. Neon에 새 프로젝트를 만든다. 개발 가지 주소는 로컬 `.env`의 `DATABASE_URL`에 넣는다. (사용자)
2. 첫 마이그레이션을 새 개발 DB와 새 배포 DB에 적용한다. 적용 전에 DB가 비어 있는지 확인한다. (사용자 승인)
3. Render의 `DATABASE_URL`을 새 배포 DB 주소로 바꾼다. 바탕 커밋이 main에 올라간 뒤에 바꾼다. 둘 사이 몇 분은 화면이 깨진다. 옛 기능을 남기지 않기로 했으므로 받아들인다. (사용자)
4. vada-m1에서 로그인, 학생회 만들기, 초대로 들이기를 확인한다.

되돌리기:

- Render의 `DATABASE_URL`을 옛 주소로 돌린다.
- Render에서 바탕 전 배포로 되돌린다.
- 옛 DB는 시범 운영이 시작할 때까지 그대로 둔다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 시작 날짜를 넘긴다(DEC-43 결과) | 가장 불확실한 것(덩어리 1)을 먼저 한다. 점검에서 되도록 할 것을 뺀다. 기한을 넘기면 늘리지 않고 범위를 자른다(Shape Up) |
| 휴대폰에서만 나는 문제를 늦게 안다 | 덩어리마다 배포하고 휴대폰으로 확인한다. 확인 결과는 `docs/device-checks.md`에 남긴다 |
| 조회용 정의가 설계와 어긋난다 | 맞춤 검사(CI)와 설계 검사(로컬) |
| 바꾸는 날 새 DB에서 막힌다 | 옛 DB와 옛 배포로 되돌린다 |
| 바탕 배포 뒤 vada-m1이 비어 섭외 때 보여 줄 화면이 없다 | 사용자가 받아들였다(20261019). 보여 줄 때는 그 시점까지 만든 것과 vada-docs의 프로토타입을 쓴다 |

## 원칙 대조

이 문서는 만드는 방법만 정하고 기능을 정하지 않는다. 사람이 새로 하는 입력, 근거 연결, 변경 이력은 덩어리마다의 spec에서 대조한다. 기록과 판(DEC-33, DEC-34)을 바탕에 두는 것이 변경 이력의 바탕이다.
