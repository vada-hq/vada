# M5b 결과보고서 설계

2026-10-12. M5a로 행사를 완료하면 옆 메뉴 "기록"으로 옮겨지고 바꿀 수 없게 됐다. 하지만 기록에는 이름과 날짜만 있다. 다음 학생회가 이 행사를 다시 할 때 몇 명이 왔는지, 돈을 얼마 썼는지, 무엇이 아쉬웠는지는 대화방을 처음부터 읽어야 안다.

M5b는 완료한 행사에 결과보고서를 붙인다. 숫자는 행사 기록에서 자동으로 채우고, 사람은 현장 운영·회고·인수인계만 쓴다. 회장단이 발행하면 그때 숫자로 고정된다. 행사에는 담당 부서와 책임자를 정할 수 있게 한다.

## 왜 이렇게

2026-10-12에 사용자가 M5 범위와 아래 비판을 승인했다(M5 전체 중 M5b 부분). 와이어프레임은 REC-01 `30:3292`(완료된 행사), REC-02 `30:3504`(아카이브), REC-02A `30:3988`(작성·검토)이다.

- **결과보고서는 "작성 중 / 발행" 둘이다.**
  - 와이어프레임은 작성 → 검토 요청 → 검토 → 발행이고, 검토자·검토 의견·판 번호(v1.0)가 있다.
  - 학생회는 회장단 몇 명이 다 같이 본다. 검토 단계를 나누면 누가 언제 검토하는지 알림이 있어야 하는데 알림이 없다.
  - 쓰기는 부서가 있는 구성원, 발행은 회장단이다. 검토 의견은 대화방에서 한다.
- **숫자는 행사 기록에서 채운다.** 신청→참석, 예산→집행, 업무 완료·지연, 구매 건수다. 완료한 행사는 바뀌지 않으므로(M5a) 이 숫자는 믿을 수 있다.
- **사람이 쓰는 칸은 다섯이다.** 현장 운영, 잘된 점, 아쉬운 점과 원인, 다음 행사 개선안, 인수인계.
- **뺀 것:** 개요 탭, 자동 타임라인, 만족도, AI 초안, 부서별 체크리스트, 다음 담당자 지정. 인수인계는 자유 글이다.
- **휴대폰은 한 단이다.** 와이어프레임의 목차·오른쪽 패널은 쓰지 않는다.

아래는 승인 범위 안에서 추천대로 정한 것이다(결과 보고에 모은다).

- **결과보고서는 완료한 행사에서만 쓴다.**
  - 와이어프레임도 "기록 > 완료된 행사 > 행사 > 아카이브 작성"이다.
  - 숫자는 완료한 뒤에야 바뀌지 않는다. 정리 중에 쓰면 숫자가 계속 바뀐다.
  - 완료하려면 정산이 끝나야 하지만, 정산은 지출만 기록하면 바로 할 수 있다(영수증은 뒤에 더해도 된다, M2-1).
- **발행 취소가 있다(회장단).** 발행한 뒤 오타를 고칠 길이다. 완료 취소(M5a)와 같은 이유다.
- **발행한 결과보고서가 있으면 완료를 취소할 수 없다.** 먼저 발행을 취소한다. 정산을 다시 열려면 먼저 완료를 취소하는 것(M5a)과 같은 순서다. 그래서 "발행한 보고서의 행사는 늘 완료한 행사"다.
- **발행 조건은 다섯 칸을 모두 쓰는 것이다.** 와이어프레임의 발행 조건(0/6) 가운데 "다음 담당자 지정"을 뺐다. 쓸 것이 없으면 "특이 사항 없음"이라고 쓴다.
- **결과보고서는 행사 탭이 아니라 기록에서 여는 화면이다.** 행사 탭은 다섯 개가 375px 폭에 맞춰져 있다(M5a에서 개요 탭을 넣지 않은 이유). 와이어프레임도 기록 아래 별도 화면이다.
- **담당 부서·책임자는 행사 정보에서 고른다.** 행사 정보(일시·장소)를 고치는 대화상자에 두 칸을 더한다. 업무의 담당 부서·담당자와 같은 규칙이다.
- **행사의 담당 부서는 지울 수 없다.** 구매 요청 기록이 있는 부서를 지울 수 없는 것과 같다. 완료한 행사는 바꿀 수 없어 담당 부서를 비울 수 없고, 비우려면 부서 지우기가 행사 행을 잠가야 해서 업무 추가(행사 → 부서 순)와 잠금 순서가 엇갈린다.

## 범위

- **넣는다**
  - 행사 담당 부서·책임자(선택): 행사 정보에서 고르고, 참가자 탭의 행사 정보·기록 목록·결과보고서에 보인다.
  - 결과보고서: 자동 수치, 다섯 칸 쓰기·저장, 발행·발행 취소
  - 기록 목록(REC-01): 결과보고서 상태, 담당, 참석·예산 집행률·완료 업무 수
  - 볼 수만 있는 행사 화면의 안내 줄에 [결과보고서], 결과보고서에 [행사 기록 보기]
  - 완료 확인 대화상자에 "기록에서 결과보고서를 써요"
  - 시연 데이터: 행사 담당, 발행한 보고서 하나, 작성 중 보고서 하나
- **넣지 않는다**
  - 검토 요청·검토자·검토 의견·판 번호, 목차, 타임라인, 근거 자료의 원본 보기(행사 기록 보기 하나로 대신), 만족도, AI 초안, 부서별 체크리스트, 다음 담당자
  - 미발행 알림 배너, 행사명 검색, 결과보고서 내려받기(PDF·엑셀), 결과보고서 처리 기록(누가 언제 고쳤는지 이력)
  - 정리 중인 행사의 보고서 미리 쓰기

## 정책

1. **행사 담당 부서·책임자**
   - 둘 다 고르지 않아도 된다. 서로 따로 고른다(책임자가 담당 부서 사람이 아니어도 된다).
   - 담당 부서는 같은 학생회 부서다. 아니면 `EVENT_DEPARTMENT_INVALID`(409)다.
   - 책임자는 같은 학생회에서 부서가 있는 구성원이다. 이미 책임자인 사람은 그 뒤 미배정이 되었어도 그대로 둘 수 있다. 아니면 `EVENT_OWNER_INVALID`(409)다.
   - 행사 정보 수정(`PATCH …/events/:eventId`)이 일시·장소와 함께 받는다. 권한(부서가 있는 구성원)과 완료한 행사 잠금은 지금 그대로다.
   - 행사의 담당 부서인 부서는 지우지 않는다(`DEPARTMENT_IN_USE`). 화면 문구는 "구매 요청 기록이 있거나 행사를 맡은 부서는 지울 수 없어요. 이름을 바꿔 쓰세요."로 바꾼다.
2. **결과보고서 상태**
   - 없음(작성 전) → 작성 중 → 발행. 발행 취소하면 작성 중으로 돌아간다.
   - 행사마다 하나다.
3. **권한**
   - 보기: 구성원 모두(미배정 포함)
   - 쓰기(저장): 부서가 있는 구성원(`manageEvents`)
   - 발행·발행 취소: 회장단(`manageOrganization`)
4. **쓰기**
   - 완료한 행사만 된다. 아니면 `EVENT_NOT_COMPLETED`(409)다.
   - 발행한 보고서는 고치지 않는다(`REPORT_PUBLISHED`, 409). 먼저 발행을 취소한다.
   - 다섯 칸을 한 번에 저장한다. 빈 칸은 null이다. 칸마다 2000자까지다.
   - 화면이 본 버전을 보낸다(없으면 0). 다르면 `VERSION_CONFLICT`다.
   - 처음 쓴 사람·때와 마지막으로 저장한 사람·때를 남긴다. 처리 기록 표는 두지 않는다(돈이 바뀌지 않는다, M5a 완료 취소와 같다).
5. **발행**
   - 회장단이 완료한 행사의 작성 중 보고서를 발행한다.
   - 다섯 칸을 모두 써야 한다. 아니면(보고서가 없어도) `REPORT_INCOMPLETE`(409)다. DB CHECK도 같다.
   - 이미 발행했으면 `INVALID_STATE`, 버전이 다르면 `VERSION_CONFLICT`다.
   - 발행하면 그때의 자동 수치와 이름(행사 이름·일시·장소, 담당 부서·책임자 이름)을 보고서에 고정한다. 그 뒤 부서 이름을 바꿔도 발행한 보고서는 그대로다.
   - 발행한 사람과 시각을 남긴다.
6. **발행 취소**
   - 회장단이 발행한 보고서를 작성 중으로 되돌린다. 글은 그대로, 고정한 수치는 지운다(다시 발행할 때 다시 센다).
   - 발행하지 않았으면(보고서가 없어도) `INVALID_STATE`다.
7. **완료 취소와의 관계**
   - 발행한 보고서가 있으면 완료 취소가 `REPORT_PUBLISHED`(409)다.
   - 작성 중인 보고서는 완료를 취소해도 남는다. 다시 완료하면 이어 쓴다. 완료하지 않은 동안은 화면에 보이지 않는다.
8. **자동 수치** (`EventReportFacts`)
   - 신청→참석: 신청 = 취소하지 않은 신청 수(보관 기간이 지나 정보를 지운 신청도 센다), 참석 = 참석을 확인한 신청 수. 참가 신청을 받지 않았으면 없음.
   - 예산→집행: 예산 = 행사 예산(미정이면 없음), 집행 = 취소하지 않은 지출 합(재정 탭의 "실제 지출"과 같다).
   - 업무: 전체, 완료, 지연. 지연 = 마감일이 있고, 마감일(한국 날짜)을 넘겨 끝냈거나 센 날까지 끝내지 않은 업무.
   - 구매: 요청 = 제출한 품목 수(작성 중 빼고 반려·취소 포함), 승인 = 승인 상태인 품목 수.
   - 작성 중이거나 없으면 지금 센다(센 시각을 함께 준다). 발행했으면 발행 때 값이다.
9. **기록 목록**
   - 완료한 행사를 최근 완료 순으로 보인다(지금과 같다).
   - 줄마다 결과보고서 상태(작성 전·작성 중·발행), 이름, 행사 날짜(연도 포함)와 담당, 참석(신청)·예산 집행률·완료 업무 수, 완료한 날.
   - 숫자는 결과보고서와 같은 값이다(발행했으면 발행 때 값).
   - 누르면 결과보고서가 열린다.

## 와이어프레임과 다른 점

| 화면 | 노드 |
|---|---|
| REC-01 완료된 행사 목록 | `30:3292` |
| REC-02 행사 아카이브 상세 | `30:3504` |
| REC-02A 아카이브 작성·검토 | `30:3988` |

- **REC-01**
  - 행사명 검색, "인수인계 문서 미발행 N건" 배너, "상세 보기 →"는 뺀다. 이름을 누르면 열린다.
  - 상태 칩은 "작성 전·작성 중·발행"이다("검토 중", "v1.0" 없음).
  - 날짜 옆은 담당 부서(없으면 책임자)다.
- **REC-02·02A를 한 화면으로**
  - 발행 전에는 쓰는 화면, 발행 뒤에는 읽는 화면이다. 쓸 권한이 없으면 발행 전에도 읽는 화면이다.
  - 목차와 오른쪽 패널(인수인계 체크리스트, 발행 조건, 검토)은 없다. 발행 조건은 아래 고정 줄의 "다섯 칸 중 N칸"이다.
  - 자동 채움 영역은 숫자 넷(신청→참석, 예산→집행, 업무, 구매)이다. 타임라인·근거 자료·만족도·행사 목표·참여 대상·행사 규모는 없다.
  - 회고의 "개선안별 담당 부서", 인수인계의 "재사용 자산·협력처·주의사항·다음 담당" 칸은 없다. 자유 글 안에 쓴다.
  - [임시 저장]은 [저장], [검토 요청]은 회장단의 [발행]이다.

## 데이터 (마이그레이션 0026)

**events** (칸 더하기, 표 맨 뒤)

| 칸 | 내용 |
|---|---|
| `owner_department_id` | text. 담당 부서, 선택. (organization_id, owner_department_id) → departments, `ON DELETE RESTRICT` |
| `owner_id` | text. 책임자의 사용자 ID, 선택. (organization_id, owner_id) → memberships(organization_id, user_id), `ON DELETE RESTRICT` |

- 행사 만들기의 `INSERT … SELECT`는 모든 칸을 고르므로 두 칸을 null로 채운다.
- 업무의 담당 부서·담당자(M4)와 같은 꼴이다.

**event_reports** (새 표)

| 칸 | 내용 |
|---|---|
| `event_id` | PK. (organization_id, event_id) → events, `ON DELETE RESTRICT` |
| `organization_id` | text |
| `status` | `draft` 또는 `published` |
| `operations`, `went_well`, `shortfalls`, `improvements`, `handover` | text, 선택. 현장 운영·잘된 점·아쉬운 점과 원인·다음 행사 개선안·인수인계 |
| `facts` | jsonb. 발행 때 고정한 자동 수치와 이름. 발행했을 때만 있다 |
| `published_at`, `published_by` | 발행한 때·사람(users) |
| `version` | 1부터 |
| `created_by`, `created_at` | 처음 쓴 사람(users)·때 |
| `updated_by`, `updated_at` | 마지막으로 저장한 사람(users)·때 |

CHECK
- `event_reports_status_valid`: status는 둘 중 하나
- `event_reports_published_state`: 발행이면 발행한 때·사람·고정 수치가 모두 있고, 아니면 모두 없다
- `event_reports_published_complete`: 발행이면 다섯 칸이 모두 있다
- 다섯 칸마다 공백만이 아니고(`~ '[^[:space:]]'`) 2000자 이하
- `event_reports_facts_object`: facts는 JSON 객체
- `event_reports_version_positive`

**배포 순서**
- 새 칸·새 표만 더한다. 위반 행이 생길 수 없다.
- 새 코드가 새 칸을 읽으므로 두 DB에 먼저 적용하고 배포한다.
- 적용 뒤 배포 전까지 옛 코드는 새 칸을 모른다. 행사를 만들 때 칸 목록을 적어 보내므로 새 칸은 null이 된다.

## API

본문은 contracts의 `z.strictObject`이고, `json(Schema)`를 인증보다 앞에 둔다. 결과보고서·기록은 새 모듈 `createReportRoutes`(`AppOptions.reports`)다.

**행사 정보** (바뀜)
- `UpdateEventSchema`에 `ownerDepartmentId`, `ownerMembershipId`(둘 다 ID 또는 null)를 더한다. 비울 때도 null로 꼭 보낸다.
- `EventSummary`에 `ownerDepartment: { id, name } | null`, `owner: { membershipId, name } | null`을 더한다. 행사 목록·만들기·수정·완료 응답이 모두 준다.

**기록·결과보고서** (앞부분 `/api/organizations/:organizationId`)

| 경로 | 권한 | 본문 → 응답 |
|---|---|---|
| `GET /records` | 구성원 | → `RecordsResponse` |
| `GET /events/:eventId/report` | 구성원 | → `EventReportResponse` |
| `POST /events/:eventId/report` | 부서가 있는 구성원 | `SaveEventReportSchema` → `EventReportResponse` |
| `POST /events/:eventId/report/publish` | 회장단 | `PublishEventReportSchema` → `EventReportResponse` |
| `POST /events/:eventId/report/unpublish` | 회장단 | `UnpublishEventReportSchema` → `EventReportResponse` |

- `SaveEventReportSchema`: `{ version(0 이상), operations, wentWell, shortfalls, improvements, handover }`. 다섯 칸은 `text(2000)` 또는 null.
- `PublishEventReportSchema`·`UnpublishEventReportSchema`: `{ version }`(1 이상).
- `EventReportResponse`: `{ event: EventSummary, report: EventReportView | null, facts: EventReportFacts, factsAt: string }`
  - `factsAt`: 숫자를 센 시각(ISO). 발행했으면 발행 시각이다.
- `EventReportView`: 상태, 다섯 칸, 버전, 처음 쓴 사람·때, 마지막 저장한 사람·때, 발행(사람·때 또는 null)
- `RecordsResponse`: `{ records: { event: EventSummary, report: { status, publishedAt } | null, facts: EventReportFacts }[] }`
- `EventReportFacts`: `{ event: { name, startsAt, endsAt, place }, owner: { department, person }(이름), registrations: { registered, attended } | null, finance: { budget, spent }, tasks: { total, done, late }, purchases: { requested, approved } }`
- 저장 본문은 다섯 칸 × 2000자라 32KB를 넘을 수 있다. `guard.ts`의 `bodyLimitOf`에 `…/events/:eventId/report`를 64KiB로 더한다.

## 거래와 잠금

- **결과보고서 쓰기·발행·발행 취소:** 행사 행 `FOR SHARE`(완료했는지 본다) → 보고서 행 `FOR UPDATE`.
  - 완료 취소(행사 행 `FOR NO KEY UPDATE`)와 하나씩 진행된다. 발행이 먼저면 완료 취소는 발행한 보고서를 보고 멈춘다. 완료 취소가 먼저면 발행은 `EVENT_NOT_COMPLETED`다.
  - 수치를 셀 때 다른 표는 잠그지 않는다. 완료한 행사의 기록을 바꾸는 쓰기는 모두 행사 행을 잠그고 완료를 보고 멈춘다(M5a).
  - 새 함수 `requireCompletedEvent(tx, organizationId, eventId)`(`events/lock.ts`): `FOR SHARE`, 없으면 `NOT_FOUND`, 완료하지 않았으면 `EVENT_NOT_COMPLETED`.
- **완료 취소:** 행사 행 `FOR NO KEY UPDATE` 다음에 보고서 상태를 읽는다. 발행·발행 취소가 행사 행을 `FOR SHARE`로 잡으므로 그사이 바뀌지 않는다.
- **행사 정보 수정:** 행사(`lockActiveEvent`) → 부서 `FOR KEY SHARE` → 소속 `FOR SHARE`. 업무 추가(행사 → 부서 → 소속)와 같은 순서다.
- **부서 지우기:** 행사 행을 잠그지 않고 담당 부서로 쓰는 행사가 있는지만 본다. 그사이 담당으로 정해지면 지우기의 FK 검사가 23503을 내고 `DEPARTMENT_IN_USE`가 된다(지금 구매 제출과 같다).
- **completion-lock.test.ts:** 결과보고서 쓰기 셋은 "완료한 행사에서 하는 일"(지금의 완료·완료 취소 목록)에 더한다. 이 셋은 반대로 완료하지 않은 행사를 막는다(`reports.test.ts`가 확인).
