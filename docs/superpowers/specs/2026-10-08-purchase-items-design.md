# 구매 품목 단위 전환 설계

2026-10-08 작성. [구매 도메인 관계 설계](../../purchase-model.md)의 품목 단위 결정(2026-10-04)을 스키마와 화면에 반영한다. 구매 재설계 세 단계 중 1차다.

| 단계 | 내용 | 이 문서 |
|---|---|---|
| 1차 | 품목 단위 전환: 데이터 구조, 요청자·재정부 화면, 배송 연결 | 이 문서 |
| 2차 | 채팅 링크 후보 목록: 링크 자동 수집, 상품 정보 미리 조회 | 나중 |
| 3차 | 채팅 알림 카드 | 나중 |

## 목표

구매의 진행 단위를 요청서에서 품목으로 바꾼다. 지금은 요청서 하나가 상태 하나를 가져서, 요청서 전체로만 승인·반려한다. 하지만 배송은 품목 단위로 연결한다.

완료 기준:
- 끼룩이 대화상자에 쿠팡 링크를 넣으면 링크마다 작성 중 품목이 하나씩 생긴다.
- 요청자는 작성 중 품목을 고치거나 지우고, 여러 개를 골라 한 번에 제출한다.
- 재정부(구매 승인 권한자)는 옆 메뉴의 "구매 검토"에서 모든 행사의 대기 품목을 본다. 같이 제출한 품목끼리 묶여 보이고, 품목마다 승인하거나 사유를 적어 반려한다.
- 요청자는 대기 품목을 요청 취소하고, 반려·취소된 품목을 다시 담는다.
- 재정부는 승인을 취소하고, 산 품목을 표시하고, 송장을 연결한다.
- 학생회 누구나 행사의 구매 진행 상황을 보고, 받은 품목을 수령 확인한다.
- 기존 요청서 데이터가 새 구조로 옮겨진다.
- 휴대폰 폭(390px)에서 모든 화면을 쓸 수 있다.

## 정책

### 사용자가 고른 것 (2026-10-08)

1. **담을 수 있는 것:** 쿠팡 상품 링크만. 쿠팡 밖 구매(현수막 제작, 인쇄, 다른 쇼핑몰)는 파일럿 반응을 보고 정한다.
2. **재정부가 검토하는 곳:** 옆 메뉴 "구매 검토" 한 곳에 모든 행사를 모은다. 메뉴에 대기 개수를 표시한다. 행사 화면의 "재정부 제출 요청 보기" 전환은 없앤다.
   - 근거: M1에는 알림이 없어서 재정부가 화면에서 직접 확인한다(2026-10-04 결정). 대학 구매 시스템은 승인할 요청을 한 목록에 모은다([CSU Chico](https://www.csuchico.edu/fin/_assets/documents/qrg-apprreturnrejectrequistion.pdf)).
3. **본인 승인:** 승인 권한자가 자기 품목을 승인·반려할 수 있다. 처리 기록과 구매 검토 화면에 "본인 승인", "본인 반려"로 표시한다.
   - 추천은 "막기"였다(대학 구매 규정, 학생회비 횡령 사례). 사용자는 혼자 운영하는 학생회도 막히지 않게 "허용하고 기록만"을 골랐다.
4. **받을 날짜:** 품목마다 날짜 또는 "상관없음". 기본은 상관없음이다.
   - 끼룩이가 대화에서 날짜를 찾으면 미리 채운다.
   - 빠른 버튼(3일 안, 1주 안, 2주 안)과 달력으로 고른다. 버튼은 저장할 때 날짜로 바뀐다(한국 시간 기준 오늘 + N일).
   - 행사에 날짜 칸이 없어서 2026-10-04에 정한 기본값 "행사 전"은 쓰지 않는다.

### 추천대로 정한 것

5. **기존 데이터:** 지우지 않고 새 구조로 옮긴다. 폐기된 초안의 품목만 옮기지 않는다(두 DB 모두 0건).
6. **품목 상태:** 작성 중(`draft`) · 대기(`pending`) · 승인(`approved`) · 반려(`rejected`) · 요청 취소(`cancelled`).
   - 구매함·배송·수령은 상태가 아니라 승인된 품목에 붙는 표시다. 화면은 이 표시로 진행 단계를 보여 준다.
   - 진행 단계: 작성 중 → 대기 → 승인 → 구매함 → 배송 예정·배송 중·배송 완료 → 수령 완료. 끝: 반려, 요청 취소.
7. **용도:** 품목마다 적는다(지금은 요청서의 "구매 목적"). 제출할 때 필수가 아니다. 끼룩이가 대화에서 찾으면 채운다.
   - 이유: 행사 자체가 맥락이다. 품목이 많을 때 품목마다 필수로 적게 하면 부담이 크다.
8. **예상 배송비 칸은 없앤다.** 배송비는 품목이 아니라 주문에 붙는다. M1에는 예산 기능도 없다. 합계는 "수량 × 예상 단가"의 합이다.
9. **작성 중 품목 지우기:** 완전히 지운다. "폐기" 상태는 없다. 지우기 전에 확인 대화상자를 띄운다.
10. **다시 담기:** 반려·요청 취소된 자기 품목을 같은 내용의 새 작성 중 품목으로 복사한다. 원래 품목은 그대로 남는다.
    - 받을 날짜는 오늘 이후일 때만 복사한다.
    - 보완 요청(FIN-SUP-01) 대신 쓴다. 다시 담기 버튼을 반려 사유 바로 옆에 둔다.
11. **수정할 수 있는 것과 시기**
    - 작성 중: 요청자가 상품명, 옵션, 옵션 필요 여부, 포장 단위, 수량, 예상 단가, 용도, 받을 날짜를 고친다.
    - 제출 뒤: 받을 날짜만 바꿀 수 있다. 구매함 표시 전까지, 요청자만 바꾼다. 바꾸면 기록에 남고, 구매 검토 화면에 "날짜 바뀜"이 붙는다.
12. **제출:** 같은 행사의 내 작성 중 품목을 1~50개 골라 한 번에 제출한다.
    - 제출 기록 하나가 생긴다.
    - 필수: 상품명, 수량 1 이상, 옵션 필요 여부 확인, 옵션이 필요하면 선택 옵션.
    - 요청 부서는 제출할 때의 요청자 부서다. 미배정이면 비어 있다.
13. **요청 취소:** 대기 품목만, 요청자만 한다.
14. **결정:** 대기 품목만, 재정부가 한다. 반려 사유는 필수(500자 이내)다.
    - 품목마다 바로 처리하고, 묶음에는 "모두 승인"이 있다.
    - 승인은 되돌릴 수 있어서 확인을 묻지 않는다. 반려는 사유 입력이 확인을 겸한다.
15. **승인 취소:** 재정부가 한다. 구매함 표시 전 승인 품목만 대기로 되돌린다.
16. **구매함 표시:** 재정부가 승인 품목에 표시한다. 송장을 연결하면 표시가 없을 때 자동으로 붙는다. 표시 취소는 송장이 연결되지 않았고 수령 확인 전일 때만 된다.
17. **수령 확인:** 학생회 누구나 구매함 표시된 품목에 한다. 누가 눌렀는지 남긴다. 잘못 누르면 누구나 취소할 수 있고, 취소도 기록한다.
18. **송장 연결:** 승인 품목이면 행사가 달라도 한 송장에 묶을 수 있다. 재정부가 쿠팡에서 여러 행사 품목을 한 번에 주문하기 때문이다. 지금의 "같은 요청서만" 규칙은 없앤다.
19. **보는 범위**
    - 작성 중 품목은 요청자만 본다.
    - 제출된 품목은 학생회 누구나 행사 화면에서 본다. 반려 사유도 보인다. 학생회비는 구성원에게 공개하는 돈이라서다.
    - 송장번호는 지금처럼 재정부에게만 전부 보이고, 다른 사람에게는 뒤 4자리만 보인다.
20. **같은 상품 다시 담기:** 합치지 않는다. 같은 행사에서 내가 이미 담은 상품(작성 중·대기·승인)을 또 담으면, 새 품목에 "이미 담은 상품이에요" 확인 사항을 붙인다.
21. **동시 처리:** 품목마다 버전을 둔다. 모든 변경은 화면이 본 버전을 보내고, 다르면 409 `VERSION_CONFLICT`를 돌려준다.
    - 변경할 품목 행은 `FOR UPDATE`로 잠근다. 여러 개면 ID 순서로 잠근다.
    - 2026-10-04 문서는 제출 기록에 버전을 두고 잠그기로 했다. 그런데 요청 취소, 날짜 변경, 구매함 표시처럼 품목 하나만 바꾸는 동작이 대부분이라 품목 버전이 더 단순하다.

## 와이어프레임과의 관계

검토한 화면: EVT-FIN-01 `28:685`, FIN-REQ-01 `30:211`, FIN-REQ-02 `30:822`, FIN-REV-01 `30:1295`, FIN-PROC-01 `30:1558`, MY-REQ-01 `30:2`, FIN-SUP-01 `30:1066`, FIN-EVID-01 `30:1763`.

와이어프레임은 요청서 단위의 데스크톱 구매 관리 도구를 그렸다. 문제는 세 가지다.
- 요청서를 단위로 삼았다. 그런데 와이어프레임 안에서도 품목마다 결과(승인 3, 보완 1)와 주문·배송 상태가 갈린다.
- M1 밖 기능(예산 카드, 증빙·정산, 업체별 발주, 첨부)이 화면 대부분을 차지한다.
- M1의 핵심인 "링크로 품목 채우기"가 없다. 품목을 손으로 적는다.

| 화면 | 판정 | 이 설계 |
|---|---|---|
| FIN-REV-01 요청 검토 | 일부 유지 | 품목마다 승인·반려와 사유. 승인액 수정, 예산, 첨부는 뺀다 |
| FIN-REQ-02 요청 상세 | 일부 유지 | 품목별 결과, 재정부 사유, 처리 기록. 결제·증빙 단계는 뺀다 |
| EVT-FIN-01 행사 재정 | 고침 | 행사 안의 구매 탭, 검토 대기 개수. 예산 카드와 4열 칸반은 뺀다 |
| MY-REQ-01 내 구매 요청 | 고침 | 행사 구매 탭의 "내 품목". 요청서 표 대신 품목 목록 |
| FIN-REQ-01 요청 작성 | 고침 | 링크로 채우고 수량·용도·받을 날짜만 입력. 카테고리, 예산 항목, 우선순위, 요청 제목은 뺀다 |
| FIN-PROC-01 구매·발주 | 고침 | 품목별 구매함 표시와 배송 상태. 업체별 발주는 뺀다 |
| FIN-SUP-01 보완 요청 | 뺌 | 반려 사유 + 다시 담기 |
| FIN-EVID-01 결제·증빙 | 뺌 | 정산은 M1 밖 |

- 칸반은 휴대폰에서 가로로 넘기기 어렵고 카드를 실수로 끌기 쉽다는 사용자 불만이 많다([CryptPad](https://forum.cryptpad.org/d/211-kanban-has-difficult-ui-for-scrolling-on-mobile-devices), [Kanboard](https://kanboard.discourse.group/t/horizontal-scrolling-with-long-columns-is-very-annoying/229)). 그래서 위아래로 쌓은 목록으로 바꾼다.
- 해당 와이어프레임 노드가 없는 화면(구매 검토 목록)은 FIN-REV-01의 품목 행을 휴대폰 카드로 옮긴 것만 비교한다.

## 데이터

마이그레이션을 두 번으로 나눈다(AGENTS.md 마이그레이션 순서).

### 0012_purchase_items (배포 전 적용)

새 표 넷을 만들고, `purchase_items`에 칸을 더하고, 기존 요청서 데이터를 옮긴다. 옛 표와 칸은 남겨 둔다.

**purchase_items에 더하는 칸**

| 칸 | 내용 |
|---|---|
| `organization_id`, `event_id`, `requester_id` | NOT NULL. 요청서에서 옮겨 채운 뒤 NOT NULL을 건다. (조직, 행사) 복합 FK |
| `generation_id` | 끼룩이 생성 기록. 다시 담기로 만든 품목은 비어 있다. (조직, 생성) 복합 FK |
| `submission_id` | 제출 기록. 작성 중이면 비어 있다. (조직, 제출) 복합 FK |
| `status` | `draft·pending·approved·rejected·cancelled`, 기본 `draft` |
| `note` | 용도. 200자 이내, 공백만 금지 |
| `needed_by` | 받을 날짜. 비어 있으면 상관없음 |
| `warnings` | 확인 사항. JSON 배열, 기본 `[]` |
| `version` | 기본 1, 0보다 크다 |
| `decided_by`, `decided_at` | 승인·반려한 사람과 시각 |
| `decision_reason` | 반려 사유. 500자 이내, 공백만 금지 |
| `purchased_by`, `purchased_at` | 구매함 표시 |
| `received_by`, `received_at` | 수령 확인 |
| `updated_at` | 마지막 변경 시각 |

- `request_id`, `position`은 NULL을 허용하도록 바꾼다. 새 코드는 쓰지 않는다.
- `shipment_items.request_id`도 NULL을 허용하도록 바꾼다.

**새 칸에 거는 제약** (모두 새 칸이라 기존 행이 위반할 수 없다)
- `(status = 'draft') = (submission_id IS NULL)`
- `(status IN ('approved','rejected')) = (decided_at IS NOT NULL)`, `decided_by`와 `decided_at`은 같이 있거나 같이 없다.
- `(status = 'rejected') = (decision_reason IS NOT NULL)`
- `purchased_at`은 `status = 'approved'`일 때만 있다. `received_at`은 `purchased_at`이 있을 때만 있다. 사람과 시각은 같이 있거나 같이 없다.
- 고유 `(organization_id, id)`: 다른 표의 복합 FK 대상이다.

**새 표**

| 표 | 칸 | 제약 |
|---|---|---|
| `purchase_generations` | id, organization_id, event_id, requester_id, idempotency_key, links(JSON 배열), created_at | 고유 (requester_id, idempotency_key). 키는 128자 이내, 공백만 금지 |
| `purchase_submissions` | id, organization_id, event_id, requester_id, department_id(NULL 허용), submitted_at | (조직, 행사)·(조직, 부서) 복합 FK. 고유 (organization_id, id) |
| `purchase_item_events` | id, organization_id, item_id, actor_id, action, reason, changes(JSON 객체), batch_id, created_at | (조직, 품목) 복합 FK. 반려만 사유가 있다 |
| `purchase_item_sources` | item_id, message_id, created_at | PK (item_id, message_id). 같은 행사방인지는 서버가 검사한다 |

- `purchase_item_events.action`: `submitted`, `approved`, `rejected`, `cancelled`, `approval_revoked`, `needed_by_changed`, `purchased`, `purchase_undone`, `received`, `receipt_undone`, `re_added`. 제출 이후만 기록한다. 고치거나 지우지 않는다.
- 모든 FK는 지금처럼 `ON DELETE RESTRICT`다. 작성 중 품목을 지울 때는 근거 대화 행을 먼저 지운다.

**데이터 옮기기** (같은 파일 안에서 순서대로)
1. 요청서마다 생성 기록을 만든다. ID는 요청서 ID, 키는 요청서의 멱등키, 링크는 생성 이력의 `inputLinks`(없으면 품목 링크 순서)다.
2. 제출·승인·반려된 요청서마다 제출 기록을 만든다. 제출 시각은 제출 이력 시각이다(없으면 요청서 수정 시각).
3. 품목에 조직·행사·요청자·생성 기록·용도(구매 목적)·받을 날짜(필요한 날짜)·확인 사항(생성 이력의 경고)을 채운다.
4. 상태는 이렇게 바꾼다: 작성 중 → `draft`, 제출 → `pending`, 승인 → `approved`, 반려 → `rejected`. 결정한 사람·시각·사유는 마지막 결정 이력에서 가져온다.
5. 이력을 품목 기록으로 옮긴다: 제출, 승인, 반려만 옮긴다. 생성·수정 이력은 제출 전 기록이라 옮기지 않는다.
6. 요청서 근거 대화를 그 요청서의 모든 품목 근거로 복사한다.
7. 폐기된 요청서의 품목은 지운다(두 DB 모두 0건).
8. 조직·행사·요청자 칸에 NOT NULL을 건다.

**배포 전후 호환**
- 새 코드는 옛 표와 `request_id`, `position`을 쓰지 않는다. 그래서 0012만 적용된 DB에서도 동작한다. 이 구간을 테스트로 확인한다.
- 0012를 적용하면 지금 배포된 코드는 새 초안을 만들 때 실패한다(조직 칸 NOT NULL). 적용 직후 바로 배포해서 이 구간을 몇 분으로 줄인다. 파일럿 전이라 사용자는 없다.

### 0013_purchase_cleanup (배포 후 만들고 적용)

0012와 새 코드를 배포한 뒤 별도 커밋으로 만든다(0011과 같은 방식). 옛 표를 지우고 기존 칸에 제약을 건다.

| 변경 | 내용 |
|---|---|
| 옛 표 삭제 | `purchase_request_history`, `purchase_request_sources`, `purchase_requests` |
| `purchase_items` | `request_id`, `position`과 관련 제약을 지운다. 상품명 500자·옵션 200자·포장 단위 50자 CHECK(공백만 금지 포함)를 건다 |
| `shipment_items` | `request_id`와 관련 FK를 지우고 (조직, 품목) 복합 FK를 건다 |

- 적용 전에 두 DB에서 확인한다.
  - 길이 위반 0건.
  - 옛 요청서 상태와 품목 상태가 모두 맞는지.
  - 0012 적용 뒤에 옛 코드로 생긴 행이 없는지.
- 새 코드를 0013 스키마로 다시 배포한 뒤에 적용한다. 드리즐은 INSERT에 스키마의 모든 칸을 넣는다. 그래서 0012 스키마로 만든 코드는 지운 칸 때문에 실패한다.

## API

모든 본문 스키마를 `packages/contracts`의 zod `z.strictObject`로 만든다. 라우트는 `json(Schema)`를 인증보다 앞에 둔다. 그래서 `boundary.test.ts`의 `schemaPending`이 빈다. 구매 모듈은 지금처럼 `AppOptions.purchases` 하나로 연결한다.

### 행사 (학생회 구성원)

경로 앞부분: `/api/organizations/:organizationId/events/:eventId/purchase-items`

| 경로 | 본문 | 동작 |

| `PATCH /:itemId` | `{ version, productName?, selectedOption?, optionRequired?, quantity?, packagingUnit?, estimatedUnitPrice?, note? }` | 작성 중 품목 수정(요청자) |

| `POST /:itemId/cancel` | `{ version }` | 요청 취소(요청자, 대기) |

| `POST /:itemId/received` | `{ version, received }` | 수령 확인·취소(누구나, 구매함 표시된 품목) |

### 구매 검토 (재정부)

경로 앞부분: `/api/organizations/:organizationId/purchase-review`

| 경로 | 본문 | 동작 |
|---|---|---|
| `GET ` | 없음 | 모든 행사의 대기 품목(제출 순)과, 수령 확인 전 승인 품목(받을 날짜 순, 상관없음은 뒤). 각 300개, `truncated` |

### 응답

- 변경은 바뀐 품목을 `{ items: PurchaseItemSummary[] }`로 돌려준다. 삭제는 `{ items: [] }`다. 화면은 ID로 목록에 합친다.
- `PurchaseItemSummary`
  - 행사: id·이름. 요청자: id·이름. 요청 부서 이름.
  - 상태, 버전, 제출 ID.
  - 상품 칸(링크, 상품명, 옵션, 옵션 필요 여부, 포장 단위, 수량, 예상 단가), 용도, 받을 날짜, "날짜 바뀜" 여부, 확인 사항.
  - 만든·제출한·결정한·구매함 표시한·수령 확인한 시각과 사람, 반려 사유.
  - 배송 목록(`DeliverySummary`).
- `PurchaseItemDetail`은 여기에 근거 대화(내용, 작성자 이름, 시각)와 처리 기록(동작, 한 사람, 사유, 바뀐 값, 시각)을 더한다.

### 끼룩이 생성

- 상품 조회, 최근 대화 100개(2만 자), 사용자당 동시 1건, 멱등키는 지금과 같다.
- 출력은 품목마다 상품명, 옵션, 포장 단위, 옵션 필요 여부, 수량, 용도, 받을 날짜, 근거 메시지 ID, 확인 사항이다. 요청서 단위의 목적·필요일·근거는 없앤다.
- 가격은 지금처럼 조회값만 쓴다. 조회 경고와 옵션 미확인 경고는 해당 품목의 확인 사항에 붙인다.
- 공통 문구("조회 가격은 참고값")는 저장하지 않고 화면에 고정 안내로 둔다.

### 배송

- `POST /shipments`
  - 품목이 모두 승인 상태이고 같은 학생회면 등록한다(`ONE_REQUEST_REQUIRED` 삭제).
  - 구매함 표시가 없는 품목에는 표시를 붙이고 기록한다.
- `GET /events/:eventId/deliveries`를 없앤다. 품목 응답이 배송 목록을 담는다.
- 송장번호 가리기(`summary`)를 공용 함수로 옮겨 구매 응답과 같이 쓴다.
- 택배사 목록·조회·등록·연결 해제는 그대로 `DELIVERY_ENABLED`일 때만 연결한다. 운영은 켜져 있다. 화면은 택배사 목록이 404면 송장 등록 칸을 숨긴다.

## 화면

### 행사 화면

탭 이름을 **대화 · 구매**로 바꾼다. 대화 탭 위의 끼룩이 버튼은 그대로 두고, 구매 탭에도 [끼룩이로 담기]를 둔다. 담기가 끝나면 구매 탭으로 가서 새 품목을 골라 둔 상태로 보여 준다.

구매 탭 위쪽에서 **내 품목 | 행사 전체**를 고른다. 기본은 내 품목이다.

```
[내 품목] [행사 전체]                [끼룩이로 담기]
작성 중 3                     □ 모두 선택
 ┌────────────────────────────────────────┐
 │ □ 모닝글로리 유성매직 12색 ↗             │
 │   12색 · 2세트 · 예상 9,800원            │
 │   용도: 부스 안내판 · 받을 날짜: 상관없음 │
 │   확인할 점 1  ▾                         │
 │                       [수정] [지우기]     │
 └────────────────────────────────────────┘
 [선택한 2개 제출]  [받을 날짜 바꾸기]
진행 중 2
 │ 박스테이프 48mm · 5개 · [대기]  [요청 취소] [날짜]
 │ 생수 500ml · 10박스 · [배송 중] CJ대한통운 ****1234  [받았어요]
```

- 품목 카드는 위아래로 쌓는다. 상품명과 용도에 `wrap-anywhere`를 준다.
- 작성 중 카드에 제출 전에 채울 칸을 "제출 전 확인: 수량, 옵션"으로 보여 준다. 고를 때 미완성 품목이 섞이면 제출 버튼이 꺼지고 이유를 보여 준다.
- 카드를 누르면 상세 대화상자가 열린다. 상세에는 상품 링크, 모든 칸, 근거 대화, 처리 기록(본인 승인 표시 포함), 배송이 있다.
- [수정]은 작성 중 품목 수정 대화상자, [받을 날짜 바꾸기]·[날짜]는 날짜 대화상자를 연다.
- 행사 전체: 제출된 품목을 진행 중·끝남으로 나눠 보여 준다. 카드에 요청자 이름과 부서를 더한다. 구매함 표시된 품목에 [받았어요], 수령 완료 품목에 [수령 취소]가 있다.

## 테스트

- **계약:** 새 스키마마다 필수값 누락, 빈 문자열·공백만, 상한+1(이모지 포함), NUL·홀로 쓰인 서러게이트, 모르는 키.
- **마이그레이션**
  - 0012: 0011까지 적용한 DB에 옛 요청서 다섯 종류(작성 중·제출·승인·반려·폐기)를 넣고 0012를 적용한다. 그다음 옮긴 결과와 새 제약을 확인한다.
  - 0013: 배포 후 커밋에서 확인한다.
- **API**
  - 동작마다 성공과 상태·권한·버전 실패를 확인한다. 다른 학생회 사용자, 미인증, 남의 작성 중 품목(404)도 확인한다.
  - 본인 승인 기록, 같은 상품 경고, 다시 담기, 송장 자동 구매함 표시를 확인한다.
  - 0012만 적용된 DB에서 새 흐름 전체가 동작하는지 확인한다.
- **경계:** `schemaPending`을 비우고 모든 구매 변경 라우트가 공통 검사를 받는지 확인한다.
- **화면:** 내 품목 묶음(작성 중·진행 중·끝남), 고르기와 제출, 날짜 대화상자의 버튼 → 날짜 변환, 반려 사유와 다시 담기, 행사 전체의 수령 확인을 확인한다.
  - 구매 검토는 묶음, 모두 승인, 반려 사유 필수, 살 품목 정렬, 송장 등록 숨김(404)을 확인한다.
  - 사이드바 대기 칩과 끼룩이 → 구매 탭 이동도 확인한다.
- **수동:** dev에서 데스크톱과 390px로 요청자·재정부 흐름을 끝까지 해 본다.

## 적용 순서

1. 브랜치에서 구현하고 전체 테스트·타입 검사·빌드를 통과시킨다.
2. dev DB에 0012를 적용하고 확인한 뒤, 배포 DB에 적용한다(승인).
3. main에 병합하고 푸시해서 배포한다.
4. 운영에서 확인한다.
5. 0013 커밋(스키마 정리, 테스트, ERD)을 푸시해서 다시 배포한다.
6. 두 DB에서 위반 0건을 확인하고 0013을 적용한다(승인).

## 하지 않는 것

- 쿠팡 밖 구매, 직접 입력 품목.
- 후보 목록, 링크 미리 조회, 상품 단위 조회 저장(2차). 제출할 때 가격 다시 확인하기도 2차에서 상품 조회와 같이 한다.
- 채팅 알림 카드(3차), 알림.
- 예산, 증빙, 정산, 업체별 발주, 첨부파일, 부분 승인.
- 행사 날짜.
