# M5c 결과보고서 다시 설계: 저절로 남는 행사 기록

2026-10-12. M5b 결과보고서는 완료한 행사에 빈 칸 다섯 개(현장 운영·잘된 점·아쉬운 점과 원인·개선안·인수인계)를 두고, 다섯 칸을 다 써야 회장단이 발행할 수 있었다. 사용자는 배포된 화면을 보고 VADA의 원칙을 어겼다고 지적했다. 기록을 남기는 수고는 지금 일하는 사람이 지고 덕은 다음 사람이 본다. 그래서 기록하려고 새로 쓰게 하면 기록은 남지 않는다.

M5c는 결과보고서를 "쓰는 문서"에서 "완료하면 이미 채워져 있는 기록"으로 바꾼다. 사실(숫자·준비 과정)은 이미 쌓인 데이터로 자동으로 채우고, 해석(회고)은 끼룩이가 초안을 쓴다. 사람은 초안을 확인하거나 고칠 수 있다. 하지 않아도 기록은 완성된다.

## 원칙 대조

기준은 `vada-product/PRODUCT.md`(작동 원칙·제품 경계·성립 조건)와 `vada-product/sources/application-v3.md` 17~33줄이다. 여기에 사용자 원칙이 더해진다. 일은 평소대로, 가치는 자연스럽게. 업무를 늘리지 않고, 지금 하는 행위가 그 사람에게 바로 이득인지로 판단한다.

| 사람이 하는 일 | 새로 생긴 일인가 | 바로 이득 | 판단 |
|---|---|---|---|
| 행사 완료(회장단, M5a) | 아니다 | 완료하면 기록이 다 차 있다 | 그대로 |
| [회고 초안 만들기] 단추 | 단추 하나 | 처음부터 쓰는 것보다 싸다 | 선택 |
| 초안 확인·고치기·답하기 | 그렇다 | 약하다(덕은 다음 기수) | 선택. 발행 조건 없음 |
| 그 밖의 입력 | 없다 | | |

- **근거 연결(작동 원칙 1):** 준비 과정의 줄은 그 기록이 있는 행사 탭으로 간다. 회고 문장은 근거(대화 원문·준비 과정 줄·숫자)를 하나 이상 단다. 근거가 없거나 모르는 근거를 단 문장은 버린다.
- **반복 작성 금지(작동 원칙 2):** 빈 칸이 없다. 끼룩이가 기록과 대화로 알 수 없는 것만 "확인 필요"로 묻는다.
- **결정 이유와 변경 이력(작동 원칙 3):** 준비 과정에 예산 변경(전 금액), 구매 반려 사유, 정산 다시 열기 사유, 늦은 업무가 남는다. 회고는 만든 사람·때와 확인한 사람·때를 남긴다.
- **제품 경계:** 끼룩이 결과는 확인하기 전까지 "초안"이다.
  - 단추 옆에 처리 사실(OpenAI로 보냄)과 목적을 적는다.
  - 신청자 정보는 보내지 않는다.
  - OpenAI 저장은 끈다(`store: false`, 구매 초안과 같다).
- **성립 조건:** 회고가 없어도 숫자와 준비 과정만으로 기록이 성립한다. 행사 대화를 VADA 밖(카톡)에서 하면 회고가 빈약해지기 때문이다.

## 왜 이렇게

- **와이어프레임도 같은 구조였다.** REC-02A는 "현장 운영·회고·인수인계는 직접 작성, 발행 조건 0/6"이었다. M5b는 이 구조를 그대로 두고, 원칙에 맞는 자동 타임라인·근거 자료·AI 초안을 뺐다. M5c는 반대로 한다.
- **기록은 저장하지 않고 열 때마다 센다.** 완료한 행사는 바뀌지 않는다(M5a). 발행이 없으니 고정할 때도 없다. 부서·사람 이름은 지금 이름이다.
- **발행·발행 취소·다섯 칸을 없앤다.** 결과보고서 때문에 완료 취소가 막히지 않는다.
- **사실은 AI가 쓰지 않는다.** 숫자와 준비 과정은 데이터 그대로라 확인할 것이 없다. 끼룩이는 해석(회고)만 쓴다. 그래서 확인할 양이 회고 몇 문장으로 준다.
- **회고는 사람이 단추를 눌러 만든다.** PRODUCT.md의 "사용자가 실행하면"이다. 완료할 때 자동으로 만들지 않는다. 아무도 보지 않을 행사에도 AI를 부르게 되고, 완료가 1분 가까이 걸리기 때문이다.
- **회고는 잘된 점·아쉬운 점·다음 행사에서·확인 필요다.** M5b의 현장 운영·인수인계 칸은 따로 두지 않는다. 언제 무엇을 했는지는 준비 과정이 보여 주고, 다음 담당자가 할 일은 "다음 행사에서"가 맡는다.
- **[저장하고 확인]은 한 번에 한다.** 고친 사람은 내용을 본 사람이므로, 고친 뒤 [확인]을 한 번 더 누르게 하지 않는다. 고치지 않고 확인만 할 때는 [확인]을 누른다.
- **화면 순서는 숫자 → 회고 → 준비 과정이다.** 읽는 사람은 교훈을 먼저 본다.
- **준비 과정의 날짜는 행사일 기준 D-n이다.** 다음 기수가 "언제 무엇을 해야 하는지"로 읽는다.
- **바로 가기는 탭까지다.** 업무·구매·지출 하나를 바로 열지는 않는다. 대화만 그 메시지로 간다(이미 있는 기능이다).
- **준비 과정에는 사람 이름을 적지 않고 부서만 적는다.** 끼룩이에 보내는 글과 같게 하기 위해서다. 다음 기수에게 필요한 것도 사람보다 부서다. 담당 부서·책임자는 머리에 있다.

## 범위

- **넣는다**
  - 결과보고서: 머리, 숫자(지금 그대로), 회고, 준비 과정(자동 타임라인)
  - 회고
    - 끼룩이 초안 만들기·다시 만들기와 확인
    - 고치기: 문장 고치기·지우기·더하기, 확인 필요에 답하기
  - 기록 목록: 회고 칩(초안·확인)
  - 결과보고서에서 행사 탭으로 바로 가기(업무·구매·참가자·재정, 대화 메시지)
  - 발행·발행 취소·다섯 칸 없애기, 완료 취소 제약 없애기
  - 저장소 AGENTS.md에 제품 원칙과 spec의 원칙 대조
  - 시연 데이터
- **넣지 않는다**
  - 지난 행사에서 시작하기(업무·구매·예산 가져오기): 다음 마일스톤 후보다. 기록의 덕이 실제로 돌아가는 곳이다.
  - 결과보고서 내려받기(PDF·엑셀), 학교 양식, 만족도, 사진
  - 업무·구매·지출 하나로 바로 가기, 회고 처리 기록(전체 이력), 문장마다 쓴 사람 표시
  - 카톡 등 외부 메신저 대화

## 정책

1. **결과보고서**
   - 구성원 모두 본다(미배정 포함). 지금 그대로다.
   - 완료하지 않은 행사도 응답은 준다(완료를 취소한 뒤 열려 있던 화면). 회고 만들기·고치기·확인은 완료한 행사에서만 된다.
2. **회고 상태**
   - 없음 → 초안 → 확인. 고쳐서 저장하면 저장한 사람이 확인한 것이다.
   - 다시 만들면 새 초안이다. 고친 문장·답·확인은 사라진다.
   - 행사마다 하나다.
3. **권한:** 만들기·다시 만들기·고치기·확인은 부서가 있는 구성원(`manageEvents`)이 한다.
4. **낡은 초안:** 초안을 만든 뒤 완료를 취소했다가 다시 완료했으면(완료 시각이 다름) 안내한다. 그대로 확인할 수도 있고 다시 만들 수도 있다. 확인하거나 고쳐 저장하면 그때의 완료 시각으로 맞춰 안내가 사라진다. 사람이 지금 기록을 보고 확인했기 때문이다.
5. **완료 취소:** 회고와 상관없이 된다. 회고는 지우지 않는다.
6. **끼룩이에 보내는 것**
   - 행사 이름·날짜·장소·담당 부서, 숫자, 준비 과정 줄(글), 행사 대화
   - 대화는 최근 것부터 400개·40,000자까지 보내고, 보낸 사람의 부서 이름을 붙인다. 사람 이름과 신청자 정보는 보내지 않는다.
   - 대화·기록 속 명령은 따르지 않는다고 지시한다(구매 초안과 같다).
7. **끼룩이 결과 검사**
   - 잘된 점·아쉬운 점·다음 행사에서는 각각 5문장까지, 확인 필요는 3개까지다. 넘으면 앞에서부터 남기고 자른다.
   - 문장은 앞뒤 공백을 지우고 1~200자다. 아니면 그 문장을 버린다.
   - 근거
     - 세 섹션의 문장은 근거가 1~8개다. 근거는 모두 보낸 것 안의 ID여야 하고, 아니면 그 문장을 버린다.
     - 확인 필요는 근거가 없어도 된다. 있으면 모두 보낸 것 안의 ID여야 한다.
   - 버리고 남은 것이 없어도 초안으로 저장한다. 화면은 "끼룩이가 근거로 정리할 내용을 찾지 못했어요."다.
   - 응답 형식이 틀리거나 시간이 지나면(90초) `GENERATION_FAILED`(502)다. 끼룩이 키가 없으면 `AI_NOT_CONFIGURED`(503)다.
8. **동시**
   - 한 행사에서 한 번에 하나만 만든다(`GENERATION_IN_PROGRESS`, 서버 하나 기준).
   - 끼룩이를 부르기 전과 저장할 때 버전을 본다. 그사이 누가 바꿨거나 완료 시각이 바뀌었으면 `VERSION_CONFLICT`이고 결과는 버린다.
9. **고치기**
   - 문장은 섹션마다 10개까지, 200자까지다. 새 문장은 근거가 없다.
   - 확인 필요는 더할 수 없고, 지우거나 답(300자까지)할 수 있다.
   - 있던 문장은 ID로 보내고, 서버가 근거를 그대로 잇는다. 모르는 ID나 같은 ID를 두 번 보내면 `INVALID_INPUT`(400)이다.

- 품목 이름은 셋까지 적고 "외 n건"을 붙인다. 이름이 없으면 "이름 없는 품목"이다.
- 작성 중 품목과 취소한 지출은 넣지 않는다.
- 늦음은 끝낸 한국 날짜에서 마감일을 뺀 날 수다. 마감일 당일에 끝냈으면 늦지 않다(M5b와 같다).
- 줄마다 ID가 있고, 회고의 근거가 이 ID를 가리킨다.
  - `task:…`, `submission:…`, `approved:2026-03-02`, `rejected:…`, `cancelled:…`, `purchased:…`, `received:…`
  - `expense:…`, `finance:…`, `registration:open`, `registration:close`, `event:created`, `event:day`, `event:completed`
- 화면은 날짜마다 "D-20 · 2월 14일"로 묶는다. 행사 시작일이 D-day이고, 행사 날짜가 없으면 날짜만 적는다.
- 참가자 탭이 보이지 않는 구성원(미배정)은 참가 신청 줄을 누를 수 없다.

| 칸 | 내용 |
|---|---|

CHECK

- `event_retrospectives_content_size`: `octet_length(content::text) <= 131072`. 문장 수·길이는 jsonb 안이라 CHECK로 다 보지 않고 서버가 본다.
- `event_retrospectives_confirmed_pair`: 확인한 사람·때는 둘 다 있거나 둘 다 없다.
- `event_retrospectives_version_positive`

**event_reports**는 마이그레이션 0028에서 지운다.

**배포 순서**
1. 0027(새 표)을 두 DB에 적용한다. 새 코드가 새 표를 읽는다.
2. 배포한다. 새 코드는 `event_reports`를 읽지 않는다.
3. 0028(`event_reports` 지우기)을 두 DB에 적용한다.
   - 옛 코드가 지운 표를 읽지 않도록 배포 뒤에 한다.
   - 지우는 행은 dev의 확인용 보고서뿐이다. 배포 DB의 시연 학생회에는 보고서가 없다.
   - 적용 전에 두 DB의 행 수를 보고 승인받는다.
- AGENTS.md "마이그레이션"에 한 줄을 더한다. "칸·표를 지우는 마이그레이션은 그것을 읽지 않는 코드를 먼저 배포한 뒤 적용한다."

| `GET /records` | 구성원 | → `RecordsResponse` |
| `GET /events/:eventId/report` | 구성원 | → `EventReportResponse` |
| `POST /events/:eventId/report/retrospective/generate` | 부서가 있는 구성원 | `GenerateRetrospectiveSchema` → `EventReportResponse` |
| `POST /events/:eventId/report/retrospective` | 부서가 있는 구성원 | `SaveRetrospectiveSchema` → `EventReportResponse` |
| `POST /events/:eventId/report/retrospective/confirm` | 부서가 있는 구성원 | `ConfirmRetrospectiveSchema` → `EventReportResponse` |

- 지우는 경로: `POST /events/:eventId/report`, `…/publish`, `…/unpublish`
- `GenerateRetrospectiveSchema`: `{ version }`. 0 이상이고, 회고가 없으면 0이다.
- `SaveRetrospectiveSchema`
  - `version`: 1 이상
  - `wentWell`, `shortfalls`, `nextTime`: `{ id: token(64) | null, text: text(200) }[]`, 10개까지
  - `questions`: `{ id: token(64), answer: text(300) | null }[]`, 3개까지
- `ConfirmRetrospectiveSchema`: `{ version }`. 1 이상이다.
- `EventReportResponse`: `{ event, facts: EventReportFacts, timeline: RecordEntry[], retrospective: RetrospectiveView | null }`
  - `RecordEntry`: `{ id, day(YYYY-MM-DD), at, kind, text, note | null, warning, tab | null }`. `at`은 ISO이고, 날짜만 있으면 null이다.
  - `RetrospectiveView`: `{ wentWell, shortfalls, nextTime: { id, text, sources }[], questions: { id, text, sources, answer }[], version, generated: { by, at }, confirmed: { by, at } | null, stale }`
  - 근거(`sources`)는 화면에 바로 쓰는 꼴로 준다.
    - 대화: `{ kind: 'message', messageId, excerpt(80자), at }`
    - 준비 과정 줄: `{ kind: 'entry', id, text, tab }`
    - 숫자: `{ kind: 'fact', id, text }`
    - 지금 찾을 수 없음: `{ kind: 'missing' }`
- `RecordsResponse`: `{ records: { event, facts, retrospective: 'draft' | 'confirmed' | null }[] }`
- 저장 본문은 32KB를 넘을 수 있다(30문장 × 200자, 이모지는 4바이트). `bodyLimitOf`에서 `…/report`를 지우고 `…/report/retrospective`를 64KiB로 더한다.
- 끼룩이는 `createRetrospectiveGenerator({ apiKey, model })`(`reports/generation.ts`)로 만들어 `AppOptions`로 넘긴다.
  - `OPENAI_API_KEY`·`OPENAI_MODEL`은 구매 초안과 같이 쓴다.
  - 테스트는 가짜 생성기를 넘긴다.

## 거래와 잠금

- **만들기**
  1. 거래 밖에서 행사가 완료됐는지, 버전이 맞는지 본다. 끼룩이를 부르기 전에 막는다.
  2. 보낼 것을 모으고 끼룩이를 부른다(최대 90초). 이때는 거래를 잡지 않는다.
  3. 거래를 연다.
     - 행사 행 `FOR SHARE`: `requireCompletedEvent`가 완료 시각을 돌려준다.
     - 회고 행 `FOR UPDATE`
     - 완료 시각과 버전을 다시 보고 쓴다.
- **고치기·확인:** 행사 행 `FOR SHARE` → 회고 행 `FOR UPDATE` → 버전 순이다.
- **완료 취소:** 회고를 보지 않는다.
- **completion-lock.test.ts:** `completedOnly`에서 옛 세 경로를 빼고 새 세 경로를 넣는다.
- 준비 과정·숫자를 셀 때는 잠그지 않는다. 완료한 행사의 기록을 바꾸는 쓰기는 모두 행사 행을 잠그고 완료를 보고 멈추기 때문이다(M5a).
