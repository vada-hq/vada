# 학생회 조직 설계

2026-10-08 작성. [가입·초대 설계](2026-10-07-invite-join-design.md)의 "부서와의 관계 (잠정)"을 확정한다.

## 목표

학생회가 DB 작업 없이 스스로 조직을 꾸린다. 지금은 학생회를 스크립트로 만들고, 재정 담당도 스크립트(`assignDepartment`)로 지정한다.

완료 기준:
- 소속이 없는 사람이 학생회를 만들 수 있다. 만든 사람은 회장단이 된다.
- 회장단은 구성원 화면에서 다음을 한다.
  - 미배정 구성원을 부서에 배정한다.
  - 직책을 적는다.
  - 부서를 추가하고, 이름을 바꾸고, 지운다.
  - 구매 승인 부서를 정한다.
- 회장단과 구매 승인 부서 소속이 구매요청을 승인한다. 재정 담당을 정하는 데 DB 작업이 필요 없다.
- 모든 구성원이 휴대폰에서 누가 어느 부서인지 본다.

## 정책 (확정)

- **소속 단위:** 학생회의 소속 단위는 회장단과 부서다. 회장단도 부서 테이블에 있는 특별한 부서다.
  - 근거는 실제 회칙이다. 부산대 한문학과 학생회 회칙 12조는 집행부를 "회장, 부회장, 각 부장"으로 정한다. 영남대 미래자동차공학과 학생회도 회장단과 부서를 나란히 둔다.
- **회장단:** 학생회마다 반드시 하나 있다. 지울 수 없지만 이름은 바꿀 수 있다.
  - 이름을 바꿀 수 있게 한 것은 선거가 무산돼 비상대책위원회가 학생회를 이끄는 경우 때문이다(연세대 총학생회 2026).
  - 회장단은 최소 한 명이다.
- **구매 승인 부서:** 선택 사항이다. 어느 부서에든 켤 수 있고, 하나도 없어도 된다. 기존 `handles_finance`를 쓴다.
  - 이름은 학생회마다 총무, 사무부, 총무부, 재정국처럼 다르다. 그래서 "재정부"라는 고정 부서를 두지 않는다.
- **한 사람의 소속:** 한 사람은 회장단 또는 부서 중 한 곳에만 속한다. 어디에도 없으면 미배정이다. 겸직은 표현하지 않는다.
- **직책:** 사람마다 자유롭게 적는 짧은 글이다(회장, 부회장, 국장, 총무 등). 표시만 하고 권한은 없다. 부서를 옮기면 지워진다.
- **권한은 두 가지뿐이다.**
  - 조직 관리(회장단): 부서 추가·이름 변경·삭제, 구매 승인 켜기·끄기, 구성원 부서 배정(회장단으로 옮기기 포함), 직책 수정.
  - 구매 승인(회장단, 구매 승인 부서): 지금의 재정 기능 전체. 구매요청 검토·승인·반려, 배송 조회·등록·연결 해제다.
  - 나머지는 모든 구성원이 한다. 학생회 만들기(로그인한 누구나), 초대, 구성원 목록 보기, 행사, 채팅, 구매 요청이다.
  - 회장단끼리는 권한이 같다.
- **미배정 구성원의 구매 요청:** 계속 허용한다(잠정 결정을 확정). 정산 단위가 행사 × 비목이라 요청 부서는 표시용이다.
- **기본 부서:** 학생회를 만들 때 총무부(구매 승인)·기획부·홍보부·복지부를 미리 채워 두고, 빼거나 고칠 수 있다. 확인한 학생회 세 곳(부산대 한문학과, 영남대 미래자동차공학과, 상명대 총학생회)에 공통으로 많았던 부서다.

## 와이어프레임과의 관계

조직 관련 화면은 ONB-02 `10:2`, ORG-00 `30:4298`, ORG-01 `11:2`, ORG-02 `12:2`, ORG-03A `30:4427`, ORG-03B `30:4684`, ORG-04 `30:6177`, ORG-04B `30:6429`, ORG-07A `30:5383`, EVT-01 `20:6519`이다. 이 화면들은 큰 학생회를 위한 완성형 관리 도구를 그렸다. M1에는 너무 무겁고, 핵심 흐름(구매 승인)에 필요한 부서는 빠져 있다.

- **맞춘 것**
  - 참여하면 미배정이 되고, 회장단이 배정한다.
  - 재정은 역할이 아니라 부서가 맡는다.
  - 처음 만들 때 기본 부서를 깔아 준다.
- **바꾼 것**

| 와이어프레임 | 바꾼 이유 | 이 설계 |
|---|---|---|
| 기본 조직이 기획·홍보·디자인부 (ORG-02) | 돈을 맡는 부서가 없어 만들자마자 승인할 사람이 없다 | 총무부(구매 승인) 포함. 회장단도 승인 |
| 조직도에 끌어다 놓아 배정 (ORG-03A·B) | 화면이 모두 1288px 데스크톱이다. 부서가 늘면 옆으로 넘친다. WCAG 2.2(2.5.7)는 끌기 외의 방법을 요구한다 | 부서별 목록, 사람마다 부서 고르는 칸 |
| 역할 3단계와 권한표 (ORG-04·04B) | 부서장 권한이 모두 M1에 없는 기능이다. "누구나 초대·행사 생성"과 부딪힌다. 회장단이 칸이기도 하고 역할이기도 하다 | 권한 두 가지(조직 관리, 구매 승인), 직책은 표시용 글 |
| 학생회 유형·학교·단과대·운영 연도 (ORG-01) | M1에서 쓰는 곳이 없고 대학·학과 데이터가 필요하다 | 학생회 이름만 |
| 조직 관리 홈, 보기·수정 모드 (ORG-00·03A·03B) | 관리할 영역이 하나뿐인데 클릭만 는다 | 화면 하나, 편집칸은 회장단에게만 |
| ONB-02 두 카드 | 대부분은 참여하러 온다. 코드 입력 화면이 이미 있다 | 코드 입력 아래에 [새 학생회 만들기] |

- **뺀 것:** 학생 명단(ORG-07, 단과대 전체 학생의 개인정보다), 행사별 운영 조직(EVT-01), 구성원 내보내기(ORG-03D).
- 구성원 화면에 해당하는 와이어프레임 노드가 없다. 그래서 AGENTS.md의 화면 비교는 ORG-03B의 미배정 패널을 목록 맨 위 묶음으로 옮긴 것만 확인한다.

## 데이터

마이그레이션 두 개로 나눈다. 새 칸을 읽는 코드보다 먼저 적용할 것(0010)과, 기존 칸에 제약을 거는 것(0011)이다. AGENTS.md의 마이그레이션 순서를 따른다.

### 0010_organization_structure (배포 전 적용)

`npm run db:generate`로 만든 파일 끝에 회장단 채우기를 직접 추가한다.

| 변경 | 내용 |
|---|---|
| `departments.is_leadership` 추가 | boolean, NOT NULL, 기본값 false. 회장단 표시 |
| 부분 고유 색인 `departments_one_leadership` | `(organization_id) WHERE is_leadership`. 학생회마다 회장단 하나 |
| CHECK `departments_leadership_not_finance` | `NOT (is_leadership AND handles_finance)`. 회장단은 항상 승인하므로 구매 승인 표시를 따로 두지 않는다. 새 칸이 모두 false라 기존 행이 위반할 수 없다 |
| `memberships.title` 추가 | text, NULL 허용. CHECK: 공백만 금지(`title ~ '[^[:space:]]'`), `char_length(title) <= 20` |
| 회장단 채우기 | `INSERT INTO departments (id, organization_id, name, is_leadership) SELECT gen_random_uuid()::text, id, '회장단', true FROM organizations` |

- 적용 직후 기존 학생회의 회장단은 비어 있다. 회장단에 넣을 사람은 배포 뒤 사용자가 정하고, 승인을 받아 스크립트로 넣는다. 그 전까지는 지금처럼 구매 승인 부서(재정부)가 승인한다.
- 지금 배포된 코드는 새 칸을 읽지 않는다. 멤버가 없는 부서가 하나 생길 뿐이라, 0010을 먼저 적용해도 그대로 동작한다.

### 0011_organization_names (배포 후 적용)

| 변경 | 내용 |
|---|---|
| `organizations.name` | CHECK 공백만 금지, `char_length(name) <= 50` |
| `departments.name` | CHECK 공백만 금지, `char_length(name) <= 20` |
| 고유 제약 `departments_organization_name_unique` | `(organization_id, name)`. 같은 학생회에서 부서 이름이 겹치지 않는다 |

- 새 API가 같은 상한을 지키므로, 배포 뒤 위반 행이 새로 생기지 않는다. 두 DB에서 위반 0건을 확인한 뒤 적용한다.
- 0011 적용 전에는 서버가 같은 이름을 미리 조회해 막는다. 적용 뒤에는 고유 제약 위반(23505)도 같은 오류로 바꾼다.

계약(`packages/contracts`)에 상수로 둔다. 화면은 숫자를 다시 적지 않는다.

| 값 | 상한 | 스키마 |

| 부서 이름 `DEPARTMENT_NAME_MAX` | 20자 | `text(20)` |

## 권한 계산

권한 규칙은 한 곳(`apps/api/src/access/membership.ts`)에 둔다.
- `permissionsOf(department)`: `manageOrganization = department?.isLeadership`, `approvePurchases = department?.isLeadership || department?.handlesFinance`.
- SQL 조건 `approvesPurchases`: `or(departments.isLeadership, departments.handlesFinance)`. 구매(`purchases/service.ts`의 `requireFinance`)와 배송(`deliveries/service.ts`의 `access`)의 재정 검사가 이 조건을 쓴다. 지금처럼 `FOR SHARE`로 잠근다.
- 배송 라우트의 재정 미들웨어(`deliveries/routes.ts`)는 `membership.permissions.approvePurchases`를 본다.

## API

계약 변경:
- `MembershipSummary`
  - `department`에 `isLeadership`을 더한다.
  - `title: string | null`과 `permissions: { manageOrganization: boolean; approvePurchases: boolean }`을 더한다.
  - 화면은 `permissions`만 보고 메뉴를 보인다.
- 새 응답 `OrganizationMembersResponse`:
  - `viewer: MembershipSummary`
  - `departments: { id, name, isLeadership, handlesFinance }[]`
  - `members: { id, name, title, departmentId }[]`
  - `members[].id`는 소속 ID, `name`은 사용자 이름이다. 이메일은 주지 않는다.

새 모듈 `apps/api/src/organization/`(`routes.ts`, `service.ts`)을 `createApp`의 `AppOptions.organization`으로 연결한다. 모든 변경 라우트는 `/api/organizations/` 아래에 있어 공통 가드를 받는다. 각 라우트는 `json(Schema)`를 인증보다 앞에 둔다.

| 경로 | 권한 | 본문 | 동작 |
|---|---|---|---|
| `POST /api/organizations/create` | 로그인 | `CreateOrganizationSchema = { name, departments: { name, handlesFinance }[] }` | 학생회, 회장단, 부서, 만든 사람의 회장단 소속을 한 트랜잭션으로 만든다. 201 `{ membership }` |
| `GET /api/organizations/:organizationId/members` | 소속 | 없음 | `OrganizationMembersResponse` |
| `POST /api/organizations/:organizationId/departments` | 회장단 | `CreateDepartmentSchema = { name }` | 부서 추가(구매 승인 꺼짐) |
| `PATCH /api/organizations/:organizationId/departments/:departmentId` | 회장단 | `UpdateDepartmentSchema = { name, handlesFinance }` | 이름과 구매 승인을 함께 바꾼다. 회장단은 `handlesFinance: false`만 받는다 |
| `POST /api/organizations/:organizationId/departments/:departmentId/delete` | 회장단 | `DeleteDepartmentSchema = {}` | 부서 삭제 |
| `POST /api/organizations/:organizationId/members/:membershipId/department` | 회장단 | `AssignDepartmentSchema = { departmentId: string \| null }` | 부서 배정. `null`은 미배정이다. 부서가 바뀌면 직책을 지운다 |
| `POST /api/organizations/:organizationId/members/:membershipId/title` | 회장단 | `UpdateMemberTitleSchema = { title: string \| null }` | 직책 수정. `null`은 지우기다 |

- 회장단 전용 변경은 모두 `OrganizationMembersResponse`를 돌려준다. 화면은 받은 값으로 목록을 통째로 바꾼다.
- `CreateOrganizationSchema`는 부서 이름이 서로 겹치거나 `회장단`과 같으면 거부한다.
- 모든 본문은 `z.strictObject`다. 문자열은 `text`·`token`으로 만들고 상한을 둔다.

### 동시 처리

회장단 전용 변경은 트랜잭션 처음에 그 학생회의 회장단 부서 행을 `FOR UPDATE`로 잠근다. 그래서 같은 학생회의 조직 변경은 한 번에 하나씩 처리된다. 잠근 뒤 요청자가 여전히 회장단인지 확인한다.
- **마지막 회장단:** 두 회장단이 동시에 서로를 옮겨도, 차례로 처리되므로 회장단이 0명이 되지 않는다.
- **승인과 동시에 옮기기:** 구매·배송의 재정 검사는 소속과 부서 행을 `FOR SHARE`로 잠근다. 그래서 승인 중인 사람을 옮기는 요청은 승인이 끝난 뒤에 처리된다.

### 오류

`ApiError(code, status)`로 던진다.

| 경우 | 결과 |
|---|---|
| 미인증 | 401 `UNAUTHENTICATED` |
| 소속 없음, 회장단이 아님 | 403 `FORBIDDEN` |
| 다른 학생회의 부서·소속, 없는 ID | 404 `NOT_FOUND` |
| 마지막 회장단을 다른 곳으로 옮김 | 409 `LAST_LEADER` |
| 같은 이름의 부서 | 409 `DEPARTMENT_NAME_TAKEN` |
| 구성원이 있는 부서 삭제 | 409 `DEPARTMENT_NOT_EMPTY` |
| 구매요청 기록이 있는 부서 삭제 (미리 조회, 외래 키 위반 23503도 같은 오류) | 409 `DEPARTMENT_IN_USE` |
| 회장단 삭제, 회장단에 구매 승인 켜기 | 409 `LEADERSHIP_FIXED` |
| 본문 형식 오류 | 400 `INVALID_INPUT` (공통) |

## 화면

### 소속이 없을 때

지금의 초대 코드 입력(`InviteCodeForm`) 아래에 "학생회를 처음 시작하나요?"와 [새 학생회 만들기]를 더한다. 누르면 같은 카드 안에 만들기 화면을 연다.

### 학생회 만들기 (`apps/web/src/organization/CreateOrganization.tsx`)

- 맨 위에 "학생회가 이미 VADA를 쓰고 있다면 초대 링크로 참여하세요."를 보여 준다.
- 입력은 학생회 이름 하나와 부서 목록이다.
  - 부서 목록 맨 위는 "회장단 · 항상 있어요"이고 고칠 수 없다.
  - 그 아래 총무부(구매 승인 표시)·기획부·홍보부·복지부가 미리 들어 있다. 각 줄은 이름 입력칸과 [빼기]다.
  - [부서 추가]는 빈 줄을 더한다.
  - 구매 승인 표시는 총무부 줄을 따라간다. 이름을 고쳐도 남고, 줄을 빼면 사라진다.
- 빈 줄은 보낼 때 뺀다. 버튼 활성화는 `CreateOrganizationSchema.safeParse`로 판단한다. 이름이 겹치면 "부서 이름이 겹쳐요"를 보여 준다.
- [학생회 만들기]는 요청 중에 꺼진다. 성공하면 소속을 다시 불러와 새 학생회의 구성원 화면을 연다. [취소]는 코드 입력으로 돌아간다.

### 사이드바

- 학생회 이름 아래 [구성원 초대] 밑에 "구성원" 메뉴(`NavItem`)를 더한다.
  - 회장단에게는 미배정 수를 함께 보여 준다(예: "미배정 2").
  - 미배정 수는 회장단일 때만 구성원 목록을 불러와 센다.
- 아래 사용자 칸은 "부서 · 직책"을 보여 준다. 승인 권한이 있으면 "구매 승인" 표시를 붙인다. 지금의 "재정 담당"을 대신한다.
- 행사를 고르면 행사 화면, "구성원"을 고르면 구성원 화면이 열린다. 머리글 제목도 "구성원"으로 바뀐다. 입력 중인 구매요청이 있으면 지금처럼 이동 전에 확인한다.

### 구성원 화면 (`apps/web/src/organization/Members.tsx`)

- 위쪽에 "구성원 N명"과 [초대]가 있다. [초대]는 지금의 초대 대화상자와 같은 내용을 연다.
- 묶음 순서는 미배정, 회장단, 나머지 부서다. 나머지 부서는 가나다순(`Intl.Collator('ko')`)이다. 묶음 안에서는 직책이 있는 사람이 먼저이고, 그다음 이름순이다.
- 묶음 머리에는 이름, 인원, 표시(회장단: "조직 관리"·"구매 승인", 구매 승인 부서: "구매 승인")가 있다.

회장단이 볼 때:
- 미배정 묶음 머리에 "배정이 필요해요"를 보여 준다.
- 사람 줄에 부서 고르는 칸(`NativeSelect`: 미배정, 회장단, 부서들)과 [직책] 버튼이 있다.
  - 칸을 바꾸면 바로 저장한다.
  - 옮기기 전후로 그 사람의 권한(조직 관리, 구매 승인) 중 하나라도 바뀌면 대화상자로 한 번 확인한다. 예: "김민준을 기획부로 옮기면 구매 승인을 할 수 없게 돼요. 직책은 지워져요." 구매 승인 부서끼리 옮기는 것처럼 권한이 그대로면 묻지 않는다.
  - [직책]은 입력칸 하나인 대화상자를 연다. 비우고 저장하면 직책을 지운다.
- 묶음 머리에 [편집] 버튼이 있다. 대화상자에서 이름과 구매 승인을 바꾼다. 회장단은 이름만 바꾼다.
  - 구성원이 없는 부서에는 [부서 삭제]도 보인다(회장단 제외).
- 맨 아래에 부서 추가 칸이 있다.
- 회장단이 한 명뿐이면 "회장단이 한 명뿐이에요. 자리를 비울 때를 대비해 한 명 더 두세요."를 보여 준다.
- 구성원이 본인 하나뿐이면 목록 대신 "링크를 보내 구성원을 모으세요"와 링크·코드 복사(`InviteShare`)를 보여 준다.

일반 구성원이 볼 때:
- 같은 목록을 보되, 고르는 칸·버튼·안내가 없다.

공통:
- 휴대폰 폭에서는 부서 고르는 칸이 이름 아래로 내려간다.
- 변경 응답의 `viewer`가 지금 소속과 다르면(본인을 옮겼을 때) 소속을 다시 불러온다. 사이드바와 재정 화면이 새 권한을 따른다. 이때 화면은 다시 그려지지 않고 구성원 화면에 그대로 있는다.

### 기존 화면

- 구매요청 검토 화면을 보이는 조건이 `department.handlesFinance`에서 `permissions.approvePurchases`로 바뀐다. 그래서 회장단에게도 보인다.
- 소속 목록(`Memberships.tsx`)의 "(재정 담당)"을 "(구매 승인)"으로 바꾼다.

## 테스트

- **API (`organization/*.test.ts`):** 다음을 확인한다.
  - 학생회 만들기: 학생회, 회장단, 부서, 소속이 생기고 `permissions`가 맞다. 초대 코드가 생긴다.

  - 회장단 전용 변경 다섯 가지: 성공, 일반 구성원 403, 다른 학생회의 부서·소속 404.

## 배포 순서

1. 브랜치에서 구현하고 테스트한다. ERD.md와 구매 모델 정책(부서 편성 확정)을 함께 고친다.
2. 두 DB(dev는 `.env`의 `DATABASE_URL`, 배포 DB는 `m1-preview`)에서 다음을 확인한다.
   - 이미 적용된 마이그레이션 기록이 로컬 파일과 순서·해시까지 일치하는지.
   - 이름이 `회장단`인 기존 부서가 없는지(있으면 0011의 고유 제약과 겹친다).
3. 승인을 받아 두 DB에 0010을 적용한다.
4. main에 병합하고 푸시한다(자동 배포). 운영에서 구성원 화면과 기존 재정 승인을 확인한다.
5. 사용자가 기존 학생회의 회장단을 정하면, 승인을 받아 스크립트로 넣는다.
6. 두 DB에서 0011 위반이 0건인지 확인하고, 승인을 받아 적용한다.

## 하지 않는 것

다음은 이번 범위에 넣지 않는다.
- 구성원 내보내기·스스로 나가기, 초대 링크·코드 재생성.
- 해마다 새 회장단으로 넘어가는 임기 교체.
- 부장에게 주는 권한, 장 표시.
- 조직도, 끌어다 놓기, 부서 순서 바꾸기.
- 학교·단과대·학생회 유형·운영 연도.
- 학생 명단, 행사별 운영 조직.
- 사이드바의 학생회 만들기 입구.
- 조직 변경 기록(누가 언제 옮겼는지).
