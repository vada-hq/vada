# 007 참가 신청과 출석

상한: 6시간(실제로 도는 시간). 시작 2026-10-22 21:53. 양식은 `docs/work-method.md`를 따른다. 가지는 `work/007-조각번호`, 진행 기록은 `.superpowers/sdd/007/progress.md`, 이슈는 vada-hq/vada-docs#52다. 옛 M3a·M3b-1·M3c 설계(`docs/superpowers/specs/2026-10-10-event-registration-design.md`, `2026-10-10-event-fees-design.md`, `2026-10-11-event-attendance-design.md`)는 무엇을 했는지만 참고한다.

## 왜

학생회는 큰 행사의 신청을 구글폼으로 받고, 학번을 엑셀 납부자 명단에서 찾아 참가비를 정하고, 당일 종이 명단에 출석을 친다. 이 기능으로 행사 책임자와 행사 담당 부서가 VADA에서 신청 양식을 열고, 학생은 로그인 없이 휴대폰으로 신청·취소하며, 당일 운영진이 학생의 QR을 찍어 출석을 남긴다. 신청자 정보는 필요한 사람만 보고, 연 기록이 남고, 기한이 지나면 지워진다. 다시 만들기의 덩어리 7(쓰기 전에) 가운데 첫째이고, RFC-7 '꼭'(참가 신청과 출석, 신청자 정보의 열람 범위와 열람 기록)이다. RFC-8 S4(외부 학생이 공개 링크로 신청하고 당일 QR로 출석)를 지킨다.

- 근거: DEC-44(신청 양식, 공개 링크는 바꾸지 않음, 개인 링크는 설계 밖), DEC-26(납부자 명단은 학번과 납부 기간만, 신청 때 대조, 같은 학번은 드러냄), DEC-28 '행사'(관리·출석은 책임자와 담당 부서, 신청자 정보 보기는 거기에 회장단·재정 역할 부서), DEC-25(담당 부서는 그 행사 업무를 맡은 부서), DEC-55(보관 기간과 기준 시각), DEC-54(행은 남기고 값을 모든 판에서 비움), DEC-56(신청자 정보를 연 기록 1년), DEC-62(짧은 고지, 계좌는 신청 뒤, 학번은 참가비에만, 명단은 재정·회장단), DEC-45(참가비 계좌).
- 이미 있는 것: 표 `registration_form`, `registration`, `attendance`, `fee_payment`, `deposit`(0000)과 drizzle 정의(`db/schema-work.ts`, `schema-money.ts`). `/api/public/*`의 공통 가드(`app.ts`)와 경계 시험의 공개 접두어, 화면 진입 `/apply/:code`·`/r`(`web.ts`), `uqr`·`zxing-wasm`과 `web/src/lib/qr-code.ts`, 계좌(006), 행사와 행사 책임자 기준(006), 속도 제한, 기록 모듈. 뒤에서 도는 작업과 그 실패 보고는 아직 없다.

### 원칙 대조

- 새로 하는 입력: 신청 양식은 구글폼에 이미 쓰던 것(기간, 정원, 안내, 참가비)이고, 응답 시트 정리·학번 대조·출석 체크가 없어지는 바로 이득이 있다. 학생은 이름(참가비가 갈리면 학번, 받을 때만 휴대폰)만 넣고 동의 체크칸은 없다(DEC-62). 납부자 명단은 재정부가 학기마다 한 번 붙여 넣고, 그 뒤 행사마다 엑셀에서 학번을 찾지 않는다.
- 근거 연결: 신청은 양식에, 양식은 행사와 참가비 계좌에, 출석은 신청에 이어진다. 적용 참가비는 신청 때 정해 저장한다(logical-model). PRIN-5: 양식과 신청 수는 모든 운영진이, 신청자 정보는 DEC-28의 사람만 본다.
- 변경 이력: 양식, 신청, 출석, 납부는 기록이라 판이 남는다. 신청자 정보를 비울 때는 판에서도 비우고(DEC-44), 판의 바꾼 사람은 신청자면 비어 있다. 출석은 지우지 않고 취소한다.

### vada-docs에 옮길 것(진행 에이전트)

이 명세 작성자는 명세 파일만 쓴다. 진행 에이전트가 조각 1 전에 vada-docs에 적고 커밋한다.
- `physical-model.md`: `registration_form`의 `name` ≤ 50, `notice` ≤ 2000, `public_code` 형식(`^[2-9A-HJ-NP-Z]{8}$`), `(payer_fee IS NULL) = (non_payer_fee IS NULL)`. `registration`의 `name` ≤ 50, `student_id ~ '^[0-9]{6,12}$'`, `phone ~ '^01[0-9]{8,9}$'`. `attendance`에 `method text NOT NULL CHECK (method IN ('qr','manual'))`, `cancelled_at timestamptz`, `CREATE UNIQUE INDEX ON attendance (registration_id) WHERE cancelled_at IS NULL`. '막지 못하는 규칙'의 DEC-56 줄을 열람 기록 항목(운영진, 학생회, 양식, 신청, 동작, 시각, IP)으로 고치고, 개인 링크 해시가 설계 밖 표라는 줄과 학번은 두 참가비가 다를 때만 받는다는 줄을 더한다.
- 새 결정 0065 '참가 신청자 정보의 열람 기록은 접속기록 항목을 따르고 IP와 함께 1년 둔다'(DEC-55 IP 3개월의 예외, DEC-56 보완). 0066 '참석 기록은 취소로 되돌리고 확인 방법을 남긴다'. 0067 '학번은 두 참가비가 다를 때만 받고, 납부 대조는 신청한 날로 하며, 같은 학번은 막지 않고 드러낸다. 회장단은 참가 신청 관리를 물려받는다'(DEC-26·28·62 읽기).

## 위험

- **표 변경 둘.** `0007`은 이미 있는 칸의 CHECK(양식·신청의 길이와 형식, 참가비 짝)다. 이 표들에 쓰는 코드는 아직 없다. 조각 1이 main에 오른다 → 두 DB에서 위반 0건 조회 → dev → production. `0008`은 새 칸(`attendance.method`·`cancelled_at`과 부분 유일 인덱스)과 설계 밖 새 표 둘이라, 그것을 읽는 조각 2보다 먼저 두 DB에 적용한다. `method`는 NOT NULL이라 적용 전에 두 DB의 `attendance`가 0행인지 본다. 둘을 한 파일에 섞지 않고, 검토가 끝난 뒤 적용한다.
- **공개 라우트를 처음 연다(다시 만들기에서).** 로그인 없이 쓰는 길이라 학생회 경계는 코드와 토큰으로만 가른다. 공개 응답에 계좌·신청자·운영진 정보가 없는지 응답 모양으로 시험한다. 공통 가드가 `Origin`을 요구하는데, 카톡 인앱 브라우저에서 공개 POST가 되는지 실기기로 본 적이 없다(옛 M3a 미확인). 사람이 할 일의 기기 확인으로 닫기 전에 본다.
- **개인정보 열람 범위.** 행사 담당 부서 기준은 업무에서 세므로, 업무를 취소하거나 부서를 바꾸면 권한이 바로 바뀐다. 맥락이 없으면 거부하고, 거르기를 지우면 실패하는 시험을 둔다(자주 잡힌 것 7, 11). 열람 기록은 응답과 같은 거래라, 기록을 빼면 실패하는 시험을 둔다(자주 잡힌 것 14).
- **새로 저장하는 개인정보:** 신청자 이름·학번·휴대폰, 납부 학번, 열람 기록의 운영진과 IP, 토큰 해시. 로그와 Sentry에 넣지 않는다(`scrubEvent`). 비울 때 `record_version.data`의 같은 키도 비운다. 보관은 DEC-55와 위 '열람 기록'.
- **뒤에서 돌리는 일(처음이다).** 기한 지우기는 같은 결과로 여러 번 돌고, advisory lock으로 겹치지 않으며, 실패는 요청 밖이라 `on-error.ts`를 타지 않는다. `http/sentry.ts`에 뒤 작업용 보고 도우미를 더해 같은 정제를 거친다. Render 무중단 배포 중 두 인스턴스가 함께 돌 수 있다.
- **동시 처리.** 마지막 자리에 두 신청(양식 행 잠금 뒤 세기), 같은 QR 두 번(부분 유일 인덱스 23505 → `already`), 스스로 취소와 출석 확인이 겹침(신청 행 잠금 뒤 다시 읽기). 셋을 pg-smoke에 더한다. PGlite는 거래를 하나씩 돌려 이것을 증명하지 못한다.
- **새 라우트 모듈 셋**(운영진 `registrations`, 공개 `public-registrations`, `fee-payments`): `AppOptions`로만 잇고 `boundary.test.ts`가 검사한다. `guard.ts`의 옛 `dues-roster` 상한과 경계 시험의 그 경로를 `fee-payments`로 바꾼다. **새 의존성과 비밀 값은 없다**(`uqr`, `zxing-wasm`은 이미 있다). 스캐너의 `.wasm`은 우리 서버가 `application/wasm`으로 주는지 본다.
- **떠볼 수 있는 것.** 남의 학번을 아는 사람은 신청해서 적용 참가비로 납부 여부를 알 수 있다(DEC-26이 받아들인 위험과 같은 뿌리). 신청은 목록에 남아 운영진이 본다.
- **시간.** 조각 7이 400줄을 넘기 쉽다(양식, 목록, 스캐너, 납부자 명단). 넘으면 납부자 명단 화면을 조각 8로 나누고, 상한이 모자라면 8을 뺀다. 그동안 화면은 납부자 참가비 칸을 감춰 두 참가비가 다른 양식을 만들지 않게 한다.

### 6. 공개 신청 화면과 내 신청(QR) [ ]
- 할 수 있게 되는 것: 학생이 카톡에서 링크를 눌러 휴대폰으로 신청하고, 내 신청에서 계좌와 출석 QR을 본다.
- 수용 기준: `/apply/{코드}`는 로그인 없이 학생회, 행사, 일시, 장소, 양식, 상태, 남은 자리, 참가비, 안내를 보이고, 받는 중일 때만 칸이 있다(학번은 참가비가 갈릴 때, 휴대폰은 받을 때). [신청하기]는 같은 스키마의 `safeParse`로 켜지고 두 번 누름을 막는다. 버튼 아래 고정 고지가 있고 체크칸과 계좌는 없다. 시작 전이면 시작 시각을 보이고 그 시각에 다시 읽어 칸을 연다. 신청하면 `/r#토큰`으로 가고, 같은 기기로 링크를 다시 열면 '이미 신청했어요 · 내 신청 보기'가 보인다. 내 신청은 내가 넣은 것, 적용 참가비, 계좌(복사), 출석 QR(흰 바탕) 또는 '출석 확인됨', 주소 저장 안내와 복사, 취소 가능할 때 [취소](확인을 거친다)를 보인다. 404면 '신청 정보를 찾을 수 없어요'를, 409 `FORM_CHANGED`면 다시 읽고, 그 밖의 409 문구는 버튼 옆에 보인다. 로그인 화면과 카톡 밖 넘기기가 없다. 390px로 확인한다.
- 닿는 곳: `apps/web/src/public/`(새), `main.tsx`(주소로 공개 화면을 따로 불러온다), `lib/qr-code.ts`, `lib/messages.ts`, `ui-gallery/`.
- 검토: 보통(쓴 `components/ui` 부품의 주석 조건). 마이그레이션: 없음.

### 7. 참가 신청 탭, 스캐너, 납부자 명단 화면 [ ]
- 할 수 있게 되는 것: 운영진이 행사의 '참가 신청' 탭에서 양식을 열고 신청자를 보며 당일 QR로 출석을 찍고, 재정부가 납부자 명단을 붙여 넣는다.
- 수용 기준: 행사 하나의 탭은 개요, 업무, 참가 신청이다. 양식 카드에 이름(`wrap-anywhere`), 기간, 신청 수/정원, 상태 배지가 있고 [신청 양식 만들기], [고치기], [멈추기]·[다시 받기]는 `actions`가 있을 때만 보인다. 만들기의 참가비 계좌는 닫지 않은 계좌이고 대표 계좌로 채워진다. 양식 하나에 공개 링크 복사와 포스터용 QR, 지울 날이 있다. 신청자 목록은 열람 권한자에게만 보이고, 아니면 신청 수만 보인다. 목록에 이름·학번 찾기, 같은 학번 표시, 납부자 칩, 출석이 있다. [QR로 출석 확인]은 카메라 가운데 정사각형만 읽고, 결과(이름, 학번, 확인함·이미 출석·찾을 수 없음)를 보이는 동안 멈추며 [다음]에 다시 읽는다. 카메라를 못 쓰면 이유와 '이름으로 찾아 [출석]'을 보인다. 이름 [출석], 출석 취소, 신청 취소(확인)가 있다. 재정 화면의 '납부자 명단' 탭은 재정부·회장단에게 보이고, 재정부는 기간과 붙여 넣기로 올리며 결과 수와 틀린 줄을 본다. 기간마다 수, 학번 찾기, 빼기가 있다. 두 번 누름, 404·403에 대화상자 닫기, 409·429 문구를 시험한다. 부품 확인 화면에 양식 카드와 상태 배지를 더하고 390px과 데스크톱으로 확인한다.
- 닿는 곳: `apps/web/src/registrations/`(새), `events/EventDetailView.tsx`, `finance/FinanceTabs.tsx`와 납부자 명단 탭(새), `lib/messages.ts`, `ui-gallery/`.
- 검토: 보통(부품 주석 조건). 마이그레이션: 없음.

## 닫기

마지막 조각을 배포하면 리허설을 하고 결과(날짜, 기기, OS, 브라우저, 단계마다 됨·안 됨)를 `docs/device-checks.md`의 새 절 '참가 신청과 출석'에 옮긴다. A는 아이폰(회장, 행사 책임자), B는 갤럭시(재정부원), 학생 역은 각자의 카카오톡이다.

1. B가 납부 기간과 학번 둘을 붙여 넣는다. A가 행사에 양식(정원 3, 참가비 납부자 0원·미납자 5,000원, 대표 계좌)을 만들고 공개 링크를 카톡방에 올린다.
2. 아이폰·갤럭시 카톡에서 링크를 열어 납부 학번과 미납 학번으로 하나씩 신청한다 → 내 신청에 0원과 5,000원(계좌·예금주), QR이 보인다. 하나를 스스로 취소한다.
3. A의 신청자 목록에 이름·학번·납부자 칩이 보이고, 열람 기록 표의 행 수가 늘었다(진행 에이전트가 개수만 조회한다, DEC-56). 권한 밖 운영진에게 신청 수만 보이는지는 시험이 맡는다.
4. A가 스캐너로 남은 신청의 QR을 찍어 출석 → 같은 QR을 다시 찍으면 '이미 출석' → 출석 취소 → 이름으로 출석.
