# 029 회의와 회의록

> 만들 때의 명세다. 결정은 vada-docs DEC-104와 logical-model.md RULE-50~52, 저장 구조는 마이그레이션이 원문이다(DEC-77).

상한: 조각마다 S 2시간·M 4시간·L 6시간(실제로 도는 시간). 시작 2026-10-29. 진행 기록은 `.superpowers/sdd/029/progress.md`다.

## 왜

운영진이 회의에서 정한 일을 업무로 옮기며 같은 내용을 다시 쓰고, 공지방에 올린 회의록은 안건·결정·후속 업무와 떨어져 있다. 이미 있는 회의·안건·결정 기록을 써서 회의 중 적은 내용이 회의록으로 남고, 안건에서 만든 업무에 나온 곳을 잇는다. 근거는 [DEC-104](https://github.com/vada-hq/vada-docs/blob/main/decisions/0104-meetings-follow-wireframe.md), RFC-8, PRIN-1~6이다. 설계 입력은 vada-hq `notes/meeting-mvp-design.md` 2.3·4·5절과 `notes/next-slices-20261029.md`의 회의 조각이다.

## 원칙 대조

- 새 입력과 바로 오는 이득: 이미 쓰던 안건·회의록·결정을 같은 안건에 적는다. 참가자는 주관 부서·행사·기수에서 미리 채우고 만든 사람을 포함한다. 시작·종료 누르기나 '없음' 확인을 요구하지 않는다. 후속 업무의 제목·행사·부서를 미리 채워 다시 쓰는 수고를 줄인다(PRIN-1).
- 근거 연결: 결정은 안건에, 후속 업무는 나온 안건에 이어지고 그 회의로 돌아간다. 첫 버전은 사람이 쓰며 AI 생성은 범위 밖이다(PRIN-2·4).
- 변경 이력: 논의 내용은 저장마다 판을 남기고 확정 뒤 수정에는 사유가 있다. 빼거나 취소해도 기록·판은 남는다. 참가자는 기록이 아닌 연결 표라 확정 전 빼면 행을 지운다(PRIN-3).
- 권한과 한 원리: 학생회 기록의 읽기는 운영진 전체, 쓰기는 RULE-51이다. 후속 업무에는 기존 업무 권한도 필요하며 회의 권한이 그것을 넓히지 않는다(PRIN-5·6).

## 범위 밖

DEC-104 '나중에'를 따른다. 참석 체크, 공지방 확정 알림·만들기 알림, 홈 회의 줄, 지난 안건 불러오기, 진행 방식·온라인 링크, 비공개 회의, 내보내기, 안건 순서 변경은 시범 운영 첫 주 뒤 판단한다. AI 요약·할 일 추출, 불참자 요약 확인, 녹음, 투표, 의결기구 회의는 사용을 확인한 뒤다. 진행 권한을 따로 주고받는 기능과 시작·종료 버튼은 만들지 않는다.

## 위험

- DB: 새 칸과 기존 칸 제약을 섞지 않는다. A 적용 전 꼴의 행·INSERT가 유효하고 스키마 정의와 마이그레이션이 같은지 시험한다. 참가자 외래 키는 인덱스로 덮고, 파기는 참가자→회의·운영진, 안건→회의 순서다. 업무의 나온 곳은 `record`를 가리켜 안건 하위 행보다 늦게 지워도 기록 파기 전이면 된다.
- 권한·격리: 조각 2·5는 다른 학생회와 부원·부서장·회장단·만든 사람·참가자 경계를 깊게 검토한다. A는 저장 자리만 만들며 같은 학생회 검사는 API 조각에서 넣는다.
- 동시 수정: 안건마다 마지막으로 본 판을 확인하고 충돌은 409로 알리며 내 글을 보존한다. 자동 저장 판 수는 시범 운영 뒤 잰다.
- 사용·개인정보: 대면 회의 뒤 옮겨 적는 길도 허용한다. 회의록의 자유 글에 담긴 개인정보 삭제 명령은 DEC-104의 다시 볼 질문이다. 팀은 실제 회의록을 열람하지 않는다(DEC-56).
- 나란히 하는 일: `paths.ts`는 조각 3→7, 회의 화면은 4→5→6 순서다. 조각 5는 v7-t5 뒤다. 캘린더 조각 7b는 7과 나란히 가능하다.
