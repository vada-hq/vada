## 왜

기능마다의 시험은 모두 통과하는데, 기능을 이어 쓰면 끊긴다. 시험 준비가 SQL과 `createRecord`로 상태를 바로 만들어(34파일 66곳) 앞 단계가 그 상태를 실제로 만드는지 아무도 보지 않는다. 시연 데이터(`demo`)는 돈을 행사보다 먼저 넣어 지출의 행사가 비고, 신청 양식·공개 신청·입금·완료를 부르지 않으며, 회장은 어느 행사도 고치지 못한다. 그래서 11/3 리허설에서 처음 드러날 끊김을 지금은 아무 시험도 잡지 못한다. 또 지출을 적은 뒤 응답만 잃으면 다시 눌러 같은 지출이 두 건 생기고, 참가 신청은 저장됐는데 개인 링크를 못 받아 다시 신청하면 자리를 하나 더 차지한다.

이 기능은 리허설 시나리오(행사 만들기 → 신청 양식 → 공개 신청 → 입금 확인 → 업무 → 구매 요청 → 결재 → 지출 → 정산 → 완료)를 한 곳에 한 번만 적고, 흐름 시험과 시연 데이터가 그것을 같은 HTTP 경로로 돌게 한다. 그리고 공개 신청과 지출 만들기에 명령 번호를 두어 같은 명령을 다시 보내도 한 번만 저장한다.

- 근거: work-method '검사와 시험'(흐름 시험 층: 한 곳에 한 번, 흐름 시험과 `demo`가 같은 시나리오, 앞 단계를 DB에 써 넣지 않고 실제 경로로), DEC-52(리허설에서 구매 부탁부터 지출, 참가 신청과 정산을 휴대폰으로 끝까지), screens.md '화면 흐름' 1(대화 → 구매 요청 → 결재 → 지출 → 정산 → 완료)과 3(참가 신청 → 입금 → 참가비 수입), product.md '기록이 생기는 방식'(승인·입금이 바로 기록이 된다, 실제 지출·신청이 기록으로 이어진다). 단계의 규칙은 012(DEC-79 끝난 행사만 완료, 회장단도 고치기, 정산 끝 판정)와 014(DEC-73 승인 품목 취소, DEC-81·RULE-40 같은 행사)를 따른다.
- 이미 있는 것: 모듈 연결 두 벌(`apps/api/src/serve.ts`의 `appOf`, `http/boundary.test.ts`의 `modulesOf`), 시험 세션과 호출기(`test-support/http.ts`의 `testSession`, `caller`), 시험 DB(`db/test-db.ts`), 가짜 저장소(`test-support/storage.ts`), 라우트 모듈마다의 `clock` 옵션(꼴이 제각각), 쓰기 한도(`purchases/write-limit.ts`), 시연 명령(`scripts/demo-*.ts`, `manage-demo-data.ts`), DB 기록 시각(`records/records.ts`의 `clockNow` = `clock_timestamp()`), 개인 링크(`registrations/link.ts`, 해시만 저장, 신청 하나에 한 줄), 지우기 일(`purge/run.ts`, 1시간마다), 화면 쪽(`web/src/public/useApply.ts`, `ApplyPage.tsx`, `saved-links.ts`, `finance/useExpenseCreate.ts`).

### 원칙 대조

- 새로 하는 입력: 없다. 명령 번호는 화면이 만들어 보내고 사람에게 보이지 않는다. 응답을 잃고 다시 누르는 사람이 중복을 지우거나 학생회에 묻지 않아도 되어 그 자리에서 이득이다(PRIN-1).
- 근거 연결: 시나리오의 구매 요청은 행사방 메시지에서 만들어 그 메시지를 근거로 잇는다(PRIN-2, DEC-71). 시연 데이터도 같다.
- 변경 이력: 다시 보낸 명령은 기록도 판도 새로 만들지 않는다. 신청의 개인 링크를 다시 줄 때 판은 생기지 않는다(링크는 기록이 아니다).
- PRIN-5: 시연 학생회의 가상 운영진은 로그인 수단이 없어 실제 사람이 그 자리로 볼 수 없다.

## 범위 밖

- Playwright 브라우저 흐름 시험(리허설 뒤). 시연 데이터를 운영 DB에 넣기(진행 에이전트가 사람의 허락을 받은 뒤 한다). 개발 DB에 넣기도 진행 에이전트가 한다.
- 수입 만들기·구매 요청 내기 등 다른 만들기의 명령 번호(Codex 3번 '모든 생성 API로 확대'는 시범 운영 뒤). 다른 기기에서 개인 링크 찾기(문자·메일 보내기).
- 다른 핵심 흐름(가입·역할 변경 뒤 다른 사람 화면 갱신, Codex 4번은 013), 회의·결과보고서(RFC-7 미룸), 잘린 목록(Codex 6번).
- 기존 기능 시험의 SQL 준비를 시나리오로 바꾸기. 흐름 시험이 따로 서고, 기능 시험은 그대로 둔다.

### 시나리오

인물: 회장(명령에 준 계정, 흐름 시험은 시험 계정), 부회장, 기획부장, 기획부원, 재정부장, 재정부원, 홍보부장, 신청자 셋(로그인 없음). 행사 A는 끝까지, 행사 B는 '구매 요청'에서 멈추고, 행사 C는 날짜 없이 만들기만 한다.

0. 준비: 회장이 학생회를 만들고, 인물이 초대 코드로 들어와 동의하고, 회장이 부서를 나눈다. 재정부장이 회계 기간·예산 항목(행사 A용 하나, 상시 하나)·대표 계좌·참가비 계좌를 만든다.
1. 행사 만들기: 기획부장이 행사 A(끝이 마지막 단계 하루 전)를 만든다. 회장이 그 장소를 고친다(DEC-79).
2. 신청 양식: 기획부장이 참가비·정원·참가비 계좌로 양식을 연다.
3. 공개 신청: 신청자 셋이 공개 경로로 신청한다. 한 명은 같은 명령을 다시 보내 새 신청이 생기지 않고 링크를 받는다.
4. 입금 확인: 재정부원이 둘의 입금을 확인한다. 한 명은 입금 뒤 취소해 환불함으로 둔다(012의 환불 규칙).
5. 업무: 기획부장이 행사 A 업무를 기획부원에게 맡기고, 기획부원이 끝낸다(015가 먼저 오르면 그 자동 전환을 따른다).
6. 구매 요청: 기획부원이 행사방에 부탁 메시지를 올리고, 그 메시지에서 품목 둘의 요청을 낸다.
7. 결재: 재정부장이 둘을 행사 A 예산 항목으로 승인하고(RULE-40), 하나는 사지 않기로 해 취소한다(DEC-73, 014).
8. 지출: 재정부원이 남은 품목을 결제한 지출을 적고(같은 명령을 한 번 더 보내도 하나), 부원이 먼저 낸 직접 지출 하나를 적는다. 흐름 시험은 가짜 저장소로 증빙 하나를 붙이고, 시연은 저장소가 없으면 이 줄을 건너뛴다.
9. 정산: 시계가 행사 끝을 지난다. 재정부원이 먼저 낸 지출을 환급하고 환불함의 환불을 마쳐 남은 것이 0이 된다(012의 정산 끝).
10. 완료: 회장이 사유와 함께 완료한다(012). 완료 뒤 행사 A에 지출을 적으면 409 `EVENT_COMPLETED`다.

### 리허설 화면 기준

시연을 넣은 뒤 회장이 읽는 화면 응답에서: 행사 목록에 완료·예정·날짜 미정이 하나씩. 행사 A는 상태 옆에 완료 사유, 신청 3·입금·환불 숫자, 참가비 수입과 지출 합계가 시나리오 값, 정산 남은 것 0. 행사 B는 받는 중인 양식, 입금을 기다리는 신청자, 결재를 기다리는 요청 하나(재정 화면 요청 목록에 보임), 진행 중 업무. 회장에게 모든 완료 전 행사의 `event.update`가 있다. 행사방에 부탁 메시지가 있고 그 메시지가 요청의 근거로 이어진다. 회장 홈의 할 일이 비지 않는다. 가상 운영진의 Google 연결은 0이다.
