# 030 기록 메뉴 뼈대

> 만들 때의 명세다. 결정은 vada-docs [DEC-110](https://github.com/vada-hq/vada-docs/blob/main/decisions/0110-records-menu-skeleton-first.md)이 원문이다. 새 표·마이그레이션은 없다.

상한: 조각마다 M 4시간(실제로 도는 시간). 시작 2026-10-29.

## 왜

시범 운영 학생회와의 미팅에서 기획자가 그린 기록 흐름(REC-01 완료한 행사 목록, REC-02 행사 기록 상세)이 작동하는 것을 보인다. 숫자는 이미 쌓인 기록(신청·출석, 예산·지출, 업무, 판, 회의, 완료 결재)에서 열 때마다 센다. 사람이 쓰는 칸은 없다. 설계 입력은 vada-hq `notes/archive-design.md` 2.1, 3.1, 4.2~4.4, 부록 D이고, 그 가운데 사람이 쓰는 칸·확정·스냅숏·마이그레이션은 이번에 하지 않는다.

## 원칙 대조

- 새 입력과 바로 오는 이득: 없다. 완료를 누르면 그 행사가 기록 목록에 저절로 들어간다(PRIN-1).
- 근거 연결: 숫자마다 원래 기록이 있고, 근거 자료 대목이 행사 화면의 업무·회의·구매 탭으로 잇는다. 타임라인의 회의 줄은 회의 기록을 가리킨다(PRIN-2).
- 변경 이력: 타임라인이 행사 판(이름·일시·장소·책임자)과 완료·완료 취소 결재를 그대로 보인다. 저장하는 값이 없어 따로 판이 없다(PRIN-3).
- 권한: 행사를 보는 운영진 모두(`council.view`)가 본다. 다른 학생회 행사는 404, 완료하지 않았거나 완료를 취소한 행사도 404다. 신청자 개인정보(이름·학번·휴대폰)는 응답에 없다(PRIN-5).

## 범위(뼈대)와 나중(살)

- 뼈대: 옆 메뉴 '기록'(재정 아래), 완료한 행사 목록(카드, 찾기, 정렬), 행사 기록 상세의 자동 대목(개요, 성과, 타임라인, 근거 자료), 완료한 행사 머리의 [기록 보기].
- 나중에 붙일 살(DEC-110): 현장 운영·회고·인수인계 쓰기, AI 인수인계 초안, 검토와 발행(스냅숏, 버전), 기록 상태 배지, 결산 탭, 결정 탭, 기수 고르기, 오른쪽 인수인계 패널. 붙이기 전에는 목차와 화면에 자리를 보이지 않는다. 응답은 대목·칸을 더하기만으로 늘린다.

| 무엇 | 정한 것 | 근거 | 되돌리기 |
|---|---|---|---|

| ② 출석률 | 출석 ÷ (신청 − 취소). 취소 수를 따로 준다 | DEC-110 | 쉬움 |

## 위험

- 격리·개인정보: 모든 셈은 줄마다 기록의 학생회로 거르고, 신청은 수만 읽는다. 조각 1은 깊게 검토한다.
- 주소: `APP_MENUS`·`RECORD_PARENTS`에 'records'를 더하는 일은 조각 2다. 그 전에는 `parseAppPath`가 기록 주소를 읽지 않는다.

## 조각

### 1. 서버: 목록·상세 API와 계약 [x]
- 할 수 있게 되는 것: `GET /api/organizations/:councilId/records/events`(완료한 행사 목록), `GET .../records/events/:eventId`(행사 기록 상세)를 읽는다. 쓰기 없음.
- 수용 기준: 완료한 행사만 나오고 완료를 취소하면 빠진다. 다른 학생회 행사·완료하지 않은 행사는 404, 다른 학생회 사람·내보낸 사람은 403, 로그인 없으면 401. 취소 포함·제외 수, 출석률 분모 0, 예산 0의 집행률 null, 돈이 정산과 같음, 응답에 신청자 이름·학번·휴대폰 없음, 타임라인 시각순을 시험한다.
- 닿는 곳: contracts `records.ts`·`paths.ts`, api `event-records/*`, `events/queries.ts`(`eventRowsAmong`), `app.ts`·`app-modules.ts`, `test-support/settlement.ts`. 검토: 깊게. 마이그레이션: 없음.

### 2. 화면 [x]
- 할 수 있게 되는 것: 옆 메뉴 '기록'(재정 아래)에서 완료한 행사 목록(REC-01)을 보고 행사 기록 상세(REC-02)로 간다. 완료한 행사 머리의 [기록 보기]가 그 행사의 기록 상세로 간다.
- 수용 기준: 목록 카드는 행사명, 일시, 담당, 완료 처리일과 칩 셋(참석 N명(신청 M명), 예산 집행 N%, 완료 업무 N건). 행사명 찾기, 정렬(완료 처리일순 기본, 행사 일시순). 상세는 2단(목차 + 본문: 개요, 성과, 타임라인, 근거 자료). 근거 자료는 행사 화면의 탭 주소로 링크한다. 오른쪽 인수인계 패널은 살이라 두지 않는다. 비율은 서버 값을 그대로 보인다.
- 닿는 곳: contracts `paths.ts`(`APP_MENUS`·`MENU_QUERY`·`RECORD_PARENTS`·`RECORD_QUERY`에 records, 기록 주소 함수를 `menuPath`·`recordPath`로), 서버 진입 목록, web 기록 화면·옆 메뉴·행사 머리, 갤러리. 검토: 보통. 마이그레이션: 없음.
- 와이어프레임(REC-01, REC-02)과 다르게 한 곳
  - 완료 처리일·행사 일시는 'YYYY. MM. DD'가 아니라 날짜 도우미 꼴('10월 24일 (토)', 올해가 아니면 '2025년 …')이다. 근거: AGENTS.md '화면 문구와 폼'의 날짜 꼴.
  - 참석 칩은 '186명 참석 (신청 210명)'이 아니라 '참석 186명 (신청 210명)'이다. 근거: DEC-110의 칩 글.
  - 예산이 0이라 집행률이 없으면 카드 칩은 '예산 없음'이고, 상세의 출석률·집행률은 그 칸을 뺀다(앞의 수가 0을 이미 보인다). 근거: 정한 것 ①(화면은 다시 계산하지 않음), 칩 자리 셋을 그대로 둬 카드끼리 견주기 쉽게.
  - 기록 상태 배지, '인수인계 문서 미발행 N건', 화면 위 설명 글, 대목의 '끼룩이가 모은 기록' 표시, 오른쪽 인수인계 패널, 발행 정보는 없다. 근거: DEC-110(살), AGENTS.md 화면 문구 최소.
  - 머리글 제목은 '행사 아카이브'가 아니라 '행사 기록'이다. 근거: 발행(아카이브)이 아직 없고 메뉴 이름이 기록이다.
  - [기록 보기]는 행사 머리의 요약 줄이 아니라 완료 사유 옆이다. 근거: 요약 줄은 메시지 탭(기본 탭)에서 방 전환으로 바뀌어, 어느 탭에서나 보이는 자리가 완료 사유 줄이다.
  - 행사 일시순은 최근 행사부터, 일시 미정은 끝이다. 근거: 완료 처리일순(최근부터)과 같은 방향.
