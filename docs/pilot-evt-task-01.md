# EVT-TASK-01(행사 업무 보드) 파일럿

**칸반은 새 계급이 아니었다.** TASK-01(상시 업무)이 이미 같은 모양이고, 열 넷은
같은 출처를 `status`만 바꿔 네 번 조회한다. 진행률 막대도 이미 있었다.

여기서 처음인 것은 **인자가 오가는 것**이다. EVT-TASK-02는 받기만 했고, 그 값을
주는 쪽이 없어 주소로만 들어갔다.

## 2. 이동할 때 인자를 넘긴다 (신규 계급 · 새 개념)

화면이 인자를 받는다면 **누군가는 그 값을 줘야 한다.** 그 자리가 없었다.

```json
"itemAction": {
  "type": "navigate",
  "targetScreenId": "EVT-TASK-02",
  "params": { "taskId": { "itemField": "id" } }
}
```

값의 출처가 셋에서 **넷**이 됐다. 새로 생긴 `itemField`가 앞의 셋과 다른 점은
**명세도 화면도 그 값을 모른다**는 것이다 — 눌린 그 행만 안다. 그래서 조회에는
쓸 수 없다(조회하는 시점에는 아직 항목이 없다). 검증기가 그 자리를 막는다.

### 명세를 읽어서는 보이지 않는 구멍

인자를 넘기지 않아도 **이동은 성공한다.** 대상 화면만 조용히 빈다. 그래서 세
가지를 검사한다.

- 넘긴 인자를 대상 화면이 받지 않으면 오류.
- 대상이 받는 인자를 아무도 주지 않으면 오류.
- 가리킨 조각이 그 목록의 출처에 없으면 오류.

셋 다 실제로 무는 것을 확인했다(인자 이름과 조각 이름을 각각 어긋내 봤다).

### 그리지 않는 조각

`event.taskBoard`의 `id`는 **카드에 그려지지 않는다.** 그런데도 데이터에 있는
이유는 그것이 넘어가는 값이기 때문이다. 제목으로 넘기면 이름이 같은 업무가 둘
생기는 날 조용히 어긋난다. design 대조는 그려지는 것만 보므로 이 조각은 검사
밖에 있다 — 그래서 카탈로그의 설명에 적어 뒀다.

## 3. 제목이 데이터다 (신규 계급 · 방아쇠가 당겨졌다)

EVT-TASK-02에서 **미해결로 적어 두고** 트리거를 걸어 둔 것이다(`눈썹에 데이터가
들어간다`). 거기서는 빵부스러기의 한 칸이었는데, 여기서는 **제목 자체**가 행사
이름이다. 두 번째이므로 자리를 만들었다.

```json
"meta": {
  "title": "행사 업무 — 칸반 보드",
  "titleFrom": { "dataSourceKey": "event.summary", "field": "title",
                 "params": { "eventId": { "screenParam": "eventId" } } }
}
```

**둘을 가른 것이 핵심이다.** `meta.title`은 지금까지 두 가지를 겸했다 — 화면의
이름이자 그려지는 제목이다(그 긴장은 INV-01에서 이미 드러나 `TITLE_NOT_DRAWN`으로
적혀 있었다). 이제 그려지는 것은 데이터이고, `meta.title`은 사람이 이 화면을
부르는 말로 남아 보드의 머리에 그려진다.

요소가 아니라 화면 자체가 값을 읽으므로 요소 검사가 지나친다. 지나치면 없는
조각을 가리켜도 **제목만 조용히 빈다** — 그래서 화면 수준 검사를 따로 뒀다.

## 4. 라벨 없이 값만 늘어놓는 묶음 (신규 계급 · 새 개념)

행사 머리는 여섯 조각인데 라벨이 하나도 그려지지 않는다. `summary.items[].label`이
필수라 지어내야 했는데, **지어낸 라벨은 디자인에 없는 카피다.**

이유가 있었다. 값이 라벨까지 품고 온다 — `담당 학술체육부 · 김바다`,
`다음 일정 · 07.20 참가자 모집 공지 작성`. 서버가 이미 완성했으므로 화면이 앞에
다시 '담당'을 적을 자리가 없다. 그래서 `label`을 선택으로 넓혔다.

같은 묶음 안에서 갈리는 것도 확인했다 — 행사 카드는 `D-DAY`·`전체 진행 현황`은
그려지고 `행사일 2026-08-20 · ERICA 체육관`은 라벨이 없다.

## 5. (A) 마찰 2건

### 없는 한 건에 답할 자리가 없었다 — 이어 보고서야 드러났다

보드에는 업무가 일곱인데 **와이어프레임이 상세로 그린 것은 T-03 하나뿐이다.**
나머지 여섯을 누르면 화면이 터졌다. `readObjectSource`가 '개발용 응답이 없다'로
오류를 냈기 때문이다.

두 경우가 섞여 있었다. **인자로 거른 결과가 빈 것은 '없다'가 아니라 '찾지
못했다'다** — 서버도 같은 답을 한다. 그리고 그 말은 이미 카탈로그에 있었다
(`messages.empty: "업무를 찾지 못했습니다"`). 아무도 쓰지 않고 있었을 뿐이다.

없는 여섯을 지어내지 않았다. 디자인에 없는 것을 만들면 그것이 명세에 없는
사실이 된다.

### 버튼 이름 부분 일치가 라벨이 겹치면 깨진다

준수 검사는 버튼 이름을 부분 일치로 본다(아이콘의 대체 텍스트가 섞이기 때문).
이 화면에는 `업무` 갈피와 `업무 추가` 버튼이 함께 있어 하나를 고르지 못했다.
있는지를 보지 몇 개인지를 보지 않는 것으로 고쳤다 — 바로 위 `meta` 카피 검사가
이미 같은 이유로 그렇게 하고 있었다.

## 6. 그대로 쓰인 것

| 이미 있던 자리 | 여기서 |
| --- | --- |
| `itemList` × 열 개수, `params.status`가 고정값 | 칸반 열 넷(TASK-01과 같다) |
| 열의 건수는 항목 수에서 나온다 | `예정 2`·`진행 중 3` |
| `select.presentation: choiceGroup` + `task.scope` | 전체 업무 / 내 업무 |
| `summary` + 상태 칩 + 아이콘 | 지연·검토 필요·내 담당·담당자 없음 |
| `ProgressBar` + `progressPercent` | 전체 진행 현황 `1 / 7 완료` |
| 톤 이름을 데이터가 준다 | 부서 색상선·부서 딱지·주의 딱지 |
| `AppShell.headerAction` | 머리의 '업무 추가' |
| 완성된 문자열로 온다 | `D-33`·`08.20 10:00`·`2026-07-18 · 지연` |

**부서 색상선의 규칙은 이미 적혀 있었다.** `task.board`의 `tone` 설명에 "기본은
부서 색이고, 담당자가 없는 업무처럼 먼저 봐야 하는 것은 경고 색으로 온다"고
TASK-01 사이클에서 써 뒀다. 빨간 카드 둘이 필터의 `담당자 없음 2건`과 정확히
맞아떨어져 그 설명이 맞다는 것도 확인됐다.

## 7. 갈피 일곱은 고르는 것이 아니라 옮겨 가는 것이다

추출기가 물었다 — 나란한 버튼 일곱을 어떻게 읽느냐. 근거로 답했다: 일곱이 전부
와이어프레임의 **다른 화면**이다(EVT-02·EVT-DOC-01·EVT-MEET-01·EVT-SCHED-01·
EVT-04·EVT-FIN-01). 한 화면 안에서 내용이 바뀌는 갈피(EVT-TASK-02의 것)와 다르다.
그래서 `select`가 아니라 버튼 일곱이고, 지금 보는 갈피는 제자리를 가리킨다 —
셸의 메뉴가 이미 그렇게 하고 있다.

**이 머리는 행사 화면 일곱이 나눠 쓸 것이다.** 그런데 지금은 하나뿐이라 화면이
갖는다. 두 번째 행사 화면을 만들 때가 자리를 만들 때다(BACKLOG).

## 10. 남긴 것

- **'업무 보드로'는 아직 pending이다.** 보드는 생겼지만 업무 상세가 '어느
  행사인지'를 어디서 얻는지 정해지지 않았다. `eventId`를 주소에 함께 실으면
  taskId와 어긋날 수 있고(업무는 행사를 하나만 가진다), `task.detail`이 그 값을
  주는 것이 맞아 보이지만 그건 아직 관측되지 않은 사실이다. 안내 문구를 그
  이유로 바꿔 뒀다.
- **상시 업무의 '업무 상세'는 여전히 미정이다.** 다섯 곳이 막혀 있다.
  EVT-TASK-02는 행사 업무의 상세임이 이제 확실해졌으므로(보드가 이어졌다)
  상시 업무를 여기로 보내는 것은 더 어려운 판단이 됐다.
