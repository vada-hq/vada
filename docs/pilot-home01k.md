# HOME-01K 파일럿 — 대시보드는 다른 계열이다

`INV-01`까지의 다섯 화면은 전부 **폼 화면**이었다(입력·선택·제출). `HOME-01K`는
처음 만나는 **읽기 전용 대시보드**이고, 처음 만나는 **데스크톱 화면**이다.

사이클을 끝내기 전에 측정부터 기록한다. 규약대로 진행 중에 적는다 — 끝난 뒤
재구성하면 과소 보고된다.

## 1. 자산 추출 실패 (해결됨)

벡터 64개 중 3개가 export를 거부당했다.

```
Failed to export node. This node may not have any visible layers.
```

두 가설이 교차 검증에서 죽었다.

| 가설 | 반례 |
| --- | --- |
| 면적이 0인 벡터(직선) | ONB-02는 면적 0 벡터 5개를 갖고도 11개 전부 성공 |
| 조상이 숨겨져 있다 | 조상 11단계가 모두 보임 |

살아남은 판별자는 `absoluteRenderBounds === null`이다. 등록된 6개 화면의 벡터
120개 중 null은 그 셋뿐이고, 그 셋은 전부 실패했다. `isVectorAssetNode`로
계급을 고쳤다(플러그인과 정규화기가 같은 규칙을 쓴다).

**부수 발견**: 진짜 오류 메시지가 `error instanceof Error`에 걸려 버려지고 있었다.
Figma 샌드박스가 던지는 값은 다른 렐름의 객체라 `instanceof`가 거짓일 수 있다.
이것 때문에 진단이 한 번 왕복했다. 플러그인 9개 지점을 `toErrorMessage`로 교체.

또한 자산 추출이 **전부 아니면 전무**여서 벡터 하나가 실패하자 나머지 63개와
`reference.png`까지 버려졌다. 이제 실패한 것만 보고하고 나머지는 건진다.

## 2. 추출기가 화면의 45%를 못 본다

| | 개수 |
| --- | --- |
| 텍스트 노드 총계 | 69 |
| 추출기가 요소로 잡은 것(전부 `button`) | 38 |
| **아예 못 본 것** | **31 (45%)** |

못 본 31개의 정체:

| 묶음 | 개수 | 예 |
| --- | --- | --- |
| 사이드바 내비게이션 + 사용자 | 12 | 홈 · 내 업무 · 운영 · 재정 · 기록 · 조직 관리 · 메시지 |
| 상단 헤더 | 3 | 제12대 소프트웨어융합대학 학생회 운영 현황 · 2026년 1학기 |
| 끼룩이 브리핑 | 4 | 박해랑님, 확인이 필요해요 · 지연된 업무가 1건 있습니다. |
| 섹션 제목 | 4 | 진행 중·예정 행사 · 다가오는 주요 일정 · 조직 주요 알림 · 전체 재정 요약 |
| 재정 요약 수치 | 8 | 전체 예산 사용률 34% · 사용 가능 예산 66% · 증빙 누락 5건 |

그리고 잡은 38개도 **유형이 틀렸다**. Figma에서 `Btn`으로 이름 붙었다는 이유로
전부 `button`이 됐지만, 실제로는 행사 카드(`기획 중`), 일정 행(`07.20`),
알림 행(`증빙 서류 누락`)이다. 추출기 질문 30건 중 22건이 이 오인에서 나온
`description·badge`와 `targetScreenId` 질문이다.

## 3. 선례 재사용은 이 화면에서 무력하다

이 화면에는 `input`·`select`가 **하나도 없다**. 선례의 확정 단위가 필드이므로
적용할 자리가 없었다. 화면당 사람 개입 절감은 **0건**이다.

선례 재사용은 폼 화면끼리만 효과가 있다 — INV-01에서 11건을 줄인 것은
ONB-01과 같은 폼이었기 때문이다.

## 4. 요구되는 신규 계급

| # | 계급 | 근거 | 사례 수 |
| --- | --- | --- | --- |
| 1 | **화면 셸**(사이드바 + 헤더) | 텍스트 15개. 화면의 요소가 아니라 모든 데스크톱 화면이 공유하는 상위 구조다 | 1 |
| 2 | **통계 타일** | 진행 중 행사 1개 · 예정 행사 2개 · 이번 주 주요 일정 8개, 재정 요약 3개 | 6 |
| 3 | **진행률 표시** | 준비 62% · 준비 18% · 전체 예산 사용률 34% | 3 |
| 4 | **읽기 전용 데이터 목록** | 행사 카드 2 · 일정 행 3 · 알림 행 2. 기존 `list`는 추가·수정·삭제하는 편집 목록(ORG-02)이라 다르다 | 3종 |
| 5 | **원격 데이터 출처** | 화면의 거의 모든 값이 서버에서 온다. 지금 원격 개념은 `optionsSource`(select 선택지)뿐이다 | 전면 |
| 6 | **브리핑 카드** | 아바타 + 눈썹 + 제목 + 문장 목록 + 액션 버튼 | 1 |

직전 사이클들과 비교하면 증가폭이 다르다.

| 사이클 | 신규 계급 |
| --- | --- |
| ORG-02 | 1 (`list`) |
| ORG-01 | 2 (`note`, `group`) |
| INV-01 | 2 (`summary`, 버튼 강조도) |
| **HOME-01K** | **6** |

요구되는 것처럼 보였던 6개 중 **실제로 만든 것은 3개**다.

| # | 처분 |
| --- | --- |
| 1 화면 셸 | **보류**. 사례가 하나뿐이라 일반화하지 않았다. 명세에서 빼고 구현에서도 그리지 않는다 |
| 2 통계 타일 | `summary`로 표현됨 — 라벨-값 쌍이고 항목이 명세에 고정이다 |
| 3 진행률 | 만들지 않음. `progressPercent`는 데이터의 조각이고 막대는 시각이라 design이 갖는다 |
| 4 읽기 전용 목록 | **`itemList` 신설** |
| 5 원격 데이터 출처 | **`data-sources.json` 신설** |
| 6 브리핑 카드 | `summary`(눈썹+제목) + `itemList`(문장) + `button`으로 분해됨. **`summary.titleField` 추가** |

즉 신규 계급은 6개가 아니라 **`itemList` · `data-sources.json` · `action.pending`
3개**다. 직전 사이클(INV-01)의 2개와 크게 다르지 않다.

### summary와 itemList의 경계

항목 수가 **명세에 있느냐 데이터에 있느냐**다.

| | summary | itemList |
| --- | --- | --- |
| 항목 수 | 명세가 정한다 | 데이터가 정한다 |
| 예 | 행사 건수 3종, 재정 요약 4종 | 행사 2건, 일정 3건, 알림 2건 |

같은 라벨-값이라도 이 축에서 갈린다. 타일이냐 행이냐 카드냐는 명세에 넣지
않았다 — INV-01의 묶음 상자 때와 같은 결론으로 **시각은 design이 갖는다**.

## 5. AI 읽기 마찰

| 분류 | 건수 |
| --- | --- |
| **(A) 스키마에 자리가 없다** | **3** |
| (B) 자리는 있는데 안 채웠다 | 0 |
| (C) 원래 명세의 관심사가 아니다 | 5 |

폼 화면 다섯 개에서 (A)는 계속 0건이었다. 대시보드에서 처음 3건이 나왔고 모두
**값이 서버에서 온다는 사실**을 담을 자리가 없어서였다(세 번째는 아래 7절의
조직 알림 아이콘 — 항목마다 다른데 데이터가 종류를 말하지 않았다).

**(A)-1 `button.description`이 서버 값을 담는다.** '내 담당 업무' 카드의
'진행 중·검토 필요 4건'은 데이터인데 `description`은 고정 문자열이다. 지금은
디자인의 예시 값을 그대로 넣어 뒀다 — 건수가 바뀌면 틀린다. `summary`가 얻은
`dataSourceKey`+`field`를 `button`에도 줄지는 같은 사례가 하나 더 나오면 정한다.

**(A)-2 두 단 배치를 명세가 말하지 않는다.** 이건 (A)로 셌지만 **자리를 만들지
않기로 한 것**이다. 배치를 명세에 넣으면 design.json과 같은 사실이 두 곳에
생긴다. 구현이 nodeId로 요소를 집어 design의 자리에 끼우는 방식으로 풀었다
(`elementByNodeId`).

(C) 5건은 전부 시각이다: 카드 radius·padding, 배지 색, 타일 배경, 아이콘,
막대 높이. design.json에서 읽어 ÷0.875로 환산했다.

## 6. 스크린샷 판독이 잡은 것

**진행률 막대 폭.** 처음엔 남는 폭을 다 쓰게 그렸는데, 디자인은 행사 카드의
막대가 **112→128px 고정**이고(16:163) 라벨이 뒤에 붙는다. 재정 요약의 막대만
카드 폭을 채운다. 명세로는 알 수 없고 design을 재야 나온다.

## 7. 자산 — 단위가 틀려 있었다 (해결됨)

처음에는 '구현이 `assetRef`를 쓰지 않는다'로 보였다. 실제 원인은 다르다.

**아이콘 하나가 벡터 여러 개로 그려지는데 벡터마다 SVG를 뽑고 있었다.**
HOME-01K는 아이콘 22개가 파일 61개로 흩어졌다. 조각난 SVG는 아무도 쓸 수
없다 — 구현이 안 쓴 게 아니라 **쓸 수 없는 것을 저장하고 있었다**.

자산의 단위를 '벡터만 품은 가장 바깥 노드'로 올렸다(`collectAssetNodes`).
판별은 이름이 아니라 구조로 한다. ONB-01은 11→7, HOME-01K는 61→21이 된다.

**끼룩이 마스코트(16:87)는 `imageRef`를 가진 이미지 fill이라 벡터로 뽑을 수
없다.** 이미지 fill을 가진 노드는 PNG로 뽑고 브리지가 `image/png`를 받도록
열었다. 시그니처가 아닌 바이트는 거부한다.

구현은 `FigmaAsset`이 `nodeId`로 자산을 집어 그린다. 어떤 자리에 어떤 자산이
오는지는 명세가 아니라 design이 갖는 사실이라 호출부가 지목한다.

### 조직 알림 아이콘 — (A) 한 건 더

알림 두 줄의 아이콘이 서로 다른데(문서형·인원형) `home.orgAlerts`에는
아이콘을 가리키는 조각이 없었다. 항목 수가 데이터에 달렸으므로 아이콘도
데이터가 말해야 한다. `kind` 필드를 계약에 넣고, 모르는 종류는 조용히
아이콘 없이 넘어가는 대신 오류로 드러나게 했다.

## 결론

**수렴이 아니라 계열의 전환이었다.** 처음 세었을 때 신규 계급 6개는 발산처럼
보였지만, 기존 어휘로 표현되는 것을 걷어내니 3개였다.

그리고 **(A)가 처음으로 0이 아니게 됐다.** 폼 화면에서는 값이 사용자에게서
왔으므로 명세가 값을 말할 필요가 없었다. 대시보드는 값이 전부 서버에서 오고,
그 사실을 담는 자리가 `select.optionsSource` 하나뿐이었다. `data-sources.json`이
그 구멍을 메웠지만 `button.description`은 아직 남았다.
