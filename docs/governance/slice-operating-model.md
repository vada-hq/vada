# VADA 슬라이스 운영 규격 v4

- 상태: 확정
- 결정일: 2026-07-27
- 최종 개정일: 2026-07-29
- 활성 프로세스 계약: `PROCESS:documentation@R8`
- 활성 착수 게이트: `PROCESS:DoR@R4`
- 활성 작업 흐름: `PROCESS:work_item_flow@R1`
- 슬라이스 실행 명세 파일럿: `SL-EVT-001`
- 계획·작업 구조 파일럿: `MS-FIN-01`
- 실행 스키마: `contracts/schemas/slice.schema.json`

## 목적

슬라이스는 화면 묶음이나 부서별 작업 묶음이 아니라, 사용자가 관찰할 수 있는 결과를 DB·API·화면·자동 테스트까지 세로로 완성하는 단위다.

정책·필드·상태·권한처럼 바뀔 수 있는 의미를 슬라이스마다 복사하지 않는다. 슬라이스는 정확한 계약 리비전을 참조하고, 자체적으로는 사용자 결과·수용 기준·범위와 관계만 소유한다.

## 작업 계층

제품 작업은 다음 책임 경계를 사용한다.

`제품 목표 → 마일스톤 → [필요할 때만 슬라이스] → 작업 항목`

- **제품 목표**는 왜 이 제품 상태가 필요한지 소유한다.
- **마일스톤**은 한 번의 연결 데모로 검증할 수 있는 제품 단계를 소유한다.
- **슬라이스**는 사용자에게 관찰되는 수직 결과와 정확한 계약 기준선을 소유한다.
- **태스크**는 그 결과를 만들기 위한 기획·디자인·개발 실행정보를 소유하며, 결정이나 실행이 적용되는 가장 가까운 계획 항목에 연결한다.

### 슬라이스를 만드는 조건

슬라이스는 의무 계층이 아니다. 다음 조건을 모두 만족할 때만 만든다.

1. 사용자가 시작부터 종료까지 관찰할 수 있는 완주 결과가 있다.
2. 다른 결과와 구분해 먼저 구현·시연·검증할 가치가 있다.
3. 고유한 수용 기준과 디자인·개발 작업 묶음을 가질 수 있다.

마일스톤 자체가 하나의 작고 검증 가능한 완주 결과라면 슬라이스를 생략하고 작업 항목을 마일스톤에 직접 연결한다. 화면, CRUD 동작, 역할, API 또는 내부 기술 계층만을 기준으로 슬라이스를 만들지 않는다.

선행 기능이 있다는 이유만으로 독립성이 사라지는 것은 아니다. 선행 완료 후 새 사용자 결과를 처음부터 끝까지 시연할 수 있다면 후속 슬라이스가 될 수 있다.

마일스톤은 릴리스나 스프린트와 다르다. 릴리스는 배포 약속이고 스프린트·사이클은 시간 상자다. 마일스톤 상태는 연결된 태스크 개수나 롤업으로 자동 완료하지 않고 데모와 종료 기준을 확인한 뒤 수동으로 확정한다.

후보 슬라이스는 주 마일스톤이 없거나 하나만 있을 수 있다. `예정`, `준비됨`, `진행 중`, `완료` 슬라이스는 정확히 하나의 주 마일스톤에 속한다. 이후 마일스톤에서 완료 행동을 확장할 때 같은 슬라이스를 재사용하지 않고 후속 슬라이스를 만든다.

## 정본과 투영

| 정보 | 실행 정본 | Notion의 역할 |
| --- | --- | --- |
| 계약의 결정 이유·승인·상태·대체 관계 | 계약 리비전 DB | 정본 |
| 코드가 소비하는 계약 내용 | `contracts/*.json`, `contracts/openapi.json` | 같은 리비전 ID의 설명·관계 |
| 슬라이스 실행 기준선·AC·범위·관계 | `contracts/slices/*.json` | 사람이 읽고 조회하는 투영 |
| 마일스톤·후보 슬라이스의 결과·관계·목표 기간 | 해당 없음 | `계획 항목 V2` 정본 |
| 담당자·검토자·우선순위·일정·추정 | 해당 없음 | `작업 항목 V2` 정본 |
| 화면 상세 설계 | 디자인 산출물·제품 코드 | 화면 DB의 탐색·관계 |

저장소와 Notion에 함께 보이는 값은 독립된 두 정본이 아니다. 저장소의 `specRevision`과 Notion의 `명세 리비전`이 같아야 하며, 에이전트는 의미 변경 시 두 표현을 같은 작업에서 갱신한다.

CI는 `contracts/notion.json`에 선언한 기대 리비전까지 검증한다. 외부 Notion의 실제 속성은 CI에서 조회하지 않으므로, 에이전트가 완료 전에 페이지를 다시 읽어 일치 여부를 확인하고 결과를 보고한다. 투영이 늦게 갱신돼도 구현 판단은 저장소 실행 명세를 따르며, Notion은 같은 리비전에서 다시 생성할 수 있어야 한다.

## Notion V2 데이터베이스 책임

현재 계획·작업 정본은 `contracts/notion.json`의 `planningDatabases.planItems`와 `planningDatabases.workItems`다. 이전 마일스톤·슬라이스·태스크 데이터베이스는 `legacyPlanningDatabases`에 두고 새 항목을 만들지 않는다.

- **계획 항목 V2**: 마일스톤과 슬라이스를 `유형`으로 구분하고 `계획 ID`, `결과`, `상위·하위 계획 항목`, `선행·후행 계획 항목`, `계약 기준선`, `완료 기준`, `목표 기간`을 관리한다.
- **작업 항목 V2**: `TSK-n` 자동 ID, `주 작업 범위`, `역할`, `상태`, `선행·후행 작업`, `참조 작업`, `담당자`, `검토자`, `우선순위`, `마감일`, `산출 계약`을 관리한다. `착수 판정`은 이 입력값에서 자동 계산하는 조회 전용 값이다.
- **실행 명세 투영**: 슬라이스가 `예정`으로 승격할 때 `실행 명세`, `명세 리비전`과 필요한 화면·변경 관계를 계획 항목에 추가하거나 연결한다.

`선행 계획 항목`처럼 원인이 되는 관계만 입력하고 `후행 계획 항목` 같은 역관계는 별도로 수정하지 않는다.

작업 항목의 `선행 상태 집계`와 `참조 상태 집계`는 `착수 판정` 계산을 위한 내부 롤업이다. 사람이 직접 관리할 입력값으로 사용하지 않으며, 실행자는 `contracts/notion.json`의 `planningDatabases.workItems.views.readiness`에 연결된 `착수 현황` 보기에서 최종 판정과 근거 관계만 확인한다.

슬라이스에는 포괄적인 `소유자`를 두지 않는다. 제품 승인 책임은 제품 의사결정에서, 기획·디자인·개발 실행 책임은 태스크에서, 계약 유지 책임은 계약 리비전에서 관리한다.

## 후보와 실행 명세

전체 목록을 만들 때 모든 후보에 계약과 AC를 미리 채우지 않는다.

- **후보**: Notion에만 존재한다. 안정 ID, 한 줄 사용자 결과, 도메인, 상위 마일스톤, 대략적인 선행관계만 가진다.
- **예정**: 실행 명세가 `contracts/slices/`에 생성되고 `specRevision: 1`부터 시작한다. 계약이나 정책이 검토 중일 수 있다.
- 후보를 예정으로 승격할 때 Notion 관계와 `contracts/notion.json` 매핑을 함께 만든다.

## 실행 명세 필드

- `$schema`, `schemaVersion`: 구조 규격 식별자
- `specRevision`: Notion 투영과 동기화하는 양의 정수
- `id`, `title`, `subsystem`, `releaseScope`, `status`: 안정 식별과 분류
- `outcome`: 역할명이나 구현 수단 없이 적은 한 줄 사용자 결과
- `screenRefs`: 영향을 받는 안정 화면 ID
- `dependsOn`: 구현·사용자 흐름의 선행 슬라이스
- `changes`: 완료된 행동을 바꾸거나 확장하는 후속 변경 대상
- `contractBaseline`: 구현이 소비하는 정확한 계약 리비전
- `acceptanceCriteria`: 안정 AC ID, 계약 참조, 관찰 가능한 결과
- `outOfScope`(선택): 포함으로 오해하기 쉬운 인접 기능, 의도적으로 미룬 기능 또는 누락 시 위험한 제한과 선택적 추적 대상

담당자, 마감일, 우선순위, 작업량, 체크리스트는 실행 명세에 넣지 않는다. 이 값들은 태스크가 소유하며 JSON Schema가 잘못된 혼입을 거부한다.

## Notion 슬라이스 본문

본문은 필요한 항목만 다음 순서로 사용한다. 속성으로 확인할 수 있는 사용자 결과, 관계, 계약 기준선은 그대로 반복하지 않는다.

1. 완주 시나리오 — 사용자가 관찰하는 시작부터 종료까지
2. 화면 흐름 — 분기나 상태 전이가 복잡할 때만
3. 수용 기준 — 예정 이상에서 AC ID와 관찰 결과의 읽기용 투영
4. 슬라이스 고유 흐름 경계 — 공통 규칙을 반복하지 않음
5. 범위 밖 — 포함으로 오해할 인접 기능, 의도적으로 미룬 기능 또는 누락 시 위험한 제한이 있을 때만
6. 현재 블로커 — 자동 계산할 수 없는 착수 장애가 있을 때만

슬라이스가 약속하는 범위는 사용자 결과·완주 시나리오·수용 기준·참조 계약과 관계에 명시된 행동으로 한정한다. 기록할 범위 밖 항목이 없으면 실행 명세의 `outOfScope`와 본문 섹션을 모두 생략한다.

공통 DoR·DoD·리비전 규칙과 파일 경로 설명은 각 슬라이스에 복사하지 않고 이 문서와 활성 프로세스 계약을 참조한다.

## 생명주기와 게이트

- **후보 → 예정**: 안정 ID·사용자 결과·범위·대략 의존성을 승인하고 실행 명세와 Notion 매핑을 생성한다.
- **예정**: 실행 명세와 안정 AC가 있는 상태다. 특정 AC의 활성 계약과 작업별 착수 조건이 갖춰지면 전체 준비 전에도 격리된 작은 구현 배치를 시작할 수 있다.
- **예정 → 준비됨**: 약속한 전체 기준선 활성, 선행 슬라이스 완료, 관련 화면과 필요한 디자인·개발 작업 연결, 자신 또는 상위 마일스톤 기획 작업의 승인·계약 반영, 계약 검증 통과가 필요하다.
- **준비됨 → 진행 중**: 팀이 완주 결과의 통합과 전달을 현재 WIP로 약속한다. 앞서 격리 구현한 배치도 이때 같은 기준선으로 통합한다.
- **진행 중 → 완료**: 모든 AC와 활성 `QUALITY:DoD`를 통과하고 구현·테스트·문서 상태가 일치해야 한다.

전체 `준비됨` 전의 구현 배치는 기능 플래그·격리된 프리뷰·Mock 등으로 사용자에게 공개하지 않는다. `준비됨` 이후 실행 의미가 바뀌면 작업을 멈추고 영향 검토와 DoR을 다시 통과한다. `완료` 이후에는 기존 명세를 고치지 않고 새 계약 리비전과 `changes` 관계를 가진 후속 슬라이스를 만든다.

완료 슬라이스는 당시 활성 상태였던 계약 리비전을 역사 기준선으로 계속 보존한다. 그 계약이 나중에 `superseded` 또는 `deprecated`가 되어도 완료본은 유효하지만, `draft`나 `review` 계약을 가진 채 완료할 수는 없다.

## 명세 리비전 증가 규칙

다음 변경은 완료 전 `specRevision`을 1 올리고 Notion의 `명세 리비전`도 맞춘다.

- 사용자 결과, 계약 기준선, AC 또는 범위 변경
- 화면 참조, 선행관계, 후속 변경 관계 변경
- 릴리스 범위나 서브시스템처럼 인벤토리 해석을 바꾸는 변경

오탈자, 설명 링크, 담당자·검토자·우선순위·일정·추정 변경은 명세 리비전을 올리지 않는다.

## 태스크 경계

- 기획 작업은 결정이 적용되는 가장 가까운 계획 항목에 연결한다. 둘 이상의 슬라이스가 같은 결정을 사용하면 상위 마일스톤에 한 번만 만들고 슬라이스마다 복제하지 않는다.
- 기획 작업 하나는 독립적으로 승인·반영할 수 있는 결정 묶음 하나만 다룬다. 같은 마일스톤 안에서도 서로 다른 슬라이스나 후속 작업의 착수 시점을 바꾸는 질문은 분리한다.
- 슬라이스가 있으면 슬라이스 고유 디자인·개발 작업은 해당 슬라이스에 연결한다. 마일스톤이 단일 전달 단위라 슬라이스를 생략했다면 해당 작업은 마일스톤에 직접 연결한다.
- 디자인·개발 작업은 적용되는 계획 항목에 동료 작업으로 직접 연결한다. 담당자·산출물·상태를 독립적으로 관리할 필요가 있을 때만 나누며, 작업을 묶기 위한 빈 상위 작업은 만들지 않는다.
- V2 작업 ID는 Notion이 자동 부여하는 불변 `TSK-n`을 사용한다. 역할·도메인·계획 범위는 ID 문자열이 아니라 `역할`과 `주 작업 범위` 관계로 조회한다.
- **기획**: 제품 정책을 결정하고 승인된 내용을 계약과 AC의 정상·예외 결과에 반영한다.
- **디자인**: AC를 화면 상태·상호작용·접근성 산출물로 구현한다.
- **개발**: DB·API·프론트·자동 테스트를 통합해 사용자 결과를 검증한다.

역할은 주 책임 전문성을 뜻할 뿐 단계별 인계 순서를 뜻하지 않는다. 기획자·디자이너·개발자는 같은 결정 배치와 AC를 함께 검토할 수 있고, 합의된 계약과 Mock이 있으면 프론트엔드·백엔드·테스트 작업을 병렬로 진행한다.

슬라이스 본문에 태스크 체크리스트를 복사하지 않는다. 태스크는 관련 계약과 AC를 참조하고, 슬라이스 완료는 태스크 상태가 아니라 AC + DoD로 판정한다.

마일스톤 공통 기획 작업은 마일스톤을 `주 작업 범위`로 직접 참조한다. 슬라이스 고유 작업은 슬라이스만 참조하고 마일스톤 관계를 중복 저장하지 않는다.

작업량과 기간은 다르다. 태스크가 노력 범위와 신뢰도를 소유하고, 슬라이스 기간은 선행관계와 병렬 가능성을 반영한 임계경로로 계산한다.

## 작업 관계와 상태

- `선행 작업`은 완료 전에는 현재 작업에서 의미 있는 산출을 시작할 수 없는 강한 차단 관계다.
- `참조 작업`은 현재 작업을 병렬로 시작할 수 있지만 완료 전에 최신 결정·산출물을 확인하고 반영해야 하는 비차단 관계다.
- 단순히 관련 있다는 이유로 선행 관계를 만들지 않는다.

상태는 다음 의미로만 사용한다.

- `백로그`: 필요하지만 아직 착수를 약속하지 않았거나 강한 선행·필수 입력이 준비되지 않았다.
- `진행 전`: 담당자와 강한 선행·착수 입력이 갖춰져 즉시 시작할 수 있다.
- `진행 중`: 실제 작업 중이며 WIP에 포함된다.
- `검토 필요`: 산출물이 기록됐고 승인 또는 수정 요청을 기다린다.
- `차단`: 착수를 약속했거나 시작한 뒤 예상하지 못한 장애로 진행할 수 없다. 원인과 해제 조건을 기록한다.
- `완료`: 완료 기준과 필요한 계약·문서·검증 반영을 끝냈다.
- `취소`: 결과가 더 이상 필요하지 않고 취소 이유를 기록했다.

파일럿에서는 담당자 한 명당 `진행 중` 주 작업을 한 개로 제한한다. `검토 필요`와 `차단`도 전체 WIP로 계속 관찰하고, 새 작업을 늘리기 전에 병목 해소를 우선한다.

`착수 판정`은 `상태`, `선행 작업`, `참조 작업`을 다음 순서로 계산한다.

- 현재 작업이 `완료` 또는 `취소`면 같은 종료 상태를 표시한다. 취소된 선행·참조 작업이 있으면 자동 진행 판단 대신 `관계 검토 필요`를 표시한다.
- 현재 작업이 `차단`이면 `착수 불가 · 별도 장애`, 완료되지 않은 선행 작업이 있으면 `착수 불가 · 선행 대기`, `백로그`면 `선택 대기`를 표시한다.
- 강한 선행이 모두 완료됐을 때 참조 작업만 남아 있으면 `부분 착수 가능 · 참조 대기`를 표시하고, 참조까지 모두 완료된 `진행 전` 작업은 `착수 가능`을 표시한다. 진행 중·검토 중 작업은 같은 원칙으로 참조 대기 여부를 함께 표시한다.

이 판정은 관계나 상태가 바뀌면 Notion이 즉시 다시 계산하므로 AI가 값을 복사하거나 사람이 동기화하지 않는다. 다만 계약 활성 여부, 필요한 입력의 실제 품질, 담당자의 작업 선택처럼 관계와 상태로 표현되지 않은 조건은 자동 판정하지 않는다. `착수 판정`은 판단 보조값이고, 실제 작업 생명주기인 `상태`를 대신 변경하지 않는다.

## 변경 시나리오 검증

### 행사 생성에 템플릿 선택이 추가됨

- API만 선택 입력을 받아도 사용자 행동이 없으면 새 호환 `DATA:event.create` 리비전만 만들고 슬라이스를 만들지 않는다.
- 화면에 템플릿 선택을 제공하면 사용자 결과가 늘어나므로 후속 슬라이스를 만든다.
- `SL-EVT-001` 완료 전 같은 결과 안에서 요구가 바뀌면 새 계약 리비전으로 기준선을 올리고 `specRevision`을 증가시킨 뒤 DoR을 다시 실행한다.
- 완료 후라면 기존 파일을 수정하지 않고 새 슬라이스의 `changes`에 `SL-EVT-001`을 기록한다.

### 행사 생성 권한이 변경됨

- 역할명을 슬라이스에서 검색·치환하지 않는다.
- 새 `AUTH:event.create@R<n>`을 만들고 계약 리비전 DB의 소비 슬라이스 관계로 영향을 찾는다.
- 진행 전 슬라이스는 기준선과 명세 리비전을 올리고, 완료 슬라이스의 실제 행동 변경은 후속 슬라이스로 처리한다.

### 담당자나 일정만 변경됨

- 태스크 DB의 담당자·검토자·일정·추정만 바꾼다.
- 계약, AC, 슬라이스 실행 명세와 `specRevision`은 변경하지 않는다.

이 세 시나리오가 여러 슬라이스 본문을 수동 검색·수정하지 않고 처리되면 유지보수 경계가 지켜진 것이다.
