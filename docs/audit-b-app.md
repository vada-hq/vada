# 구조 감사 B: 화면 구현

A 회차(`audit-a-pipeline.md`)는 파이프라인을 봤고, 거기서 나온 가장 큰 결함은
**앱에 있었다.**

> `FIN-REQ-01`의 명세는 "필수 칸이 다 차야 실행된다"고 적혀 있는데
> (`executeWhen` + `onExecutionBlocked`), 화면은 그냥 제출했다.
> **게이트 넷이 다 놓쳤다** — 계약 검사는 판정기를 따로 시험하고, 준수 검사는
> 글자만 보고, 대조기는 누르지 않고, **e2e는 제출이 되는 것을 단언했다.**

A는 판정기를 보다가 그것을 우연히 발견했다. 앱을 겨눠서 본 적은 한 번도 없다.

## 이 감사가 묻는 것 — 하나가 중심이다

> **화면이 자기 명세를 지키는가.**

이 저장소의 주장은 "명세 하나만 보면 화면을 만들 수 있다"이다. 그 주장이 참이려면
**명세에 적힌 것이 화면에 다 나타나야 한다.** 위의 FIN-REQ-01은 그 반대였고,
그런 자리가 몇 개 더 있는지 아무도 모른다.

화면 26개, 7,203줄이다. **명세가 말한 것 중 화면이 안 하는 것을 찾아 달라.**

무엇을 대조할지 예를 든다 — 이게 전부는 아니다.

| 명세가 말하는 것 | 화면이 안 할 수 있는 것 |
| --- | --- |
| `executeWhen` / `onExecutionBlocked` | 판정 없이 그냥 실행 |
| `enabledWhen` | 늘 활성 |
| `initiallyDisabled` | 늘 활성 |
| `resetOnChangeOf` | 값이 남음 |
| `validation` | 검사 안 함 |
| `messages.loading` / `error` | 상태를 안 그림 |
| `optionCounts` | 개수를 안 그림 |
| `paging` | 쪽을 안 넘김 |
| `action: pending`의 `note` | 아무 일도 안 일어남 |
| `readOnly` | 고칠 수 있음 |
| `unit` · `descriptionField` | 안 그림 |

## 볼 것

| 무엇 | 어디 |
| --- | --- |
| 화면 26개 | `apps/vada-web/src/screens/` |
| 부품 | `apps/vada-web/src/components/` |
| 명세를 읽는 층 | `apps/vada-web/src/spec/` |
| 데이터·선택지 층 | `apps/vada-web/src/data-sources/` · `option-sources/` |
| 대조기 | `apps/vada-web/src/design-check/` |
| 무엇을 지켜야 하는지 | `specs/figma/vada-wireframe/screens/*/screen.json` · `packages/contracts/schemas/` |
| 이 저장소의 결정 | `docs/decisions/`(특히 `vada-conventions.md`) |

파이프라인(`packages/contracts` · `apps/spec-service`)은 A 회차에서 이미 봤다.
필요하면 읽되 지적은 앱에 대해 해 달라.

## 답해 달라

### 1. 명세를 안 지키는 자리 (이것이 가장 중요하다)

화면마다 `screen.json`을 읽고 그 화면 코드와 대조해 달라. **26개를 다 보는 것이**
**목표다** — 표본만 보면 "몇 개나 있는지"를 말할 수 없다.

찾은 것마다: 어느 화면 · 명세의 어느 줄 · 코드의 어느 줄 · 사용자에게 무엇이
다르게 보이는가.

### 2. 되풀이와 경계

- `elementByNodeId(...).spec as XxxSpec` 꼴의 타입 단언이 **108개**다. 명세는 그
  노드에 무슨 유형이 있는지 이미 아는데 타입이 그것을 못 쓴다. 어떻게 없애는가.
- 화면 19개가 `elementByNodeId`·`readObjectSource`를, 21개가 `data-node-id`를 쓴다.
  **같은 배선이 26번 되풀이된다.** 어디까지가 화면의 고유한 일이고 어디부터가
  공용으로 올라가야 하는가.
- 부품 경계가 옳은가. `DataTable`·`GroupedDataTable`처럼 비슷한 것이 둘 있다.

### 3. 개발용 응답

- `fixtures.ts`가 1,880줄 한 파일이고 **화면당 ~70줄씩 선형으로 는다.** 85화면이면
  약 5,000줄이다. 언제 무엇이 깨지는가.
- 개발용 응답끼리 어긋나는 것을 보는 검사가 하나 있다
  (`src/spec/navigation-arrival.test.ts` — 실제로 `PR-01`/`PR-2026-0031` 어긋남을
  잡았다). 그 검사가 놓치는 자리가 있는가.

### 4. 대조기

`src/design-check/index.ts`가 802줄이다. BACKLOG에 이미 적혀 있듯 **재는 일과
봐주는 일을 겸한다**(예외 장치 92줄). 그것 말고 다른 문제가 있는가.

특히: 대조기가 **조용히 아무것도 안 보는** 자리가 있는가. 글이 없는 칸은 자리를
찾을 방법이 없어 못 본다는 것은 이미 안다(BACKLOG). 그런 사각이 더 있는가.

### 5. 접근성·상태

- 로딩·오류·빈 상태를 화면이 그리는가. 카탈로그가 `messages`를 갖고 있는데 쓰는가.
- 키보드로 쓸 수 있는가. `aria-*`가 뜻대로 붙었는가.
- **e2e가 단언하는 것이 실제로 옳은 동작인가.** FIN-REQ-01의 e2e는 깨진 동작을
  옳다고 단언하고 있었다. 같은 것이 더 있는가.

## 지켜야 할 것

**근거 없는 지적은 받지 않는다.** 이 저장소에는 일부러 그렇게 한 것이 많고 그
이유가 `docs/decisions/`와 스키마 설명에 적혀 있다. 이상해 보이면 **먼저 왜 그런지**
**찾아보고**, 그래도 틀렸다고 보면 그 근거를 반박해 달라.

지적마다 셋을 붙여 달라.

1. **증거** — 파일과 줄 번호, 명세의 어느 줄과 어긋나는가, 재현 방법.
2. **사용자에게 무엇이 다른가** — 지금 잘못 동작하는가, 아니면 언제부터인가.
3. **바꾸는 비용** — 몇 파일, 무엇이 깨지는가.

그리고 **우선순위를 매겨 달라.**

## 안 받는 답

- 취향(파일 이름, 들여쓰기, 주석 언어, Tailwind 클래스를 인라인으로 쓰는 것).
- "컴포넌트를 더 쪼개라" 같은 일반론. 어느 것을 왜인지 말해 달라.
- 색을 화면에서 하드코딩했다는 지적 — 그건 이미 `design/tones.ts`가 한 곳에서
  갖는 규칙이고, 어기는 자리가 있으면 **그 자리를 짚어** 달라.
- 파이프라인·계약의 문제(A 회차에서 이미 봤다).

## 코드는 고치지 마라

이 감사의 산출물은 코드가 아니라 판단이다. 읽고, 재고, 보고서만 써 달라.

## 가장 값진 답

**"명세가 이렇게 말하는데 화면은 이렇게 한다"를 26개 화면에서 몇 개나 찾았는가.**

그 수가 0이면 이 저장소의 주장이 한 겹 더 단단해진다. 0이 아니면 그것이 이 감사의
값이다.
