버그 사냥이 아니라 **구조 판단**을 원합니다. 이 구조가 앞으로 6번 더 복제될 예정이라,
복제 전에 잘못된 모양을 잡는 것이 목적입니다.

## 먼저 읽을 것

`docs/architecture.html` — 이 저장소의 층 구조와 데이터 흐름을 정리한 문서입니다.
브라우저로 열거나 HTML을 그대로 읽으면 됩니다. 여기 적힌 수는 전부 저장소에서 직접 센 것입니다.

그다음 이 파일들:

```
apps/vada-web/src/data-sources/served.ts        진짜/가짜를 가르는 목록
apps/vada-web/src/data-sources/server.ts        읽기가 서버로 가는 길
apps/vada-web/src/spec/mutations.ts             쓰기가 서버로 가는 길
apps/vada-web/src/screens/outside-spec.ts       명세 밖 화면 등록부
apps/vada-web/src/design/deviations.ts          그림과 다르게 그린 것 등록부
specs/figma/vada-wireframe/not-screens.json     안 만들기로 한 그림 등록부
packages/contracts/src/spec-validation.mjs      명세 검증기
apps/api/src/app.ts                             서버가 계약을 자리에 잇는 곳
```

## 이 저장소가 걸고 있는 주장

> **명세 하나만 보면 개발자가 화면을 만들 수 있다.**

원본은 `specs/figma/vada-wireframe/` 하나입니다. 그림(Figma)에서 명세가 나오고,
명세에서 계약(`openapi.json`)이 나오고, 계약에서 서버와 화면이 나옵니다.
서버와 화면은 나란히 서서 **원본만 읽고 서로를 읽지 않습니다.**

원칙:
- 명세가 표현을 정하지 않는다
- **조용한 대체를 하지 않는다**
- 지어내지 않는다
- 두 화면 이상에서 나온 것만 어휘로 만든다
- 서버가 완성된 글을 준다
- **눈금을 만들고 심어서 터뜨려 증명한다**

## 방금 있었던 일 (판단의 근거로 쓰세요)

흐름 하나(학생회에 들어오기)를 서버에 붙이고 배포했습니다. 결함 여섯이 나왔는데
**셋은 사람이 배포된 화면을 눌러 보고서야** 드러났습니다.

가장 심한 것:

> `runMutation`이 **아무 데도 안 보내고 무조건 성공을 돌려주고 있었습니다.**
> '조직 만들기'를 누르면 학생회가 안 생기는데 다음 화면으로 넘어갔습니다.
> 진도 눈금이 **읽기만 세고 쓰기는 안 세고 있어서**, 없는 것이 없어 보였습니다.

그 뒤 같은 모양을 하나 더 찾았습니다:

> 명세는 84벌인데 화면 코드가 읽는 것은 80벌입니다.
> `EVT-03C` · `EVT-04C` · `OPS-MEET-01B` · `OPS-MEET-01D` 넷은
> **아무 검사에도 안 걸립니다.** 역시 세는 자리가 없습니다.

두 사고가 같은 계열입니다: **세는 자리가 없으면 없는 것도 없어 보인다.**

## 물어볼 것 다섯

### ① 원본이 아직 하나인가

명세를 원본으로 두는 저장소인데, 작업 중 `specs/figma/vada-wireframe/option-sources.json`의
`authorize.area`를 7개 손으로 고쳤습니다(`member` → `signedIn`/`public`).
화면(`viewer: joining`)과 출처(`area: member`)가 서로 모순이었고, 화면 쪽이 그림에서
나온 것이라 출처를 고쳤습니다.

**코드가 명세를 끌고 가는 선례를 만든 것은 아닌가?** 이런 모순이 또 나올 때
어느 쪽을 고쳐야 하는지 규칙이 필요한가?

### ② `served.ts`가 옳은 메커니즘인가

무엇이 진짜 서버에서 오는지를 **손으로 관리하는 문자열 목록**으로 들고 있습니다.
지금 읽기 9/196, 쓰기 2/44입니다. 5개에서 9개로 늘 때는 괜찮았습니다.

- 240개까지 갈 때도 이 모양이 버티나?
- 명세에서 **유도**해야 하는 것 아닌가? (예: 서버가 실제로 답하는 자리를 계약과 대조)
- 손으로 관리하는 목록 자체가 새로운 "기억에 기대는 자리"는 아닌가?

### ③ 조용한 통과가 또 어디 있나 — 가장 중요

위의 두 사고와 **같은 모양**을 찾아 주세요:

> 실패했는데 성공으로 보이는 자리. 안 하고 있는데 하고 있는 것처럼 보이는 자리.
> 세는 눈금이 없어서 빠진 것이 안 보이는 자리.

구체적인 파일과 줄로 짚어 주세요. 없으면 없다고 해 주세요.

### ④ 검사 네 겹의 분할이 옳은가

```
명세 검증기   209개  명세끼리 맞는가
화면 검사     767개  명세대로 그리는가 (대부분 화면 80벌에서 생성)
서버 검사     255개  계약대로 답하는가 (진짜 Postgres/PGlite)
시나리오 검사 429개  브라우저에서 명세를 지키는가 (개발용 응답으로 돈다)
통합 검사       2개  진짜 서버+진짜 Postgres에 대고 화면을 그린다
```

- 시나리오 429개를 **개발용 응답**으로 돌리기로 한 판단이 옳은가?
  (근거: 그 검사들은 '명세가 말한 것을 화면이 그리는가'를 재고, 개발용 응답이 곧
  명세가 든 예시 값이다. 진짜 서버로 돌리면 명세가 아니라 저장소에 든 것을 재게 된다.)
- 진짜 통합이 **둘뿐**인데 충분한가? 배포 후에야 드러난 사고 셋이 여기 없어서 났다.
- 429개가 과한가? 겹치는 것이 많아 보이는데 줄일 자리가 있나?

### ⑤ 등록부가 넷인 게 맞나

"원본에서 벗어난 것"을 담는 자리가 넷이고 **모양이 다 다릅니다**:

| 파일 | 담는 것 | 형식 |
|---|---|---|
| `specs/.../not-screens.json` | 안 만들기로 한 그림 | JSON |
| `apps/vada-web/src/data-sources/served.ts` | 진짜 서버에서 오는 것 | TS 문자열 배열 |
| `apps/vada-web/src/design/deviations.ts` | 그림과 다르게 그린 것 | TS 객체 |
| `apps/vada-web/src/screens/outside-spec.ts` | 명세 없이 손으로 그린 화면 | TS 객체 |

하나로 합쳐야 하는가, 아니면 나뉜 것이 옳은가? 판단과 근거를 주세요.
