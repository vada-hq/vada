# OPS-MEET-01A(회의 목록) 파일럿

**TASK-01과 같은 계열의 화면이다** — 목록을 거르고, 항목을 누르면 상세로 간다.
TASK-01(신규 계급 1건)에 이어 이 화면이 수렴을 판정한다.

## 1. 수렴 판정: 아직 아니다

기준은 "연속 2개 화면 사이클에서 새로운 마찰 계급 0건"이다. **3건이 나왔다.**

| 사이클 | 신규 계급 | 새 개념 | (A) 마찰 |
| --- | --- | --- | --- |
| INV-01 | 2 | 2 | 0 |
| HOME-01K | 3 | 3 | 1 |
| MY-01 | 4 | 1 | 1 |
| OPS-00 | 3 | 0 | 1 |
| TASK-01 | 1 | 0 | 0 |
| **OPS-MEET-01A** | **3** | **2** | **3** |

추세가 꺾였다. 그런데 **꺾인 방향이 중요하다** — 세 건 모두 "목록"이라는 같은
요소가 지금까지 다뤄 본 적 없는 모양을 요구한 것이고, 셋 다 스키마를 넓혀서
풀렸다. 표현력이 모자란 자리가 정확히 어디였는지가 드러났다는 뜻이다.

TASK-01이 1건으로 내려간 것을 보고 "수렴이 가깝다"고 읽었는데, 그것은 TASK-01이
MY-01과 **거의 같은 화면**이었기 때문이다. 같은 계열 안에서도 모양이 한 단계
달라지면 계급이 다시 나온다. `docs/pilot-ops00.md`에서 "연속을 같은 계열로 세라"고
배웠는데, **계열 안에서도 무엇이 같아야 하는지**는 아직 정하지 못했다.

## 2. 묶음이 데이터에서 온다 (신규 계급 · 새 개념)

칸반의 열 넷은 **명세에 고정**이라 요소를 넷 등록하고 `params.status`에 고정값을
박았다. 회의 목록의 묶음은 **행사**라서 행사가 늘면 묶음도 는다. 명세가 조회를
미리 적을 수 없다.

`itemList.group`을 넓혔다. 묶음 하나가 곧 목록의 항목이고, `itemsField`가 그
묶음에 든 것들을 담는다.

```json
{
  "type": "itemList",
  "dataSourceKey": "meeting.groups",
  "group": { "itemsField": "meetings", "collapsible": true }
}
```

`data-sources.json`의 조각도 중첩할 수 있게 넓혔다(`fields[].fields`). 묶음마다
따로 조회하지 않는 이유는 위와 같다 — 묶음 수를 명세가 모른다.

**대안을 하나 버렸다.** 묶음 목록과 항목 목록을 두 출처로 나누고 묶음마다 조회하는
방법이 칸반의 모양과 더 닮았지만, 그러려면 `params`의 값이 "지금 그리고 있는 묶음
행의 조각"을 가리킬 수 있어야 한다. 그것이 중첩보다 큰 새 개념이다.

## 3. 항목의 버튼 문구·강조도가 행마다 다르다 (신규 계급 · 새 개념)

같은 자리에 다섯 가지 문구가 온다.

| 회의 상태 | 문구 | 강조도 |
| --- | --- | --- |
| 완료 | 회의록 보기 | secondary |
| 예정 | 회의 상세 보기 | secondary |
| 진행 중 | **회의로 돌아가기** | **primary** |
| 정리 중 | 회의 내용 보기 | secondary |
| 취소 | 취소 내용 보기 | secondary |

`itemAction`의 `label`은 명세에 담긴 **고정 문자열**이었다. `labelField`·
`emphasisField`를 더해 "이 문구는 데이터가 준다"를 적을 수 있게 했다.

`emphasis`가 데이터에서 오는 것이 어색해 보이지만, `button.emphasis`는 이미
"시각 형태가 아니라 역할"로 정의돼 있다. 어느 회의를 앞세울지는 조직의 사실이지
디자인의 사실이 아니다.

## 4. 접기 (신규 계급 · 개념은 작다)

묶음 머리의 화살표는 접기·펴기다(사용자 확인). 지금까지의 화면 안 상태는 전부
**데이터를 다시 조회하는 것**이었다(MY-01의 탭, TASK-01의 범위 토글). 접기는
조회를 일으키지 않는 순수 표시 상태라 자리가 없었다.

`group.collapsible`로 넓혔다. 기본은 펴짐이다.

## 5. (A) 마찰 3건 — 구현하다 막힌 것

### 5-1. 추출기가 화면을 잘못 읽었다

카드 안의 **참가자·안건·회의록 상태 세 쌍**을 "되풀이되는 항목"으로 보고 **카드
하나하나를 `itemList`로** 뽑았다. 7개 카드 = 7개 목록이 됐고, 진짜 목록(묶음)과
필터·안내 카드는 아예 못 봤다. 질문 15건 중 14건이 이 오독에서 나왔다.

되풀이 판정이 **깊이를 보지 않는다.** 어느 수준의 되풀이가 목록인지 가릴 근거가
필요하다 — 이 화면에서는 "형제가 같은 이름의 Container이고 그 안에 또 되풀이가
있는" 쪽이 진짜 목록이었다.

### 5-2. 같은 아이콘이 자리마다 다른 파일로 나온다

같은 달력 아이콘이 카드마다 다른 파일로 뽑히는데, 그 파일들이 세 가지로 달랐다.

1. `clipPath`로 감싸인 것과 아닌 것
2. 좌표의 소수 다섯째 자리(`6.12498` 대 `6.12501`)
3. 색이 진짜 다른 것(TASK-01의 지연 카드)

자산 대조가 "같은 그림"을 가릴 때 1·2를 지워야 3만 남는다. `drawingKey`를
넓혔다 — 잘라내는 틀과 껍데기를 지우고 좌표를 소수 첫째 자리로 반올림한다.
소수 둘째 자리로는 위 둘이 `6.12`와 `6.13`으로 갈린다.

### 5-3. 아이콘 셋이 한 덩이로 뽑혔다

한 카드에서 달력·장소·주최자 아이콘이 583×7짜리 한 파일이 됐다. 사이에 글이 없으면
나란한 아이콘이 한 자산이 되는 규칙 때문이다. **OPS-00 `16:615`에 이어 두 번째다
— BACKLOG의 트리거가 충족됐다.**

지금은 `design/deviations.ts`에 자리로 적어 두었다. 추출기가 고쳐지거나 이 화면을
다시 저장하면 그 예외가 쓰이지 않게 되고, 검사가 지우라고 알려 준다.

또 하나: **묶음 4의 아이콘은 아예 자산으로 나오지 않았다.** 같은 아이콘이 다른
카드에서는 나오는데 거기서만 빠졌다. 원인 미상.

## 6. 그대로 쓰인 것

| 이미 있던 자리 | 여기서 |
| --- | --- |
| `summary` + `dataSourceKey` + `items[].field` | 안내 카드의 '확인 필요한 회의 2건' |

| 빈 드롭다운은 명세에서 뺀다(MY-01) | 거르는 줄의 드롭다운 둘 |

## 7. design 대조는 6곳에서 시작했다

첫 화면(MY-01)은 30곳, 아홉 화면 전체로는 234곳이었다. 이 화면은 **6곳**이다.

| 어긋난 것 | 원인 |
| --- | --- |
| 검색칸의 배경·테두리(2) | 등록 노드를 안쪽 `input`에 달았다. 테두리를 가진 칸은 바깥이다 |
| 상태 딱지의 테두리(4) | 색 있는 상태에는 `-200` 테두리가 있다 |

색·굵기는 처음부터 하나도 어긋나지 않았다. `design/tones.ts`와 부품 표가 자리를
잡은 뒤로 **손으로 고를 것이 거의 없어졌다**는 뜻이다.

상태 딱지의 규칙은 **바탕 -50 / 테두리 -200 / 글씨 -700**이다. 무채색(완료·비공개)만
테두리 없이 gray-100/gray-500인데, 흔들림이 아니라 이유가 있다 — gray-50은 흰 카드
위에서 보이지 않고, 끝난 것을 테두리로 앞세울 이유도 없다. 그래서 예외로 적지 않고
표에 담았다.

## 8. (B) 마찰 — 절차

**e2e가 낡은 화면을 보고 있었다.** `playwright.config.ts`의 `reuseExistingServer`
때문에 새 `screen.json`이 생기기 전부터 떠 있던 개발 서버가 계속 쓰였고, 새 e2e
5개가 전부 실패했다. 서버를 죽이고 다시 돌리니 전부 통과했다.

화면을 새로 만드는 사이클에서만 나는 문제라 흔치는 않지만, **실패가 구현의 문제로
보인다**는 것이 나쁘다. 다음에 또 겪으면 트리거로 본다.
