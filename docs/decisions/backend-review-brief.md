# 백엔드 설계 교차검증 브리프

다른 도구/사람에게 **독립적인 판단**을 받으려고 쓴 글이다. 이 저장소에서 이미 내린
결론은 일부러 뺐다 — 읽는 쪽이 그 틀 안에서 생각하게 되면 교차검증의 값이 없어진다.

아래는 **사실과 제약과 물음**뿐이다. 숫자는 전부 저장소에서 잰 것이다.

---

## 1. 무엇을 만드는가

대학 학생회 하나가 쓰는 운영 도구. 조직·행사·회의·업무·재정·기록·메시지를 다룬다.
**실제로 학생회가 쓸 서비스**이고 한국에서 운영한다.

프런트엔드와 명세는 이미 있다. 백엔드는 **한 줄도 없다.**

### 이미 있는 것

```
와이어프레임 프레임 85개 → 화면 명세 82개 → 전부 구현됨 (React/TS)
데이터 출처 145개  전부 GET. method·path·조회 인자·조각·값의 종류를 갖는다
변이 44개          POST 37 · PUT 6 · DELETE 1
조각 920개         이름·설명·필수 여부·값의 종류
OpenAPI 3.0.3      위 카탈로그에서 기계로 생성. 자리 207 · 동작 216
개발용 응답        4,400줄의 손으로 쓴 fixture가 서버 대역을 한다
```

프런트엔드는 그 개발용 응답을 동기로 읽는다. `fetch`가 한 줄도 없다.

### 도메인의 성질 (측정치)

- 145개 조회가 저마다 **다른 축으로 자른다** — 행사로, 사람으로, 상태로, 날짜로.
- 경로에 인자가 든 것 46개. 조회 인자를 갖는 것 110/145.
- 화면 하나가 부르는 출처: **평균 2.6개 · 최대 8개.**
- 트래픽은 **행사 때만 몰리고 평소 0에 가깝다.** 구성원 수십 명, 학생 명단 수천 명.

### 응답의 성질 (측정치)

조각 890개(잎)를 이름으로 갈라 본 것이다.

```
완성된 글 — 서버가 만들어 보낸다   195 (21.9%)   'lastModifiedNote', 'viewerNote'
색 이름                            69 ( 7.8%)   'statusTone': 'violet'
센 값                              40 ( 4.5%)   'progressPercent', 'delayedTaskCount'
판정                               17 ( 1.9%)   'canStart', 'canEditMinutes'
열쇠                               62 ( 7.0%)
그 밖                             507 (57.0%)
```

값의 종류로는 **글 835 · 수 50 · 참거짓 5 · 목록 30**이다. 이 저장소는
"**서버가 완성된 글을 준다**"를 규칙으로 삼아 왔다 — 화면은 값을 이어 붙이거나
형식을 만들지 않는다. 예: 화면은 `'부원 2명'`을 받지 부원 수를 받아 세지 않는다.

## 2. 권한

### 권한 행렬 (데이터다. 화면 ORG-04가 이 표를 그린다)

13개 영역 × 3개 역할. 역할은 `chair`(회장단)·`head`(부서장)·`member`(부원) 셋으로
고정이고, 역할을 새로 만드는 화면은 어디에도 없다.

| 영역 | chair | head | member |
| --- | --- | --- | --- |
| 재정 현황·사용 내역 열람 | 가능 | 가능 | 가능 |
| 예산 수정·구매 승인·증빙 처리 | 가능 | **재정부만** | **재정부만** |
| 회의 생성 | 가능 | 가능 | — |
| 행사 만들기 | 가능 | 가능 | — |
| 행사 정보 수정·종료 처리 | 가능 | **행사 조직만** | **행사 조직만** |
| 행사 완료 처리 | 가능 | — | — |
| 행사 운영 조직 구성·수정 | 가능 | **행사 조직 관리자만** | **행사 조직 관리자만** |
| 조직 구조 수정 | 가능 | — | — |
| 구성원 초대 | 가능 | **자기 부서만** | — |
| 학생 명단 열람 | 가능 | 가능 | 가능 |
| 학생 명단 업로드·갱신 | 가능 | — | — |
| 학생회비 납부 명단 업로드 | 가능 | **재정부만** | **재정부만** |
| 학생 명단 내보내기 | 가능 | — | — |

굵은 칸은 **조건**이다. '자기 부서만'은 주체의 부서와 객체의 부서가 같아야 한다는
뜻이고, '행사 조직만'은 주체가 그 행사의 운영 조직에 속해야 한다는 뜻이다.

### 지금 상태

- **145개 출처 중 자기가 어느 영역에 속하는지 말하는 것: 0개.** 변이 44개도 같다.
- 반면 **서버가 판정해서 내려보내는 조각은 17개 있다.** 화면이 그것을 보고 단추를
  그릴지 정한다.

```
meeting.detail.canStart · canEnd · canEdit · canCancel · canManageHostRole · canEditMinutes
event.listViewer.canCreateEvent · finance.overviewViewer.canPlanBudget
meeting.attention.canCreateMeeting · event.surveyActivation.canActivate
attendance.checkInResult.canRetry · meeting.minutesProgress.canComplete  (외 5)
```

- 화면 82개 중 **10개가 '보는 사람에 따라 갈리는 변형'**이다. 같은 주소인데 권한에
  따라 다른 것이 그려진다. 예: `OPS-MEET-03B`는 "canEdit·canCancel·canManageHostRole·
  canStart가 **모두 참**일 때", `OPS-MEET-03C`는 "canStart만 참일 때".

### 로그인 없이 열리는 자리

`/api/public/*` 다섯. QR로 온 참석자와 링크로 온 설문 응답자가 연다. 로그인이 없고
주소가 실어 온 토큰이 무엇을 볼 수 있는지 정한다.

바꿀 수 있지만 지금은 이렇게 정해져 있다.

| | |
| --- | --- |
| 언어 | TypeScript / Node 22 (프런트와 같은 저장소, 타입 공유가 목적) |

| DB 호스팅 | RDS Postgres t4g.micro, 서울 |

### 법

한국 개인정보보호법. 학번·이름·학과·학생회비 납부 상태를 다룬다.

- 개인정보처리시스템 접속 기록 **1년 이상** 보관 (5만 명 미만)
- 권한 부여·변경·말소 기록 **3년** 보관
- 저장·전송 암호화

정보주체가 국내이므로 데이터를 국내에 두기로 했다(국외 이전 절차를 피하려고).

## 4. 물음 셋

### (1) 조건부 권한을 어떤 모델로 표현하고, 어떻게 145개 자리에 매는가

행렬의 칸이 가능/불가능이 아니라 '자기 부서만'·'행사 조직만'·'재정부만'처럼
**주체와 객체의 관계**에 달려 있다. 지금 어느 자리도 자기가 어느 영역인지 말하지
않는다.

고려할 만한 축:
- 영역을 카탈로그에 선언하고 미들웨어가 강제 vs 핸들러마다 검사
- 조건을 코드로 vs 데이터로(정책 엔진·ReBAC 같은 것)
- 화면에 내려보내는 `can*` 판정과 서버가 강제하는 검사를 **한 곳에서** 낼 것인가,
  두 곳에서 낼 것인가 (두 곳이면 갈릴 위험, 한 곳이면 결합)

각 접근의 **실패 모드**가 궁금하다. 이 규모(13영역 × 3역할 × 216자리, 개발자 소수)에서
무엇이 과하고 무엇이 모자란가.

### (2) 읽는 자리 145개를 손으로 쓸 것인가, 카탈로그에서 만들 것인가

카탈로그가 각 응답의 모양을 이미 정확히 안다(경로·인자·조각·값의 종류). 그런데
응답의 21.9%가 '서버가 완성한 글'이고 7.8%가 색 이름이라, **단순한 표 조회로는
안 되고 자리마다 만드는 규칙이 다르다.**

- 손으로 145개를 쓰면: 카탈로그의 정보를 두 번 적는다. 갈릴 수 있다.
- 생성하거나 표로 몰면: 규칙이 자리마다 달라 표현력이 모자랄 수 있다.

이 저장소는 다른 자리(추출기·OpenAPI 생성기)에서 생성을 골랐고 그때마다 실제 결함을
잡았다. 백엔드에서도 같은 판단이 맞는가, 아니면 여기는 다른가?

**곁들여**: "서버가 완성된 글을 준다"는 규칙 자체가 이 규모에 맞는 거래인가.
색 이름(`statusTone: 'violet'`)이 API를 건너가는 것을 포함해서.

### (3) Lambda + VPC 안의 RDS

- Lambda는 요청마다 연결을 연다. RDS t4g.micro의 연결 수는 제한적이다.
- RDS Proxy는 **밑에 깔린 인스턴스의 vCPU마다 시간당 $0.015**다. t4g.micro는 2 vCPU라
  월 약 **$22**이고, **DB 자체($11.68)의 거의 두 배**다.
- 대안: 컨테이너(App Runner/Fargate) + 상시 풀, 또는 서버리스 Postgres, 또는
  Lambda에서 연결 수를 예약 동시성으로 묶기.

평소 트래픽이 0에 가깝고 행사 때만 몰리는 이 성질에서, 서버리스 전제를 유지할
값이 있는가? 유지한다면 연결 문제를 무엇으로 푸는가?

## 5. 답할 때 부탁

- **이 규모에 맞는 답**을 달라. 개발자가 소수이고 학생회 하나가 쓴다.
- 일반론 대신 **이 사실들에 걸린 답**이면 좋겠다. 위 표와 숫자를 근거로 삼아 달라.
- 각 권고의 **실패 모드**와 **되돌리는 비용**을 함께 적어 달라 — 지금 되돌리는 것은
  싸지만(216자리 중 2개 구현) 나중에는 비싸다.
- 우리가 **묻지 않았는데 물어야 했던 것**이 있으면 그것부터 말해 달라.
