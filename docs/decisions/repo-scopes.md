# 저장소 스코프 모델

(2026-08-17 확정)

이 저장소는 **제품 무관 파이프라인**과 **여러 제품의 콘텐츠**를 담는 모노레포다. 모든 산출물과 결정 기록은 아래 세 스코프 중 하나에 속하며, 무엇을 어디에 기록·구현할지는 스코프를 따른다. 특정 제품 하나에 구조를 맞추지 않는다.

## 세 스코프

1. **파이프라인(제품 무관)**: `apps/figma-plugin`, `apps/spec-service`, `packages/contracts`, `tests`, 그리고 `docs/decisions/`의 접두어 없는 문서. 파이프라인 코드·스키마·브리지에는 제품명을 하드코딩하지 않는다(불변식).
2. **제품**: 제품별 앱(`apps/<제품>-web`), 제품 결정 문서(`docs/decisions/<제품>-*.md`), 도메인 카탈로그의 내용(선택지 key, 상태 스코프의 의미). 첫 제품은 `vada`다.
3. **wireframe(제품 디자인 원본의 출처 단위)**: `specs/figma/<wireframeKey>/` 전체 — 화면·카탈로그 JSON과 `interpretation.md`. wireframe은 제품의 경계가 아니라 "어느 Figma 파일에서 추출됐나"의 기록이다.

## 네임스페이스 규칙

- `wireframeKey`는 `<제품>-` 접두를 관례로 한다(예: `vada-wireframe`).
- `screenId`, 선택지 카탈로그 `key`, 상태 스코프 `key`는 **제품 안에서 유일**하다. wireframe 파일이 여러 개로 나뉘어도 같은 제품이면 하나의 ID 공간이다.
- 화면 이동(`targetScreenId`)과 상태 스코프 공유는 제품 안에서 wireframe 경계를 넘을 수 있다. 제품 사이에서는 넘지 않는다.

## 확장 트리거

두 번째 제품(또는 한 제품의 두 번째 wireframe 파일)이 **실제로 등장하는 시점**에, 그 사례를 증거로 다음을 결정한다. 그 전에 미리 만들지 않는다(증거 기반 형식화 원칙).

- specs 경로에 제품 차원을 도입할지(`specs/figma/<제품>/<wireframeKey>/`) 아니면 접두 관례를 유지할지
- 검증 CLI의 제품 단위 교차 검사(제품 내 screenId·key 유일성, wireframe 경계를 넘는 이동 대상 해석)
- 브리지 API 경로 확장, 제품 문서의 물리적 디렉터리 분리
