# 백엔드 아키텍처 (2026-08-29)

이 저장소는 지금까지 **명세와 화면**만 만들었다. 서버는 없고 `fixtures.ts` 4,400줄이
서버 대역을 한다. 여기서는 무엇을 어떻게 지을지와 **왜 그것인지**를 적는다.

사람이 정한 것 넷은 맨 아래에 있다.

---

## 명세가 이미 요구하는 것

재본 것이다.

```
읽기 145개 · 쓰기 44개(POST 37 · PUT 6 · DELETE 1)
경로에 인자가 든 것 46개 · 조회 인자를 갖는 것 110/145 · 경로 겹침 0
갈래  ops 86 · org 16 · records 15 · finance 8 · home 7 · public 5 · my 3
조각 920개 — 이름과 설명은 있고 **값의 종류가 0개**
```

세 가지가 설계를 정한다.

- **도메인이 관계형 그 자체다.** 조직↔역할↔권한 행렬, 행사↔업무↔회의↔재정의 다대다,
  구매 요청의 다섯 단계 승인. 145개 조회가 저마다 다른 축으로 자른다.
- **트래픽이 행사 때만 몰린다.** 학생회 하나가 쓰는 도구다. 평소는 0에 가깝다.
- **로그인 없이 여는 자리가 다섯 있다**(`/api/public/*`). QR 참석 확인과 설문 링크는
  학생회 밖 사람이 토큰만으로 연다.

## 고른 것

| 층 | 고른 것 |
| --- | --- |
| 언어·런타임 | TypeScript / Node 22 |
| 프레임워크 | Hono + `@hono/zod-openapi` |
| DB | PostgreSQL |
| ORM | Drizzle |
| 인증 | Better Auth (구글·카카오) |
| 파일 | S3 + presigned URL |
| 배포 | AWS Lambda + API Gateway (ap-northeast-2) |
| DB 호스팅 | RDS Postgres t4g.micro (**서울**) |
| 저장소 | 이 저장소 안(`apps/api`) |

### 언어를 TypeScript로

명세·타입·검증기가 전부 TypeScript다. 같은 언어로 지으면 **계약이 갈릴 때 컴파일
오류로 드러난다** — 업계가 drift를 막는 첫째 수단으로 드는 것이 이것이다. 다른
언어를 고르면 이 프로젝트가 여태 쌓은 이점의 절반이 사라진다.

### 프레임워크를 Hono로

Zod로 라우트를 적으면 **OpenAPI가 저절로 나온다**(`@hono/zod-openapi`). 이 저장소는
이미 계약 우선이라 그 흐름과 맞물린다. 런타임을 가리지 않아 Lambda로 시작해 나중에
컨테이너로 옮겨도 코드가 그대로다.

Fastify는 JSON Schema 기반으로 성숙하지만 타입 추론이 Zod 흐름보다 약하고, NestJS는
이 규모에 견줘 얼개가 무겁다.

### DB를 PostgreSQL로

145개 조회가 전부 다른 축으로 자른다 — 행사로, 사람으로, 상태로, 날짜로. 키 하나로
찾는 모양이 아니므로 DynamoDB는 맞지 않는다. 권한 행렬과 승인 워크플로도 관계로
푸는 것이 자연스럽다.

### ORM을 Drizzle로

서버리스에서 콜드스타트와 번들이 작고 SQL에 가깝다. 승인 워크플로 조회가 복잡해질
도메인이라 SQL을 통제할 수 있는 쪽이 낫다. Prisma도 되지만 서버리스에서 Drizzle이
앞선다는 것이 2026년의 일반적 결론이다.

### 인증을 Better Auth로

**Auth.js(NextAuth)는 2026년 초부터 유지보수 모드**이고 그 팀이 Better Auth로
옮겨 갔다. Better Auth는 Hono를 공식 예제로 지원하고, **세션이 우리 Postgres에
앉는다** — 밖의 서비스가 죽어도 우리가 죽지 않는다.

카카오는 기본 제공 목록에 없으므로 generic OAuth 플러그인으로 붙인다.

### 배포를 Lambda로 — **아직 풀리지 않은 것이 있다**

평소 트래픽이 0에 가까운 도구라 안 쓰면 안 낸다. 2026년 Node 콜드스타트는 200ms
이하다. OpenAPI를 API Gateway가 그대로 import하므로 명세가 곧 배포 산출물이 된다.

**그런데 DB는 서버리스가 아니다.** Lambda는 요청마다 연결을 열고 t4g.micro의 연결
수는 제한적이다. RDS Proxy로 풀면 되지만 그 값이 **밑에 깔린 인스턴스의 vCPU마다
시간당 $0.015** — 2 vCPU면 월 약 $22로 **DB 자체($11.68)의 거의 두 배다.**

처음 "서버리스가 싸다"고 적었을 때 이 값을 셈에 넣지 않았다. 갈래는 셋이다 —
Proxy를 쓰거나, 예약 동시성으로 연결 수를 묶거나, 컨테이너로 가거나.
**아직 정하지 않았다**(docs/decisions/backend-review-brief.md의 물음 3).

## 실서비스라서 바뀌는 것

진짜 학생회가 쓴다. **학번·이름·학과·학생회비 납부 상태는 개인정보다.**

### DB를 서울에 둔다 — Neon을 쓰지 않는다

처음에는 Neon을 골랐다. 안 쓰면 0으로 내려가 월 $7.66이고, Aurora Serverless v2의
최소 0.5 ACU(월 $44)보다 훨씬 싸다.

**그런데 Neon에는 서울 리전이 없다.** 개인정보를 국외에 두면 개인정보보호법상
국외 이전에 해당해 고지와 동의가 따로 필요하다. 학생회 도구가 감당할 절차가 아니다.

그래서 **RDS Postgres t4g.micro를 서울(ap-northeast-2)에** 둔다. 월 $11.68로 Neon보다
$4 비싸다 — **그 차이는 국외 이전 절차 하나보다 훨씬 싸다.** 0으로 내려가지 않는
것은 잃지만, 학생회 예산에서 월 4달러는 판단의 축이 아니다.

### 처음부터 지어야 하는 것

2026-09-11 시행 기준이다.

- **접근 기록을 1년 이상 보관한다.** 5만 명 미만이므로 1년이다. 재정 승인 워크플로가
  있으니 "누가 무엇을 언제 승인했는가"는 어차피 도메인의 요구이기도 하다.
- **권한을 주고 바꾸고 없앤 기록은 3년 보관한다.** `org.permissionMatrix`가 이미
  데이터이므로 그 변경 이력을 남기면 된다.
- **저장할 때와 보낼 때 암호화한다.** TLS는 API Gateway가, 저장 암호화는 RDS가 준다.
  민감한 조각(학번)은 그 위에 한 겹 더 둘지 정해야 한다.
- **EXT-02A에 이미 '개인정보 수집 동의'가 있다.** 그 동의가 무엇을 어디까지
  받는지를 처리방침과 맞춰야 한다.

이것들은 나중에 붙이는 것이 훨씬 비싸다. 감사 로그는 **첫 테이블부터** 있어야 한다.

## 저장소를 이 저장소 안에 둔다

사람이 "유지보수성을 기준으로 판단하라"고 했다. 모노레포다.

**까닭 셋.**

1. **명세가 원본이고 백엔드와 프론트가 둘 다 거기서 나온다.** 계약이 바뀌면 셋이
   함께 바뀐다 — 한 커밋에 담기면 갈릴 수가 없다. 저장소를 가르면 그 순간 "어느
   쪽이 먼저 배포됐는가"가 문제가 된다.
2. **타입 공유가 이 프로젝트의 핵심 이점이다.** 별도 저장소로 가면 npm 패키지로
   주고받아야 하고, 그 사이에서 버전이 갈린다. 갈리는 것을 막으려고 만든 체계가
   갈릴 자리를 새로 만드는 셈이다.
3. **이미 모노레포다.** `apps/spec-service` · `apps/vada-web` · `packages/contracts`가
   있고 게이트 하나가 전부를 지킨다. 셋째 앱을 더하는 것이 자연스럽다.

**대가도 적어 둔다.** 게이트가 길어진다(지금 57.7초). 백엔드 검사가 더해지면
`scripts/run-tests.mjs`가 다시 예산에 닿는다. 그때는 **경로별 실행이 이제야 값을
갖는다** — 지금은 앱 둘이 나란히 돌아 못 줄이지만, 셋이 되면 느린 쪽이 바뀐다.

## 순서

```
1. 조각 920개에 값의 종류를 붙인다          ← 끝냈다 (2026-08-30)
2. 카탈로그 → OpenAPI 생성기                ← 끝냈다 (2026-08-30)
3. apps/api 뼈대 (Hono + Drizzle + 감사 로그)  ← 조직 층까지 (2026-08-30)
4. 인증 (Better Auth · 구글/카카오)
5. 프론트의 fetch 층 (명세에서 뽑은 타입)
6. AWS 배포 (OpenAPI를 API Gateway가 import)
```

### 1·2를 끝내며 알게 된 것

**3.1이 아니라 3.0.3을 낸다.** 3.1은 JSON Schema 2020-12와 같아 이 저장소의 ajv와
결이 맞지만, 받아 가는 쪽 하나가 API Gateway이고 그쪽 가져오기는 3.0을 기준으로
삼는다. 지금 명세에 3.1이라야 적을 수 있는 것이 없으므로 받는 쪽을 넓게 둔다.

**만드는 일이 계약의 어긋남을 둘 드러냈다.**

- 값의 종류를 재다가 구매 요청 초안의 수량·단가가 **때로 수, 때로 빈 글**로 오는
  것을 찾았다. 아직 안 적은 수는 빈 글이 아니라 오지 않는 것이다(0은 값이다).
- OpenAPI를 뽑다가 `GET /api/org/departments`를 **두 카탈로그가 다른 모양으로**
  가리키는 것을 찾았다 — 조직도가 읽는 나무와 고르는 목록이다. 한 자리가 두 모양을
  줄 수 없으므로 고르는 목록에 제 자리를 줬다(`/api/org/departments/options`).

둘 다 **검사가 아니라 만드는 일이 잡았다.** 계약을 다른 말로 옮겨 적는 것 자체가
검사다 — 옮겨지지 않는 자리가 곧 어긋난 자리다.

**세션 경계를 문서가 든다.** 뿌리에 세션 쿠키를 걸고 `/api/public/*` 다섯에는
`security: []`를 둔다. 학생회 밖 사람이 QR과 링크로 여는 자리라 로그인이 없고,
무엇을 볼 수 있는지는 주소가 실어 온 토큰이 정한다.

**아직 없는 것을 문서가 적어 둔다.** 기계가 읽는 오류 코드, 쪽 나눔 규약, 배포
주소. 지어내지 않고 자리만 비웠다 — 여기서 지어내면 그 거짓이 생성된 클라이언트와
서버 뼈대까지 간다.

### 3을 시작하며 — 테이블은 읽는 자리와 상관이 없다

카탈로그의 조각 890개를 갈라 보니 **43%가 컬럼이 아니었다.**

```
완성된 글 — 서버가 만든다   195 (21.9%)   viewerNote · lastModifiedNote · actionLabel
색 이름 — 표현               85 ( 9.6%)   statusTone · departmentTone · tone
센 값 — 서버가 센다          40 ( 4.5%)   progressPercent · delayedTaskCount
판정 — 서버가 한다           17 ( 1.9%)   canStart · hasDocuments
열쇠                         62 ( 7.0%)
그 밖 — 저장된 값일 수 있다 507 (57.0%)
```

**이 수는 이름으로 가른 것이지 뜻을 잰 것이 아니다.** 처음 적을 때 색 이름을 69로
셌는데 `/Tone$/`로만 물어서 **이름이 그냥 `tone`인 16개를 놓쳤다**(2026-08-30 교차검토).
완성된 글 195도 `survey.linkState.note` 같은 것이 빠져 있으므로 21.9%는 아래끝이다.

`memberCountLabel`('부원 2명')은 저장하는 값이 아니라 세어서 말로 만든 것이고
`roleTone`('violet')은 표현이다. **그래서 읽는 자리 145개와 테이블 수는 아무 상관이
없다** — 테이블은 저장해야 없어지지 않는 것만 담고, 나머지는 읽을 때 만든다.

**역할은 테이블이 아니라 값이다.** 권한 행렬의 열이 chair·head·member 셋으로
고정이고 역할 수도 그 셋을 센다. 학생회가 역할을 새로 만드는 화면은 어디에도
없다 — 생기면 그때 테이블이 된다.

**감사 로그를 둘로 가른다.** 접속 기록은 1년, 권한 변경은 3년이다. 한 표에 담으면
1년치를 지울 때 3년치가 함께 지워지거나, 3년을 지키려고 1년치를 3년 들고 있게 된다.

### 붙이면서 걸린 것

- **drizzle-orm에 high 등급 SQL 인젝션이 있었다**(<0.45.2). 개인정보를 담을
  것이라 그냥 넘어갈 수 없어 0.45.2로 올렸다. 남은 moderate 넷은 drizzle-kit의
  esbuild이고 **배포 런타임에 없는 개발용 마이그레이션 도구**다.
- **명세에 안 적은 상태 코드로 답하려다 타입이 막았다.** 404를 responses에
  빠뜨린 채 쓰고 있었다 — 문서에 없는 답을 내놓으면 받는 쪽이 그것을 다룰 수 없다.
  프레임워크가 그 자리를 지킨다.
- **서버가 명세 밖으로 새면 검사가 잡는다.** Hono가 라우트에서 문서를 뽑아 주므로
  카탈로그의 OpenAPI와 견줄 수 있다 — 없는 자리를 열면 빨간불이다(심어서 확인).

**이제 4번이 다음이다.** 원래 여기 적혀 있던 말: 1·2가 막고 있던 것이 풀렸다 — `specs/figma/vada-wireframe/
openapi.json`이 자리 207개·동작 216개를 들고 있고, 여기서 타입도 서버 뼈대도 나온다
(`openapi-typescript`로 실제로 뽑아 `activeEvents: number`까지 살아 오는 것을 봤다).

**그 문서는 손으로 고치지 않는다.** `npm run openapi`가 만들고, 검사가 카탈로그에서
다시 만들어 견준다(`tests/openapi.test.mjs`) — 손으로 한 글자만 고쳐도 빨간불이다.

### 인자가 이름뿐이었다 (2026-08-30, 교차검토 4번)

검토가 "인자·오류·멱등성을 계약이 말하지 않는다"고 했다. 그중 인자를 고쳤다.

카탈로그의 인자는 **이름만 든 문자열 배열**이었다(`params: ["eventId", "status"]`).
그래서 셋을 말하지 못했다 — 무엇인지, 없이 불러도 되는지, 어떤 값인지. 뽑아낸
OpenAPI의 조회 인자 115개가 **전부 `required: false`에 설명 없는 문자열**이었다.
`/api/ops/event/summary`를 eventId 없이 부르는 것이 계약상 허용됐다는 뜻이고,
그 답은 거르지 않은 전부다 — 화면은 그것이 걸러진 것인 줄 알고 그린다.

응답의 조각(`fields`)은 처음부터 이름·설명·필수·값의 종류를 갖고 있었다. 선을
건너는 이름 붙은 값이라는 점에서 둘은 같은 것이라, 한쪽만 문자열로 둘 까닭이 없었다.

**필수 여부를 짐작으로 정하지 않았다.** 값이 어디서 오는지가 답한다.

| 값이 오는 곳 | 빌 수 있나 | 자리 |
| --- | --- | --- |
| 경로에 박힌 것 | 못 뺀다 | 53 |
| 주소가 실어 온 것(`screenParam`) | 화면이 멈춘다 | 53 |
| 반드시 채우는 칸(`fieldKey` + `required`) | 늘 채워진다 | 14 |
| 명세가 박은 값(`value`) | 고정이다 | 3 |
| 눌린 항목(`itemField`) | 그 줄이 있다 | 2 |
| 안 채워도 되는 칸 · 안 넘기는 자리 | **뺄 수 있다** | 42 |

167자리 중 **필수 125 · 선택 42**. 화면 인자에 `optional: true`가 붙은 넷은 규칙이
필수로 몰 뻔했는데 명세가 이미 "없어도 열린다"고 적어 두어 갈렸다 — 장부의 결재
단계, 구매 요청 초안, 회의 초안이 그것이다.

**세 가지가 함께 드러났다.**

1. **변이 27개의 경로 인자 29자리가 선언조차 없었다.** `/api/ops/meetings/{meetingId}/start`의

### 권한이 어디에도 매여 있지 않았다 (2026-08-30, 교차검토 5번)

검토가 짚은 것 중 가장 컸다. **145개 출처와 44개 변이 중 자기가 어느 권한 영역인지
말하는 것이 하나도 없었다.** 규칙은 ORG-04이 그리는 표 열세 줄에 글로만 있었고, 그
표와 실제 자리를 잇는 것이 아무 데도 없었다 — 서버를 만드는 사람이 자리마다 스스로
판단해야 했고, **판단을 빠뜨린 자리는 조용히 열린다.**

#### 권한 모델은 두 겹이었다

행렬만 보면 13행 × 3역할이 전부인 줄 안다. 그런데 ORG-04은 표 아래에 문단 셋을 더
두고 있었다 — 「회의·행사에서 별도로 부여되는 역할」.

> 회의 진행 권한자 — **회의별로 부여되며** 회의 시작·종료와 안건 진행을 할 수 있습니다.
> 다른 사람의 권한은 변경할 수 없습니다.
>
> 회의 생성자 — 기본 진행 권한자이며, 진행 권한을 **부여·해제할 수 있는 유일한 역할**입니다.

카탈로그도 같은 말을 하고 있었다(`canEdit`·`canCancel`·`canManageHostRole`에 "생성자만").
**조직 역할(chair·head·member)이 답하지 않는 자리가 있다** — 회장단이라도 그 회의의
진행 권한자가 아니면 시작할 수 없다.

#### 규칙을 기계가 읽는 자리로 옮겼다

`specs/figma/vada-wireframe/permissions.json` — 영역 19개와 조건 12개. 새 사실이 아니라
글로 있던 것을 옮긴 것이고, **ORG-04이 그리는 표도 여기서 나온다**(개발용 응답이 열세
줄을 따로 들고 있었다 — 두 벌을 들면 갈린다).

행렬 밖에 넷이 필요했다. `member`(그 학생회 구성원이면 된다) · `signedIn`(로그인만
하면 된다 — 학생회를 새로 만들거나 초대 코드를 확인하는 사람은 **아직 어느 구성원도
아니다**) · `public` · `unstated`.

#### 216동작이 저마다 영역을 든다

| 영역 | 동작 |
| --- | --- |
| `member` 그 학생회 구성원이면 된다 | 131 |
| `finance.read` · `students.read` 행렬이 "전원 가능"이라 한 열람 | 37 |
| `public` 로그인 없음 | 9 |
| `event.*` · `finance.manage` · `org.*` · `meeting.*` 행렬이 제한하는 것 | 31 |
| **`unstated` 명세가 아직 말하지 않는 것** | **8** |

남은 8은 회의록(누가 정리하고 완료하는가) · 기록 쓰기 · 대화방 만들기다. **지어내지
않고 그 사실을 적어 두었다** — 이 값을 가진 자리의 수가 곧 남은 일이다.

#### 매달다가 모순이 드러났다

**행렬은 '구성원 초대'를 부서장에게 '자기 부서만' 준다. 그런데 초대 코드는 학생회
하나에 하나뿐이라 부서를 가릴 수가 없다.** 부서장이 코드를 다시 만들면 학생회 전체의
코드가 바뀐다. 셋(`org.regenerateInvite`·`...Code`·`...Link`)이 경고로 남아 있다 —
사람이 정할 일이라 임의로 한쪽을 고르지 않았다.

검사가 이 자리를 잡는다: **조건이 대상을 요구하는데 그 대상을 가리키는 인자가 자리에
없으면** 경고다. 그러지 않으면 서버는 막거나 열거나를 짐작으로 하게 된다.

#### 정책은 한 곳에서 낸다

`apps/api/src/permissions.ts`의 `can(viewer, area, object, lookups)` 하나다. 화면이
받는 `can*` 조각과 서버가 막는 검사가 **같은 함수에서 나온다** — 두 곳에서 나오면
언젠가 갈리고, 갈리는 쪽은 늘 화면이다(단추를 그렸는데 눌리면 막히는 것이 그 모습이다).

규칙은 그 파일에 없다. `permissions.json`이 갖고 있고 여기서는 조건 이름마다 '어떻게
판정하는가'만 정한다. 대상을 봐야 아는 것(그 행사의 조직원인가)은 `Lookups`로 밖에서
받는다 — 판정 함수가 저장소를 직접 열면 검사에서 저장소가 필요해진다.

막는 자리는 셋이다.

- **명세가 말하지 않은 자리(`unstated`)는 막는다.** 지어내서 열어 두면 규칙 없이
  열려 있고 아무도 그 사실을 모른다.
- **조건이 대상을 요구하는데 대상이 없으면 막는다.** 열면 '어느 행사인지 모르지만
  되기는 된다'가 되고, 그것은 조건이 없는 것과 같다.
- **계약에 없는 자리는 막는다.** 명세 밖의 자리가 열려 있으면 아무 검사도 받지 않은
  채 도는 코드다.

강제는 미들웨어가 한다(`authorize.ts`). **자리마다 손으로 부르지 않는다** — 216번
부르면 그중 몇은 잊고, 잊은 자리는 조용히 열린다. 그것이 이 일 전체가 막으려던 것이다.
미들웨어는 생성된 계약(`x-authorize`)을 읽으므로 새 자리를 열면 자동으로 걸린다.

**붙이면서 하나 걸렸다.** `*`에 건 미들웨어에서 Hono의 `c.req.routePath`는 `'*'`를
돌려준다 — 그 값으로 계약을 찾으면 **전부 '계약에 없는 자리'가 되어 막힌다**(검사
다섯이 그렇게 잡았다). 계약이 든 틀로 직접 맞추도록 고쳤고, 이제 미들웨어를 어디에
걸든 같다.

#### 표에서 두 가지가 바뀌었다

- **권한 행렬 테이블을 없앴다.** 행렬이 고정이므로 조직마다 한 벌씩 저장할 까닭이
  없다 — 저장하면 조직이 늘 때마다 같은 열세 줄이 늘고, 규칙을 고칠 때 이미 만들어진
  조직들은 옛 규칙을 든 채 남는다.
- **부서에 '재정을 맡는가'를 달았다.** 행렬의 '재정부만'을 판정하는 유일한 근거다.
  **명세에 이것을 켜는 자리가 아직 없다** — 조직을 만들거나 고치는 화면에 새로 만들어야
  한다.

#### 아직 하지 않은 것

- 화면에 내려보내는 `can*` 11개를 이 함수에서 내는 일. 지금은 개발용 응답이 값을
  들고 있다.
- `Lookups` 넷의 실제 구현. 행사 운영 조직·회의 진행 권한자 테이블이 아직 없다.
- 명세가 말하지 않는 여덟 자리(회의록 4 · 기록 3 · 대화방 1). 2026-08-30에 **나중에
  정하기로 했다** — 그때까지 서버는 그 자리를 막는다.

## 한 화면을 끝까지 뚫었다 (2026-08-30)

216자리 중 서버가 답하는 것이 둘이었다. 계약은 다 갖췄는데 **그 계약이 실제로 쓸 만한지
아무도 재 본 적이 없었다** — 그 상태로 나머지를 쌓으면 틀린 전제 위에 쌓게 된다.

그래서 ORG-04(역할 및 권한)을 골라 **그림 → 명세 → 계약 → 서버 → 저장소 → 화면**을
한 줄로 이었다. 화면이 작아서가 아니라 그 줄에 읽기·권한·법정 기록이 다 걸려서다.

### 진짜 Postgres에 대고 잰다

**PGlite**를 골랐다 — WASM으로 옮긴 진짜 Postgres라 프로세스 안에서 돌고, 도커도 설치도
필요 없다. 그래서 **게이트가 이것을 돌린다.**

흉내 낸 저장소로 재면 흉내가 틀린 곳을 영원히 못 본다. 실제로 도는 것은 그 저장소가
아니기 때문이다. 이 저장소는 줄곧 '재는 것이 진짜여야 한다'로 판단해 왔고 여기서도 같다.

표를 만드는 SQL은 `schema.ts` 하나에서 나온다(`npm run db:schema`). **파일이 아니라
모듈로 낸다** — 파일로 두고 읽었더니 Node에서는 되는데 Vite 아래서는 `import.meta.url`이
다른 곳을 가리켜 못 읽었다.

### 자리를 계약이 만든다

`routes.ts`의 `attach(app, deps, handlers)` 하나다. 자리마다 method·path·응답 모양을
다시 적지 않는다 — 그것은 명세를 두 번 적는 일이고, 두 벌은 갈린다.

**새 자리를 여는 값이 '답 하나'다.** 남은 210자리가 되풀이 작업이 되는 것이 이 층의
목적이었다. 계약에 없는 이름을 붙이면 시작할 때 멈춘다 — 오타 하나가 조용히 안 열리는
자리가 되지 않는다.

응답이 계약의 모양을 지키는지는 **검사가 ajv로 견준다.** 자리마다 zod를 손으로 쓰는 대신
그렇게 했다 — 손으로 쓰면 그것도 명세를 두 번 적는 일이다.

### 권한 표는 저장소에서 오지 않는다

`org.permissionMatrix`가 `permissions.json`에서 나온다. **표는 정책의 그림이다** —
권한을 판정하는 것과 표를 그리는 것이 같은 원본에서 나오므로 규칙을 고치면 화면이
저절로 따라온다. 실제로 초대를 '회장단만'으로 고치자 화면의 그 칸이 함께 바뀌었다.

### 화면이 진짜로 서버를 부른다

`ScreenRouter`가 이미 화면의 출처를 기다리고 있었으므로(`useSourceLoading`) 그 자리에서
받아 오게 했다. 켜면 같은 화면이 같은 값을 서버에서 받는다.

종단 검사가 그것을 못 박는다 — **개발용 응답은 1·3·3인데 저장소에는 1·1·1이 들어 있다.**
화면에 1이 셋 보이면 그 값이 저장소에서 세어져 온 것이다. 서버가 실패하면 카탈로그의
글이 그려지는 것도 함께 잰다(이제 실제로 실패하는 순간이 생긴다).

**아직 인자 없는 자리만 된다.** 그릇은 화면이 무엇을 읽는지는 알지만 요소마다 어떤
인자로 부르는지는 모른다 — 그것은 요소를 그리는 층이 알고, 지금 그 층은 화면 일흔여덟에
흩어져 있다. 숨기지 않고 부르면 터뜨린다. 자리마다의 기다림을 만들 때 함께 풀린다.

### 뚫으면서 나온 것

- **`org.changeRole`이 누구의 역할을 무엇으로 바꾸는지 계약에 없다.** 그래서 이번 세로에
  쓰기는 넣지 못했다 — `meeting.grantHostRole`과 같은 갈래의 구멍이 하나 더 있었다.
- **검증기가 3,608번 걷고 있었다.** 변이 44개마다 화면 82개를 전부 걸어 검증이 14초에서
  41초가 됐다. 재는 저울이 느려지면 사람이 덜 재게 된다 — 한 번만 걷게 고쳐 4.7초가 됐다.

### 이어서 조직 관리를 통째로 (2026-08-30)

세로가 뚫린 뒤 그 층이 정말로 '답 하나씩'인지 재 봤다. **읽기 여섯과 쓰기 셋**을
이어 붙이는 데 새로 지은 것은 저장소 함수와 답뿐이었다 — 자리·권한·실패·모양은
계약이 이미 갖고 있었다.

**쓰기가 처음 붙었다.** 초대 다시 만들기 셋이고, 그 자리에 세 가지가 함께 걸린다.

- **회장단만.** 그림은 부서장에게 '자기 부서만'을 그렸지만 코드가 학생회에 하나뿐이라
  부서를 가릴 수 없어 회장단만으로 정했다. 부서장이 부르면 403이다.
- **멱등 키를 실제로 지킨다.** 계약이 요구한다고 적어 두는 것과 지키는 것은 다른
  일이다 — 지키는 코드가 없으면 두 번 눌린 요청이 그대로 두 번 돌아 **방금 복사한
  링크가 죽는다.** 같은 키로 다시 오면 처음의 답을 그대로 준다.
- **키가 없으면 막는다(422).** 없이 받아 주면 그 자리는 계약과 다르게 도는 것이고,
  두 번 눌린 요청을 가릴 방법이 사라진다.

멱등도 자리마다 손으로 부르지 않는다. **어느 자리가 키를 요구하는지는 계약이 안다** —
미들웨어가 그것을 읽는다.

#### 붙이면서 나온 것

- **회장과 부회장을 가를 자리가 표에 없었다.** 역할은 셋으로 고정인데 조직도는 둘을
  다른 색으로 그린다 — 권한은 같고 자리 이름만 다르다. 권한 행렬에 넣으면 역할이
  넷이 되어 '셋으로 고정'이 깨지므로 `executiveTitle`을 따로 두었다.
- **검사가 진짜 Postgres를 열넷 번 띄우고 있었다.** `beforeEach`로 두었더니 그것만으로
  108초다. 한 번 띄우고 바뀌는 표만 되돌리게 고쳐 23초가 됐다. 재는 저울이 느려지면
  사람이 덜 재게 된다 — 그것이 검사를 없애는 가장 흔한 길이다.

### 고른 것이 값이 되는 어휘 (2026-08-30)

`org.changeRole`이 막혀 있었다. **누구의 역할을 바꾸는지 계약에 없었고**, 화면도 고른
사람을 넘길 길이 없었다 — 목록의 `itemAction`이 `pending`이었고 그 자리에 이렇게 적혀
있었다: "어느 구성원을 고를지가 아직 주소로 오가지 않습니다."

그동안 **서버가 '마지막으로 고른 사람'을 기억해 주고 있었다**(`org.selectedRoleAssignment`).
그것은 사람마다 다른 서버 상태라 **두 사람이 같은 화면을 열면 서로의 고른 것을 본다.**

#### 어휘 하나를 늘렸다

`itemAction: { type: 'choose', fieldKey, itemField }` — **눌린 항목이 이 화면의 값이 된다.**
이동과 다른 점은 화면을 떠나지 않는다는 것이다. 고른 뒤에도 목록이 그대로 있고, 곁의
요소들이 그 칸을 **조회 인자로** 읽는다 — 그 부분은 이미 있던 어휘다.

그래서 `org.selectedRoleAssignment`가 `/api/org/members/{memberId}/role-assignment`가 되고,
`org.changeRole`이 `PUT /api/org/members/{memberId}/role`이 되었다. 서버가 기억하던 자리가
사라졌다.

MSG-02가 필요로 하는 **여럿 고르기**는 아직 없다. 고른 것들이 쌓이는 칸을 그리는 어휘가
따로 필요하고, 그것은 이 화면이 요구하지 않는다.

#### 늘리자 열일곱 자리가 한꺼번에 틀렸다

동작의 갈래가 셋이 되자 `action.type !== 'navigate'`로 좁히고 `.note`를 읽던 자리 일곱과
`.params`를 읽던 자리 열이 전부 타입에서 걸렸다. **좁힌 뒤에 남는 것이 하나뿐이라는 가정**이
갈래가 늘면 깨진다. 자리마다 다시 좁히는 대신 읽는 함수를 하나씩 뒀다(`noteOf`·`paramsOf`) —
갈래가 또 늘어도 부르는 쪽은 그대로다.

#### 제출 인자를 화면이 적지 않는다

`useSubmitAction`이 `action.params`를 명세에서 읽어 넘긴다. 처음에는 화면이 직접 넘기게
했더니 **e2e 열둘이 한꺼번에 깨졌다** — 스물한 자리 중 스무 자리가 넘기지 않고 있었다.
이 갈고리가 생긴 까닭이 바로 그 옮겨 적기였는데 같은 실수를 반복할 뻔했다.

#### 법이 보는 자리가 실제로 남는다

역할을 바꾸면 `permission_changes`에 남는다(3년 보관). **바뀐 때만 남긴다** — 같은 역할로
다시 눌린 것은 변경이 아니고, 변경이 아닌 것을 적으면 3년치 기록이 눌린 횟수가 된다.
그리고 조직을 지워도 남는 것을 검사가 못 박는다.

붙이면서 하나 걸렸다: **누가 바꿨는지가 `users`를 가리키는데** 검사가 그 사람을 안 심어
외래 키가 막았다. 막는 것이 옳다 — 누구인지 모르는 권한 변경 기록은 기록이 아니다.

#### 곁들여 저울이 훨씬 빨라졌다

`vitest.config.ts`가 `poolOptions`를 쓰고 있었는데 **Vitest 4에서 없어져 경고만 뜨고
조용히 안 걸리고 있었다.** 최상위 옵션으로 고치자 진짜 Postgres가 한 번만 뜨고
api 검사가 **33초 → 5.4초**가 됐다.

## 두 번 눌리면 어떻게 되는가 (2026-08-30, 교차검토 3번의 나머지)

검토가 "필수 인자·오류·멱등성을 계약이 말하지 않는다"고 했다. 인자는 앞에서 고쳤고
나머지 둘이 여기다.

### 216자리가 성공 하나만 들고 있었다

응답 코드가 `200`과 `default` 둘뿐이었다. 받는 쪽은 실패를 다룰 수 없고, 다룰 수 없는
실패는 화면에 '알 수 없는 오류'로 나온다.

**코드를 자리마다 손으로 적지 않는다.** 216번 적으면 언젠가 하나가 빠지고, 빠진 자리는
조용하다. 명세가 이미 아는 것에서 끌어낸다.

| 오는 것 | 어디서 끌어내나 | 자리 |
| --- | --- | --- |
| **401** 로그인이 필요하다 | 권한 영역이 `public`이 아니다 | 207 |
| **403** 권한이 없다 | `public`도 `signedIn`도 아니다 | 204 |
| **404** 가리킨 것이 없다 | 자리에 인자가 박혀 있거나, 한 건을 집어 오는데 열쇠가 필수다 | 106 |
| **409** 이미 그 상태다 | 되풀이될 때의 성질이 `conflict` | 15 |
| **422** 보낸 값이 받을 수 없다 | 보내는 값이 있다 | 23 |
| **429** 너무 자주 눌렀다 | 밖에서 열리는 자리 — **토큰을 마구 넣어 보는 것을 막지 않으면 그것이 유일한 벽이다** | 9 |

### 되풀이될 때의 성질을 네 갈래로 갈랐다

보내는 쪽은 두 번 보낼 수 있고 그것을 막을 방법이 없다 — 사람이 두 번 누르고, 화면이
느려 또 누르고, 네트워크가 끊겨 다시 보낸다. **44개 변이 중 이것을 말하는 것이 하나도
없었다.**

| 갈래 | 뜻 | 수 |
| --- | --- | --- |
| `overwrite` | 같은 것을 다시 보내면 같은 상태다. 장치가 필요 없다 | 16 |
| `naturalKey` | 이미 있는지 **데이터가 답한다.** 두 번째는 첫 번째의 답을 그대로 준다 | 3 |
| `idempotencyKey` | 자연 열쇠가 없다. 보내는 쪽이 `Idempotency-Key`를 붙인다 | 10 |
| `conflict` | 상태를 옮긴다. 이미 그 상태면 **409** | 15 |

**QR 출석은 `naturalKey`다.** 열쇠는 `(checkInToken, studentNumber)` — 같은 사람이 같은
QR에 두 번 낸 것은 한 번이고, 두 번째에는 첫 번째의 영수증을 그대로 준다. 2026-08-30에
사람이 정했다: **"같은 결과를 다시 보인다."** 줄 서서 기다리는 사람에게 빨간 글을 보이지
않는다 — 두 번 눌렸는지 사람은 모르고 알 이유도 없다.

**`conflict`는 조용히 넘어가지 않는다.** 이미 시작된 회의를 또 시작하려는 것은 대개 남이
먼저 시작한 것이다. 성공으로 답하면 '남이 먼저 했다'와 '내가 두 번 눌렀다'가 같은 모양이
된다.

### 되돌릴 수 없는 자리 여섯

카탈로그가 **스스로 두 번 짚어 두었다** — 회의록 정리 완료와 진행 권한 빼기에 "확인
모달이 그려지지 않았다"고 적혀 있었다. 그림에 없다고 위험이 없는 것이 아니므로 계약이
그 사실을 든다(`irreversible`). 2026-08-30에 사람이 **셋 다 확인을 넣기로** 정했다.

- **회의록 정리 완료** — 되돌릴 수 없고 참석자에게 **알림이 밖으로 나간다**
- **진행 권한 빼기** — 주는 쪽(D03)에만 확인이 있었다. 뺏는 쪽이 더 위험한데 그림에 없다
- **초대 링크·코드·QR 다시 만들기 넷** — 방금 나눠 준 것이 그 순간 죽는다

### 매달다가 셋이 드러났다

1. **`meeting.grantHostRole`이 누구에게 주는지 계약에 없었다.** 빼는 쪽(DELETE)은 자리에
   사람이 박혀 있는데 주는 쪽은 없었다 — 서버가 누구인지 알 길이 없었다. 두 쪽을 같은
   자리로 맞췄다(`/hosts/{memberId}`).
2. **제출이 인자를 넘길 길이 없었다.** 검증기가 "이동하지 않는데 인자를 넘깁니다"로
   막고 있었다 — 인자는 다음 화면에 넘기는 것뿐이라는 착각이었다. 변이도 자리에 인자가
   박혀 있다. 막아 둔 탓에 **21곳 중 20곳이 화면 인자와 이름이 우연히 같아서** 돌고
   있었다. 이제 전부 명시하고 검사한다.
3. **`mutations[].result`가 문서로 이어진 적이 없었다.** 성공 응답이 줄곧 빈 객체였고,
   출석 확인이 영수증을 준다는 사실이 문서 어디에도 없었다.

### 내가 만든 눈금에도 구멍이 있었다

- **경로 인자 130자리를 검사가 건너뛰고 있었다.** '경로는 주소가 들고 있으니 넘기는
  인자로 셀 것이 아니다'라고 적어 두었는데, 주소를 만드는 것은 **부르는 쪽**이다.
  하필 그 자리가 `meetingId`·`eventId` 같은 가장 중요한 인자들이다.
- **제출 검사가 인자를 아예 안 적으면 조용했다.** `params`가 있을 때만 보고 있었다 —
  그것이 바로 이 검사가 잡으려던 모양이다.

둘 다 심어서 터지는 것을 확인했다.

### 아직 하지 않은 것

확인 모달 셋을 화면에 만드는 일. 계약은 `irreversible`로 그 사실을 들고 있지만
**화면 명세에 그 자리가 아직 없다** — 그림에 없는 것을 새로 만들어야 한다.

## 서버가 실제로 선다 (2026-08-31)

**도는 서버가 없었다.** `serve.ts`가 없어 모든 것이 검사 안에서 `app.request`로만 돌았고,
`who()`는 밖에서 주입되는 스텁이었다 — 23자리가 전부 '누군가 로그인했다고 치고' 돌았다.
교차검토가 그것을 짚었고(“도는 서버가 아니라 인프로세스 구현”) 여기서 세운다.

### 없는 채로 서지 않는다

`config.ts`가 켤 때 전부 확인하고, 하나라도 없으면 **멈춘다.**

- `AUTH_SECRET`이 **32자 미만이면 거절한다.** 짧은 비밀은 있는 것과 없는 것 사이라 더
  나쁘다 — 있다고 믿게 하면서 지키지 못한다.
- **들어올 길이 하나도 없으면 서지 않는다.** 로그인할 수 없는 서버는 아무도 쓸 수 없고,
  그 사실이 켤 때가 아니라 사람이 눌렀을 때 드러나면 늦다.
- **자격증명이 반만 있어도 거절한다.** 반쯤 켜진 것은 꺼진 것보다 나쁘다.

값은 전부 밖에서 온다. **저장소에 비밀을 두지 않는다** — 들어가면 되돌릴 수 없다.

### 로그인은 직접 짓지 않는다

Better Auth를 쓴다. 비밀번호를 다루지 않고(`emailAndPassword: false`) 소셜 로그인만
연다 — **저장할 것이 없으면 샐 것도 없다.**

세션을 표에 두는 까닭은 **끊을 수 있어야** 하기 때문이다. 쿠키에만 있으면 잃어버린
기기에서 로그아웃시킬 방법이 없고, 개인정보를 다루는 서비스에서 그것은 요구사항이다.

`users` 표는 처음부터 그 모양이었다(첫날 Better Auth를 염두에 두고 지었다). 더한 것은
`sessions` · `accounts` · `verifications` 셋이고, **손으로 적지 않고 라이브러리가 아는
모양을 읽어 옮겼다.**

### 세션이 '누구'까지만 말한다

그 사람이 어느 학생회의 어떤 역할이고 재정을 맡는 부서인지는 `members`가 안다 —
그리고 **그것이 권한 판정의 전부**다. `viewer.ts`가 그 둘을 잇는다.

- **구성원이 아니어도 로그인한 사람이다.** 학생회를 만들려는 사람과 초대 코드를
  확인하는 사람이 그렇다. 이 자리를 막으면 아무도 들어올 수 없다.
- 재정을 맡는 부서인지는 **부서에 단 표시**가 정한다(이름으로 보지 않는다).

### 누구인지는 감사가 확정한다

세션을 읽는 일이 비동기가 되면서 '요청마다 한 번'을 어디서 할지가 정해졌다 —
**가장 먼저 도는 층**이다. 감사가 세션을 읽어 문맥에 담고, 권한과 핸들러가 그것을 쓴다.
막힌 요청도 누가 보냈는지 남는다.

### 로그인 자리는 계약 밖이다

명세에 로그인 화면이 없으므로 `/api/auth/*`는 `openapi.json`에 없다. 그래서 권한
미들웨어보다 **앞에** 둔다 — 뒤에 두면 '계약에 없는 자리'로 막힌다.

`/api/auth-ways`가 어느 길이 열려 있는지 답한다. 화면이 단추를 그릴지 정할 때 쓴다.

### 아직 사람이 해야 하는 것

**구글·카카오 자격증명은 사람이 발급받아야 한다.** 없으면 서버가 서지 않으므로
그때까지 이 서버는 켜지지 않는다 — 그 사실을 숨기지 않는 것이 이 설계의 뜻이다.

## 표가 없던 층으로 (2026-08-30)

조직 층이 끝나고 행사로 넘어갔다. 행사는 읽는 자리 43개 · 쓰는 자리 12개라 한 번에
다 하지 않고 **행사를 만들고 · 목록에서 보고 · 열어서 머리를 그리는** 줄부터 뚫었다.

### 저장하는 것과 그리는 것이 다르다

표에는 `startAt`이 때 하나로 들어 있고, 화면은 `'2026. 08. 20 10:00'`이나 `'일시 미정'`을
받는다. **어느 쪽인지 고르는 것도 형식을 만드는 것도 서버의 일이다** — 화면이 하면 그
규칙이 화면마다 흩어진다.

같은 이유로 이것들이 전부 서버에서 나온다.

- 단계를 사람이 읽는 말과 색으로(`기획 중`·`blue`). 단계가 늘어도 화면은 그대로다.
- 남은 날(`D-33`). **오늘이 언제인지 화면이 알 수 없다.**
- 마지막으로 손댄 때(`어제 수정`). 상대적인 말은 오늘을 아는 쪽이 만든다.
- 아직 안 채운 것들. 기획 중이면 무엇이 비었는지가 눈에 띄어야 하고 **개수가 행사마다
  다르다** — 명세가 개수를 고정하지 않은 까닭이 그것이다.

**빈 글을 저장하지 않는다.** 저장하면 '아직 안 정했다'와 '비워 두기로 했다'가 같은
모양이 된다. 비어 있으면 읽을 때 `'장소 미정'`으로 완성해 준다.

### 아직 없는 표를 지어내지 않는다

업무·일정 표가 아직 없다. 진행률을 `0`으로 주면 '아무것도 안 했다'로 읽히므로
**`'업무가 아직 없습니다'`라고 말한다.** 다음 일정도 같다.

### can*가 정책에서 나온다

`event.listViewer.canCreateEvent`가 화면에 내려가는데, 그 값이 **막는 검사와 같은
함수에서 나온다**(`can(viewer, 'event.create', …)`). 두 곳에서 나오면 언젠가 갈리고,
갈리는 쪽은 늘 화면이다 — 단추를 그렸는데 눌리면 막히는 것이 그 모습이다.

작업공간 머리의 `permissionNote`도 같다. **역할 이름을 들지 않는다** — 무엇을 할 수
있는지로 말한다.

### 계약이 조각 이름을 잡았다

`highlights`의 조각을 `text`로 냈더니 검사가 막았다 — 명세는 `label`이라 한다.
자리마다 손으로 zod를 쓰는 대신 응답을 계약의 모양에 견주기로 한 것이 여기서 값을 했다.

## 값을 기준에 넣는다 (2026-08-30)

사람이 물었다 — "지금 세팅이 가격도 고려한 거야?" **거의 안 했다**가 정확한 답이다.

| 고른 것 | 무엇으로 골랐나 |
| --- | --- |
| TypeScript · Hono · Drizzle · Better Auth | 유지보수성 (사람이 그 기준을 댔다) |
| PostgreSQL · 서울 · RDS | 법(PIPA 국외이전 회피). Neon을 뺀 것도 값이 아니라 **서울이 없어서**다 |
| Lambda | 사람이 서버리스를 골랐다 |

값을 실제로 잰 것은 RDS Proxy 하나뿐이고 **그것도 틀렸다.** NAT은 빠뜨렸는데 그게 가장
컸다. 다행히 **아직 아무것도 배포하지 않아 지금 나가는 돈은 0원**이다.

### 스택은 공짜다. 값은 전부 인프라에서 난다

TypeScript · Hono · Drizzle · PostgreSQL · Better Auth · Vite/React 모두 오픈소스다.
**Better Auth를 고른 덕에 Auth0·Clerk의 사용자당 과금은 이미 피했다** — 유지보수성으로
고른 것이 값에서도 옳았던 자리다.

### 무료 티어가 바뀌었다

**2025년 7월 15일 이후에 만든 계정은 예전의 'RDS 750시간 12개월 무료'를 받지 않는다.**
$100(+최대 $100) 크레딧을 12개월 안에 쓰는 방식이다. 이 프로젝트는 **계정이 아직 없으므로
크레딧 모델이고**, 그 크레딧을 무엇에 쓸지 지금 고를 수 있다.

```
월 $55짜리 모양이면  →  크레딧이 3~4개월에 소진
월 $25짜리 모양이면  →  8개월
```

### 세 가지 모양의 실제 값

환율 1,400원 기준. 서울 리전은 US-East보다 조금 비싸므로 아래는 **하한**이다.

| | 계산 | DB | 나가는 길 | 합 | 대가 |
| --- | --- | --- | --- | --- | --- |
| **A** Lambda + VPC + NAT | ~$0 | $14 | **$32~43** | **~$50 (7만원)** | 없음. 다만 값의 3/4가 배관이다 |
| **B** Fargate 공용 서브넷 | ~$13 | $14 | **$0** | **~$27 (3.8만원)** | 패치할 기계 없음. 늘 켜져 있어 몰리면 손으로 늘린다 |
| **C** 작은 기계 공용 서브넷 | ~$6 | $14 | **$0** | **~$20 (2.8만원)** | **OS를 직접 패치한다** |

**NAT이 사라지는 까닭**: 공용 서브넷에 둔 계산은 인터넷 게이트웨이로 바로 나간다.
게이트웨이는 **공짜다**. NAT은 *사설* 서브넷의 계산이 밖으로 나갈 때만 필요하다.
RDS는 그대로 사설 서브넷에 남는다 — 개인정보가 인터넷에 노출되지 않는다.

### 고른 것: B

**계산은 Fargate, DB는 사설 RDS, NAT 없음.**

- **A보다 싸다** — 배관에 매달 4만원을 내지 않는다. 학생회가 낼 돈이다.
- **C보다 안전하다** — 패치 안 된 기계가 개인정보 곁에 서 있지 않는다. 소수 개발자가
  운영하므로 '패치해야 하는 것'을 하나라도 줄이는 값이 월 1만원보다 크다.
- **연결 문제가 아예 없어진다** — 상시 풀이라 RDS Proxy가 영원히 필요 없다($22 절약).
  콜드 스타트도 없다.
- **되돌리기 싸다** — Hono는 Lambda 어댑터 한 장이면 A로 간다. 몰림이 실제로 문제가
  되면 그때 옮긴다.

프런트엔드는 정적 파일이라 S3 + CloudFront로 거의 공짜다. 증빙·문서·명단이 올라가는
자리가 아홉이므로 S3는 어차피 필요하다(10GB에 월 $0.3).

### 값이 올라가면 무엇부터 손대나

**몰리는 자리는 `/api/public/attendance/*` 셋뿐이다.** 나머지 213자리는 절대 안 몰린다.
그러니 몰림이 문제가 되어도 전체를 탄력적으로 만들 까닭이 없다 — 그 셋만 떼면 된다.

| 이런 일이 생기면 | 이렇게 한다 |
| --- | --- |
| 행사 때 출석이 밀린다 | 그 세 자리만 Lambda로 뗀다. 나머지는 그대로 |
| 평소에도 계산이 모자란다 | Fargate 작업 크기를 올린다(설정 한 줄) |
| DB 연결이 모자란다 | 그때 RDS Proxy를 산다. **지금은 사지 않는다** |

## 배포는 지금 정하지 않는다 (2026-08-30, 교차검토 6번)

검토가 "Lambda + VPC 안의 RDS, 연결 문제를 무엇으로 푸느냐"를 물었다. 다시 재 보니
**지금 답할 물음이 아니었다.** 답을 미루는 것이 아니라, 지금 정하면 짜지 않은 숫자로
정하게 된다.

### 먼저 내 숫자가 틀렸다

| | 처음 적은 것 | 실제 |
| --- | --- | --- |
| RDS Proxy | $15/월 | **~$22/월** — vCPU-시간당 $0.015이고 프로비저닝 인스턴스는 **2 vCPU가 최소**다 |
| NAT Gateway | **아예 빠뜨렸다** | us-east-1 기준 시간당 $0.045(월 ~$32) + GB당 $0.045. 서울은 더 비싸다 |
| 동시 QR 인원 | — | **모른다.** 한때 '1000명 이상'으로 적었다가 사람이 바로잡았다 |

### 문제는 Lambda가 아니라 NAT였다

계산해 보면 이렇다. DB는 $11.68인데 **NAT이 그 서너 배다.**

```
Lambda + VPC + NAT Gateway     계산 ~$0 · DB $11.68 · 나가는 길 ~$32~43   합 ~$44~55
늘 켜진 작은 서버(공용 서브넷)  계산 $5~10 · DB $11.68 · 나가는 길 $0      합 ~$17~22
Fargate 작업 하나              계산 ~$29 · DB $11.68 · 나가는 길 별도      합 ~$41+
```

NAT이 생기는 까닭은 하나뿐이다 — **사설 RDS와 바깥 인터넷을 둘 다 필요로 할 때.**
RDS는 개인정보를 담으므로 사설이어야 하고, 소셜 로그인은 토큰 교환을 서버가 하므로
바깥이 필요하다. 그 둘을 함께 요구하면 NAT을 산다.

전제를 깨는 길 셋을 재 봤고 셋 다 지금은 답이 아니었다.

- **Aurora Serverless v2 + Data API** (VPC 밖에서 HTTPS로 DB를 쓴다) — 멈춰 있을 때
  0 ACU까지 내려가지만, 학생회 도구는 낮 동안 조금씩 계속 쓰여 **거의 안 멈춘다.**
  깨어 있는 0.5 ACU를 24시간 물면 t4g.micro보다 비싸다. (RDS Proxy와 함께 못 쓴다.)
- **NAT 인스턴스** (월 ~$4) — 싸지만 **패치해야 하는 기계**가 하나 생긴다. 개인정보를
  다루는 서비스에서 패치 안 된 관문은 아낀 돈보다 비싸다.
- **인증만 VPC 밖 함수로 떼기** — NAT이 $0이 되지만 인증 얼개를 직접 짜게 된다.
  Better Auth를 고른 까닭이 그것을 안 짜려던 것이었다.

### 그래서 지금 정하지 않는다

세 가지가 겹친다.

1. **결정을 가르는 숫자를 모른다.** Lambda의 값어치는 '몰릴 때 알아서 늘어난다'인데,
   얼마나 몰리는지 모르면 그 값어치를 살 이유가 아직 없다.
2. **바꾸는 값이 싸다.** Hono는 Lambda에서도 컨테이너에서도 기계 한 대에서도 그대로
   돈다 — 배포는 얇은 어댑터 한 장이다. 지금 고른 것을 나중에 바꾸는 데 하루다.
3. **지금 안 정해도 막히는 것이 없다.** 서버 코드는 아직 두 자리뿐이다. 배포는 코드가
   찼을 때 한다.

**대신 무엇을 알면 정해지는지 적어 둔다.**

| 재는 것 | 어디서 | 무엇이 갈리는가 |
| --- | --- | --- |
| 행사 한 번의 **동시 QR 인원과 걸린 시간** | 실제 행사 한 번 | 초당 몇 회인지. 몰리는 자리는 `/api/public/attendance/*` **셋뿐**이고 나머지 213자리는 안 몰린다 |
| 평소 **분당 요청 수** | 학기 중 하루 | 늘 켜진 서버로 충분한지 |
| **NAT을 지나는 트래픽** | OAuth 호출 수 | GB당 $0.045이 유의미한지 |

**한 가지는 지금 말할 수 있다.** 몰리는 자리가 셋뿐이므로, 몰림이 문제가 되면
**그 셋만 따로 다루면 된다** — 나머지를 위해 전체를 탄력적으로 만들 까닭이 없다.

### 결판난 것은 그대로다

- **Neon은 아직 서울에 없다**(2026-08-30 확인). 국외 이전 절차를 피하려면 못 쓴다.
- **RDS Proxy는 보류.** 연결 수가 문제가 된 적이 없는데 DB의 두 배를 물 까닭이 없다.
