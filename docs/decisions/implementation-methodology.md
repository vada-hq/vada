# 화면 구현 방법론

(2026-08-17 확정. 파이프라인 스코프 — 모든 제품에 적용)

## 시스템 완성의 조작적 정의

이 시스템(파이프라인+스펙 체계)은 다음 두 조건이 관측될 때 "충분"하다고 판정한다. 충족 전까지 화면 사이클은 제품 진도가 아니라 **표현력 시험**으로 취급한다.

1. **신규 마찰 수렴**: 연속 2개 화면 사이클에서 새로운 마찰 계급이 0건이다(기존 계급의 재발은 시스템 결함으로 즉시 처리한다).
2. **사람 개입 고정**: 화면당 사람의 개입이 고정 목록 — Figma에서 화면 등록·원본 저장, 결과 최종 확인 — 을 벗어나지 않는다.

참고 지표(누적): ONB-01 사이클 마찰 11건, ONB-02 사이클 5건(신규 계급 2건) — 아직 수렴 전.

## 요소 등록의 분업

요소 등록은 **AI가 초안을 뽑고 사람은 디자인에 없는 값만 답한다**. 근거는 실측이다(2026-08-18): `figma.design.json`만 읽는 추출기가 등록된 요소 18개 중 17개를 nodeId·유형·라벨까지 정확히 재현했고, 유일한 미달인 `note`는 완성된 문자열만 그려져 있어 원리적으로 유도할 수 없다. 계층 깊이(최대 7단계)는 장애물이 아니었다. 오히려 사람이 등록한 결과에 일관성이 없어 등록 노드 계약을 별도로 세워야 했다.

- 기계가 확정하는 것: 등록 노드, 요소 유형, 라벨·필수, placeholder(비활성이면 `disabledPlaceholder`), `searchable`, `presentation`, 묶음과 그 제목·설명·멤버
- 사람만 아는 것: `fieldKey` 작명, 선택지 출처(드롭다운은 선택지가 디자인에 없다), 활성 상태 문구, `inputType`·`valueType`, 이동 대상 화면, `note`의 파생 의도
- 추출기는 후자를 **추측하지 않고 질문으로 보고한다**. ORG-01(요소 9개) 기준 질문 15건이었다 — 이 수치가 "화면당 사람 개입"의 실측값이며, 줄어드는지가 수렴의 지표다.

```powershell
node apps/spec-service/src/draft-screen-spec.mjs <wireframeKey> <screenId>            # 초안 + 질문
node apps/spec-service/src/draft-screen-spec.mjs <wireframeKey> <screenId> --verify   # 등록된 명세와 대조
```

## 원칙

- 각 제품의 화면 구현은 이 저장소의 `apps/<제품>-web`에서 한다. 스펙 번들과 구현이 한 저장소·한 git 히스토리로 묶여, 구현 AI가 같은 컨텍스트에서 스펙을 읽고 스펙 버전과 구현 변경이 함께 추적된다.
- **화면 구현은 파이프라인 검증 실험이다.** 구현 중 스펙 번들만으로 답할 수 없었던 것을 화면별 파일럿 문서의 마찰 로그에 기록한다.
- 스펙·파이프라인의 추가 형식화(예: interpretation의 JSON 승격, 2차 정규화 단계, 검증기 확장)는 마찰 로그와 실제 사례의 증거로만 결정하고, 추측으로 형식화하지 않는다.
- **구현·검증에서 발견된 문제는 개별 수정 대상이기 전에 시스템 결함의 증상이다.** 처분하기 전에 "어떤 계층(스키마·계약·검증기·관례·파이프라인)이 이 문제 계급을 막았어야 했는가"를 먼저 묻고, 그 계층에 반영하는 것을 기본 처분으로 한다. 앱 코드 수정은 시스템 반영의 파생물이지 대체물이 아니다.
- 화면 구현의 완료 점검에는 "동작 명세의 모든 필드를 소비했거나 미사용 사유를 명시했는가"를 포함한다. **점검은 사람의 체크리스트가 아니라 스펙 준수 테스트로 한다**(`apps/<제품>-web/src/spec/conformance.test.tsx`): 기대값을 스펙 JSON에서 읽어 렌더 결과와 대조하므로 스펙을 고치면 검사가 자동으로 따라간다. 스키마에 필드를 추가하면 이 테스트에 단언을 한 줄 늘리는 것이 그 필드의 완료 조건이다.
- **"이 화면은 아직 구현되지 않았다"를 단언하는 테스트를 쓰지 않는다.** 그 화면을 구현하는 순간 깨지고, 회귀가 아니라 진도를 신호로 착각하게 만든다(실제로 flows.test → ScreenRouter.test → org-creation.e2e 세 번 재발했다). 미등록 계약을 검사하려면 구현에 절대 등록되지 않을 id를 쓰고, 실제 화면으로의 이동은 도착을 단언한다.
- 화면 검증은 Playwright 시나리오(e2e)로 자동화한다: AI가 직접 브라우저 시나리오를 실행해 스크린샷을 생성·판독하고 reference와 대조한다. 사용자 육안 검증은 최종 확인으로 축소된다.
- 스택·폰트·반응형 같은 구현 관례는 제품 결정 문서(`docs/decisions/<제품>-*.md`)에 둔다. vada는 `vada-conventions.md`.
