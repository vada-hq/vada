# EVT-DOC-01(행사 문서) 파일럿

**행사 작업 공간의 세 번째 화면이다.** 앞의 둘(EVT-02·EVT-TASK-01)은 한 사이클에서
함께 만든 것이라 **자리가 맞았을 뿐일 수 있었다.** 이 화면의 목적은 그 자리가
정말 맞는지 보는 것이었다 — 공간을 고치지 않고 세 번째가 들어가는가.

계급이 셋 → 둘 → 하나로 줄었고 **(A) 마찰이 처음으로 0건이다.** 아직 판정 조건
(연속 2회 0건)은 아니지만 방향은 분명하다.

## 2. 작업 공간은 고치지 않았다

이번 사이클에서 **`shell.json`의 작업 공간에 손댄 것은 한 줄뿐이다** — `문서`
갈피의 `note`가 `targetScreenId: EVT-DOC-01`로 바뀌었다. 갈피 목록도, 상태 줄의
여섯 조각도, 제목의 출처도 그대로다.

화면이 새로 적은 것도 두 줄이다.

```json
"workspace": { "key": "event", "source": { "tabs": "28:489", "status": "28:511" } }
```

**세 화면이 같은 머리를 나눠 쓴다는 것이 이제 관측이다.** 두 화면일 때는 우연일
수 있었다.

## 3. 표 (신규 계급 · 새 개념)

지금까지의 목록은 전부 카드였다. 여기서 처음으로 **열 머리를 가진 표**가 나왔다
(`문서 / 상태 / 최근 갱신`).

열 머리는 **그려지는 글**이다. "그 조각을 어떻게 그리는지는 figma.design.json이
갖는다"는 규칙이 여기서는 답을 주지 못한다 — 화면은 design.json을 실행 중에 읽지
않기 때문이다. 그래서 명세가 갖는다.

```json
"columns": [
  { "label": "문서",      "fields": ["category", "title", "description"] },
  { "label": "상태",      "fields": ["status"] },
  { "label": "최근 갱신", "fields": ["updatedNote"] }
]
```

`fields`까지 적는 것이 핵심이다. 라벨만 적으면 표는 그려지고 **칸만 비는** 어긋남을
아무도 못 본다. 검증기가 둘을 본다: 가리킨 조각이 출처에 있는가, 한 조각이 두 열에
오지 않는가(오면 어느 칸에 그릴지를 화면이 정하게 된다).

열 **폭**은 명세에 없다. 명세는 무엇이 어느 열에 오는지만 말하고, 비율은 design이
그린 것을 화면이 안다.

## 4. 이미 있던 것이 인자를 받게 됐다

문서 상태 필터는 선택지마다 개수를 곁들인다(`전체 4 · 작성 중 1 · …`). 그런데
`select.optionCounts`는 **MY-01의 업무 탭에서 이미 있던 것**이다 — 무엇을 고를 수
있는지는 명세가, 몇 건인지는 데이터가 정한다.

여기서 늘어난 것은 `params` 하나다. 개수가 **어느 행사의 것인지**에 달렸기 때문이다.
새 어휘가 아니라 `itemList.params`·`summary.params`와 같은 축이고, 그래서 판정도
한 곳으로 합쳤다(`checkArgumentMap`) — 인자의 출처가 넷에서 다섯이 되는 날 두
자리를 따로 고치지 않아도 된다.

**개수는 고른 상태와 무관하게 전체를 센다.** 거른 뒤에 세면 하나를 고르는 순간
나머지 선택지가 전부 0이 되어 옮겨 갈 곳이 사라진다.

## 5. 그대로 쓰인 것

| 이미 있던 자리 | 여기서 |
| --- | --- |
| `workspace` + `workspace.source` | 갈피 줄·상태 줄·행사 이름 |
| `screen.params` + `screenParam` | 어느 행사의 문서인지 |
| `select.presentation: choiceGroup` | 문서 상태 필터 |
| `select.optionCounts` | 선택지마다의 개수 |
| `summary` 라벨-값-보조 3단 | 문서 현황 타일 셋 |
| `itemList.params`의 fieldKey | 고른 상태로 걸러서 다시 조회 |
| `STATE_CHIP` | 확정·검토 중·작성 중·작성 전 딱지 **네 색이 그대로 맞았다** |
| 톤 이름을 데이터가 준다 | 줄 왼쪽 강조선 |
| 그리지 않는 조각(`id`) | 문서를 여는 화면이 생길 때 넘길 값 |
| `meta.title`이 본문 머리에 온다 | EVT-TASK-01과 같다 |
| 없으면 드러낸다 | eventId가 없으면 오류 카드 |

## 6. design 대조가 처음부터 0곳이었다

26곳(EVT-TASK-01) → 49곳(EVT-02) → **0곳**.

바뀐 것은 순서다. 이번에는 **화면을 쓰기 전에 design.json에서 색을 읽었다.**
그전에는 먼저 짐작으로 쓰고 대조가 짚어 준 것을 고쳤다.

`STATE_CHIP` 네 색이 손대지 않고 맞은 것도 컸다 — 상태 딱지는 회의 화면에서
만든 것인데 문서 상태에 그대로 들어갔다. 색 이름을 데이터가 주기 때문이다.

새로 적은 색은 하나다: **표 한 줄 왼쪽의 강조선은 톤의 -500, 무채색만 -400.**
흔들림이 아니라 이유가 있다 — `gray-500`은 본문 글자의 색이라 장식인 선이 글보다
진해진다. design과 같으므로 `deviations.ts`는 늘지 않았다.

## 7. 갈피가 갈 곳이 생기면 앞 화면의 검사가 깨진다

EVT-TASK-01의 e2e가 `문서` 갈피를 눌러 "아직 명세되지 않았습니다"를 확인하고
있었다. 그 화면이 생겼으니 검사가 깨진 것이 맞다 — **의도가 바뀐 것이므로 검사를
고쳤다**(아직 명세되지 않은 `관련 회의`로 옮겼다).

이런 검사는 갈피가 하나씩 채워질 때마다 한 번씩 옮겨 다닌다. 남은 넷이 채워지면
사라진다. 지금 일반화하지 않는다.

## 8. 남긴 것

- **문서를 여는 화면이 없다.** 표의 줄을 눌러도 갈 곳이 없어 `pending`이다.
  `id`는 이미 데이터에 있으므로 화면이 생기면 넘기기만 하면 된다.
- **추출기가 표를 못 봤다.** 요소 3개 중 필터 하나만 버튼 다섯으로 뽑았고, 통계
  타일과 표는 통째로 놓쳤다. 질문 20건을 냈는데 그중 13건이 갈피 줄과 필터를
  버튼으로 읽은 데서 나온 것이다 — **작업 공간을 아직 모른다.**
- **셸 메뉴가 꺼져 있다.** 와이어프레임은 사이드바의 `운영`을 켜서 그리는데 화면은
  끈다. 사이드바는 `targetScreenId === screenId`일 때만 켜지고, **메뉴 하나가 화면
  여럿을 품는다**는 것이 아직 어디에도 없다 — 갈피가 `workspaces`로 풀린 것과 같은
  종류의 구멍이고 행사 화면 넷이 전부 그렇다. 셸은 대조기가 보지 않아 조용하다.

## 9. 게이트가 시간 예산에 걸렸고, 원인은 6MB였다

검사는 전부 통과했는데 **63.4초**가 걸려 예산(60초)에서 실패했다. 예산의 안내대로
검사를 지우지 않고 원인을 쟀다.

파일별로 재니 `design-check`가 39초 중 14초였고, 프로젝트 전체에서 가장 큰 값은
**`import` 36초**였다. 그 정체는 `import.meta.glob`으로 불러오던 **design 파일
6MB**다 — vite가 화면마다 JSON을 ES 모듈로 바꾸고 있었다.

검사는 Node에서 돈다. 번들러를 거칠 이유가 없어 `readFileSync`로 바꿨다.

| | 전 | 후 |
| --- | --- | --- |
| vada-web 검사 | 53.9초 | **35.3초** |
| 게이트 전체 | 63.4초(실패) | **41.4초** |

**화면이 늘 때마다 커지던 자리를 없앤 것이다.** 화면 하나가 400KB씩 붙는 곳이었다.
