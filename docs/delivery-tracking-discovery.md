# 배송 상태 자동 공유 검증 계획

- 작성일: 2026-09-30
- 상태: 공개 화면 및 구형 API 단건 조회 확인 / 현행 API·자동 갱신 미검증
- 범위: M1 구매요청 승인 이후의 다음 마일스톤 검토

## 목적과 확정된 요구

재정부가 승인한 구매요청의 배송 진행 상황을 학생회 소속 모든 팀원이 확인할 수 있게 한다. 재정부가 구매처에서 확인한 배송 상태를 VADA에 반복 입력하지 않도록 하는 것이 핵심이다.

- 구매요청 승인 이후의 구매·배송 업무는 재정부가 담당한다.
- 공유하려는 배송 상태는 배송 대기, 배송 중, 배송 완료다.
- 기존 구상과 와이어프레임은 재정부가 상태를 직접 변경하는 방식이다.
- 단순히 기능을 추가하기보다, 배송 문의·답변과 중복 입력을 합친 실제 업무 부담을 줄여야 한다.

## 아직 확정하지 않은 사항

- 실제 주문·배송 정보를 가져올 수 있는 경로, 필요한 권한과 이용 조건
- 구매요청서와 실제 주문·배송을 연결하는 방법
- 최초 연결에 필요한 사용자 행동과 반복 작업의 허용 수준
- 갱신 주기, 비용, 지원 가능한 배송 유형
- 승인과 주문 완료 사이의 상태 표현 및 분할 배송의 표시 단위

완료된 배송 1건의 외부 조회 가능성은 확인했다. 자동 갱신과 실제 서비스 연동 가능성은 아직 확인하지 않았다. 이 문서는 검증 계획과 관찰 기록이며 구현 명세는 아니다.

## 검증할 가설

1. 권한 있는 구매자의 주문·배송 정보를 안전하고 지속 가능한 경로로 조회할 수 있다.
2. 요청서와 주문을 적은 노력으로 연결하고, 이후에는 반복 입력 없이 상태를 갱신할 수 있다.
3. 자동 공유로 줄어드는 배송 문의·답변 부담이 최초 연결과 예외 처리 부담보다 크다.

## 설계 전에 확인할 경계

- 승인과 실제 주문 완료를 구분한다. 승인만으로 주문된 것으로 표시하지 않는다. `구매 대기 → 주문 완료·배송 대기 → 배송 중 → 배송 완료`는 검토 후보이며 확정 상태 모델은 아니다.
- 상품 링크만으로 실제 주문을 식별할 수 있다고 가정하지 않는다. 주문 식별에 필요한 추가 정보를 확인한다.
- 요청서 하나에 여러 주문·배송이 연결될 수 있는지 확인한다. 일부만 도착했을 때 전체를 완료로 표시하지 않아야 한다.
- 조회 실패·오래된 정보와 실제 배송 상태를 구분한다. 마지막 확인 시각과 확인 불가 안내가 필요한지 검토한다.
- 배송 상태 공유와 주문 원본 정보 공개를 구분한다. 주소·연락처 등 불필요한 개인정보는 팀원에게 노출하지 않는다.

## 검증 순서

### 1. 현재 업무 확인

재정부의 실제 구매 과정을 확인한다. 구매에 사용하는 계정, 주문하는 방식, 배송 문의 빈도, 답변 부담, 분할 배송 경험을 기록한다. 최초 주문 연결에 어느 정도의 행동을 감수할 수 있는지도 확인한다.

산출물: 현재 업무 흐름과 줄이고 싶은 작업, 허용 가능한 입력 부담.

### 2. 연동 경로 조사

공식 문서 중심으로 구매자 주문 조회와 배송 조회 수단을 조사한다. 판매자용 API가 구매자 주문에도 사용 가능한 것으로 간주하지 않는다.

각 후보에 대해 다음을 기록한다.

- 제공 정보와 필요한 식별자: 주문 번호, 운송장 번호 등
- 접근 자격·인증·사용자 동의·이용 조건
- 요청서와 주문을 연결하는 데 필요한 사용자 행동
- 갱신 방식·조회 제한·비용·지원 범위
- 인증 만료·권한 철회 시 필요한 조치
- 공식 근거 URL, 확인일, 확인된 사실과 남은 추정

공식 경로가 부족하면 대체 수단의 가능성과 제약만 검토한다. 비밀번호·세션 쿠키 수집이나 접근 제한 우회를 전제로 진행하지 않는다.

산출물: 후보별 가능·불가능·미확인 비교와 작은 실험에 사용할 후보 하나. 적합한 후보가 없으면 여기서 보류할 수 있다.

### 3. 최소 실험

사용 권한과 동의가 확인된 최소 데이터로, 제품 코드와 분리된 작은 실험을 진행한다. 유료 서비스 가입이나 실제 구매가 필요하면 실행 전에 별도 승인을 받는다.

1. 요청서 하나와 주문·배송 하나를 연결한다.
2. 이후 사용자 입력 없이 상태를 다시 조회할 수 있는지 확인한다.
3. 원본 정보와 조회 결과·시각을 비교한다.
4. 최초 설정, 주문별 연결, 반복 갱신에 필요한 사용자 행동을 각각 기록한다.

실제 배송 상태 변화 관찰이 어려우면 조회 가능 여부만 확인한 것으로 기록한다. 모의 응답으로 상태 전환을 확인한 것을 실배송 추적 검증으로 취급하지 않는다.

산출물: 연결 절차, 관찰 결과, 사용자 작업량, 지연·실패·비용과 미검증 항목.

### 4. 예외와 신뢰성 확인

- 여러 품목·주문·운송장, 일부 배송 완료
- 운송장 미발급 또는 조회 불가
- 네트워크 오류·조회 제한·인증 만료
- 취소·반품 등 단순 배송 상태로 표현하기 어려운 경우
- 오래된 정보가 최신 상태로 오해될 가능성

실제로 확인한 항목, 모의 데이터로 확인한 항목, 미확인 항목을 분리해서 기록한다.

## 진행 여부 판단 기준

| 기준 | 확인할 내용 |
| --- | --- |
| 업무 부담 | 최초 연결 이후 반복 입력이 없는가? 예외 처리까지 포함해 기존 업무보다 부담이 줄어드는가? |
| 접근 가능성 | 실제 구매 주체가 사용할 수 있는 권한·연동 경로인가? |
| 최신성 | 관찰한 갱신 지연이 팀의 사용 목적에 적합한가? 오래된 정보임을 구분할 수 있는가? |
| 정확성 | 요청서와 배송을 잘못 연결하거나 일부 도착을 전체 완료로 표시하지 않는가? |
| 안전성 | 인증정보와 개인정보를 필요한 범위에서 안전하게 취급할 수 있는가? |
| 운영 부담 | 비용·조회 제한·인증 유지·장애 대응을 감당할 수 있는가? |

허용 지연·입력 횟수·비용의 수치 기준은 현재 업무 확인 후, 실험 전에 정한다. 근거 없이 임의의 목표치를 확정하지 않는다.

## 결과 기록

- 판단: 미정 — 구현 진행 / 범위 축소 후 재검증 / 보류
- 근거와 조사 출처: 아래 단건 조회 실험 참고
- 실제로 검증한 범위: 공개 조회 화면, V1 및 V2 인증 API에서 완료 배송 1건의 기록 일치
- 미확인 항목과 위험: 웹훅 수신, 실배송 자동 갱신, 지원 범위, 입력 부담 및 운영 비용
- 다음 행동: 배송 중인 송장이 없어 가상 송장 웹훅 실험 진행. 실배송 전환 검증은 별도 보류

### 2026-09-30 단건 조회 실험

- 사용자가 제공하고 외부 조회에 동의한 쿠팡 로지스틱스 송장 1건을 사용했다. 전체 송장번호는 저장하지 않는다.
- 사용자가 Delivery Tracker 공개 화면에서 쿠팡 앱과 배송 이력이 일치함을 확인했다.
- 별도의 PowerShell 일회성 GET 요청으로 공식 문서의 V1 테스트 경로를 호출했다. 인증정보 없이 1회 조회했으며 제품 코드·DB·추적 등록은 변경하지 않았다.
- 경로: `https://apis.tracker.delivery/carriers/{carrierId}/tracks/{trackingNumber}`, 택배사: `kr.coupangls`.
- JSON 응답의 현재 상태: `delivered` / 배송완료.
- 완료 시각: `2026-09-23T10:04:03+09:00`. 쿠팡 앱의 분 단위 표시 10:04와 일치한다.
- 이전 이력도 집하 02:37, 캠프상차 02:45, 캠프도착 07:03, 배송출발 08:53으로 화면과 일치했다.
- 출력은 상태와 시각만 추려 확인했다. 주소·연락처·원본 응답 파일은 저장하지 않았다.
- 한계: 이미 완료된 송장의 과거 이력을 조회한 실험이다. 새 배송의 갱신 속도·웹훅 수신·조회 실패 대응·모든 쿠팡 배송 지원을 입증하지 않는다.
- V1은 폐기 예정으로 안내된 구형 API다. 문서의 무인증 테스트 허용 경로를 사용했을 뿐, 이를 제품 의존성으로 채택하지 않는다.
- 이후 사용자가 `scripts/check-delivery.ps1`로 V2 GraphQL 인증 조회에 성공했다. `DELIVERED`와 완료 시각 및 이전 이력이 일치했다. 인증정보는 채팅·문서·Git에 남기지 않는다.

### 가상 송장 웹훅 실험 준비

- 제품 코드·DB와 분리된 `scripts/delivery-webhook.mjs` 및 PowerShell 실행기를 추가했다.
- 로컬 수신 관련 테스트 2개와 Node/PowerShell 구문 검사를 통과했다. 외부 등록·실제 웹훅 수신은 아직 미검증이다.
- [실행 절차와 한계](delivery-webhook-test.md)를 따라 가상 송장으로 알림 수신 후 인증 재조회를 확인한다.

공식 근거 (확인일 2026-09-30):

- [V1 API 및 테스트용 무인증 안내](https://tracker.delivery/docs/api-versioning/v1)
- [현행 API 인증](https://tracker.delivery/docs/authentication)
- [Tracking API](https://tracker.delivery/docs/tracking-api)

자동 추적이 어렵다는 이유만으로 수동 상태판을 대안으로 확정하지 않는다. 수동 방식도 업무 부담 감소를 별도로 확인한다.

## 이번 단계에서 하지 않는 일

- 배송 화면 구현, DB·ERD·API 명세 확정
- 기존 승인 기능이나 상태 값 변경
- 서비스 배포 및 실사용 계정 연동

M1 프론트엔드의 실환경 검증은 별도로 보류 중이다. 이번 조사 진행을 M1 검증 완료로 간주하지 않으며, 후속 기능을 연결하기 전 실제 환경에서 핵심 흐름을 확인한다.
