# 에이전트 실행 기준

## 책임 구조

- **사람 책임자**는 제품·정책의 최종 결정, 위험 수용, 병합과 운영 배포를 승인한다. 에이전트가 만든 결과의 법적·조직적 책임을 에이전트에게 넘기지 않는다.
- **총괄 에이전트**는 승인 기준선을 읽고 착수 가능한 작업을 판정하며, 작업 패킷 작성·할당·최종 diff·문서 영향을 검토한다. 직접 구현했더라도 자기 판단만으로 완료 승인하지 않는다.
- **작업 에이전트**는 할당된 작업 하나를 격리된 브랜치·worktree에서 구현하고 증거와 잔여 위험을 인계한다. **검증 에이전트**는 작성자와 분리된 새 컨텍스트에서 계약·테스트·보안·범위 준수를 확인한다.

작업자 수는 고정하지 않는다. 독립 작업 수, 충돌 가능성, 검토 처리량, 실행 환경의 동시성 한도를 근거로 총괄이 정한다.

## 착수 가능 판정

다음을 모두 만족할 때만 `착수 가능`이다.

1. `delivery-work/R<n>.json`에 작업이 `ratified`로 존재하고 정확한 작업 ID·리비전이 지정됐다.
2. `blocked_by`의 모든 작업이 요구한 완료 증거를 통과했다. 단순히 코드가 존재하거나 작업자가 완료라고 말한 것은 증거가 아니다.
3. 참조한 제품 명세·계약 묶음·구현 아키텍처가 승인 상태이고 해시가 유효하다.
4. 결과를 바꾸는 미결정 질문이 없고, 허용 변경 경로·필수 검증·사람 승인 게이트가 분명하다.
5. 동시에 실행할 다른 작업과 같은 파일, 스키마, 계약 의미 또는 마이그레이션 순서를 경쟁적으로 수정하지 않는다.
6. `just preflight`와 작업 패킷에 지정된 추가 프로필이 통과했다. 사람 실행자는 작업 내용을 전달받고 착수를 명시적으로 확인했다.

선행 작업의 산출물을 실제로 읽지 않아도 독립적으로 증명할 수 있다면 병렬화할 수 있다. 같은 파일을 서로 다른 worktree에서 수정할 수 있다는 사실만으로 독립 작업이 되지는 않는다.

## 작업 패킷

총괄은 작업 에이전트에게 최소한 다음 정보를 전달한다.

- 작업 ID·리비전, 목표 결과, `blocked_by`, 완료 증거 ID
- 정확한 제품·계약·아키텍처 참조와 읽어야 할 경로
- 허용 변경 경로, 변경 금지 경로, 대상 테스트 명령과 전체 검증 명령
- 착수 전 검사 프로필과 작업자·검증자가 각각 실행할 범위별 검사 명령
- 보안·데이터·마이그레이션 위험, 사람 승인이 필요한 행동, 유한한 재시도 조건

작업 패킷에 없는 제품 의미를 작업자가 추정해서는 안 된다. 구현 중 계약 변경이 필요하다고 발견하면 코드로 우회하지 말고 총괄에게 `발견된 차이`, `영향`, `필요한 결정`을 보고한다.

## 실행 흐름

1. 총괄이 Git 상태·필수 실행 환경·사람 인계 확인과 착수 가능 여부를 확인한 뒤 작업별 브랜치·worktree를 준비한다.
2. 작업자가 가장 작은 실패 테스트로 현재 부족분을 재현하고 의도한 이유로 실패하는지 확인한다.
3. 최소 구현으로 테스트를 통과시킨 뒤 구조를 정리하고 작업 패킷에 지정된 범위별 검증만 실행한다. 병렬 작업자는 저장소 전체 `just check`를 반복 실행하지 않는다.
4. 작업자는 작업 ID, 변경 파일, RED·GREEN·범위별 검증 결과, 계약·문서 영향, 잔여 위험을 인계한다.
5. 검증 에이전트가 승인 기준선과 diff를 처음부터 대조하고 필요한 검증을 독립 실행한다.
6. 총괄은 실패를 구체적인 미충족 증거와 함께 재작업시키거나, 통과 결과만 통합한 뒤 저장소 전체 `just check`를 한 번 실행하고 사람 책임자에게 병합 후보로 보고한다.

재시도는 실행 계획에서 유한하게 정한다. 같은 원인의 실패가 반복되거나 제품·계약 입력이 부족하면 더 많은 시도를 소모하지 않고 사람 책임자에게 올린다.

## 반드시 멈추고 보고할 때

- 승인되지 않은 제품 의미·권한·필수 입력·상태 전이를 결정해야 할 때
- 활성 계약이나 승인 리비전을 덮어써야만 구현할 수 있다고 판단될 때
- 비밀정보 접근, 운영 배포, 운영 데이터 변경, 파괴적 마이그레이션이 필요할 때
- 작업 범위를 넘어선 대규모 리팩터링이나 공유 기반 변경 없이는 진행할 수 없을 때
- 테스트가 환경 문제로 재현되지 않거나 검증 결과가 서로 모순될 때
- 착수 전 검사에서 필수 도구·서비스·연결을 확인하지 못했거나 사람 담당자의 실제 인계 확인이 없을 때
