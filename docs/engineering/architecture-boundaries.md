# 아키텍처 경계

## 의미에서 구현으로의 방향

VADA의 의존 방향은 다음과 같다.

```text
승인 제품 명세
  → 목표 동작 설계
  → 실행 계약
  → 구현 아키텍처
  → 전달 작업 그래프
  → 코드·테스트·운영 산출물
```

뒤 단계는 앞 단계의 의미를 참조하지만 새 제품 정책을 만들지 않는다. 런타임 제품 코드는 계획 문서나 와이어프레임을 읽어 동작을 결정하지 않는다.

## 최상위 디렉터리 책임

- `product-specs/` — AI가 읽는 승인 제품 의미와 출처
- `contracts/` — 코드와 직접 결합되는 권한·데이터·도메인·API·오류·품질 계약
- `delivery-units/` — 승인 계약을 적용할 기술 결정과 불변 작업 그래프
- `apps/api/`, `apps/web/` — 실제 운영 제품 구현
- `packages/` — 명시적 소비자가 있는 순수 공유 TS 계약·생성 클라이언트
- `prototypes/wireframe/`, `docs/reference/` — 화면 탐색과 과거 근거; 구현·정책 정본이 아님
- `infra/` — 재현 가능한 배포·권한·관측·데이터 기반
- `docs/engineering/` — 제품 의미와 무관한 개발 실행·품질·운영 규칙

제품 앱은 `prototypes/wireframe/`의 코드를 import하지 않는다. 화면을 구현할 때는 승인 화면 명세와 계약을 사용하며, 프로토타입은 시각적 근거로만 대조한다.

## 코드 책임 규칙

- 파일과 모듈 이름은 기술 단계가 아니라 소유한 제품 기능이나 경계 책임을 드러낸다.
- 한 모듈은 변경 이유가 응집돼 있어야 하고, 외부에는 필요한 최소 인터페이스만 노출한다. 임의의 줄 수 제한으로 파일을 나누지 않는다.
- 공유 추상화는 실제 소비자와 안정된 공통 의미가 확인됐을 때 만든다. 우연히 모양이 비슷하거나 미래에 재사용할 것 같다는 이유로 공용 계층을 만들지 않는다.
- 웹은 서버 권한 판정을 대체하지 않고, API는 UI 상태나 프로토타입에 의존하지 않는다. 조직·권한·트랜잭션 불변식은 서버와 DB가 보장한다.
- 생성 산출물은 입력과 생성 명령을 추적할 수 있어야 하며 사람이 직접 수정하지 않는다. 같은 입력으로 재생성했을 때 차이가 없어야 한다.

`apps/api`와 `apps/web` 내부의 구체적인 폴더 구조는 승인된 구현 아키텍처와 실제 첫 기능의 책임을 확인한 뒤 경로별 `AGENTS.md`에 확정한다. 초기 뼈대만 보고 전체 프로젝트의 영구 구조를 추정하지 않는다.

## 화면이 권한을 아는 방법

화면이 버튼을 보일지 결정하려면 사용자가 무엇을 할 수 있는지 알아야 한다. 서버 판정을 대체하지 않는 **표시용 정보**이며, 실제 차단은 언제나 서버가 한다. 화면 판단이 틀려도 안전해야 한다.

VADA 권한은 전역이 아니다. 세 계층이며 **계층마다 나오는 곳이 다르다.**

| 계층 | 예 | 무엇에 달렸나 | 어디서 오나 |
| --- | --- | --- | --- |
| 전역 | `canSubmitPurchaseRequest` | 기본 역할 + 부서 | 세션 응답 |
| 행사별 | `isEventManager`, `canEndEvent` | 그 행사에서의 맥락 역할 | 그 행사 조회 응답 |
| 레코드별 | `canCancelPurchaseItemRequest` | 원래 요청자 본인인지 | 그 레코드 조회 응답 |

권한 목록 하나를 세션에서 받아 전부 판단하려 하지 않는다. 행사별·레코드별 권한은 세션이 답할 수 없다. **권한은 리소스를 따라온다.**

서버는 역할이 아니라 **판정 결과**를 보낸다. `{ "role": "부서장" }`을 보내고 화면이 조건을 다시 계산하면 같은 규칙이 두 언어에 생겨 언젠가 갈라진다. `{ "canSubmitPurchaseRequest": true }`처럼 이미 판정한 값을 보낸다. 화면에서 역할 이름을 비교하지 않는다는 권한 매트릭스 규칙과 같은 이유다.

신원과 권한을 한 응답에 섞더라도 **수명이 다르다는 것을 잊지 않는다.** 이름은 거의 안 바뀌고 권한은 자주 바뀐다. 세션 값을 오래 캐시하면 회수된 권한이 화면에 남는다. 표시용이라 위험하지 않지만, 그래서 화면 판단을 신뢰의 근거로 쓰지 않는다.

세션 계약이 아직 없다. 그전까지 화면은 권한을 추측하지 않고 행동을 노출하며, 권한 없는 사용자는 서버 거부를 명시적인 화면 상태로 만난다. 화면마다 다른 우회책으로 권한을 추정하지 않는다. 그렇게 하면 세션 계약이 생길 때 전부 다시 고쳐야 한다.

## 변경 동기화

- 제품 의미가 바뀌면 새 제품 명세 리비전부터 시작하고 계약·아키텍처·작업 영향도를 다시 계산한다.
- 공개 API·권한·데이터 의미가 바뀌면 새 계약 리비전과 호환성 분류를 먼저 만든다.
- 구현 선택만 바뀌면 ADR 재평가 트리거와 구현 아키텍처 리비전을 확인한다.
- 순수 내부 리팩터링은 외부 동작이 그대로임을 테스트로 증명하며 승인 제품·계약 리비전을 불필요하게 갱신하지 않는다.
