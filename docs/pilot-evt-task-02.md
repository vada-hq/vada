# EVT-TASK-02(업무 상세) 파일럿

**새 계열이다.** 지금까지의 열두 화면은 폼·대시보드·목록이었고, 이것은 처음으로
**한 건의 상세**다. 그리고 이 화면은 플러그인을 한 번도 열지 않고 받았다.

## 1. 수렴 판정: 아직 아니다 (3건)

새 계열이므로 계급이 다시 난 것 자체는 놀랍지 않다. 세 건의 성격이 다르다 —
하나는 스키마를 넓혔고, 하나는 적을 자리가 없어 남의 자리를 빌렸고, 하나는
아직 풀지 않았다.

## 2. 화면이 인자를 받는다 (신규 계급 · 새 개념)

**지금까지 열두 화면은 전부 인자가 없었다.** 무엇의 상세인지는 화면 안 어디에도
없으므로 밖에서 와야 한다.

```json
"params": [
  { "key": "taskId", "valueType": "string", "example": "T-03",
    "description": "어느 업무의 상세인지. 업무 보드에서 항목을 눌러 들어올 때 그 항목이 정한다." }
]
```

요소는 `screenParam`으로 그 값을 가리킨다. 조회 인자의 출처가 둘(`fieldKey`·`value`)에서
셋이 됐고, 셋이 됐으므로 그 모양을 `element-params.schema.json`으로 뽑았다 —
`itemList`와 `summary`가 같은 것을 쓴다.

세 가지를 함께 했다.

- **검증기**: `screenParam`이 화면의 `params`에 없으면 오류다. 화면에 그 값을 담은
  필드가 없는 것이 **정상**이라 이 검사가 없으면 조용히 아무것도 못 집어 온다.
  `taskId`를 `eventId`로 바꿔 네 곳을 정확히 짚는 것을 확인했다.
- **주소가 값을 나른다**: `#/EVT-TASK-02?taskId=T-03`. 화면 하나만 따로 여는 성질을
  지키려면 앞 화면을 반드시 거치게 할 수 없다.
- **없으면 드러낸다**: 인자가 없으면 조용히 아무 업무나 보여주지 않고 오류 카드를
  띄운다. 미등록 화면 오류 카드와 같은 태도다.

### 예시 값은 명세가 갖는다

검사는 앞 화면을 거치지 않고 화면을 바로 그리므로 `taskId`를 어디선가 얻어야 한다.
**검사가 지어내면 그것은 명세에 없는 사실이 된다.** 그래서 `params[].example`을 두고
검사가 읽기만 한다(`summary.items[].value`와 같은 성격이다). 구현은 이 값을 쓰지
않는다 — 인자가 없으면 드러내야 하기 때문이다.

## 3. 명세되지 않은 갈피를 적을 자리가 없다 (신규 계급 · 미해결)

갈피(탭)가 둘인데 '처리 기록'의 내용이 디자인에 없다. `itemAction`에는 `pending`이
있지만 **선택지 하나가 아직 명세되지 않았다**를 적을 자리는 없다.

지금은 선택지의 부연 설명(`options[].description`)을 빌렸다. 뜻이 가깝지만 정확히
그것은 아니다. 같은 일이 한 번 더 나오면 자리를 만들어야 한다.

## 4. 눈썹에 데이터가 들어간다 (신규 계급 · 미해결)

디자인의 빵부스러기는 `운영 > 행사 > 2026 소프트웨어융합대학 체육대회 > 업무 > 업무 상세`인데
**행사 이름이 데이터**다. `meta.eyebrow`는 고정 문자열이라 담을 수 없어
`운영 · 행사 · 업무`로 줄였다.

대조기가 셸을 보지 않아 이 차이는 검사에 걸리지 않는다. 그래서 여기 적는다 —
검사가 못 보는 것은 문서가 봐야 한다.

## 5. 그대로 쓰인 것

| 이미 있던 자리 | 여기서 |
| --- | --- |
| `summary` + `titleField` + `items` | 상세 카드(라벨-값 여섯 쌍) |
| `AppShell.headerAction`(EVT-00A에서 만든 자리) | 머리의 버튼 **둘** |
| `select.presentation: choiceGroup` | 갈피 |
| `itemList` + `title` | 공식 참고 문서 · 작업 문서 |
| 조각 중첩(`fields[].fields`) | 연결된 항목(개수가 업무마다 다르다) |
| 톤 이름을 데이터가 준다 | 상태·우선순위·검토 딱지 |
| 완성된 문자열로 온다 | `dueDate`('2026-07-18 · 지연')·`nextStepNote` |
| 화면 카드의 모양은 화면이 안다 | 표의 열 이름은 design이 정한 카피다 |

**표는 새 계급이 아니었다.** 열 머리는 확정된 카피이고 행은 `itemList`의 항목이다 —
TASK-01의 카드, OPS-MEET-01A의 회의 카드와 같은 축이다.

## 6. (A) 마찰 1건 — 자산 규칙이 또 틀렸다

이번에도 자산이었지만 **앞과 다른 원인**이다. 그리고 이번 것은 앞 것을 고치다
드러났다.

`absoluteRenderBounds`가 null인 것을 '아무것도 그리지 않는다'로 읽어 왔는데,
그 값은 **틀 밖으로 잘렸다**는 뜻이기도 하다. 화면 프레임(1288×740)보다 아래에 있는
내용은 전부 null이다. 그래서 **접힌 아래쪽 아이콘이 자산에서 조용히 빠져 있었다** —
이 화면의 '파일 추가'(25:1822)와 '재제출 필요'(25:1849)가 그랬고, 다시 세어 보니
여섯 화면에서 11개가 빠져 있었다.

| 화면 | 자산 |
| --- | --- |
| OPS-MEET-01A | 33 → 39 |
| HOME-01K | 22 → 23 |
| OPS-00 | 21 → 22 |
| EVT-TASK-02 | 16 → 18 |

가르는 것은 좌표다 — **잘린 것은 틀 경계를 넘어간다.** 숨긴 것은 Figma가
`visible: false`로 명시하므로 그것만 건너뛴다. 고친 뒤 네 화면을 다시 받았고
자산 추출 실패가 하나도 없었다 — 잘린 것도 정상적으로 뽑힌다는 실증이다.

## 7. design 대조는 79곳에서 시작했다

새 계열이라 손으로 고를 것이 많았다. 대조기가 79곳을 전부 짚어 주었고, 그중
**데이터가 틀린 것이 둘**이었다.

- 제출 상태 딱지가 초록인 줄 알았는데 design은 파랑이다(`submissionTone`).
- 마감일이 지연이면 붉게 그렸는데 **design은 그러지 않는다.** 지연이라는 사실은
  글에 이미 들어 있다. 쓰이지 않게 된 `overdue` 조각을 카탈로그에서 지웠다.

색을 눈으로 맞췄다면 둘 다 못 봤을 것이다.

## 9. 정하지 않은 것

**상시 업무의 '업무 상세'가 이 화면인지 정하지 않았다.** MY-01·TASK-01·OPS-MEET-01A의
5곳이 여전히 막혀 있다.

근거는 갈렸다. 와이어프레임 85개 중 업무 상세는 이 하나뿐이고 행사 아래에 있는데,
이 화면의 '공식 참고 문서'는 *행사 공용 원본*이라 상시 업무에는 뜻이 없다. 지금
이어 붙이면 아무도 정하지 않은 제품 의미를 지어내는 것이다.

**비용이 비대칭이라 미룬다.** 나중에 잇는 것은 pending 다섯 줄을 바꾸는 일이지만,
잘못 이어 놓으면 화면 모양까지 틀린다.
