# VADA 파일럿 시연 스크립트 (M1)

기준일: 2026-09-01
대상 마일스톤: `VADA_ROADMAP.md` M1 — 유인 가설 검증

## 0. 이 시연이 답해야 하는 것

**주질문**

> 구매 요청·승인이 지금 카톡으로 처리될 때 **실제로 비용이 발생하는가.** 그 비용이 별도 도구에 따로 입력할 만큼 큰가.

`VADA_FINANCE_SCREENS.md` 10장 미해결 4번이다. 재정 기능 전체의 전제이며, "카톡으로 충분하다"가 답이면 M4의 재정 축 설계가 바뀐다.

**부질문**

| # | 질문 | 검증 대상 |
|---|---|---|
| 1 | 승인 전에 되묻는 일이 실제로 얼마나 있나 | `MVP_SPEC` §2 "재정부와 요청자가 서로 확인해야 한다" |
| 2 | 요청자가 상태를 몰라 물어보는 일이 있나 | 가설 3 (상태 가시성이 확인 비용을 줄인다) |
| 3 | 요청자가 그냥 카톡으로 보내면 재정부는 어떻게 대응하나 | **도구가 우회당하는지** — 가장 결정적 |

**이 시연은 반응을 얻으러 가는 게 아니라 반증을 얻으러 간다.** 2026-08-15 인터뷰가 유용했던 것은 "파일 정리가 가장 확실한 가치"라는 초안 가정을 반증했기 때문이다. 같은 결과를 기대하고 설계한다.

## 1. 준비

### 대상

| 역할 | 인원 | 왜 |
|---|---|---|
| 재정부원 (또는 재정부장) | 학생회당 1명 | 처리하는 쪽 |
| 구매 요청을 올려 본 부서원 | 학생회당 1명 | 요청하는 쪽. **고통이 양방향이라는 게 문서의 주장이므로 한쪽만 보면 검증이 안 된다** |

**학생회 3곳을 잡는다.** 판정 기준이 "2곳 이상 우세"인데 2곳만 확보하면 결과가 갈리는 순간 바로 막힌다. 섭외는 늘 예상보다 어려우므로 여유분이 아니라 기본값이다.

> **두 역할을 한자리에서 만나지 않는다. 반드시 따로 만난다.**
>
> 4부의 우회 질문이 무너지기 때문이다. 요청자가 앞에 있는데 재정부원이 "그냥 제가 대신 넣죠"라고 말하기 어렵고, 요청자도 재정부원 앞에서 "답답했다"고 말하기 어렵다. 학생회는 상하관계가 있는 조직이고 이 두 질문은 정확히 그 관계를 건드린다. **가장 결정적인 신호가 가장 먼저 죽는다.**
>
> **순서는 재정부원 → 요청자.** 재정부원에게서 실제 처리 흐름을 먼저 들으면 요청자 세션에서 "○○님은 이렇게 하신다던데 그때 어떠셨나요"로 구체화할 수 있다.

최소 요건이 하나 있다.

> **사후 일괄 기록형 재정부원을 최소 1명 확보한다.** 2026-08-15 표본은 실시간 기록형 1명이었고, `VADA_FINANCE_SCREENS.md` 10장 미해결 5번이 "사후 일괄 기록형에게 같은 질문을 하면 판단이 달라질 수 있다"고 남겨 둔 상태다. 섭외 시 "거래가 생길 때마다 바로 적으시나요, 나중에 몰아서 적으시나요"를 미리 물어 분류한다.

### 사전 세팅

- 화면: `EVT-FIN-DEMO` 재정 시연 허브 (좌측 `운영 — 행사 · 재정(빈 상태·시연)` 그룹)
- **시연 전 `시연 초기화`를 누른다.** 앞 사람이 만든 데이터가 남아 있으면 빈 행사에서 시작하는 의미가 사라진다
- 새로고침하면 로컬 상태가 초기화되므로 시연 도중에는 새로고침하지 않는다

> **허브 5단계는 `완료 확인`이다.** 증빙 묶음은 2026-08-19에 MVP 제품화에서 제외됐고(`MVP_SPEC` 6.1), 허브 안내가 아직 `증빙`으로 남아 있던 것을 2026-09-01에 고쳤다. 이제 마지막 단계가 `EVIDENCE_STAGE_ENABLED` 스위치를 따라가므로 증빙을 다시 제품화하면 안내도 함께 돌아온다. **제외한 기능을 제품인 것처럼 보여주면 시연 전체의 신뢰가 깨진다.**

### 진행 형태

**대면으로 한다.** 2부의 핵심 데이터가 "어디서 멈추는가, 클릭하려다 만 곳"인데 화면 공유로는 보이지 않는다. 마우스를 실제로 넘겨야 한다. 원격이 불가피하면 최소한 원격 제어를 넘긴다.

**첫 학생회는 가장 편한 곳으로 잡는다.** 첫 자리는 스크립트 자체를 시험하는 자리다. 문항이 안 먹히면 고쳐서 나머지 두 곳에 쓴다. 다만 **첫 곳의 결과도 버리지 않고 기록한다** — 문항을 고쳤다는 사실과 함께 남긴다.

### 시간

**역할당 45분.** 1부 12분 / 2부 15분 / 3부 10분 / 4부 8분. 한 학생회에 두 세션이므로 이동 포함 반나절을 잡는다.

### 기록

녹음하되(동의 받고), 기록은 **답을 그대로 옮긴다.** 요약하면 판정 기준에 걸 수 없다. 특히 숫자와 "있었다/없었다"는 원문 그대로.

## 2. 진행 순서

**순서를 바꾸지 않는다.** 1부를 시연 전에 하는 것이 이 스크립트의 핵심이다. 화면을 먼저 보여주면 상대가 화면에 맞춰 자기 경험을 재구성한다.

```text
1부 현재 방식 재현  →  2부 시연  →  3부 반응  →  4부 비용·전환
   (화면 없음)          (조작 넘김)     (뺄 것)      (우회 시나리오)
```

### 1부 — 현재 방식 재현 (12분, 화면을 보여주지 않는다)

여는 말:

> 저희가 만든 걸 보여드리기 전에, 지금 어떻게 하고 계신지부터 여쭤보고 싶습니다. 잘 되고 있는 부분도 그대로 알아야 해서요. 최근 기억나는 건으로 구체적으로 말씀해 주시면 좋겠습니다.

**재정부원에게**

1. 최근에 처리한 구매 요청 하나를 떠올려 주세요. 그 요청이 어디로 들어왔나요? (개인 카톡 / 단톡방 / 구두 / 양식)
2. 그 건 하나를 승인하기까지 메시지를 몇 번쯤 주고받으셨나요?
3. 되물어야 했던 게 있었나요? 뭘 물으셨나요?
4. 승인한 다음에, 그게 지금 주문됐는지 물건이 왔는지는 누가 어떻게 아나요?
5. **"그거 어떻게 됐어요?"라는 질문을 받은 적 있나요?** 최근 한 달에 몇 번쯤이요?
6. 지난 학기에 처리한 구매 요청이 대략 몇 건이었나요?
7. 요청이 여러 부서에서 동시에 들어올 때, 지금 어디까지 왔는지는 어떻게 파악하세요?

**요청자에게**

1. 최근에 구매 요청 올리신 걸 떠올려 주세요. 어디에 어떻게 보내셨나요?
2. 보내신 다음에 결과를 어떻게 아셨나요? 먼저 물어보셨나요, 알려주셨나요?
3. 기다리는 동안 궁금했던 게 있었나요? 뭐가 궁금하셨어요?
4. 반려되거나 보완 요청 받은 적 있나요? 이유를 어떻게 전달받으셨나요?
5. 그때 왜 반려됐는지 지금도 기억나세요?

> 전부 **과거 행동**이다. 의향이 아니라 사실이라 검증 가능하고, 여기서 이미 반증이 나올 수 있다 — 되물음 없음 · 상태 문의 없음 · 반려 사유 명확 기억이면 그 학생회에는 문제가 없는 것이다.

### 2부 — 시연 (15분)

여는 말:

> 이제 만든 걸 보여드릴게요. 빈 행사에서 시작해서 방금 말씀하신 것과 같은 요청을 하나 처리해 보겠습니다.

**설명하지 말고 조작을 넘긴다.**

| 순서 | 하는 일 | 넘기는 말 |
|---|---|---|
| 1 | 예산 편성 | (진행자가 빠르게 수행) |
| 2 | 요청 작성 | **요청자에게 마우스를 넘긴다.** "방금 말씀하신 그 물건을 여기 올린다면, 어디부터 누르시겠어요?" |
| 3 | 검토·승인 | **재정부원에게 넘긴다.** "이 요청이 들어왔습니다. 어떻게 하시겠어요?" |
| 4 | 구매·수령 처리 | **재정부원에게 그대로 둔다.** "주문했고 물건이 왔습니다. 어떻게 기록하시겠어요?" |
| 5 | 처리 단계 보드 · 완료 확인 | "지금 이 행사의 구매가 전부 여기 있습니다." — 설명은 여기서 멈춘다 |

**관찰이 답변보다 중요하다.** 다음을 기록한다.

- 어디서 멈추는가, 무엇을 못 찾는가
- 묻지 않았는데 먼저 하는 말
- 클릭하려다 만 곳

침묵이 흘러도 채우지 않는다. 헤매는 3초가 데이터다.

### 3부 — 반응 (10분)

1. 지금 하시는 방식이랑 비교하면 뭐가 달라지나요?
2. **이 중에 없어도 되는 건 뭔가요?** ← 있으면 좋겠는 걸 묻지 않는다. 뺄 것을 물어야 진짜 가치가 드러난다
3. 보시면서 이상하다 싶은 데 있었나요?
4. (재정부원에게) 이 보드를 하루에 한 번 열어 보실 것 같으세요, 아니면 필요할 때만요?
5. (요청자에게) 내 요청이 어디까지 갔는지 이 화면에서 알 수 있던가요?

### 4부 — 비용·전환 (8분)

**가장 중요한 부분이다.** 의향이 아니라 비용과 우회를 묻는다.

1. **요청자가 이걸 안 쓰고 그냥 단톡에 올리면 어떻게 하시겠어요?**
   → 답이 "그럼 제가 대신 넣죠" 또는 "그냥 카톡으로 받죠"면 **도구는 쓰이지 않는다.** 강제할 수단이 없다는 뜻이다
2. 요청 하나 올리는 데 2분쯤 걸린다고 하면, 카톡으로 보내는 것보다 나은가요? 어떤 경우에요?
3. **학생회에서 새 도구를 도입해 보신 적 있나요?** (노션·구글폼·엑셀 등) 어떻게 됐나요? 지금도 쓰시나요?
   → 과거 도구 도입의 생존 여부가 가장 강한 예측 신호다
4. 지금 진행 중이거나 곧 시작하는 행사가 있나요? 그 행사의 구매를 이걸로 해보실 수 있을까요? 언제부터요?
   → "쓰실 건가요"의 대체 문항. 구체적 시점을 못 말하면 의향은 없는 것이다

닫는 말:

> 오늘 말씀 중에 저희 생각이 틀렸다는 게 나오는 게 제일 도움이 됩니다. 안 맞는 부분 있으면 편히 말씀해 주세요.

## 3. 하지 말 것

| 금지 | 왜 | 대신 |
|---|---|---|
| "이거 쓰실 건가요?" | 거의 항상 예 | "진행 중인 행사에 언제부터 적용해 보실 수 있나요?" |
| "편해 보이지 않나요?" | 동의를 요구하는 문장 | 침묵 |
| "이 기능 필요하시죠?" | 유도 | "이 중에 없어도 되는 건요?" |
| 기능을 길게 설명하기 | 설명이 이해를 대신하면 사용성 문제가 가려진다 | 마우스를 넘긴다 |
| 헤맬 때 바로 알려주기 | 헤매는 지점이 데이터 | 3초 기다린 뒤 "어디를 찾고 계세요?" |
| 증빙 화면 보여주기 | MVP 제외 기능 | 허브 5단계(`완료 확인`)에서 멈춘다 |
| 부정적 반응에 해명하기 | 그다음 말이 끊긴다 | "그 부분 더 말씀해 주세요" |

## 4. 판정 기준 — 시연 전에 정한다

**결과를 보고 기준을 만들면 무슨 답이 나와도 지지로 읽힌다.** 아래를 미리 고정한다.

| 신호 | 지지 | 반증 |
|---|---|---|
| 승인 전 되물음 (1부 Q3) | 되물은 건이 실재하고 무엇을 물었는지 기억함 | "거의 없다" · "양식에 다 있다" |
| 상태 문의 (1부 Q5) | 최근 한 달 1회 이상 | 받은 적 없음 |
| 요청자의 대기 불안 (요청자 Q3) | 궁금했던 내용을 구체적으로 말함 | "그냥 기다리면 됨" |
| **우회 대응 (4부 Q1)** | "다시 올려달라고 하겠다" | **"제가 대신 넣죠" · "그냥 카톡으로 받죠"** |
| 과거 도구 생존 (4부 Q3) | 도입한 도구를 지금도 씀 | 만들고 안 씀 |
| 적용 시점 (4부 Q4) | 구체적 행사·시점을 말함 | "나중에" · "좋을 것 같아요" |

**판정**

| 결과 | 다음 |
|---|---|
| 2곳 이상에서 지지 우세 | M2로 간다. 재정 축을 `ROADMAP` M4 그대로 유지 |
| 2곳 이상에서 반증 우세 | **재정 축을 뒤로 미루고 업무·회의 축(가설 1·2)을 먼저 세운다.** `ROADMAP` M1 분기의 오른쪽 |
| 갈림 | 표본을 1곳 더. 특히 기록 방식(실시간/사후 일괄)이 다른 곳으로 |

**우회 대응(4부 Q1)은 단독 거부권을 갖는다.** 다른 신호가 모두 지지여도 두 곳 모두 "제가 대신 넣죠"라고 답하면 재정 축은 보류한다. 되물음과 상태 문의가 아무리 많아도 재정부가 우회를 허용하면 데이터가 VADA에 쌓이지 않고, 그러면 조회도 결산안 대사도 성립하지 않는다.

기록 방식(재정부원): 실시간 □  사후 일괄 □

[1부] 요청 유입 경로:
      승인까지 메시지 왕복 횟수:
      되물은 내용:
      상태 문의 빈도(최근 한 달):
      지난 학기 요청 건수:
      요청자가 궁금했던 것:
      반려 사유 기억 여부:

[2부] 멈춘 지점:
      먼저 한 말:
      못 찾은 것:
