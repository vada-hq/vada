# TASK-01(상시 업무 칸반 보드) 파일럿

**MY-01과 같은 계열의 화면이다** — 목록을 거르고, 항목을 누르면 상세로 간다.
OPS-00이 판정하지 못한 수렴을 이 화면이 판정한다.

## 1. MY-01이 연 자리가 그대로 쓰였다

| MY-01의 자리 | TASK-01에서 | 고쳤나 |
| --- | --- | --- |
| `itemList.params` | 열마다 `scope`·`status`를 넘긴다 | **고정값을 넘길 자리 하나 추가** |
| `itemList.itemAction` | 카드를 누르면 업무 상세로 | 그대로 |
| `select` + `choiceGroup` | 전체 업무 / 내 업무 토글 | 그대로 |
| `summary` + `items[].unit` | 상태 칩 4개 | 그대로 |
| `shell.json` | 사이드바 | 그대로 |
| `meta.description` | 화면 설명 문장 | 그대로 |

**신규 계급 1건.** 그리고 그 하나도 새 개념이 아니다 — 뒤에서 설명한다.

| 사이클 | 신규 계급 | 새 개념 |
| --- | --- | --- |
| INV-01 | 2 | 2 |
| HOME-01K | 3 | 3 |
| MY-01 | 4 | 1 |
| OPS-00 | 3 | 0 |
| **TASK-01** | **1** | **0** |

## 2. 조회 인자에 고정값이 필요했다

칸반은 같은 출처를 `status`만 바꿔 네 번 조회한다. 그런데 `itemList.params`의
값은 **화면 필드의 fieldKey**만 가리킬 수 있었다. 열의 `status`("예정")는 화면
어디에도 없는, 명세가 정한 고정값이다.

이미 저장소에 같은 문제와 그 답이 있었다 — `summary.items`의 `field`(서버에서
온다) 대 `value`(명세에 담겨 있다). 같은 축이므로 같은 모양으로 풀었다.

```json
"params": {
  "scope":  { "fieldKey": "taskScope" },
  "status": { "value": "planned" }
}
```

MY-01의 `params`도 같이 옮겼다. **새 개념이 아니라 이미 있던 구분을 한 자리 더
적용한 것이다.**

## 3. 열의 건수는 명세에 넣지 않았다

디자인이 열 머리에 `예정 2`, `진행 중 4`처럼 개수를 그린다. 네 열의 개수가
카드 수와 정확히 일치한다(2·4·1·2).

`select.optionCounts`를 만들 때와는 다른 판단을 했다. 탭의 배지는 **보이지 않는
탭의 개수**라 목록에서 셀 수 없었지만, 칸반은 네 열이 모두 화면에 있으므로
그 열의 항목 수가 곧 건수다. **선언하지 말고 유도한다.**

같은 이유로 mock의 상태 칩 건수(지연·검토 필요·내 담당·담당자 없음)도 업무
목록에서 센다. 목록과 칩이 어긋날 수 없다.

## 4. AI 읽기 마찰

| 무엇을 | 어디서 | 왜 명세에 없었나 | 추측했나 |
| --- | --- | --- | --- |
| 상태 칩·카드 날짜 아이콘 | `figma.design.json`의 assetRef | (C) 시각은 design이 갖는다 | 아니오 |
| 칸반 4열 배치 | 디자인 스크린샷 | (C) 배치는 design이 갖는다 | 아니오 |
| 업무 상세가 MY-01과 같은 화면인지 | 사용자와 함께 판단 | (C) 제품 기획이다 | 판단 근거를 남김 |
| 카드 조각의 fieldKey 작명 | 지어냄 | (C) 명세를 만드는 쪽의 몫 | 예 |

**(A) 0건이다.** 명세에 자리가 없어 막힌 것이 하나도 없었다. HOME-01K에서
(A)가 처음 0이 아니게 된 뒤 다시 0으로 돌아왔다.

## 5. 업무 상세는 MY-01과 같은 화면으로 판단했다

사용자가 "기획이 완벽하지 않으니 같이 판단해 달라"고 했다. 근거는 데이터다.

| | MY-01 카드 | TASK-01 카드 |
| --- | --- | --- |
| 조각 | 제목·부서·상태·다음 행동·맥락·기한 | 제목·부서·주기·담당자·기한·주의 |
| 대상 | 내가 처리할 업무(행사 포함 전체) | 상시 업무(부분집합) |

같은 대상의 부분집합이므로 상세 화면도 같다고 본다. 두 화면의 pending 문구를
`업무 상세 화면이 아직 명세되지 않았습니다.`로 같게 맞춰 두었다 — 그 화면이
생기면 두 곳을 한 번에 잇는다.

## 6. 이번 사이클에서 깨진 것

`OPS-00`의 상시 업무 카드가 `pending`에서 `navigate`로 바뀌면서 그 화면의
준수 테스트와 e2e가 깨졌다. **의도한 변화이므로 테스트를 고쳤다.**

이것은 MY-01 사이클에서 `HOME-01K`의 '내 담당 업무'가 겪은 것과 같은 일이다.
화면이 이어질 때마다 앞 화면의 pending 하나가 진짜 이동이 되고, 그것을
단언하던 테스트가 깨진다. **깨지는 것이 정상이고 그 자리를 알려 주는 것이
테스트의 값이다** — 방법론이 금지하는 "이 화면은 아직 구현되지 않았다를 단언하는
테스트"와는 다르다. 여기서 단언하는 것은 화면의 부재가 아니라 명세가 선언한
동작이다.

## 7. 흐름

`운영 → OPS-00 → 상시 업무 → TASK-01`. 세 단계 깊이의 첫 경로다.
OPS-00의 카드 넷 중 하나가 진짜 이동이 됐고, 나머지 셋은 pending이다.
