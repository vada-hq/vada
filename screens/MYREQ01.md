## 화면 구조

와이어프레임 위계를 따른다.

- **머리말** — 왼쪽에 화면 제목과 범위 설명(이 행사에서 내가 제출한 구매 요청), 오른쪽에 새 구매 요청 행동. 행사 재정으로 돌아가는 복귀 행동을 둔다.
- **표** — 열 머리글을 가진 표로 표시한다. 열은 `요청 번호 · 요청 제목 · 요청액 · 요청일 · 상태`. 요청 제목이 상세로 가는 링크다.

## 상태

**로딩** — 진행 상태만 알리고 이전 샘플이나 결과를 실제 데이터처럼 표시하지 않는다. `status`로 전달한다.

**빈 결과** — "아직 제출한 구매 요청이 없습니다." `status`로 전달한다.

**결과 있음** — 서버가 준 순서(생성 시각 내림차순)를 그대로 쓴다. 각 행에 요청 번호, 제목, 총액, 생성 시각, 검토 대기 상태를 표시하고 `overBudget`이면 예산 초과 표시를 상태 옆에 나란히 둔다. 색상만으로 구분하지 않는다.

**권한 없음(403)·찾을 수 없음(404)** — 다른 조직 데이터의 존재를 노출하지 않는 같은 수준의 안내를 표시한다. 재시도를 제공하지 않는다. 머리말의 복귀 행동은 유지된다.

**일시 장애(503)** — 재시도를 제공한다. 재시도가 성공하면 그 결과를 `status`로 알린다.

**인증 필요(401)** — 재인증 안내만 표시하고 과거 목록이나 캐시를 대신 보여주지 않는다. `alert`로 전달하고 복귀 행동을 키보드로 제공한다.

## 와이어프레임과 다르게 하는 것

**품목 수·필요한 날짜 열을 뺀다** — 목록 계약 `DATA:purchase_request.own_list@R1`에 없는 필드다. 표시하려면 별도 조회가 필요한데 그 계약이 없다.

**요약 통계 카드 5개를 뺀다** — 와이어프레임은 검토 대기·보완 필요·승인 완료·구매 진행·처리 완료를 센다. 지금 계약에 존재하는 상태는 검토 대기뿐이다. 나머지는 후속 흐름이며 지금 표시하면 거짓 상태가 된다.

**예산 초과 표시를 추가한다** — 와이어프레임에 없지만 `DATA:purchase_request.record@R1`에 `overBudget`이 있다. 와이어프레임의 상태 칩과 같은 형태로 표시한다.

**새 구매 요청 행동은 와이어프레임처럼 항상 노출한다** — 와이어프레임은 권한이 있을 때만 보여준다(`canSubmitPurchaseRequest`: 재정부·부서장). 제품 웹은 그 판정을 할 수단이 아직 없다. 세션 계약이 없어 화면이 사용자의 역할·부서를 알지 못한다.

작성 맥락 조회를 미리 한 번 더 호출해 성공 여부로 추정하는 방법을 검토했으나 쓰지 않는다. 요청이 늘고, 화면마다 다른 추정 방식이 생기며, 세션 계약이 생기면 전부 다시 고쳐야 한다. 근거는 `docs/engineering/architecture-boundaries.md`의 `화면이 권한을 아는 방법`에 남긴다.

그동안 권한 없는 사용자는 버튼을 볼 수 있고, 누르면 작성 팝업 안에서 서버 거부(403)를 화면 상태로 만난다. 보안은 서버가 지킨다. 클라이언트가 역할 이름을 비교하지 않는다는 규칙은 그대로 지킨다 — 추측하지 않고 노출한다. 세션 계약이 생기면 그 판정 결과로 노출을 가른다.

**사이드바·브레드크럼·행사 탭** — 공통 셸이며 아직 제품 웹에 없다. 별도 화면 작업으로 다룬다.
