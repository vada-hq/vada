## 이 화면이 MVP에서 갖는 범위

와이어프레임의 `EVT-FIN-01`은 재정 생애주기 **전체**를 그린다. 예산 요약 넷, 품목 현황 8열, 재정부 처리 단계 7개 업무 영역, 기록 세 묶음.

그런데 그 값을 만들어 내는 흐름 대부분이 아직 없다. `VADA_MVP_SPEC.md` §6이 `FIN-PROC-01`(구매·발주)·`FIN-EVID-01`(증빙)·`FIN-LEDGER-01`을 **후속 범위**로 미뤘기 때문이다. MVP 성공 기준 5번이 요구하는 것은 여기까지다.

> 구매 요청 1건이 제출되어 **승인·반려·보완 요청 중 하나의 결과**를 가진다.

그래서 이 화면은 **검토 단계까지**를 실제로 다루고, 그 뒤 단계는 자리를 지우지 않되 값이 있는 것처럼 꾸미지 않는다.

| 와이어프레임 요소 | MVP에서 | 이유 |
| --- | --- | --- |
| 예산 요약 — 배정·승인 예약·사용 가능 | **표시한다** | 검토 승인에서 값이 나온다 |
| 예산 요약 — 실제 지출 | **자리를 두되 미도입으로 표시** | `실제 지출`은 증빙 완료로만 확정된다(`CONTEXT.md`). 증빙 흐름이 없으므로 0원이 "지출 없음"인지 "집계 없음"인지 구분되지 않는다 |
| 품목 현황 — 확인 필요·검토 중 | **표시한다** | 검토 상태에서 계산된다 |
| 품목 현황 — 구매 준비 이후 6열 | **열을 두되 미도입으로 표시** | 주문·수령·이행·증빙 상태의 원본이 아직 없다 |
| 처리 단계 — 요청 검토 영역 | **표시한다** | 재정부의 실제 업무다 |
| 처리 단계 — 나머지 6개 업무 영역 | **표시하지 않는다** | 채울 실행분 자체가 없다. 빈 영역 6개는 정보가 아니라 소음이다 |
| 기록 — 구매 요청 | **표시한다** | 요청 단위 열람은 지금 가능하다 |
| 기록 — 승인 묶음 | **표시하지 않는다** | 선진행 동의 흐름이 없어 파생할 원본이 없다 |
| 기록 — 증빙 묶음 | **표시하지 않는다** | 완료 저장되는 레코드가 아직 생기지 않는다 |

**빈 상태와 미도입은 다르게 말한다.** 데이터가 없어 비어 있는 것("아직 요청이 없습니다")과 그 단계 자체가 없는 것("이 단계는 아직 제공하지 않습니다")을 같은 문장으로 쓰지 않는다. 사용자가 기다려야 할지 다른 곳을 찾아야 할지가 달라진다.

## 화면 구조

와이어프레임 위계를 따른다.

- **상단 행동** — 셸 머리말 오른쪽에 `내 구매 요청`, 그리고 `새 구매 요청`(작성 팝업을 연다).
- **예산 요약** — 카드를 가로로 나열한다. 각 카드에 작은 레이블과 큰 금액. 사용 가능액은 주 색상으로 강조한다.
- **하위 메뉴** — 재정부에게만 `작업 보드`(품목 현황·처리 단계)와 `기록`(구매 요청) 두 묶음으로 나눈다. 일반 구성원·부서장에게는 `품목 현황`만 보인다.
- **품목 현황** — 품목 카드를 진행 단계 열에 배치한다. `전체 요청 / 내 요청` 필터. 같은 요청의 카드가 한 열에 2개 이상이면 스택으로 묶는다.
- **처리 단계** — 재정부 전용. 요청 검토 영역의 처리 대기 실행분.
- **기록 · 구매 요청** — 재정부 전용. 요청 단위 표.

## 품목 현황 열이 무엇으로 채워지는가

칸반 열은 저장된 값이 아니다. `VADA_FINANCE_SPEC.md` §11.1의 **대표 진행 상태**를 원본 상태에서 계산해 배치한다. 대표 상태는 "요청자의 응답이 필요한 것"과 "정상 흐름을 중단한 예외"를 먼저 세우고, 없으면 마지막으로 달성된 결과를 쓴다.

검토 단계까지만 실체가 있으므로 MVP에서 채워지는 열은 둘이다.

| 열 | 들어가는 대표 상태 | 원본 |
| --- | --- | --- |
| **확인 필요** | `보완 필요` | 보완 요청된 품목 중 **현재 사용자가 요청자**인 것 |
| **검토 중** | `검토 중`, `보완 중` | 재정부 검토 대기 + 타인이 보완 중인 품목 |
| 구매 준비 이후 6열 | — | 주문·수령·이행·증빙 원본이 없다 |

**같은 품목이 사람에 따라 다른 열에 놓인다.** 보완 요청된 품목은 요청자에게 `확인 필요`, 다른 구성원에게 `검토 중`(보완 중)이다. 이건 버그가 아니라 화면정의서가 정한 예외다. 그래서 이 열은 서버가 요청자 기준으로 계산해 내려줘야 하고, 클라이언트가 목록을 다시 가르지 않는다.

**활성 칸반에서 빠지는 것** — `요청 취소`된 품목은 제외한다(§11.1). 요청 아카이브에는 남는다. `반려`는 종결이지만 요청자가 결과를 알아야 하므로 제외하지 않는다.

## 상태

**로딩** — 예산과 목록을 함께 불러온다. 진행 상태만 알리고 이전 값이나 샘플을 결과처럼 표시하지 않는다.

**성공 · 재정부** — 작업 보드와 기록 두 묶음이 모두 보이고 기본 탭은 처리 단계다.

**성공 · 일반 구성원·부서장** — 품목 현황만 보인다. 처리 단계와 기록 그룹은 노출하지 않는다. 본인 요청 열람은 `내 구매 요청`으로 간다.

**빈 결과** — 구매 요청이 없으면 단계별 0건과 빈 상태를 표시한다. 예산 요약은 그대로 보여준다.

**미도입 단계** — 구매 준비 이후 열과 실제 지출 카드는 "아직 제공하지 않습니다"로 구분해 표시한다. 0원·0건으로 표시하지 않는다.

**예산 미배정** — 배정 예산이 0원이면 사용 가능액을 초과로 강조하지 않고 배정이 없다고 알린다. 승인 예약액은 실제 값이므로 그대로 표시한다.

**보완 상태의 표현이 사람마다 다르다** — 요청자에게는 `보완 필요`, 다른 구성원에게는 `보완 중`으로 표시한다(화면정의서 예외).

**권한 없음(403)·찾을 수 없음(404)** — 다른 조직 데이터의 존재를 노출하지 않는 같은 수준의 안내를 표시한다. 재시도를 제공하지 않는다.

**일시 장애(503)** — 재시도를 제공한다.

**인증 필요(401)** — 재인증 안내만 표시하고 과거 값이나 캐시를 대신 보여주지 않는다.

## 와이어프레임과 다르게 하는 것

**뒤 단계를 지우지 않고 미도입으로 말한다** — 와이어프레임은 8열과 4카드를 모두 채운 상태로 그린다. 그 값을 만드는 흐름이 MVP 범위 밖이므로 데이터를 지어내지 않는다. 다만 자리를 없애면 이 화면이 무엇으로 자랄지 알 수 없게 되므로, 열과 카드는 두고 상태 문구로 구분한다.

**처리 단계의 업무 영역을 7개에서 1개로 줄인다** — 나머지 6개는 채울 실행분이 구조적으로 존재할 수 없다. 빈 탭 6개는 사용자에게 정보를 주지 않고 화면만 무겁게 한다. 열과 달리 탭은 없어도 이 화면의 성장 방향이 가려지지 않는다.

**기록 그룹에서 승인 묶음·증빙 묶음 탭을 빼고 구매 요청만 둔다** — 같은 이유다. 승인 묶음은 선진행 동의에서, 증빙 묶음은 증빙 완료에서 생긴다. 둘 다 없다.

**항목을 누르면 가는 곳** — 화면정의서대로 재정부는 검토 화면(`FIN-REV-01`), 일반 구성원은 자신의 요청 상태 확인 화면으로 간다. 검토 화면은 이 슬라이스에서 함께 만든다.

**사이드바·브레드크럼·행사 탭** — 공통 셸이 제공한다.

**예산 배정을 이번 범위에서 다루지 않는다** — 배정을 만드는 화면(총예산 편성)이 MVP 화면 묶음에 없다. 배정 0원을 기준으로 계산한다(제품 소유자 판정 2026-08-07).

그러면 승인이 하나라도 생기는 순간 사용 가능액이 음수가 되어 화면이 항상 `예산 초과`를 외치게 된다. 그건 사실이 아니라 배정이 없다는 뜻이다. 그래서 **배정이 0원일 때는 예산 요약을 초과로 물들이지 않고 "예산이 배정되지 않았습니다"로 말한다.** 승인 예약액은 그대로 보여준다 — 그건 실제 값이다.

배정을 만드는 흐름이 생기면 이 예외를 걷어낸다.

## 구현하며 정한 것 (2026-08-08)

**승인된 품목은 활성 목록에서 빠진다.** 승인 품목이 갈 곳은 `구매 준비` 열인데 그 열은 미도입이고, 계약 `DATA:purchase_request.event_item_board@R1`의 `progressState`에도 그 값이 없다(`needs_attention`·`under_review`·`rejected` 셋뿐). 놓을 자리가 없는 품목을 다른 열에 끼워 넣으면 그 열의 뜻이 무너진다.

그 결과 **예산 요약의 승인 예약액에는 잡혀 있는데 아래 품목 현황에는 안 보이는 상태가 정상이다.** 미도입으로 표시된 `구매 준비` 열이 그 자리를 설명한다. 구매 실행 흐름이 생기면 이 예외가 사라진다.

**보완 요청된 품목에는 `financeStage`를 붙이지 않는다.** 그 품목은 재정부가 아니라 **요청자**를 기다린다. 붙이면 재정부의 처리 대기 목록이 재정부가 지금 할 수 없는 일을 할 일로 센다. 재제출(`FIN-SUP-01`)이 생기면 그때 `revision_review_pending`이 채워진다.

**부서에 배정되지 않은 구성원도 이 화면을 볼 수 있다.** 계약 `AUTH:event_budget.read@R1`이 요구하는 것은 활성 구성원과 조직 일치뿐이다. 서버의 기존 권한 게이트가 부서 관계를 모든 동작의 공통 조건으로 갖고 있었는데, 계약이 요구하지 않는 조건이라 이 두 읽기에서는 걷어냈다. 요청을 만들고 검토하는 동작은 그대로 부서 사실을 요구한다.

**품목 현황 8열은 와이어프레임 정의를 그대로 쓴다.** `App.tsx`의 `itemProgressColumns`가 원본이다. 앞 두 열만 채워지고 나머지 여섯은 "아직 제공하지 않습니다"로 말한다. 0건으로 표시하지 않는다 — 사용자에게 "아직 없다"와 "그 단계가 없다"는 다른 뜻이다.

## 열린 질문 — 계약이 정본을 다 표현하지 못한다 (2026-08-08)

구현하며 드러난 것 셋이다. 지금은 계약이 말하는 것만 화면에 적고 지어내지 않았다.

**보완 중과 검토 중을 화면이 구분할 수 없다.** 위 `상태`는 보완 요청된 품목을 다른 구성원에게 `보완 중`으로 표시하라고 한다. 그런데 계약 `DATA:purchase_request.event_item_board@R1`은 그 경우를 `under_review`로 합쳐 내려보낸다("다른 구성원에게는 under_review입니다"). 화면에 구분할 재료가 없다. 지금은 둘 다 `검토 중`으로 적는다. 구분이 필요하면 계약에 새 리비전이 있어야 한다.

**보는 사람이 재정부인지 응답에서 추론한다.** `financeStage`가 하나라도 있으면 재정부로 본다. 계약이 "필드의 존재 자체가 권한 판정 결과"라고 정한 대로다. 다만 **처리 대기 품목이 0건이면 재정부도 일반 구성원처럼 보인다.** 그때는 처리 단계와 기록이 어차피 비어 있어 잃는 정보가 없지만, 반려·보완만 남은 행사에서는 재정부가 기록 탭을 잃는다. 세션 계약(`CB-IDENTITY-001`, 아직 서버 미구현)이 서면 이 추론을 걷어낸다.

**기록 · 구매 요청 표에 제목과 신청일이 없다.** 계약에 요청 단위 조회가 없어 품목 목록에서 묶어 만든다. 요청 번호·요청자·부서·품목 수·요청액·확인 필요 건수까지만 서버 값으로 채울 수 있다. 없는 값을 지어내지 않는다.
