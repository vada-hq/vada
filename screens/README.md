# 화면 정본

화면 하나당 파일 하나다. 그 화면을 구현하는 데 필요한 정보가 전부 여기 있고, 다른 곳을 찾아다니지 않는다.

## 왜 이 형식인가

이전에는 같은 화면 하나의 의미가 제품 명세·계약 묶음·구현 아키텍처·작업 그래프·실행 계획·실행 런타임·화면 명세 일곱 곳에 나뉘어 있었다. 한 곳을 바꾸면 나머지를 맞춰야 했고, 그 일관성을 강제하려고 검증기가 늘었다. 검증기는 분산의 해법이 아니라 분산의 증상이었다.

실제로 그 구조는 목적을 달성하지 못했다. 화면 명세가 와이어프레임 위계를 무시하도록 구현을 유도했고, 사람이 브라우저를 열어본 뒤에야 발견됐다.

## 정본은 둘뿐이다

| 정본 | 소유하는 것 |
| --- | --- |
| `contracts/` | 서버 API·권한·데이터·오류. 와이어프레임이 알려주지 못하는 것 |
| `screens/<ID>.md` | 화면 구조와 상태, 와이어프레임과 다르게 한 결정 |

와이어프레임은 `prototypes/wireframe/src/app/App.tsx`가 원본이다. UI 구조와 시각 표현은 와이어프레임이 기준이고, 데이터 저장 위치·접근성·서버 계약 필드는 `contracts/`가 기준이다. 충돌하면 그 판정을 화면 파일의 `와이어프레임과 다르게 하는 것`에 남긴다.

## 진행 상태는 여기 적지 않는다

착수·검토·완료는 GitHub Issue와 PR이 소유한다. 파일에 상태를 복사하면 브랜치마다 다른 답이 나온다. 실제로 그런 일이 있었다.

## 형식

프런트매터는 기계가 검사하고, 본문은 사람이 읽는다.

```yaml
---
id: MYREQ01                                   # 와이어프레임 컴포넌트 이름
title: 내 구매 요청
wireframe: prototypes/wireframe/src/app/App.tsx   # 줄 번호를 쓰지 않는다
wireframe_screen: MY-REQ-01                   # 와이어프레임 SCREENS의 화면 ID
route: /events/$eventId/purchase-requests/mine
contracts:                                    # contracts/ 안에 존재해야 한다
  - API:purchase_request.list_own@R1
  - DATA:purchase_request.own_list@R1
---
```

**줄 번호로 가리키지 않는다.** 예전에는 `App.tsx:14171`처럼 줄을 적었다. 와이어프레임 공유본을 한 번 반입하자 세 파일의 줄 번호가 동시에 전부 틀렸는데, 검증기는 "경로가 있다"만 보고 통과시켰다. 화면 ID는 움직이지 않는다. 위치가 필요하면 App.tsx에서 그 ID를 찾는다.

```bash
grep -n '"MY-REQ-01"' prototypes/wireframe/src/app/App.tsx
```

본문에는 이 셋만 쓴다.

1. **화면 구조** — 와이어프레임에서 가져오는 위계
2. **상태** — 구현하고 테스트할 수 있게. 각 상태에 무엇이 보이고 무엇을 할 수 있는지
3. **와이어프레임과 다르게 하는 것** — 무엇을, 왜. 근거 없이 다르게 하지 않는다

## 검증

`just validate-screens`는 프런트매터의 필수 항목, 와이어프레임 경로와 화면 ID의 실재, 계약 참조가 `contracts/`에 실재하는지만 확인한다. 문장의 내용은 검사하지 않는다. 그건 사람이 브라우저에서 본다.

`just validate-wireframe-sync`는 저장소 와이어프레임이 공유본 기준선과 같은지 본다. `VADA_WIREFRAME_SHARE`에 공유본 폴더를 주면 반입하지 않은 새 공유본이 있는지 확인하고, 없으면 "확인하지 못했다"고 알린다. 조용히 통과시키지 않는다.
