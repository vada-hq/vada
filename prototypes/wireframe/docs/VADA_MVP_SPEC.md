# VADA MVP 기준서

기준일: 2026-07-21  
기준: 현재 VADA 와이어프레임 80개 화면, 메뉴 구조, 권한 매트릭스, 행사 아카이브 정의  
상태: 제품 구현 범위 확정용 초안

## 1. 한 줄 정의

VADA는 학생회가 행사를 기획하고, 업무·회의·참가자·구매 요청을 연결해 운영한 뒤, 최소한의 결과 기록을 남길 수 있게 하는 웹 기반 운영 도구다.

MVP의 목표는 기능을 많이 제공하는 것이 아니라, 한 학생회가 **행사 하나를 실제로 끝까지 운영**하도록 만드는 것이다.

```text
학생회 설정
→ 행사 생성
→ 업무 배정·진행
→ 회의 결정과 후속 업무 연결
→ 참가 신청·현장 출석
→ 구매 요청 검토
→ 행사 완료와 결과 기록
```

## 2. 문제와 목표 사용자

### 해결할 문제

- 행사 업무가 카카오톡, 노션, 개인 메모에 흩어져 담당자와 마감일을 놓친다.
- 회의에서 정한 일이 실제 업무로 이어지지 않아 같은 내용을 반복 논의한다.
- 구매 요청과 승인 상태가 개인 메시지에 남아 재정부와 요청자가 서로 확인해야 한다.
- 행사 참여 신청과 현장 출석 결과를 별도 도구로 관리한다.
- 임원 교체 뒤 이전 행사에서 무엇을 했는지, 무엇이 남았는지 알기 어렵다.

### 1차 사용자

- 회장단: 학생회와 행사 생성, 행사 책임자 지정, 전체 운영 현황 확인
- 부서장·행사 운영진: 업무·회의·참가자·구매 요청을 실제로 운영
- 부원: 본인 업무 확인·처리, 구매 요청 제출, 회의 참여
- 재정부: 구매 요청 검토·승인 또는 보완 요청
- 외부 학생: 로그인 없이 행사 신청 및 QR 출석

### MVP에서 검증할 가설

1. 행사 운영진은 개인 메신저 대신 VADA 업무 보드를 매일 확인할 의향이 있다.
2. 회의록에서 후속 업무를 만들면 업무 누락과 반복 논의가 줄어든다.
3. 구매 요청의 제출·검토 상태를 한 화면에서 보이면 재정부와 요청자 사이의 확인 비용이 줄어든다.
4. 공개 신청 링크와 QR 출석을 함께 제공하면 행사 참가자 명단 관리가 단순해진다.

## 3. MVP 성공 기준

파일럿 학생회가 실제 행사 1건에서 아래 흐름을 완수하면 MVP를 통과로 본다.

1. 권한 있는 사용자가 학생회와 행사를 만들고 운영진을 지정한다.
2. 운영진이 최소 5개의 업무를 만들고 담당자·마감일·상태를 관리한다.
3. 회의 1건을 만들고, 회의 결정에서 후속 업무 1개 이상을 생성한다.
4. 외부 학생이 공개 링크로 신청하고, 행사 당일 QR로 출석 처리된다.
5. 구매 요청 1건이 제출되어 승인·반려·보완 요청 중 하나의 결과를 가진다.
6. 행사를 완료하고 참석 인원, 완료 업무 수, 구매 요청 요약, 회고 메모를 기록한다.

### 측정 지표

- 활성 행사 중 업무가 하나 이상 등록된 비율
- 업무가 담당자와 마감일을 모두 가진 비율
- 회의 후속 업무 생성률
- 구매 요청의 평균 검토 완료 시간
- 신청자 대비 QR 출석 처리율
- 완료 행사 중 결과 기록을 남긴 비율

초기 파일럿에서는 절대 수치 목표보다 데이터 수집과 사용자 인터뷰를 우선한다. 첫 파일럿 종료 후에 기준선을 만들고 다음 릴리스 목표를 설정한다.

## 4. MVP 범위

### 포함: 반드시 제공할 핵심 기능

#### A. 워크스페이스와 권한

- 학생회 생성 또는 초대 코드 참여
- 기본 역할: 회장단 / 부서장 / 부원
- 구성원 초대와 기본 역할 변경
- 미배정 구성원은 조직 수정 화면의 오른쪽 패널에서 관리하며, 회장단은 확인 후 학생회 구성원에서 삭제 가능
- 행사별 운영진 지정
- 권한 없는 사용자는 관리·승인 행동을 실행할 수 없음

MVP 원칙: 권한은 화면을 숨기는 것에 그치지 않고 서버에서도 검증한다.

#### B. 행사와 업무 운영

- 행사 생성: 행사명, 일시, 장소, 책임 부서·책임자, 기본 설명
- 행사 상태: `기획 중 → 진행 중 → 후속 정리 중 → 완료`
- 행사별 업무 보드: `예정 / 진행 중 / 검토 필요 / 완료`
- 업무 생성: 제목, 설명, 담당자, 마감일, 상태, 우선순위
- 업무 상태 변경과 처리 메모 기록
- 내 업무: 현재 사용자에게 배정된 미완료 업무 모아보기
- 행사·업무 마감·회의 일정을 보여 주는 읽기 중심 캘린더

MVP 원칙: 업무의 담당자와 마감일은 둘 다 선택 가능하지만, 비어 있는 업무는 운영진이 바로 찾을 수 있어야 한다.

#### C. 회의와 후속 업무

- 회의 생성: 제목, 일시, 장소, 참가자, 안건
- 회의 상태: `예정 → 진행 중 → 정리 중 → 완료`, 예정 상태의 취소
- 안건별 논의와 결정사항 기록
- 안건별 후속 업무 생성: 업무명, 담당자, 마감일
- 생성한 후속 업무는 행사 업무 보드와 담당자의 내 업무에 즉시 표시
- 완료 회의록 열람

MVP 원칙: AI 요약 없이도 회의 정리가 완료되어야 하며, 결정이 없는 안건은 명시적으로 `결정사항 없음`으로 닫는다.

#### D. 행사 참가 신청과 출석

- 행사별 공개 참여 설문 링크 생성
- 기본 문항: 이름, 학번, 연락 수단, 개인정보 동의
- 운영진의 신청자 명단 열람
- 행사 당일 QR 출석 페이지
- 중복 출석 및 비활성 QR 안내
- 신청자와 실제 참석자 수를 행사 결과 기록에 반영

MVP 원칙: 외부 학생은 계정 생성·로그인·앱 설치 없이 신청과 출석을 할 수 있다.

#### E. 경량 구매 요청 흐름

- 행사에 연결된 구매 요청 작성: 제목, 필요일, 목적, 품목, 예상 금액
- 상태: `제출 → 검토 중 → 승인 / 반려 / 보완 요청`
- 재정부·회장단의 검토 의견과 상태 변경
- 요청자의 보완 후 재제출
- 행사 재정 화면에서 요청별 상태와 예상 총액 확인

> 재정 도메인과 향후 화면 범위는 `docs/VADA_FINANCE_SPEC.md`가 우선한다. 아래 내용은 초기 MVP 범위를 기록한 이력이며 현재 재정 기준으로 사용하지 않는다.

MVP 원칙: 실제 결제·발주·세부 증빙 관리가 아니라, **요청과 검토의 책임 흐름**을 먼저 검증한다.

#### F. 행사 완료 기록

- 행사 완료 처리
- 자동 집계: 신청자 수, 참석자 수, 완료 업무 수, 구매 요청 예상/승인 금액
- 운영진이 입력하는 최소 회고: 잘된 점, 개선할 점, 다음 담당자에게 남길 메모
- 완료 행사 목록에서 결과 기록 열람

MVP 원칙: 이 단계는 정식 문서 발행 워크플로가 아니라, 다음 운영진이 최소 맥락을 확인할 수 있는 완료 기록이다.

## 5. MVP 제외 범위

아래 항목은 와이어프레임에는 존재하거나 후속 논의가 있었지만, 첫 파일럿 MVP에서는 구현하지 않는다.

### 다음 릴리스 후보

- AI 회의 전체 요약 생성·검토·오래된 요약 경고
- 구매·발주·결제 수정·증빙 완료의 전체 집행 프로세스
- 예산 편성, 사용 내역 원장, 상세 증빙 관리
- 검토 요청·승인·버전 발행이 포함된 정식 행사 아카이브
- 학생 명단 파일 업로드, 학생회비 납부 상태 대조
- 행사 참가비 조건별 자동 판정과 결제 연동
- 반복 상시 업무의 고급 반복 규칙
- 다중 행사·학교 단위 통합 관리 및 브랜딩
- 알림센터, 메시지방, 실시간 채팅, 이메일·카카오톡 발송 자동화
- 문서 편집·파일 버전 관리·외부 도구 연동
- 통계 대시보드, 데이터 내보내기, 감사 보고서

### 명시적으로 하지 않을 것

- 회의·업무·행사 상태를 AI가 임의로 확정하지 않는다.
- 예산·결제·증빙 수치를 AI가 생성하거나 수정하지 않는다.
- 파일럿 단계에서 개인 학생 데이터를 마케팅·추천 목적으로 사용하지 않는다.
- 공지·메신저·회계·문서 협업 도구를 한 번에 대체하려 하지 않는다.

## 6. 화면 구현 기준

현재 80개 와이어프레임을 그대로 80개 기능으로 구현하지 않는다. MVP는 아래의 핵심 화면과 상태만 제품화한다.

### MVP 화면 묶음

| 영역 | 우선 화면 | 구현 기준 |
|---|---|---|
| 온보딩·조직 | `ONB-01`, `ONB-02`, `ORG-01`, `ORG-02`, `INV-00`, `INV-01`, `ORG-03A/C`, `ORG-04B` | 학생회 생성·초대·기본 역할 관리만 제공 |
| 홈·내 업무 | `HOME-01`, `MY-01` | 활성 행사, 내 미완료 업무, 검토 대기 요청을 요약 |
| 행사 | `EVT-00A2`, `EVT-00B`, `EVT-02`, `EVT-01`, `EVT-03A`, `EVT-TASK-01/02`, `EVT-SCHED-01` | 한 행사 운영의 중심. 행사 상태와 운영진·업무 관리 |
| 회의 | `OPS-MEET-01C`, `OPS-MEET-02`, `OPS-MEET-05B`, `OPS-MEET-06B`, `OPS-MEET-07` | 생성, 안건 기록, 후속 업무 생성, 완료 회의록 |
| 참가자 | `EVT-04`, `EVT-05`, `EXT-02A/B/C`, `EXT-01A/B` | 공개 신청, 명단, QR 출석 |
| 재정 | `EVT-FIN-01`, `FIN-REQ-01/02`, `FIN-REV-01`, `FIN-SUP-01` | 행사별 구매 요청·검토·보완, 전체 현황 요약 |
| 캘린더·기록 | `OPS-CAL-01`, `REC-01`의 경량 완료 기록 | 파생 일정 열람과 완료 행사 요약 |

### MVP에서 생략·축소할 화면

- 역할별 상세 분기 화면은 하나의 화면 내 권한 제어로 통합할 수 있다.
- 확인 모달, 빈 상태, 예외 상태는 핵심 흐름 안에서 구현하되 독립 화면 단위로 분리하지 않아도 된다.
- `FIN-PROC-01`, `FIN-LEDGER-01`, `FIN-EVID-01`, `REC-02`, `REC-02A`, `ORG-07A/B/C`, 메시지 관련 화면은 후속 범위다.

## 7. 핵심 데이터와 상태 기준

### 최소 데이터 모델

- Organization: 학생회 기본 정보
- User: 이름, 학번/식별자, 연락 수단, 기본 역할, 소속 부서
- Event: 기본 정보, 상태, 책임자, 운영진
- Task: 행사 ID, 제목, 설명, 담당자, 마감일, 상태, 우선순위, 처리 이력
- Meeting: 행사 ID, 일시, 장소, 상태, 생성자, 참가자
- Agenda: 회의 ID, 논의, 결정사항 또는 없음, 후속 업무 연결
- ParticipantApplication: 행사 ID, 설문 응답, 신청 상태, 신청 시각
- Attendance: 행사 ID, 신청자 ID 또는 식별 정보, 출석 시각, QR 검증 결과
- PurchaseRequest: 행사 ID, 요청자, 품목, 필요일, 예상 금액, 상태, 검토 의견
- EventSummary: 행사 ID, 자동 집계 수치, 회고 메모, 완료 시각

### 상태 전이 원칙

```text
행사: 기획 중 → 진행 중 → 후속 정리 중 → 완료
업무: 예정 → 진행 중 → 검토 필요 → 완료
회의: 예정 → 진행 중 → 정리 중 → 완료
구매 요청: 제출 → 검토 중 → 승인 / 반려 / 보완 요청 → 재제출
```

- 상태 변경은 변경 시각, 변경자, 변경 전후 값, 메모를 남긴다.
- 완료 상태는 임의로 과거 상태로 되돌리지 않는다. 정정이 필요하면 권한자만 새 기록을 남긴다.
- 행사 완료 뒤에도 업무·회의·신청·구매 요청은 읽기 전용으로 유지한다.

|---|---|---|---|---|---|
| 학생회·조직 설정 | 가능 | 불가 | 불가 | 불가 | 불가 |

| 행사 업무 생성·상태 변경 | 가능 | 가능 | 배정·참여 범위에서 가능 | 가능 | 불가 |
| 회의 생성·정리 | 가능 | 가능 | 참여·의견·후속 업무 제안 | 가능 | 불가 |
| 구매 요청 작성 | 가능 | 가능 | 가능 | 가능 | 불가 |
| 구매 요청 검토 | 가능 | 불가 | 불가 | 가능 | 불가 |
| 신청·QR 출석 | 불가 | 운영 | 불가 | 불가 | 가능 |
| 행사 완료·결과 기록 | 가능 | 행사 운영진이면 가능 | 불가 | 불가 | 불가 |

권한은 [VADA 권한 매트릭스](./VADA_PERMISSION_MATRIX.md)를 기본으로 하되, MVP에 없는 행동은 노출하지 않는다.

## 9. 사용자 흐름과 수용 기준

### 흐름 1: 행사 운영 시작

1. 회장단 또는 부서장이 행사를 만든다.
2. 책임 부서와 운영진을 지정한다.
3. 운영진이 업무를 만들고 담당자·마감일을 배정한다.
4. 담당자는 내 업무에서 배정된 업무를 확인하고 상태를 변경한다.

수용 기준:

- 새 업무는 행사 업무 보드, 담당자의 내 업무, 캘린더에 같은 데이터로 반영된다.
- 담당자가 없는 업무는 운영진이 필터 또는 경고로 확인할 수 있다.

### 흐름 2: 회의에서 실행으로

1. 운영진이 회의와 안건을 만든다.
2. 진행 중 안건별 논의와 결정을 입력한다.
3. 정리 단계에서 후속 업무를 만들거나 `후속 업무 없음`을 확정한다.
4. 완료된 회의록에서 결정과 연결된 업무를 확인한다.

수용 기준:

- 후속 업무를 생성하면 새 업무 ID가 회의 안건에 연결된다.
- 회의의 결정사항 또는 없음, 후속 업무 또는 없음이 채워지기 전에는 완료 처리할 수 없다.

### 흐름 3: 외부 학생 참여

1. 운영진이 행사 참여 설문을 공개한다.
2. 외부 학생이 링크에서 신청한다.
3. 운영진은 신청자 명단을 확인한다.
4. 행사 당일 학생이 QR 페이지에서 출석한다.

수용 기준:

- 동일한 식별 정보로 중복 신청·중복 출석을 만들지 않는다.
- QR이 비활성 상태이거나 유효 시간이 아니면 출석을 기록하지 않는다.

### 흐름 4: 구매 요청 검토

1. 구성원이 행사에 연결된 구매 요청을 제출한다.
2. 재정부가 승인·반려·보완 요청 중 하나를 선택하고 의견을 남긴다.
3. 요청자는 보완 내용을 확인하고 재제출할 수 있다.

수용 기준:

- 요청자와 재정부가 같은 상태·검토 의견을 본다.
- 요청의 변경 이력이 남는다.

### 흐름 5: 행사 마무리

1. 운영진이 행사를 후속 정리 중으로 전환한다.
2. 완료되지 않은 업무와 미결 구매 요청을 확인한다.
3. 완료 처리 시 자동 집계와 회고를 남긴다.
4. 완료 행사 목록에서 결과를 열람한다.

수용 기준:

- 완료 화면은 신청·출석·업무·구매 요청을 행사 ID 기준으로 집계한다.
- 회고가 없는 행사는 `기록 미완성` 상태를 보여 주되, 완료를 막지는 않는다.

## 10. 비기능 기준

- 반응형: 운영진 화면은 데스크톱 우선, 외부 신청·QR은 모바일 우선
- 개인정보: 학번·연락 수단은 행사 운영 목적에만 접근·처리하며, 외부 신청 페이지에 수집 목적과 동의를 표시
- 감사성: 업무·회의·구매 요청·출석의 주요 변경은 작성자와 시각을 저장
- 데이터 격리: 사용자는 자신의 학생회와 초대·배정된 행사 데이터만 접근
- 신뢰성: 공개 설문과 QR 출석은 새로고침·재시도에도 중복 기록을 만들지 않음
- 성능: 일반 학생회 규모(수백 명, 행사 수십 건)에서 목록·업무 보드·신청 페이지가 일상적인 네트워크 환경에서 사용 가능해야 함

## 11. 개발 순서

### 1단계: 행사 운영의 뼈대

- 인증·학생회 생성·초대·기본 역할
- 행사 생성·운영진 지정·행사 상태
- 행사 업무·내 업무·통합 캘린더

완료 기준: 내부 운영진만으로 행사 업무를 만들고 배정·완료할 수 있다.

### 2단계: 결정과 참가자 연결

- 회의·안건·후속 업무 생성
- 공개 참여 설문·신청자 명단
- QR 출석

완료 기준: 회의에서 만든 후속 업무와 공개 신청·출석이 하나의 행사에 연결된다.

### 3단계: 재정과 완료 기록

- 구매 요청·검토·보완 흐름
- 행사 결과 집계·회고·완료 기록
- 파일럿 QA와 권한·중복 처리 검증

완료 기준: 실제 행사 1건의 시작부터 종료까지 핵심 흐름을 완주한다.

## 12. 출시 전 검증 체크리스트

- [ ] 역할별로 허용되지 않은 생성·수정·승인 행동이 서버에서 차단된다.
- [ ] 행사·업무·회의·구매 요청·신청·출석이 모두 같은 행사 ID로 연결된다.
- [ ] 회의 후속 업무가 업무 보드와 내 업무에 중복 없이 나타난다.
- [ ] 공개 설문과 QR 출석이 로그인 없이 작동하고 중복 기록을 막는다.
- [ ] 구매 요청 상태와 검토 의견이 요청자와 재정부에 일관되게 표시된다.
- [ ] 완료 행사 집계가 원본 데이터와 일치한다.
- [ ] 개인정보 수집·열람 권한·보관 정책을 파일럿 학교 기준으로 검토한다.
- [ ] 파일럿 운영진이 실제 행사 데이터로 최소 한 번의 리허설을 마친다.
